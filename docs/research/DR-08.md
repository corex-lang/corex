# Optimal Concurrency, Structured Async & High-Performance I/O Architecture for CoreX (.cx)

To power both **high-throughput, sub-millisecond tail-latency web backends** (scaling to hundreds of thousands of concurrent connections per node) and **responsive TUI, `wasm32`, and native GUI applications** under a **zero-garbage-collection (zero-GC), statically verified Mutable Value Semantics (MVS) memory model**[cite: 1, 2, 3, 5], **CoreX (`.cx`)** adopts a **Structured Stackless Coroutine and Thread-Per-Core Completion I/O Architecture**. Rather than relying on runtime-scheduled stackful fibers (which require dedicated per-fiber stacks, runtime stack management, and foreign-function stack-switching wrappers such as Go's `cgocall`)[cite: 3] or unstructured multi-threaded work-stealing executors (which require cross-thread `Send` bounds, atomic synchronization wrappers like `Arc[Mutex[T]]`, and incur L1/L2 cache invalidation when tasks migrate across cores), CoreX compiles `DR-03`'s `async fn` and postfix `.await` into **caller-inlined and arena-allocated state machines** driven by **share-nothing, thread-per-core OS completion reactors** (`io_uring` on Linux, `IOCP` on Windows, `kqueue` on macOS/BSD, and the host event loop / WASI Poller on `wasm32`)[cite: 1].

This architecture addresses two central challenges in modern zero-GC asynchronous systems programming:

First, it unifies **Zero-Annotation MVS Borrowing with Concurrent Tasks via Scoped `TaskGroup` Nurseries**. In languages with unstructured concurrency like Rust (`tokio::spawn`), spawning a concurrent task requires `'static` lifetime bounds and `Arc<Mutex<T>>` heap wrappers because a detached child task can outlive its parent lexical stack frame. CoreX forbids unstructured detached task spawning in safe code; all intra-request concurrency occurs inside lexically scoped **`TaskGroup` nurseries** (`async::with_task_group(|group| { ... })`) whose scope exit implicitly awaits and cancels all child tasks in deterministic reverse-registration order (`defer` / `errdefer` semantics from `DR-06` and `DR-07`)[cite: 4, 5]. Because the `MIR` SAST verifier (`DR-06` Pass 3) verifies that every child task's symbolic region depth satisfies $\text{Depth}(\rho_{\text{child}}) > \text{Depth}(\rho_{\text{parent}})$, child tasks can directly borrow parent stack variables via immutable **`let` (`&T`)** projections and mutate provably disjoint **`inout` (`&mut [T]`)** slice partitions or per-task **`BumpArena`** sub-arenas in parallel without `Arc`, `Mutex`, or `<'a>` lifetime annotations[cite: 2, 3, 5].

Second, it resolves the **Completion I/O DMA Buffer Cancellation Hazard at Compile Time**. Completion-based kernel APIs (`io_uring` and Windows `IOCP`) retain kernel access to user-space memory buffers while operations are in flight. In poll-based models like Rust, synchronously dropping a `Future` (for instance, on a timeout or `select!` branch) while the kernel holds a borrowed `&mut [u8]` stack slice allows the kernel DMA engine to write into freed or reused stack memory—an architectural mismatch that forced Rust `io_uring` runtimes (`monoio`, `tokio-uring`, `glommio`) to abandon standard borrowed `AsyncRead` traits in favor of owned buffers. CoreX prevents this hazard by combining **`@linear` ownership (`DR-06`)** with **asynchronous two-phase scope cancellation**: I/O operations either consume an `@linear` **`IoBuf`** by MVS `own` (`sink`) transfer and return it inside the completion tuple `Result[(usize, IoBuf), IoError]`[cite: 3, 4, 5], or lease kernel-registered **`ProvidedBuf`** descriptors from an `io_uring_buf_ring` (`IORING_REGISTER_PBUF_RING`). When a `TaskGroup` or timeout cancels an in-flight operation, the reactor's operation slot quarantines the buffer until it submits `IORING_OP_ASYNC_CANCEL` (or `CancelIoEx` on Windows) and reaps the terminal CQE / `OVERLAPPED` completion packet.

## 1. Concurrency & Async Execution Model: Stackless State Machines vs. Stackful Fibers

### 1.1 Architectural Trade-Off Analysis Across CoreX Target Workloads

Selecting the execution model for `DR-03`'s `async fn` and postfix `.await` requires evaluating **stackless coroutines** (compiler-synthesized state machines, as in Rust, C++20, and Swift) against **stackful fibers / green threads** (virtual stacks managed by a language runtime, as in Go) across five systems engineering dimensions[cite: 1, 3]. While no single independent benchmark in the literature measures all four models across identical workloads, synthesizing compiler architecture studies (`P0981R0`, `P2006R1`, USENIX Security 2025) and cross-language `wasm32` / runtime evaluations (`DR-02`, `DR-06`) clarifies their structural trade-offs[cite: 3, 5].

| Architectural Dimension | Stackful Fibers (Go Goroutines / Runtime Green Threads) | Traditional Stackless Coroutines (Rust `Future` / C++20 `std::coroutine`) | **CoreX (`.cx`) Unified Stackless State Machine Model** |
| :--- | :--- | :--- | :--- |
| **Per-Task Memory Footprint** | Allocates a dedicated contiguous or segmented virtual stack per fiber (`StackInuse` spans in Go), scaling poorly across hundreds of thousands of idle tasks[cite: 3]. | Compiles to a compact coroutine frame holding only parameters and variables live across suspend points. | **32 B `TaskHeader` + overlaid live-variable union**; child `.await` frames inline directly into the parent frame; root frames bump-allocate in $O(1)$ inside per-connection 64 KiB `BumpArena` slabs[cite: 2]. |
| **Allocation Cost per `.await` Call** | Zero heap allocation per call once the fiber stack is allocated, unless stack growth triggers stack reallocation and copying. | **Rust:** 0 allocations (inline state machine), except dynamic trait futures (`Box<dyn Future>`).<br>**C++20:** Heap-allocates a frame per call unless HALO (`P0981R0`) successfully inlines the ramp function. | **Zero heap allocations per `.await`.** Direct calls inline into the caller's state union (`P2006R1` operation-state pattern); dynamic trait calls allocate inside the caller's `context.temp_allocator` (`BumpArena` checkpoint)[cite: 2, 3]. |
| **C FFI & OS Syscall Interop** | **Runtime Wrapper Required (`cgocall`):** Calling C from a runtime-managed fiber requires transitioning through runtime FFI wrappers (`cgocall`) and managing stack tracebacks across Go-to-C transitions. | **Zero-Cost Direct ABI:** Executes directly on the native OS thread stack; calling `@extern fn` C code is a standard machine `call` instruction[cite: 1]. | **Zero-Cost Native C ABI:** Coroutines run on the native OS thread stack between `.await` points; C FFI calls (`@extern fn`) execute via the standard platform ABI with zero stack switching[cite: 1, 3]. |
| **`wasm32` Footprint & Browser Interop** | **2 MB – 10 MB+ binary bloat** in developer comparisons (bundles scheduler + GC) with 100–500 ms startup pauses; TinyGo reaches 15.1 KB with scheduler or 5.95 KB by dropping goroutines/channels[cite: 3]. | **1.5 KB – 10 KB minimal `wasm32` modules**; compiles to standard Wasm state-machine functions that integrate with browser microtasks[cite: 3, 5]. | **1.5 KB – 10 KB minimal `wasm32` modules** (`DR-02` / `DR-06`); state machines lower to standard Wasm `switch` blocks with zero runtime scheduler bloat[cite: 3, 5]. |

### 1.2 Why CoreX Selects Caller-Inlined & Arena-Allocated Stackless Coroutines

Stackful fibers conflict with three foundational CoreX invariants established in `DR-01`, `DR-02`, and `DR-06`. First, on `wasm32` targets, bundling a stackful scheduler and runtime inflates minimal WebAssembly modules to 2–10 MB+ with 100–500 ms initialization pauses in industry comparisons, whereas stripping the scheduler (as in TinyGo's 5.95 KB mode) sacrifices concurrency primitives[cite: 3]. Second, stackful runtimes must mediate transitions between managed fiber stacks and native C stacks via runtime wrappers such as Go's `cgocall`, whereas CoreX mandates zero-cost direct C FFI (`@extern fn`)[cite: 1, 3]. Third, under CoreX's zero-GC MVS memory model (`DR-06`), dynamically reallocating and relocating a growable fiber stack would invalidate interior MVS `inout` (`&mut T`) and `let` (`&T`) pointer projections passed down the call stack[cite: 3, 5].

CoreX's stackless coroutine model achieves ergonomic asynchronous composition while preserving zero-cost C FFI and compact memory footprints through three compiler mechanisms. In C++20 coroutines, the coroutine frame layout is hidden from the type system to permit separate compilation, which forces the compiler to emit a heap allocation in the coroutine ramp function unless the optimizer can inline the ramp function, `get_return_object()`, `await_suspend()`, `await_ready()`, `await_resume()`, and `coroutine_handle::destroy()` under the **Heap Allocation eLision Optimization (HALO, `P0981R0`)**. As C++ sender/receiver analyses (`P2006R1`) demonstrate, when an asynchronous operation instead returns an **unboxed operation-state value** to its caller, the caller chooses where to allocate that state—inline as a data member within the parent coroutine frame or on the stack for `block_on`/`sync_wait`—eliminating leaf heap allocations unconditionally without relying on fragile middle-end inlining heuristics. In CoreX, an `async fn foo(x: u32) -> Result[u64, IoError]` has a compiler-synthesized concrete frame layout `AsyncFrame[foo]` computed during `MIR` `StateTransform` in bottom-up Tarjan Strongly Connected Component (SCC) order (`DR-06` Pass 3)[cite: 5]. When a parent `async fn bar()` executes `foo(42).await?`, `AsyncFrame[foo]` is embedded **directly as a variant inside `AsyncFrame[bar]`'s suspension-state union**. A call chain of nested `async fn` calls thus coalesces into a **single flat state machine** with **zero heap allocations per `.await`**.

Only at the **root spawn boundary**—when a new network connection is accepted by the reactor or a child task is spawned into a `TaskGroup`—does a coroutine frame require independent storage. Rather than invoking general-purpose heap `malloc`/`free`, the reactor allocates the root `TaskHeader` and root `AsyncFrame` inside a pooled **64 KiB `BumpArena`** (`DR-01` §4.1) attached to `context.temp_allocator`[cite: 2, 3]. If a dynamically dispatched `async` trait method (`dyn AsyncHandler`) or recursive `async fn` requires dynamic frame allocation, its child frame is bump-allocated in $O(1)$ time inside the caller's `BumpArena` (`aligned_offset + size <= slab.capacity` in `DR-01`) prior to `.await` and rewound via `arena.restore(cp)` immediately when `.await` resumes[cite: 2, 4].

Furthermore, CoreX eliminates Rust's `Pin<&mut Self>` and `Unpin` surface complexity. In Rust, `Future` is a first-class value type that user code can bind, move in memory prior to polling, and poll manually (`Future::poll`), forcing the type system to expose `Pin<&mut T>` so self-referential coroutine frames cannot be moved after their first poll. In CoreX, because references are **second-class (`DR-02` / `DR-06`)**[cite: 3, 5] and `.await` is a built-in postfix operator (`DR-03`)[cite: 1], an unawaited coroutine frame is an **`@linear` immovable operation state** (`~Copy`, `~Move` once initialized in place via MVS `set` mode `ref mut frame`)[cite: 3, 5]. Because the frame is constructed directly inside its final parent-frame union slot or `BumpArena` address before execution starts (`connect()`/`start()` separation in `P2006R1`) and cannot be moved by user code, interior pointers across `.await` points are permanently stable without exposing `Pin<T>` in user signatures[cite: 3, 5].

### 1.3 Clean Interoperation Between Synchronous and Asynchronous Code

A recurring ergonomic friction in stackless coroutine languages is the "function coloring" divide: synchronous higher-order functions (`slice.map(...)`, `iter.filter(...)`, `arena.with_checkpoint(...)`) cannot accept closures that contain `.await` points unless duplicated into `async_map` or `Stream` combinators. CoreX resolves this without runtime overhead through **Inlined `@local` Closure Suspension Transparency**. As specified in `DR-02` and `DR-06` §1.3, every closure parameter in CoreX defaults to a **non-escaping `@local` closure** (`fn map[T, U](slice: &[T], f: |&T| -> U)`)[cite: 3, 5]. Because non-escaping `@local` higher-order functions (`for_each`, `map`, `filter`, `Result::map_err`, `mem::with_arena`) are **inlined into their caller's `MIR` body prior to the `StateTransform` coroutine pass**, any `.await` expression inside a `@local` closure passed to a synchronous higher-order iterator inside an `async fn` lowers directly as a suspension point of the enclosing `async fn`[cite: 1, 3, 5]. Consequently, developers do not need duplicate `AsyncIterator` or `async_map` APIs for sequential collection pipelines (`items |> Slice::map(|x| fetch_item(x).await?)`), while escaping `own` closures and function pointers remain explicitly typed as `fn(...)` or `async fn(...)` at module boundaries[cite: 1, 5]. Conversely, when a synchronous entrypoint (`fn main() -> Result[unit, AnyError]`) or CLI tool invokes an asynchronous pipeline, `std::async::block_on(async_expr)` allocates the root operation state directly on the current OS thread stack and drives the thread-local completion reactor to completion with zero background thread creation[cite: 4].

## 2. Structured Concurrency & Zero-GC Memory Unification (`TaskGroup` Nurseries)

### 2.1 The Lexical Nursery Invariant and `defer` / `errdefer` Unification

Unstructured concurrency—spawning background tasks (`tokio::spawn(f())`) whose lifetimes are decoupled from the lexical call stack—conflicts with both structured error handling (`DR-07`) and zero-GC region lifetime verification (`DR-06`)[cite: 4, 5]. If a spawned child task can continue running after the function that spawned it returns, the compiler must prevent the child task from borrowing any variable on the parent's stack frame or per-request `Arena`, forcing programmers to wrap shared state in heap-allocated `Arc[Mutex[T]]` structures and annotate tasks with `'static` bounds.

CoreX enforces **Strict Lexical Structured Concurrency** via **`TaskGroup[T, E]`**. A `TaskGroup` can only be entered through a scoped lexical block:

```rust
pub async fn with_task_group[T, E, R](
    body: |&mut TaskGroup[T, E]| -> Result[R, E],
) -> Result[R, E]
```

Every `TaskGroup` upholds four deterministic lifecycle invariants that unify directly with `DR-06` and `DR-07`[cite: 4, 5]. First, under its **Lexical Containment Barrier**, no child task spawned into `group` (`group.spawn(async { ... })` or `group.spawn_local(async { ... })`) can outlive the `with_task_group` lexical block; before `with_task_group` returns to its caller—whether via normal `.Ok(val)` completion, early `.Err(e)` propagation via `?`, or scope exit—the `TaskGroup` epilogue unconditionally awaits the termination of every spawned child task[cite: 4, 5]. Second, under its **Sibling Failure & Early-Return Cancellation Cascade**, if any child task in `TaskGroup[T, E]` returns `.Err(err)` (or if the parent body exits early via `?` or `return`), the `TaskGroup` immediately flags its **`CancelToken`**, submits kernel cancellation requests (`IORING_OP_ASYNC_CANCEL` on Linux, `CancelIoEx` on Windows, `EV_DELETE` on macOS) for all in-flight I/O operations belonging to sibling tasks in the group, awaits their terminal completions and `defer`/`errdefer` cleanup chains, and propagates the first `.Err(err)` to the parent[cite: 4]. Third, each spawned child task receives its own lightweight `BumpArena` checkpoint slice (or core-local slab) bound to its implicit `context.temp_allocator` (`DR-01`, `DR-02`), which is bulk-reclaimed when the `TaskGroup` exits[cite: 2, 3]. Fourth, `TaskGroup` provides two explicit placement modes: `group.spawn_local(async { ... })` pins the child task to the **current core's completion reactor** (zero cross-thread synchronization, zero atomic instructions, ideal for concurrent I/O multiplexing within a single HTTP request or UI component), whereas `group.spawn(async { ... })` makes the child task eligible for **cross-core execution** across worker threads (ideal for parallel CPU-bound batch processing), subject to the compile-time data-race verifier rules in Section 3.

> **Visual — Structured TaskGroup Nurseries Eliminate Heap Locks and Kernel DMA Cancellation Hazards:** Left: In unstructured async models, tasks can outlive their spawner (requiring `'static` and `Arc[Mutex[T]]`), and synchronously dropping a `Future` while an `io_uring` or `IOCP` request is in flight causes a kernel DMA Use-After-Free into freed stack memory. Right: CoreX's lexical `TaskGroup` guarantees $\text{Depth}(\text{Parent}) = 1 < \text{Depth}(\text{TaskGroup}) = 2$, enabling lock-free `&T` sharing, Pentagon-verified disjoint `&mut [T]` slice mutation, and safe two-phase kernel cancellation before arena reclamation[cite: 5].

### 2.2 Formal Proof of MVS + Structured Concurrency Synergy (`DR-02` & `DR-06` Integration)

Because child tasks spawned inside a `TaskGroup` are guaranteed by the language grammar and `MIR` lowering to join before the `TaskGroup` block exits, CoreX's four-pass `MIR` SAST verifier (`DR-06`) unlocks three zero-copy borrowing capabilities across concurrent tasks **with zero lifetime annotations**[cite: 3, 5].

#### 1. Lock-Free Multi-Task Sharing of Immutable `let` (`&T`) Trees (Pass 2 + Pass 3)
Suppose a parent function at lexical scope depth $d_p$ holds a local variable `config: ServerConfig` or an arena-allocated document `doc: JsonDoc` ($\text{Region} = \rho_{\text{local}}(f, d_p)$ with $\text{Depth} = d_p + 1$) and enters `async::with_task_group(|group| { ... })` at nested block depth $d_g = d_p + 1$ ($\text{Depth}(\rho_{\text{group}}) = d_p + 2$)[cite: 5]. When the parent spawns $N$ child tasks that each capture `&config` (an MVS `let` projection), the compiler emits `%loan_i = access.let %config` at each `group.spawn(...)` call and places the corresponding `access.end %loan_i` at the **`TaskGroup` join barrier** (`with_task_group` scope exit)[cite: 3, 5].

In Pass 2 (Law of Exclusivity), because `access.let` permits arbitrary concurrent readers ($\text{let\_count}[\text{config}] = N$) so long as $\text{InoutLoan}(\ell) \cap \text{Conflict}(\text{config}) == \emptyset$, neither the parent nor any child task can mutate or move `config` while the `TaskGroup` is active[cite: 5]. In Pass 3 (Region Depth Escape Check), every child task $c_i$ in `group` has its lifetime strictly bounded by $\rho_{\text{group}}$, where $\text{Depth}(\rho_{\text{group}}) = d_p + 2 > \text{Depth}(\rho_{\text{config}}) = d_p + 1$[cite: 5]. Because the borrow flows from a longer-lived outer region ($\text{Depth} = d_p + 1$) into a shorter-lived inner scope ($\text{Depth} = d_p + 2$) that terminates at the join barrier before $\rho_{\text{config}}$ reaches `storage.dead`, dangling stack or arena escapes are statically prevented[cite: 5]. All $N$ child tasks read `&config` directly via a `const ServerConfig* noalias` pointer with **zero `Arc` atomic reference-count traffic**—avoiding the 14.9x overhead of `Arc` clone+drop (`373.53 ms` vs. `25.01 ms` for `Rc` across 50 million iterations) measured in the February 2026 `include.gr` microbenchmarks[cite: 3, 5].

#### 2. Parallel In-Place Mutation of Disjoint Struct Fields and Slice Partitions (Pass 1 + Pass 4)
Under Strict MVS (`DR-02` / `DR-06`), two `inout` (`&mut`) projections can coexist concurrently if and only if their underlying memory subtrees are provably disjoint ($\text{Subtree}(p_1) \cap \text{Subtree}(p_2) = \emptyset$)[cite: 3, 5]. Inside a `TaskGroup`, CoreX statically verifies disjointness for both **struct sub-trees** and **array/slice partitions**. For **Disjoint Struct Sub-Trees (`MovePath` Trie in Pass 1)**, if `var state: AppPipeline` has fields `state.network_stats` ($p_1$) and `state.disk_index` ($p_2$), Pass 1's precomputed bitmasks satisfy $p_1 \notin \text{Conflict}(p_2)$[cite: 5]. Task 1 can capture `&mut state.network_stats` (`access.inout %p_1`) while Task 2 captures `&mut state.disk_index` (`access.inout %p_2`) simultaneously inside the same `TaskGroup` without a `Mutex`[cite: 3, 5].

For **Disjoint Slice Partitions (`split_at_mut` & `for_each_chunk_mut` via Pass 4 Pentagons)**, `DR-06` collapses arbitrary dynamic index expressions `arr[i]` onto their parent array's `MovePathId` unless partitioned through a verified slice-splitting primitive[cite: 5]. CoreX's standard slice library provides two compiler-recognized partitioning intrinsics backed by `DR-06` Pass 4's **Pentagon Abstract Domain ($\text{Pntg} = \text{Intv} \times \text{Sub}$)**[cite: 5]:
1. `slice.split_at_mut(mid: usize) -> (&mut [T], &mut [T])`: Takes an exclusive `access.inout %slice` loan and projects two fresh synthetic child `MovePathId`s, $p_{\text{left}}$ (representing interval $[0, \text{mid} - 1]$ with $\text{mid} \in s(\text{idx}_{\text{left}})$) and $p_{\text{right}}$ (representing interval $[\text{mid}, \text{len} - 1]$)[cite: 5]. Because $\sup(b^*(p_{\text{left}})) = \text{mid} - 1 < \inf(b^*(p_{\text{right}})) = \text{mid}$, Pass 4 proves $p_{\text{left}} \cap p_{\text{right}} = \emptyset$[cite: 5].
2. `group.for_each_chunk_mut(slice: &mut [T], chunk_size: usize, body: |usize, &mut [T]| -> Result[unit, E])`: Partitions `slice` into non-overlapping sub-slices $[k \cdot C,\; \min((k+1)\cdot C, \text{len}) - 1]$ for $k \in [0, \lceil \text{len}/C \rceil)$ and spawns a child task per chunk inside `group`. Because every chunk interval is pairwise disjoint, all worker tasks mutate `slice` in place concurrently with zero mutexes, zero heap allocations, and zero runtime bounds checks inside the inner loop[cite: 3, 5].

## 3. Compile-Time Data-Race Freedom in the `MIR` SAST Verifier

### 3.1 Eliminating Viral `Send` / `Sync` Annotation Clutter via MVS Disjointness

In Rust, preventing data races across threads requires two viral marker traits (`Send` and `Sync`), while Swift 5.5–5.10 initially required pervasive `Sendable` conformance across types—creating heavy annotation friction until **Swift 6.0 introduced Region-Based Isolation (`SE-0414`) and `sending` Parameters/Results (`SE-0430`)** to prove via control-flow analysis that non-`Sendable` values residing in a *disconnected isolation region* can be safely transferred across concurrency boundaries if never accessed again by the sender.

Because CoreX is built from the ground up on **Strict Mutable Value Semantics (`DR-02`)** and **Second-Class References (`DR-06`)**, it achieves **Swift 6 `SE-0414`/`SE-0430` Region-Based Isolation naturally as a consequence of its existing ownership model**[cite: 3, 5]. In Swift, region-based isolation (`SE-0414`) requires a dedicated control-flow alias analysis because Swift retains reference-type classes (`class`) that can form arbitrary aliased pointer graphs inside a single variable[cite: 3]. In CoreX, **classes do not exist (`DR-02`)** and **references cannot be stored inside structs (`DR-06`)**[cite: 3, 5]. Every composite value (`struct`, `enum`, `Vec[T]`, `Map[K, V]`, `String`, `OwnPtr[T]`, `IoBuf`) already forms a **self-contained, disconnected topological tree**[cite: 3, 5]. When a variable `var batch = Vec[Record]::with_capacity(1024);` is passed via **`own batch` (`sink` mode)** to a cross-core task (`group.spawn(own || process(own batch))`) or sent over a channel (`tx.send(own batch).await?`), `DR-06` Pass 2 emits `storage.move %batch`, setting $\mathcal{M}(\ell)[\text{batch}] = 1$ and $\mathcal{U}(\ell)[\text{batch}] = 1$[cite: 5]. Any subsequent attempt by the sending task to read or write `batch` is immediately rejected by Pass 2 as **`E0301 (UseAfterMove)`**[cite: 5]. Because the sender loses all access at the transfer point and no interior aliases can exist outside `batch`'s value tree, transferring a pure value tree via `own` across OS threads is statically verified to be data-race free without requiring a `Sendable` or `Send` trait annotation[cite: 3, 5].

### 3.2 The `@thread_local` Marker and Formal `MIR` Concurrency Verification Rules (`E0309`)

Instead of forcing developers to annotate every thread-safe type, standard CoreX value types are transferable (`own`) and shareable (`&T`) across threads by default[cite: 3, 5]. Only the subset of OS or runtime primitives whose internal state is physically bound to a specific OS thread or core reactor—such as a core-local `IoRing` handle, a thread-local `BumpArena` slice referencing thread-local slab lists, a browser DOM `JsRef` on `wasm32`, or an `unsafe` raw pointer `*mut T` without an explicit `@trusted_share` wrapper—carries the negative marker attribute **`@thread_local`**[cite: 5]. By structural induction, any `struct` or `enum` containing a `@thread_local` field inherits `@thread_local` automatically.

During `DR-06` Pass 2 and Pass 3, the `MIR` SAST verifier enforces **Four Compile-Time Data-Race Verification Laws**, emitting diagnostic **`E0309 (ConcurrentExclusivityOrEscapeViolation)`** on any violation:

$$\text{Rule 1 (Cross-Core Task Capture):} \quad \forall v \in \text{Captures}(\tau_{\text{cross}}).\; \neg\text{IsThreadLocal}(\text{Type}(v)) \land \text{Mode}(v) \in \{\texttt{own}, \texttt{let}, \texttt{inout}_{\text{disjoint}}\}$$

1. **Cross-Core Spawn Rule (`group.spawn` vs. `group.spawn_local`):** A task spawned via **`group.spawn_local(...)`** executes on the **same OS thread / reactor core** as its parent and may capture `@thread_local` values (such as a local UI handle or core-local slab pool) by `&T` (`let`), `&mut T` (`inout`), or `own` (`sink`). However, because sibling `spawn_local` tasks interleave cooperatively across `.await` points on the same core, Pass 2 holds every captured `access.let` and `access.inout` loan active across the entire `TaskGroup` scope—preventing two `spawn_local` tasks from holding aliased `&mut T` loans across `.await` suspensions (`E0305` / `E0309`)[cite: 5]. Conversely, a task spawned via **`group.spawn(...)`** (or an OS thread spawned via `thread::scope(|s| s.spawn(...))`) may execute on a **different CPU core**; Pass 2 verifies that no captured binding has `@thread_local` in its type metadata, halting with **`E0309`** (`"cannot capture @thread_local resource across multi-core TaskGroup::spawn; use TaskGroup::spawn_local to pin to the current core"`) if violated.
2. **Concurrent Loan Persistence Across `TaskGroup` Barriers:** Whenever a child task (`spawn` or `spawn_local`) is spawned inside `group` (associated with region $\rho_{\text{group}}$) and captures a parent path $p$ via `%loan = access.let %p` or `%loan = access.inout %p`, Pass 2 extends the liveness of `%loan` to the **dominating `task_group.join` terminator** of $\rho_{\text{group}}$ rather than terminating `%loan` immediately after the `group.spawn(...)` call returns[cite: 5]. Consequently, attempting to spawn two child tasks in the same `TaskGroup` that both capture `&mut x` (where $p_1 \in \text{Conflict}(p_2)$), or attempting to read `x` in the parent task while a child task in `group` holds `&mut x`, triggers **`E0309`** until `with_task_group` finishes and executes `access.end %loan_1`[cite: 5].
3. **Linear Channel Ownership Transfer (`Channel[T]`):** CoreX's bounded and rendezvous channels (`async::channel[T](cap) -> (Sender[T], Receiver[T])`) require `send(own msg: T)` to take `msg` by **`own` (`sink`)** convention and verify $\neg\text{IsThreadLocal}(T)$ (unless created via `async::local_channel[T](cap)` for single-core task messaging)[cite: 3, 5]. Because `own msg` consumes the value tree at the `send` call site ($\mathcal{M}(\ell)[\text{msg}] = 1$) and `DR-06` Pass 3's `FnRegionSummary` verifies that `msg` contains no local stack/arena region references ($\text{RegionMask}(\text{msg}) \cap \rho_{\text{local}} == \emptyset$), channel message passing transfers only the container header in registers/ring slots and is statically race-free[cite: 3, 5].
4. **Ban on Unsynchronized Global Mutable State:** Top-level `const` items (`DR-03`) are deeply immutable (`let` trees in $\rho_{\text{static}}$) and freely readable by all threads[cite: 1, 5]. Mutable global variables are forbidden in safe `.cx` code (allowed only inside `unsafe` blocks or via explicit atomic primitives `AtomicU64`, `AtomicBool`, or `Shared[Mutex[T]]` when dynamic cross-thread lock contention is explicitly desired)[cite: 1].

## 4. OS-Native Completion I/O Reactor Architecture

### 4.1 Thread-Per-Core (Share-Nothing) vs. Work-Stealing: Empirical Benchmark Synthesis

A defining architectural choice for CoreX's runtime is how concurrent tasks and OS I/O completion events are scheduled across multi-core hardware. Traditional async runtimes like Rust's **Tokio** and Go's runtime use a **multi-threaded work-stealing scheduler** coupled (on Linux) with readiness-based `epoll`. In contrast, modern high-performance completion runtimes—including **Monoio** (ByteDance), **Glommio** (Datadog), **Compio** / **Apache Iggy** / **RobustMQ**, and C++'s **Seastar**—have converged on a **Thread-Per-Core (Share-Nothing) architecture** paired with kernel completion rings (`io_uring`, `IOCP`).

> **Visual — Thread-Per-Core Completion I/O Delivers 5.7x Higher Throughput and Cuts P9999 Tail Latency by Up to 92%:** Top: On a 24-core Intel Core i9-14900K (100 connections, 64B payload), thread-per-core Monoio achieves 1.65M msg/s vs. Tokio's 288K msg/s (5.7x faster), touching 54% less memory and incurring 37% fewer L1 cache misses. Middle: Under heavy concurrent streaming with `fsync` on AWS, thread-per-core `compio` + `io_uring` reduces P9999 tail latency by 81% to 92% (from 86.30 ms to 7.17 ms at 16x16 streams). Bottom: Eliminating cross-thread `Send` bounds avoids the 14.9x `Arc` and 30.0x `AtomicU64` penalties while maintaining superior p99 tail latency even under 50x synthetic task load imbalance.

As a February 2026 engineering benchmark on `include.gr` (24-core Intel Core i9-14900K, 32 threads, Rust 1.93.0 on Linux) and a February 2026 AWS persistence benchmark report by the RobustMQ team (`compio` + `io_uring` vs. Tokio) indicate, work-stealing imposes four substantial microarchitectural costs on I/O-intensive and low-latency workloads:

First, **Scheduler Coordination & Cross-Thread Wakeup Contention** dominate message-passing overhead. In the `include.gr` 24-core echo benchmark (100 concurrent connections sending 64-byte payloads), Tokio + `epoll` achieved **284,216 msg/sec** with a single listener and **287,951 msg/sec** with `SO_REUSEPORT` (`2,880 msg/sec` per connection), whereas thread-per-core Monoio achieved **1,648,251 msg/sec** on `epoll` (`16,483 msg/sec` per connection) and **1,633,198 msg/sec** on `io_uring` (`16,332 msg/sec` per connection)—a **5.7x throughput advantage** driven by eliminating cross-thread work-stealing queues and atomic waker notifications.

Second, **L1/L2 Cache Invalidation** degrades memory efficiency when tasks migrate. When a suspended task in a work-stealing runtime is stolen by Worker Thread B after an `.await` point, task state and request buffers sitting hot in Worker Core A's L1/L2 cache are invalidated and must be reloaded from L3 or main memory. Pinning tasks to fixed cores in Monoio touched **54% less memory per message** and incurred **37% fewer L1 cache misses per message**.

Third, **Extreme Tail Latency Spikes Under Concurrency** arise from queue delays and blocking thread pools. In RobustMQ's February 2026 AWS benchmarks (1,000 MB/s target throughput with per-message `fsync`), Tokio's work-stealing queue contention and auxiliary blocking thread pool for disk writes (up to 512 threads because Linux `epoll` treats regular file descriptors as always ready) caused severe P9999 tail latency spikes. Across 16 producers × 16 streams, P9999 latency dropped from **86.30 ms** on Tokio to **7.17 ms** on thread-per-core `compio` + `io_uring` (**92% improvement**, with P95 dropping 28% from `2.52 ms` to `1.82 ms` and P99 dropping 32% from `3.01 ms` to `2.05 ms`). At 8 producers × 8 streams, P9999 latency fell from **34.00 ms** to **6.51 ms** (**81% improvement**, with P999 dropping 23% from `2.36 ms` to `1.81 ms`), and at 32 producers × 32 streams, P95, P99, and P9999 dropped by **57%**, **60%**, and **57%** (`27.52 ms` to `11.83 ms`), while 16-partition `fsync` throughput rose **18%** (`843 MB/s` to `992 MB/s`) and sequential block reads rose **>25%** (from `10–12 GB/s` on Tokio + `epoll` to `15+ GB/s` on Monoio + `io_uring`).

Fourth, **The Single-Threaded Hardware Tax of `Send` (`LOCK XADD`)** slows down every operation even when no contention occurs. Because a work-stealing scheduler may migrate any task to another core at any `.await` point, futures must use thread-safe primitives. In the `include.gr` single-threaded microbenchmarks across 50,000,000 iterations, atomic `Arc` clone+drop (`373.53 ms`) was **14.9x slower** than non-atomic `Rc` (`25.01 ms`), `AtomicU64::fetch_add` (`250.34 ms`, which issues a cache-line-locking `LOCK XADD` instruction) was **30.0x slower** than non-atomic `Cell` get+set (`8.33 ms`), and `Mutex<HashMap>` across 5,000,000 accesses (`90.42 ms`) was **1.7x slower** than `RefCell<HashMap>` (`52.50 ms`).

#### Addressing the Load-Imbalance Edge Case: Thread-Per-Core Default + Bounded Cooperative Task Quotas & Explicit Compute Offload
As the `include.gr` benchmark also demonstrates, pure round-robin thread-per-core assignment has a notable trade-off under severe **50x CPU load imbalance** (1,000 tasks consisting of 900 light tasks and 100 heavy tasks requiring 50x more work across 16 cores): Tokio's work-stealing finished the total batch **1.55x faster** (`5.88 ms` vs. `9.10 ms`) and had lower p50 latency (`10.91 µs` vs. `13.16 µs`) by rebalancing heavy tasks to idle threads, although pinned thread-per-core still achieved better p90 (`315.94 µs` vs. `339.19 µs`), p99 (`644.45 µs` vs. `789.61 µs`), and max latency (`730.87 µs` vs. `790.29 µs`).

CoreX captures the strengths of both models without polluting I/O tasks with `Send` synchronization overhead. Each worker thread is pinned to a physical CPU core and owns an independent OS completion ring (`io_uring` / `IOCP` / `kqueue`), its own `SO_REUSEPORT` listener socket, its own `BumpArena` slab pool, and its own local run-queue of `@thread_local`-capable tasks (`spawn_local`)[cite: 2, 5]. Following Datadog's Glommio architecture, each core's event loop enforces a cooperative task quota to preempt CPU-heavy tasks and prevent I/O starvation on the same core. Finally, while tasks spawned via `group.spawn_local(...)` (and all default per-connection I/O handlers) stay strictly in the core-local non-stealable queue, tasks explicitly spawned via multi-core `group.spawn(...)` (which the `MIR` SAST verifier has proven free of `@thread_local` state per Section 3.2) are placed into a per-core stealable deque that idle cores can rebalance when their local I/O ring is empty.

#### Deep-Dive on Linux `io_uring` Configuration & Mandatory `epoll` Fallback
On Linux kernels 6.1+, CoreX initializes each core's `io_uring` instance with three setup flags that eliminate asynchronous kernel-to-userspace interrupts and internal ring locking. First, **`IORING_SETUP_SINGLE_ISSUER` (Linux 6.0+)** informs the kernel that only a single thread submits requests to the ring, enabling internal kernel lock elision (returning `-EEXIST` if violated). Second, **`IORING_SETUP_DEFER_TASKRUN` (Linux 6.1+, requires `SINGLE_ISSUER`)** prevents the kernel from interrupting userspace execution at arbitrary kernel/scheduler transitions when completions arrive; instead, completion task work is deferred until the owning reactor thread explicitly calls `io_uring_enter` with `IORING_ENTER_GETEVENTS`. Third, **`IORING_SETUP_TASKRUN_FLAG` (Linux 5.19+)** sets `IORING_SQ_TASKRUN` in the submission ring flags whenever deferred completions are pending so `io_uring_peek_cqe()` knows to enter the kernel. On Linux 6.6+, CoreX also enables **`IORING_SETUP_NO_SQARRAY`** to remove the SQ indirection array (saving a cache line of bookkeeping per submission) and registers the ring FD via **`IORING_REGISTER_RING_FDS`** to reduce per-syscall overhead in `io_uring_enter`.

Rather than fixed batching—which waits until $B$ messages accumulate or a timeout fires and introduces Nagle-style latency penalties at low load—CoreX implements Martin Thompson's **Natural (Smart) Batching**. As illustrated in HFT latency analyses (`tepy.dev`), a wakeup involving a syscall and sleep/wake costs roughly `1.5 µs` fixed overhead (vs. `0.3 µs` when nothing sleeps, `200 ns` of per-message work, and `700 ns` extra per message when every message issues its own `recv`). Under natural batching, when the reactor loop wakes, it reaps all currently available CQEs up to a batch cap, runs the woken coroutines (which stage outbound SQEs in shared memory via release stores `io_uring_smp_store_release` with zero syscalls), flushes all replies in a single `io_uring_enter` submission, and returns to polling. At low load, batch size is 1 for minimal latency; under heavy load, batches grow naturally while the loop is busy.

Because production container runtimes (default `seccomp` profiles) or administrators setting the `kernel.io_uring_disabled` sysctl (`1` or `2`) can block `io_uring_setup`, and kernels 5.11 and earlier charge ring memory against `RLIMIT_MEMLOCK` (`-ENOMEM`), CoreX's Linux reactor (`LinuxFusionReactor`, modeled on Monoio's `FusionDriver`) probes `io_uring_setup` at startup and falls back cleanly to an `epoll` backend when `io_uring` is unavailable or when low-concurrency workloads do not benefit from batching.

#### Generation-Tagged 64-Bit `user_data` Correlation Key
In `io_uring` (64-byte SQEs and 16-byte CQEs by default, or 32-byte CQEs with `IORING_SETUP_CQE32`), Windows `IOCP`, and macOS `kqueue` (`kevent64_s.udata` and `ext[0]`/`ext[1]`), requests can complete in any order, making the 64-bit `user_data` field the sole correlation key linking a kernel completion back to the suspended coroutine. Following the `SlotMap` generational arena design from `DR-02` and `DR-06` and the Glass Cannon (`gcannon`) `io_uring` load generator architecture[cite: 3, 5], CoreX packs a **64-bit `IoUserData` value** into every submission: `slot_index: u32` (bits 0..31, indexing the core reactor's `InFlightOpTable`), `generation: u24` (bits 32..55, incremented whenever a slot is recycled so stale completions from reconnected or cancelled sockets are ignored in $O(1)$ time), and `op_tag: u8` (bits 56..63, identifying the operation type)[cite: 5].

### 4.3 Safe DMA Buffer Management & Two-Phase Cancellation Protocol

To eliminate the `Future`-drop / `io_uring` DMA Use-After-Free hazard, CoreX enforces two invariants at the intersection of `DR-06` (`@linear` types) and the OS reactor[cite: 5]:

#### 1. `@linear` `IoBuf` Ownership Transfer and Kernel `ProvidedBuf` Rings
In CoreX, asynchronous I/O methods never accept a borrowed `&mut [u8]` stack slice that could expire before kernel DMA finishes. Instead, CoreX provides two completion buffer pathways. First, for **Owned `@linear` `IoBuf` Transfer**, `IoBuf` is a 24-byte `@linear` value struct (`ptr: *mut u8`, `len: u32`, `cap: u32`, `slab_id: u32`, `reg_or_pbuf_id: u16`, `flags: u16`) allocated from the core's pre-registered page-locked buffer pool (`IORING_REGISTER_BUFFERS` -> `IORING_OP_READ_FIXED` / `IORING_OP_WRITE_FIXED`, with sparse buffer tables `IORING_RSRC_REGISTER_SPARSE` on Linux 5.19+)[cite: 5]. Submitting a read or write **consumes `own buf: IoBuf` by MVS `sink` value** (`let (bytes_n, buf) = socket.read_owned(own buf).await?;`), statically preventing the coroutine from reading, mutating, or freeing `buf` while the kernel owns it (`DR-06` Pass 2 sets $\mathcal{M}[\text{buf}] = 1$)[cite: 3, 5]. When the CQE arrives, ownership of `IoBuf` returns to the coroutine inside the `Result[(usize, IoBuf), IoError]` tuple[cite: 4].

Second, for **Kernel-Selected `ProvidedBuf` Rings (`IORING_REGISTER_PBUF_RING` + Multishot Recv)**, high-concurrency servers avoid pre-allocating a buffer per idle connection by registering shared-memory provided buffer rings (`struct io_uring_buf_ring`, Linux 5.19+) paired with multishot receive (`io_uring_prep_recv_multishot`, Linux 6.0+). A single SQE arms continuous receive on a socket without specifying a concrete memory address; as data arrives, the kernel selects a buffer from the `buf_group` list and posts a CQE carrying `IORING_CQE_F_MORE` (indicating the multishot request remains armed; when `IORING_CQE_F_MORE` is absent, the request has terminated and must be re-armed). CoreX wraps the selected buffer ID in an `@linear` `ProvidedBuf` handle whose `defer buf.recycle();` statement returns the buffer to the ring via `io_uring_buf_ring_add` and `io_uring_buf_ring_advance`[cite: 5].

#### 2. Two-Phase Cancellation Protocol & Zombie Buffer Quarantine
When an `async fn` awaiting `socket.read_owned(own buf).await` inside a `TaskGroup` or timeout scope is cancelled before the read completes, CoreX executes a **Two-Phase Cancellation Protocol**. In **Phase 1 (Cancellation Submission)**, the reactor submits an `IORING_OP_ASYNC_CANCEL` SQE on Linux or calls `CancelIoEx(handle, &slot.overlapped)` on Windows. In **Phase 2 (Terminal CQE / `OVERLAPPED` Drain & Quarantine)**, on both Linux `io_uring` and Windows `IOCP`, cancelling a pending asynchronous operation still queues a final completion packet: on Linux, the operation completes with `-ECANCELED` (or normal byte count if completion raced with cancellation); on Windows, `GetQueuedCompletionStatusEx` returns the original `OVERLAPPED*` pointer with `NumberOfBytes = 0` and `ERROR_OPERATION_ABORTED` (converted from `STATUS_CANCELLED`) or normal completion. Because `IoBuf` was moved (`own buf`) into `InFlightOpTable[slot_index]` at submission, **even if the coroutine exits immediately upon cancellation, `InFlightOpTable` retains ownership of `IoBuf` and the `OVERLAPPED` structure in a `CancellingQuarantine` state until the kernel posts the terminal CQE or `OVERLAPPED` packet**, at which point the reactor safely returns `IoBuf` to the slab pool. Similarly, zero-copy sends (`IORING_OP_SEND_ZC`) keep their buffer pinned in `InFlightOpTable` until **both** the initial CQE (`IORING_CQE_F_MORE`) and the second notification CQE (`res = 0`, `IORING_CQE_F_NOTIF`) have arrived.

### 5.2 Complete `.cx` Showcase: Zero-GC Structured Async HTTP & Parallel Batch Engine

The following `.cx` module demonstrates `TaskGroup` structured concurrency, zero-copy MVS `&T` sharing, Pentagon-verified disjoint `&mut [T]` parallel slice mutation, `@linear` `IoBuf` / `ProvidedBuf` completion I/O, linear channel ownership transfers, and `defer`/`errdefer` cleanup—all with **zero `Arc`, zero `Mutex`, and zero `<'a>` lifetime annotations**[cite: 1, 3, 4, 5]:

```rust
// File: src/net/telemetry_ingest.cx
mod telemetry_ingest;

use std::async::{self, TaskGroup, Duration};
use std::io::{IoError, TcpSocket, ProvidedBuf};
use std::mem::{BumpArena, Slice};
use db::pg::PgPool;

const MAX_PACKET_BYTES: usize = 32_768;
const PARALLEL_CHUNK_SIZE: usize = 64;

pub struct IngestConfig {
    pub cluster_name: str,
    pub weight_scale: f64,
    pub timeout_ms: u64,
}

pub struct SamplePoint {
    pub sensor_id: u32,
    pub raw_reading: f64,
    pub calibrated: f64,
}

pub struct IngestSummary {
    pub samples_processed: usize,
    pub db_rows_inserted: u64,
    pub audit_log_seq: u64,
}

pub enum IngestError {
    @from Io(IoError),
    TimeoutExceeded,
    MalformedPayload,
    StorageFailure(str),
}

// 1. ZERO-ANNOTATION CONCURRENT HANDLER:
// Borrows `socket` (&mut), `config` (&), `pool` (&), and `req_arena` (&mut)
// across multiple `.await?` points and a parallel `TaskGroup` with ZERO <'a> lifetimes!
pub async fn handle_ingest_stream(
    socket: &mut TcpSocket,
    config: &IngestConfig,
    pool: &PgPool,
    req_arena: &mut BumpArena,
) -> Result[IngestSummary, IngestError] {
    errdefer |err| context.note("cluster='{config.cluster_name}', ingest failed: {err}");

    let cp = req_arena.checkpoint();
    defer req_arena.restore(cp);

    // 2. LEASE KERNEL PROVIDED BUFFER (io_uring IORING_REGISTER_PBUF_RING / kqueue / IOCP):
    // `@linear` ProvidedBuf is returned to the kernel buffer ring automatically by `defer`.
    let recv_buf: ProvidedBuf = async::with_timeout(
        Duration::from_millis(config.timeout_ms),
        socket.recv_provided_bounded(MAX_PACKET_BYTES),
    ).await catch {
        return .Err(.TimeoutExceeded);
    }?;
    defer recv_buf.recycle();

    var samples: [SamplePoint] = parse_samples_into_arena(req_arena, recv_buf.as_slice())?;
    if samples.is_empty() {
        return .Err(.MalformedPayload);
    }

    // 3. PHASE 1: PARALLEL IN-PLACE SLICE MUTATION VIA DISJOINT `&mut [SamplePoint]` CHUNKS:
    // `DR-06` Pass 3 proves child tasks cannot outlive `with_task_group` (Depth 3 > Depth 1).
    // `DR-06` Pass 4 (Pentagons) proves each `chunk` interval is pairwise disjoint!
    // Result: Multi-core parallel mutation of `samples` with ZERO Arc and ZERO Mutex!
    async::with_task_group[unit, IngestError, unit](|group| {
        group.for_each_chunk_mut(&mut samples, PARALLEL_CHUNK_SIZE, |_chunk_idx, chunk| {
            // `config` (&IngestConfig) is shared read-only (`access.let`) across all cores!
            for ref mut item in chunk {
                item.calibrated = item.raw_reading * config.weight_scale;
            }
            .Ok(())
        })?;
        .Ok(())
    }).await?;

    // 4. PHASE 2: CONCURRENT I/O FAN-OUT (DB INSERT + AUDIT STREAM) BORROWING `&samples`:
    // Once Phase 1's TaskGroup exits, the `access.inout %samples` loan ends immediately!
    // Phase 2 can now share `&samples` (`access.let`) across two concurrent I/O tasks.
    let (db_rows, audit_seq) = async::with_task_group[(u64, u64), IngestError, (u64, u64)](|group| {
        let (tx_chan, rx_chan) = async::local_channel[u64](1);

        // Task A (Core-local I/O): Insert calibrated batch into Postgres
        group.spawn_local(async {
            let inserted = pool.insert_samples(config.cluster_name, &samples).await
                |> Result::map_err(|e| IngestError::StorageFailure(e.message()))?;
            // Transfer result via linear channel
            tx_chan.send(own inserted).await catch {};
            .Ok((inserted, 0))
        });

        // Task B (Core-local I/O): Append batch digest to remote audit socket concurrently
        let seq_id = write_audit_digest(socket, config, &samples).await?;
        let inserted_count = rx_chan.recv().await.unwrap_or(0);

        .Ok((inserted_count, seq_id))
    }).await?;

    .Ok(IngestSummary {
        samples_processed: samples.len(),
        db_rows_inserted: db_rows,
        audit_log_seq: audit_seq,
    })
}

fn parse_samples_into_arena(
    arena: &mut BumpArena,
    raw: &[u8],
) -> Result[[SamplePoint], IngestError] {
    if raw.len() % 12 != 0 {
        return .Err(.MalformedPayload);
    }
    let count = raw.len() / 12;
    var out = arena.alloc_slice[SamplePoint](count);
    for i in 0..count {
        out[i] = SamplePoint {
            sensor_id: i as u32,
            raw_reading: (raw[i * 12] as f64),
            calibrated: 0.0,
        };
    }
    .Ok(out)
}

async fn write_audit_digest(
    socket: &mut TcpSocket,

        own ack_buf,
        "OK cluster={config.cluster_name} count={samples.len()}\n",
    ).await?;

    .Ok(samples.len() as u64)
}
```

## 6. Deliverable 2: Compiler Lowering & Runtime Scheduler Blueprint

### 6.1 Coroutine State-Machine Lowering (`StateTransform`) in Block-Argument SSA `MIR`

Crucially, **CoreX runs all four `MIR` SAST and Lifetime Verification passes (`DR-06` Passes 1–4) and `defer`/`errdefer` Cold-Cleanup Elaboration (`DR-07`) *before* lowering coroutines into state machines**[cite: 4, 5]. In pre-transform Block-Argument SSA `MIR`, a postfix `.await` expression is represented as a single instruction `%res = coro.suspend %child_frame, ^resume_bb, ^cancel_unwind_bb`. This ordering provides two compiler engineering advantages: first, the SAST verifier analyzes an `async fn` as a standard structured CFG—verifying `MovePath` initialization, `access.let`/`access.inout` exclusivity across `coro.suspend` points, `FnRegionSummary` escape depths, and Pentagon slice bounds in linear time without having to reconstruct control flow from synthesized state-machine `switch` tables[cite: 5]; second, the `StateTransform` pass directly uses the liveness bitsets already computed by `DR-06` Pass 2 (`MaybeInit` $\cap$ `LiveAcrossSuspend`) to pack the coroutine frame layout with minimal byte footprint[cite: 5].

> **Visual — Block-Argument SSA StateTransform and Conflict-Graph Packing Shrink Task Frames to 64–192 Bytes:** Top: After running `DR-06` SAST verification and `DR-07` `errdefer` elaboration on pre-transform `MIR`, the `StateTransform` pass splits basic blocks at `coro.suspend` points, colors the live-variable interference graph so non-overlapping locals and child frames share memory offsets, and generates a jump-table dispatcher[cite: 4, 5]. Bottom: Packing non-overlapping states into a 128-byte `BumpArena` frame allows 511 concurrent tasks per 64 KiB slab—consuming 64 MiB for 500,000 idle connections compared to 1,024 MiB for 2 KiB stackful fibers[cite: 2].

#### Step-by-Step `StateTransform` Algorithm (`stage0/src/mir_async.zig` -> `src/mir/mir_async.cx`)
Given a verified `MirBody` containing $K$ suspension instructions (`coro.suspend_0` $\dots$ `coro.suspend_{K-1}`), the `StateTransform` pass executes three deterministic steps:

1. **Cross-Suspend Liveness & Conflict Graph Coloring (Storage Overlay):** A local variable or temporary `%v` must be spilled into `AsyncFrame` if and only if its live range crosses at least one `coro.suspend_i` point (i.e., `%v` is defined before `coro.suspend_i` and read in a block reachable from `^resume_i` or `^cancel_i`). Any variable whose live range is strictly contained between two suspension points stays purely in hardware SSA registers and consumes **0 bytes** in `AsyncFrame`. For all variables $V_{\text{spill}}$ and inlined child coroutine frames $C_{\text{inline}}$ that cross suspension points, the compiler constructs an **Interference Bitmatrix** of size $|V_{\text{spill}} \cup C_{\text{inline}}|^2$: two items interfere if and only if there exists some suspension point $s_i \in \{0, \dots, K-1\}$ where **both** items are simultaneously live. Using greedy graph coloring sorted by alignment and byte size (largest alignment first to eliminate internal padding, matching `DR-01` and `DR-02`), non-interfering variables and sequential child `.await` frames (`ChildFrame_A` at suspend 0 and `ChildFrame_B` at suspend 1) are assigned to **overlapping byte offsets (an overlaid `union`)** inside `AsyncFrame`[cite: 2, 3].
2. **Splitting `coro.suspend` into Resume and Cancel Landing Pads:** Each `coro.suspend_i %child, ^resume_i(%val: T), ^err_unwind_Sk(%err: E)` at suspension index $i \in \{1, \dots, K\}$ (where state `0` is `Unstarted`, state `0xFFFE` is `Completed`, and state `0xFFFF` is `Cancelled`) is rewritten to store newly live spilled SSA values into their assigned `AsyncFrame` offsets, write `frame.state_idx = i`, and invoke the child frame's poll function `call @child_poll(%frame.child_slot_i, %reactor_ctx)`. Extending `DR-07`'s register/flag calling convention (`cx_result_cc` -> `cx_poll_cc`)[cite: 4], if the child returns **`Pending`** (`CF = 1` and `RAX = 0`), the parent immediately executes `ret Pending` (`stc; xor eax, eax; ret` on `x86_64`), propagating suspension up the inline chain in 3 instructions; if the child completes synchronously (**`Ready(.Ok(v))`**, `CF = 0`), control branches directly to `^resume_i(%v)` without suspending to the reactor.
3. **Synthesizing the Entry Jump-Table Dispatcher (`resume` + `cancel` Unified Entry):** In C++20 coroutines, every coroutine frame stores two raw 8-byte function pointers (`resume_fn` and `destroy_fn`), adding 16 bytes per frame and exposing a Control-Flow Hijacking surface via Controlled Frame Pointers (CFP) if an adjacent buffer overwrites the frame's function pointers or suspend index. CoreX instead stores a `u16` state index (`state_idx`) alongside a `u16` dispatch-table index (`poll_fn_id` into a read-only compile-time function table) inside the 32-byte `TaskHeader`, passing a `PollAction` mode flag (`0 = Resume`, `1 = CancelDestroy`) in a register. At the entry of `@coro_poll(frame: *mut AsyncFrame, action: PollAction, cqe_res: i64)`, a single multi-way `switch` jumps directly to `^resume_i` (when `action == Resume`) or directly to the `DR-07` cold cleanup block `^err_unwind_Sk(IoError::Cancelled)` (when `action == CancelDestroy`), running all active `defer`, `errdefer`, and `AutoDrop` destructors for suspension point $i$ before marking `state_idx = 0xFFFF`[cite: 4, 5].

### 6.2 Concrete Zig Stage-0 Implementation (`stage0/src/mir_async.zig`)

The following Zig Stage-0 module (`DR-01` §4.1 conventions: `MultiArrayList` SoA storage, `enum(u32)` handles, `BumpArena` 16-byte/64-byte alignment, 0 padding bytes) defines the exact data structures for `MIR` coroutine lowering, task-frame arena layout, and the unified OS completion ring interface (`io_uring` / `IOCP` / `kqueue` / `wasm32`)[cite: 2, 4, 5]:

```zig
//! CoreX Stage-0 Compiler & Runtime Blueprint (`stage0/src/mir_async.zig`)
//! Module: Block-Argument SSA MIR Coroutine StateTransform, TaskFrame Arena Layout,
//!         and Cross-Platform Completion Reactor ABI (io_uring / IOCP / kqueue / wasm32).
//! Maps 1-to-1 to self-hosted `src/mir/mir_async.cx` and `std/async/reactor.cx`.

const std = @import("std");
const assert = std.debug.assert;
const mem = @import("mem_foundation.zig");
const mir_err = @import("mir_error.zig");

pub const TypeId = mem.TypeId;
pub const MirBlockId = mem.MirBlockId;
pub const MirValueId = mem.MirValueId;
pub const CleanupScopeId = mir_err.CleanupScopeId;

// ============================================================================
// 1. MIR COROUTINE SUSPENSION & STATE-MACHINE LOWERING STRUCTURES
// ============================================================================

/// Canonical 32-bit handle for a suspension point (`coro.suspend`) inside a MirBody.
pub const SuspendPointId = enum(u32) {
    initial_entry = 0,
    completed = 0xFFFF_FFFE,
    cancelled = 0xFFFF_FFFF,
    _,
};

/// Metadata per `.await` suspension point in a pre-transform Block-Argument SSA MirBody.
/// Stored in `MirAsyncTransform.suspend_points` (MultiArrayList SoA).
pub const SuspendPointMeta = extern struct {
    /// Basic block where execution resumes on normal completion (`Ready`).
    resume_bb: MirBlockId,
    /// Cascading cold cleanup block (`DR-07`) invoked if cancelled while suspended here.
    cancel_cleanup_bb: MirBlockId,
    /// Active lexical cleanup scope (`defer` / `errdefer` / `AutoDrop`) at this `.await`.
    cleanup_scope: CleanupScopeId,
    /// TypeId of the inlined child coroutine frame (or `.none` for leaf OS I/O op).
    child_frame_ty: TypeId,
    /// Assigned byte offset of the inlined child frame inside the parent `AsyncFrame`.
    child_frame_offset: u32,
    /// Index into `extra_data` holding the DenseBitSet words of locals live across this point.
    live_locals_bitset_extra: u32,
};

/// Computed layout descriptor for a lowered `async fn` state-machine frame (`AsyncFrame[F]`).
pub const CoroFrameLayout = extern struct {
    /// Total byte size of the frame (including TaskHeader when allocated as a root task).
    total_size: u32,
    /// Required byte alignment (16 or 64 bytes for cache-line aligned root tasks).
    alignment: u16,
    /// Number of `.await` suspension states (1..65533).
    suspend_count: u16,
    /// Byte offset where the overlaid union of non-conflicting spilled locals begins.
    union_storage_offset: u32,
    /// Start index in `extra_data` mapping each spilled `MirValueId` -> frame byte offset.
    local_offsets_extra: u32,
};

// ============================================================================
// 2. CACHE-LINE ALIGNED TASK HEADER & ARENA FRAME LAYOUT (32 BYTES)
// ============================================================================

/// Intrusive 32-byte header placed at offset +0 of every spawned root task in `BumpArena`.
/// Replaces C++20's dual 16-byte function pointers (`resume_fn`/`destroy_fn`) with compact
/// table indices to prevent Control-Flow Hijacking (CFP) and halve header overhead.
pub const TaskHeader = extern struct {
    /// Next task in the core reactor's intrusive ready queue or TaskGroup child list.
    next_in_queue: u32,
    /// Parent `TaskGroup` nursery slot ID (`0xFFFF_FFFF` if root connection task).
    task_group_id: u32,
    /// Current suspension state index (`0` = unstarted, `1..K` = suspended, `0xFFFF` = done).
    state_idx: u16,
    /// Index into the compile-time `CoroPollDispatchTable` (mitigates CFP pointer overwrite).
    poll_fn_id: u16,
    /// Lifecycle & ownership flags (`IS_LOCAL_PINNED`, `CANCEL_REQUESTED`, `IN_FLIGHT_IO`).
    flags: TaskFlags,
    /// Count of active child tasks or un-reaped kernel I/O operations pinning this frame.
    pin_ref_count: u16,
    /// Saved `BumpArena` checkpoint (`SlabHeader*` + `used` offset) restored on completion.
    arena_slab_idx: u32,
    arena_used_offset: u32,
    /// 64-bit result/completion payload slot or pointer to parent destination slot.
    result_slot: u64,

    pub const TaskFlags = packed struct(u16) {
        is_local_pinned: bool = true,
        cancel_requested: bool = false,
        has_in_flight_io: bool = false,
        completed_err: bool = false,
        _reserved: u12 = 0,
    };
};

// ============================================================================
// 3. UNIFIED OS COMPLETION REACTOR ABI (io_uring / IOCP / kqueue / wasm32)
// ============================================================================

/// 64-bit correlation key packed into `io_uring_sqe.user_data`, `kevent64_s.udata`,
/// Windows `CxOverlapped.user_data`, and Wasm32 callback arguments.
pub const IoUserData = packed struct(u64) {
    /// Index into the core reactor's `InFlightOpTable` (`0..2^32 - 1`).
    slot_index: u32,
    /// 24-bit monotonic generation counter (prevents ABA stale socket/timer wakeups).
    generation: u24,
    /// Operation opcode discriminator.
    op_tag: OpTag,

    pub const OpTag = enum(u8) {
        nop = 0,
        accept_multishot = 1,
        recv_owned = 2,
        recv_provided_multishot = 3,
        send_owned = 4,
        send_zc = 5,
        fs_read = 6,
        fs_write_fsync_linked = 7,
        timer_deadline = 8,
        async_cancel = 9,
    };
};

/// `@linear` DMA-safe buffer descriptor (`24 bytes`).
/// Ownership is moved (`own`) into `InFlightOpTable` during kernel submission
/// and quarantined if cancelled until the kernel posts the terminal CQE / OVERLAPPED.
pub const IoBuf = extern struct {
    ptr: [*]u8,
    len: u32,
    cap: u32,
    /// Arena or registered pool slab identifier.
    slab_id: u32,
    /// Index in `io_uring_register_buffers` fixed table (`0xFFFF` if unregistered)
    /// or `bid` in `io_uring_buf_ring` (`IORING_REGISTER_PBUF_RING`).
    reg_or_pbuf_id: u16,
    flags: u16,
};

/// Per-operation tracking slot in the core reactor's `InFlightOpTable`.
/// Guarantees that neither `IoBuf` nor Windows `OVERLAPPED` is freed while DMA is active.
pub const InFlightOpSlot = extern struct {
    /// Coroutine task ID waiting on this operation (`0xFFFF_FFFF` if task was cancelled
    /// and this slot is in `CancellingQuarantine` waiting for terminal kernel CQE).
    awaiting_task_id: u32,
    /// Current 24-bit generation + 8-bit state (`Active`, `CancellingQuarantine`, `Free`).
    gen_and_state: u32,
    /// Pinned DMA buffer owned by the kernel while in flight.
    pinned_buf: IoBuf,
    /// Platform-specific 32-byte inline header (`OVERLAPPED` on Windows; `timespec64`/aux on Unix).
    platform_overlapped: [4]u64,
};

/// Normalized 16-byte Completion Event produced by all 4 platform backends
/// (`io_uring` CQE, Windows `OVERLAPPED_ENTRY`, macOS `kevent64_s`, Wasm32 host callback).
pub const ReactorCqe = extern struct {
    user_data: IoUserData,
    /// Bytes transferred (>= 0) or negated OS errno (`-ECANCELED`, `-ETIMEDOUT`, etc.).
    result: i32,
    /// Flags (`CQE_F_MORE` for multishot, `CQE_F_BUFFER` + `bid`, `CQE_F_NOTIF` for zero-copy).
    flags: u32,
};

// Compile-time byte-size and zero-padding verification
comptime {
    assert(@sizeOf(SuspendPointMeta) == 24);
    assert(@sizeOf(CoroFrameLayout) == 16);
    assert(@sizeOf(TaskHeader) == 32);
    assert(@sizeOf(IoUserData) == 8);
    assert(@sizeOf(IoBuf) == 24);
    assert(@sizeOf(InFlightOpSlot) == 64); // Exactly 1 CPU cache line (64 bytes)!
    assert(@sizeOf(ReactorCqe) == 16);     // Matches 16-byte Linux io_uring_cqe layout!
}
```

### 6.3 Summary Verification Checklist for `stage0/corex` & `src/` Implementation

To operationalize this concurrency and I/O architecture across the Zig Stage-0 bootstrap compiler (`stage0/corex`) and the self-hosted `.cx` compiler (`src/`), the implementation enforces six core invariants:
1. **Zero-Heap-Per-Await Stackless Lowering (`StateTransform`):** Lower `async fn` and postfix `.await` into flat state machines where direct child `.await` frames are union-packed into the caller's `AsyncFrame` via liveness conflict-graph coloring, and root task frames allocate in $O(1)$ inside per-core 64 KiB `BumpArena` slabs[cite: 2].
2. **Lexical `TaskGroup` Nursery Enforcement:** Prohibit detached unstructured task spawning in safe code; guarantee that `with_task_group` awaits and cancels all child tasks on both `.Ok` and `.Err` (`?`) exits in LIFO `defer`/`errdefer` order[cite: 4, 5].
3. **Zero-Annotation MVS Borrowing Across Tasks:** Use `DR-06` Pass 3 ($\text{Depth}(\rho_{\text{group}}) > \text{Depth}(\rho_{\text{parent}})$) and Pass 4 (Pentagon `Intv × Sub` slice interval disjointness) to permit lock-free `&T` sharing and parallel `&mut [T]` chunk mutation without `Arc[Mutex[T]]` or `<'a>` lifetime bounds[cite: 3, 5].
4. **Compile-Time Data-Race Verification (`E0309`):** Verify that every cross-core `group.spawn` capture and `Channel::send(own v)` payload is a disconnected MVS value tree free of `@thread_local` resources, while persisting `access.let`/`access.inout` loans across `TaskGroup` join barriers[cite: 5].
5. **DMA-Safe `@linear` `IoBuf` & Quarantine Cancellation:** Require `own IoBuf` transfer or kernel `ProvidedBuf` leasing for all completion I/O operations, holding cancelled `InFlightOpSlot` entries in `CancellingQuarantine` until the terminal `IORING_OP_ASYNC_CANCEL` CQE or `CancelIoEx` `OVERLAPPED` packet arrives[cite: 5].
6. **Thread-Per-Core Share-Nothing Reactor with Universal Fallback:** Configure Linux `io_uring` with `IORING_SETUP_SINGLE_ISSUER | IORING_SETUP_DEFER_TASKRUN | IORING_SETUP_TASKRUN_FLAG` (with automatic `epoll` `FusionDriver` fallback), Windows with per-core `IOCP` (`GetQueuedCompletionStatusEx`), macOS/BSD with `kevent64_s`, and `wasm32` with the host microtask / WASI poller bridge.
