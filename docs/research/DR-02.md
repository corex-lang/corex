# Optimal Programming Paradigm and Core Semantics Specification for CoreX (.cx)

To simultaneously achieve instant compilation, compile-time memory safety without garbage collection, C-level execution speed, and a flat learning curve across CLI/TUI tools, high-throughput web backends, and `wasm32`/native GUI applications, **CoreX (`.cx`)** should reject both classical object-oriented reference graphs and first-class lifetime-annotated borrow checking. Instead, CoreX should adopt a **Value-Oriented Algebraic Data-Oriented Hybrid (VO-ADOH)** paradigm. At the foundation of this paradigm is **strict Mutable Value Semantics (MVS)** paired with **Second-Class References** (inspired by Hylo and early Rust/Austral designs) and **First-Class Data-Oriented Layout Primitives** (inspired by Odin, Zig, and OxCaml). In this model, every composite instance is a pure value forming a disjoint topological tree rooted at a lexical binding. By prohibiting references from being stored inside structs or returned from functions – and instead expressing all zero-copy access through four parameter-passing conventions (`let`, `inout`, `sink`, `set`) and lexical coroutine projections (`subscript` / `yield`) – CoreX achieves the compile-time "mutable XOR shared" Law of Exclusivity of Rust while eliminating lifetime parameters (`'a`), lifetime variance, and borrow-checker cognitive friction.

On top of this memory model, CoreX unifies five orthogonal semantic rules designed specifically for its target workloads and compiler throughput:
1.  **Bindings and State**: Local bindings default to immutable (`let`) to maximize Static Single Assignment (SSA) folding and local reasoning, while explicit mutable bindings (`var`) enable in-place path-wise mutation (`&x.field += 1`) across disjoint value trees without allocating intermediate copies.
2.  **Data Composition**: CoreX omits class inheritance and per-object virtual pointers (`vptr`), composing data exclusively through algebraic product types (`struct`), niche-optimized sum types (`enum` and `Result[T, E]` / `T?`), and static capability contracts (`trait` with Hylo-style method bundles).
3.  **Control Flow**: Control flow is expression-oriented (`if`, `match`, `loop` with `break val`, and `{ ... }` blocks yield values), eliminating uninitialized temporary variables and lowering deterministically via Maranget decision trees into a **Block-Argument SSA Intermediate Representation (IR)** modeled after MLIR `cf`, Cranelift CLIF, and Swift SIL.
4.  **Data-Oriented Ergonomics**: Cache-optimal layouts are first-class type constructors – specifically Odin-style `#soa[]T` slices that rewrite AoS syntax (`items[i].x`) into contiguous column accesses (`items.x[i]`), Least-Significant-Bit (LSB) integer-backed `bit_field` types projected by value, unboxed 32-bit buffer spans (`Span16 = { off: u16, len: u16 }`), and generational `SlotMap[K, V]` arenas for cycle-free UI widget and entity graphs.
5.  **Compiler Frontend Invariants**: To guarantee sub-100 ms incremental compilation, the frontend enforces **mode-correct Bidirectional Type Checking** (linear time complexity, banning ad-hoc untyped overload disjunctions), strict left-to-right argument evaluation with post-argument callee sequencing, a single-pass **Ghost-Instruction Abstract Interpreter** for exclusivity checking, and static monomorphization with pointer-shape binary deduplication.

Two structural trade-offs in this paradigm require explicit architectural mitigations in the CoreX standard library and compiler diagnostics. First, banning first-class references in data structures introduces the *part-whole conflict* when representing cyclic graphs, doubly-linked lists, string pools, or retained GUI trees; CoreX resolves this without unsafe pointers or reference counting by elevating generational arena keys (`SlotKey[T]`) and Xilem-style declarative `IdPath` lenses to standard library primitives. Second, inline algebraic sum types suffer from severe L1 data cache bloat when a cold variant (such as a 512-byte diagnostic payload) inflates the byte stride of 1,000,000 hot zero-payload variants; the CoreX compiler mitigates this by automatically applying multi-layer bit-pattern niche optimization and emitting a compile-time layout lint whenever variant size disparity exceeds a single 64-byte cache line.

## Comparative Analysis of Systems Programming Paradigms

Designing CoreX requires navigating a central trilemma in systems language design: balancing **runtime efficiency** (avoiding copies, boxing, and garbage collection pauses), **local reasoning** (preventing hidden aliasing and "spooky action at a distance"), and **developer velocity** (maintaining a flat learning curve and instant compilation). Evaluating the five dominant systems programming paradigms against CoreX's workload targets reveals why no existing single paradigm satisfies all constraints without structural synthesis.

> **Visual – Zero-GC Value and Unboxed Region Models Eliminate Runtime Bloat Across Target Workloads:** Empirical comparison across systems paradigms. Top: **Zero-runtime compilation** in Rust and Zig reduces minimal WebAssembly payloads by over 99% compared to Go's bundled garbage collector and scheduler, while TinyGo sacrifices goroutines or memory reclamation to shrink output. Middle: Eliminating minor-heap boxing via OxCaml local modes and unboxed 16-bit spans (*httpz*) more than doubles HTTP/1.1 throughput and cuts parsing latency in half with zero heap allocations. ### 1. Pure Imperative and Procedural Models (C, Odin, Go)

Pure procedural languages prioritize control-flow transparency, flat structural types, and rapid compilation, but diverge sharply in how they manage memory lifetimes and polymorphism. Odin modernizes C's procedural model by replacing undefined behavior and preprocessor macros with distinct typing, zero-initialization by default, bounds-checked slices, first-class Structure-of-Arrays (`#soa`), and an implicit `context` system passed to every procedure. Because Odin avoids global type inference, lifetime solvers, and implicit function overloading, its frontend achieves sub-second compilation – in a developer compilation profile on the Odin forum, type-checking took just 63.315 ms (32.22% of total compile time). Furthermore, Odin's `context.allocator` allows developers to swap heap allocators for per-frame or per-request arena allocators across an entire call tree without polluting function signatures. However, Odin and C rely entirely on manual memory management (`new`, `free`, `delete`) and raw pointers (`^T`, `rawptr`). Without static aliasing or lifetime verification, dangling pointers, double frees, use-after-free bugs, and multithreaded data races remain runtime hazards – detectable in Odin only dynamically via debug-mode `mem.Tracking_Allocator` maps.

Go achieves rapid onboarding and near-instantaneous single-pass compilation by pairing a minimalist imperative syntax with a concurrent tracing garbage collector and goroutine scheduler. While this makes Go highly productive for cloud microservices, its runtime architecture conflicts with CoreX's constraints across three dimensions. First, industry developer comparisons report that Go's embedded runtime and lack of fine-grained dead-code elimination inflate native HTTP server binaries to 15–25 MB (compared to 5–10 MB in Rust) and bloat `wasm32` browser modules to 2–10 MB+ with 100–500 ms runtime initialization pauses. Community benchmarks note that TinyGo can shrink a minimal `wasm32` file to 15.1 KB with the scheduler or 5.95 KB without goroutines and channels, and down to 3.59 KB using `-gc leaking`, but only by sacrificing concurrency primitives or never freeing allocated memory. Second, industry benchmarks indicate that on CPU-bound workloads, Go trails zero-GC native code by 2–10x (and 20–40% on I/O-bound services) while introducing GC tail-latency pauses. Third, as PlanetScale's March 2022 engineering analysis demonstrates, Go 1.18+ implements generics via **GCShape stenciling with runtime dictionaries**: while value/slice constraints (`[]byte | string`) preserve register calling conventions and run at parity with concrete code (e.g., 811 ns generic vs. 930 ns concrete on 16-byte ASCII UTF-8 validation, and 2.67 µs generic vs. 2.63 µs concrete on Japanese UTF-8), all pointer types (`*time.Time`, `*uint64`, `*bytes.Buffer`, `*strings.Builder`) collapse into a single `*uint8` GCShape. Passing a runtime dictionary in the `AX` register on AMD64 shifts argument registers right by one slot and forces dynamic vtable (`itab`) lookups on generic pointer method calls, preventing devirtualization and function inlining.

### 2. Expression-Oriented Algebraic and Imperative Hybrids (Rust, Zig, Kotlin)

Modern systems and application hybrids pair imperative mutation with algebraic sum types (`enum` / tagged `union`) and expression-oriented control flow. Rust demonstrates that C-level execution speed, deterministic memory management, and compact `wasm32` footprints (1.5–2 KB minimal modules in developer comparisons, and ~7.5 KB gzipped across five `SIMD128` numerical compute kernels) can coexist with strict compile-time memory and thread safety. However, Rust achieves this via an affine type system with **first-class references** (`&'a T`, `&'a mut T`) that can be stored in structs and returned from functions. Treating references as first-class types forces the language to propagate explicit lifetime parameters (`'a`) and precise capturing clauses (`+ use<>` in Rust 2024) across type definitions, trait bounds, and closures, creating a multi-week to multi-month learning curve. Architecturally, first-class borrow checking also clashes with traditional retained-mode GUI widget trees and cyclic graphs, while heavy monomorphization and borrow-checking passes increase compile times.

Zig strips away hidden control flow, operator overloading, and garbage collection, offering explicit allocator passing, comptime type reflection (`std.MultiArrayList(T)`), payload-capturing error unions (`!T`), and – in size-tuned browser EVM benchmarks (Guillotine) – roughly 20% smaller `wasm32` binaries than equivalent Rust builds. Yet Zig relies on manual deallocation (`defer`/`errdefer`) without compile-time temporal safety in `ReleaseFast` builds, and two of its low-level design choices introduce compiler and semantic hazards. First, Zig's implicit **Pass-by-Reference Optimization (PRO)** allows the compiler to silently convert by-value struct parameters into `*const noalias T` references; however, as documented in Zig GitHub Issues #16343 and #17580, taking the address of a parameter (`&v`) causes the compiler to copy the entire struct onto the stack on each reference in `ReleaseFast`, causing `&v == &v` to evaluate to `false` and triggering unwanted `memcpy` overhead. Second, allowing first-class pointers to bit-aligned fields inside `packed struct(u64)` required inventing opaque "bit pointers" (`*align(8:10:5) u9`, proposed for replacement by `*packed(u35, 10) u9` in Issue #24061), which break volatile pointer coercions and standard ABI alignment assumptions.

Kotlin exemplifies the ergonomic benefits of expression-oriented syntax, `val`/`var` bindings, exhaustive `when` pattern matching over `sealed` hierarchies, and `@JvmInline value class` wrappers that inline single-property domain types (`UserId`, `Token`, `Meters`) into primitive values at compile time. Nevertheless, Kotlin's object model defaults to heap-allocated reference types managed by a garbage collector, and `@JvmInline` value classes box onto the heap whenever assigned to nullable types, generic parameters, or interface references – violating CoreX's zero-GC and predictable-layout mandate.

### 3. Functional-First Systems Models (Koka, Roc, and OxCaml)

Recent advances in functional language compilation aim to achieve imperative in-place speed without exposing mutable aliases to the programmer. Koka and Roc compile purely functional data transformations using **Perceus** (*PrEcise Reference Counting with rEUse and Specialization*) and the **Functional-But-In-Place (FBIP)** paradigm. Grounded in the $\lambda^1$ linear resource calculus (Reinking, Xie, de Moura, and Leijen, PLDI 2021), Perceus passes parameters as owned and emits reference-count decrements (`drop`) immediately after a variable's last lexical use rather than at scope exit, guaranteeing that cycle-free programs are *garbage-free*. Crucially, Perceus pairs `drop` operations inside pattern-match branches with constructors of identical byte size via a `drop-reuse` token: at runtime, the generated code executes a fast-path uniqueness branch (`if (is_unique(xs))` where `refcount == 1`) to mutate the memory block in place (`ru->left := y`), falling back to fresh heap allocation only when the structure is shared. In the PLDI 2021 benchmark suite (where benchmarks run 1–5 seconds with a peak working set up to 300 MiB), Koka's purely functional FBIP tree performs 42 million red-black tree insertions (`rbtree`) within 10% of C++'s in-place `std::map` while benefiting from 8-byte allocator alignment versus C++'s 16-byte alignment. However, for CoreX, Perceus carries four significant limitations: (1) reference count traffic scales linearly with operations and requires expensive atomic instructions whenever objects are shared across threads; (2) in-place reuse is *opportunistic* at runtime rather than statically guaranteed, meaning an unintended second reference silently degrades an in-place update into a copying allocation path; (3) dropping the last reference to a large tree can trigger a recursive, cascading `drop` chain that affects tail latency; and (4) reference counting cannot reclaim cyclic graphs automatically.

To eliminate GC pauses in low-latency trading and systems workloads, Jane Street's **OxCaml (`5.2.0+flambda2`)** extends OCaml with **modal type axes** – specifically **Locality** (`local` stack/region-bound vs. `global` heap-escaping, where `global < local`), **Uniqueness** (`unique` single-reference vs. `aliased` shared, where `unique < aliased`), and **Affinity/Linearity** (`once` vs. `many` for closures) – alongside **unboxed product types** (`#{}`, `int16#`, `char#`, `float#`) and stack-allocated `let mutable` variables. In Anil Madhavapeddy's February 2026 synthetic `Core_bench` evaluation of `httpz` (an OxCaml HTTP/1.1 parser), replacing standard 4-word minor-heap boxed `Cstruct.t` slices with unboxed 32-bit spans (`type span = #{ off : int16#; len : int16# }`) over a 32 KB `local_` buffer and returning unboxed local tuples via `exclave_` reduced 35-byte request parsing latency from 300+ ns to 154 ns (and 439-byte requests from 2,000+ ns to 1,150 ns), increased throughput from 3 million req/sec to 6.5 million req/sec, and dropped minor-heap allocations from 100–800 words to **zero**. CoreX should directly adopt OxCaml's unboxed value spans and non-escaping local semantics, while making stack/inline value allocation the *universal default* rather than an opt-in modal extension over a garbage-collected runtime.

### 4. Data-Oriented Design (DOD / SoA-First – Odin, Zig, Jai)

Data-Oriented Design organizes software around hardware memory hierarchies – specifically 64-byte CPU cache lines, TLB page locality, and SIMD vector lanes – rather than object-oriented domain nouns. When iterating over a single 4-byte `u32` field inside an Array of Structs (AoS) where each struct is 64 bytes, the CPU fetches an entire 64-byte cache line per element and wastes 15/16ths (60 of 64 bytes, or 93.75%) of the memory bandwidth on unused fields. By transposing the layout into a **Structure of Arrays (SoA)**, 100% of every fetched cache line contains active `u32` elements, enabling compiler auto-vectorization. While Jai and Odin provide compiler-level `#soa` array modifiers that preserve natural `entity[i].field` syntax, pure Entity-Component-System (ECS) archetype tables (which group entities into dense tables for branchless batch loops) fit poorly with sparse, hierarchically ordered GUI and web workloads. Consequently, CoreX should integrate DOD layout primitives (`#soa`, `bit_field`, and `SlotMap` generational arenas) as ergonomic type transformations within a general-purpose algebraic language rather than forcing all application logic into rigid ECS tables.

### 5. Mutable Value Semantics (MVS – Swift vs. Hylo)

Formalized by Racordon, Shabalin, Zheng, Abrahams, and Saeta (Journal of Object Technology, 2022), **Mutable Value Semantics (MVS)** upholds a single foundational law: every variable is an independent value, and all values form disjoint topological trees where no two variables ever share mutable state. Unlike pure functional programming – where updating a deeply nested node `x.left.left.right = v` requires cumbersome functional reconstruction `updateLeft(x, ...)` or runtime refcount checks – MVS supports direct, part-wise **in-place mutation** (`&x.left.left.right = v`) while preserving local reasoning.

Crucially, Swift and Hylo implement MVS in fundamentally different ways. Swift provides MVS for `struct` and `enum` types, using hidden **Atomic Reference Counting (ARC)** and **Copy-on-Write (CoW)** buffers to back variable-sized collections (`Array`, `String`, `Dictionary`). However, Swift compromises strict MVS in four ways that make it unsuitable as a direct blueprint for CoreX: (1) Swift retains reference-type `class` inheritance, reintroducing shared mutable state, data races, and dynamic vtable dispatch; (2) CoW introduces recurring atomic reference-count checks on mutation and creates memory unsoundness hazards when `inout` parameters interact with interior buffer pointers; (3) violating the Law of Exclusivity via closure captures (e.g., passing a variable `inout` while a called closure also accesses it) compiles without error and crashes at **runtime**; and (4) Swift's ABI resilience relies on runtime **Value Witness Tables (VWT)**, heap boxing for unknown-sized existentials, and an overloaded constraint solver susceptible to exponential compile-time stalls.

In contrast, **Hylo (formerly Val)** eliminates GC, ARC, CoW, and reference-type classes entirely. All types are non-copyable and immovable by default unless explicitly conforming to `Copyable` or `Movable`, and copies are explicit (`.copy()`). Instead of first-class reference types, Hylo uses four parameter conventions (`let`, `inout`, `sink`, `set`) and coroutine-based **subscripts** (`subscript ... yield`) to project temporary views of interior values. Verified statically at compile time via ghost instructions in Hylo IR, Hylo achieves Rust-grade memory and concurrency safety with zero runtime overhead and **zero lifetime annotations**.

## State, Mutability, and Value vs. Reference Semantics

### 1. Binding Mutability and Strict Mutable Value Semantics (MVS)

A foundational question for CoreX is whether bindings should default to immutable (`let`/`val`) with explicit mutability (`mut`/`var`), or use Mutable Value Semantics. **The optimal design is a strict synthesis of both**: CoreX enforces **Strict Mutable Value Semantics (MVS)** as its global memory and aliasing discipline, while using **immutable bindings (`let`) by default and explicit mutable bindings (`var`) for local and field declarations**.

In traditional imperative and object-oriented languages (such as Java, Python, Go, or C#), assignment (`b = a`) and argument passing copy a *reference* to shared mutable storage on the heap, creating an arbitrary graph of aliases where mutating `b.pos.x` silently alters `a.pos.x` at a distance. Conversely, pure functional languages preserve local reasoning by outlawing mutation entirely, forcing developers to express a simple in-place tree update (`x.left.left.right = v`) as a deeply nested chain of functional reconstructions (`updateLeft(x, updateLeft(x.left, ...))`) that rely on optimizer heroics or runtime reference-count checks to avoid heap churn.

Under CoreX's strict MVS model, **every composite type (`struct`, `enum`, fixed array `[N]T`, and dynamic collection `Vec[T]`, `Map[K, V]`) has pure value semantics**. Values form **disjoint topological trees** rooted at lexical variables (`let` or `var`): no two variables ever share mutable state, and a whole/part relationship is always represented by logical containment rather than shared pointers. Within this disjoint-tree model, distinguishing `let` (immutable value root) from `var` (mutable value root) establishes two core guarantees. First, **deep mutability inheritance** ensures that mutability is a transitive property of the root binding and access path: if a struct `r` is bound via `let r = Rect(...)`, neither `r` nor any nested sub-part `r.pos.x` can be mutated or passed to an `inout` parameter, whereas if bound via `var r = Rect(...)`, any interior path `&r.pos.x` can be mutated in place without copying the surrounding `Rect`, provided the **Law of Exclusivity** is upheld. Second, **eliminating Copy-on-Write (CoW) and hidden ARC** ensures predictable systems performance: unlike Swift – which emulates value semantics for variable-sized arrays and strings using hidden Atomic Reference Counting and runtime Copy-on-Write checks on mutation – CoreX follows Hylo in making ownership unique and copies explicit. Small register-sized scalar and composite types (such as primitives, `Vec2`, or unboxed `Span16`) implement the marker trait `Copy` (allowing implicit bitwise duplication), whereas heap-owning containers (`Vec[T]`, `String`, `OwnPtr[T]`) are move-only by default and require an explicit `.copy()` or `.clone()` call to duplicate their backing storage.

### 2. Second-Class References, Parameter Conventions, and Subscript Projections

To achieve zero-copy performance without exposing raw pointers or Rust-style lifetime annotations (`'a`), CoreX adopts **Second-Class References** governed by four explicit **parameter-passing conventions** (`let`, `inout`, `sink`, `set`) and **lexical subscript projections**.

As Fernando Borretti's analysis of Rust codebases highlights, roughly 90% of references in systems code are passed solely as arguments to functions, a small fraction are returned to project interior fields, and a vanishingly small percentage are stored inside struct definitions (primarily for exterior iterators). Yet permitting that small fraction of usage – storing references inside arbitrary structs – forces the entire language to adopt lifetime parameters (`struct Iter<'a, T>`), lifetime subtyping variance, higher-ranked trait bounds (`for<'a>`), and complex non-lexical borrow checking.

In CoreX, references are **second-class**: they **cannot** be stored in struct fields or global variables, and they **cannot** be returned as ordinary function values. Instead, references exist strictly as scoped parameter conventions and lexical projections:

*   **`let` Convention (Default Immutable Borrow)**: Written implicitly as `fn process(v: Vec2, data: Vec[u8])` (or explicitly `let v: Vec2`), `let` parameters are notionally passed by immutable value. Semantically, the callee cannot mutate `v` or allow it to escape; operationally, the compiler passes small `let` values in CPU registers and larger `let` values as `const noalias` pointers without copying a single byte. Because the Law of Exclusivity prohibits any concurrent mutable access path (including via closure captures or other threads) for the duration of the call, `let` provides the exact static guarantee of Rust's `&T` without lifetime syntax.
*   **`inout` Convention (Exclusive In-Place Mutation)**: Written as `fn offset(target: inout Vec2, by delta: Vec2)` and invoked with an explicit call-site ampersand `offset(&v, delta)`, `inout` enables zero-copy in-place mutation across function boundaries. Conceptually framed as "move-in/move-out," an `inout` parameter is passed operationally as a unique, non-escaping pointer to the caller's storage. Inside the callee, the function may even temporarily deinitialize (`v.deinit()`) or move out of an `inout` parameter via `sink`, provided it re-initializes the storage (`v = Vec2(...)`) before returning – a pattern that is forbidden on Rust's `&mut T` without `std::mem::replace` or `unsafe` code.
*   **`sink` Convention (Ownership Transfer / Move)**: Written as `fn consume(base: sink Buffer) -> Packet`, `sink` transfers unique ownership of the argument from caller to callee, allowing the value to escape (e.g., be stored in a collection or returned). At the call site, the passed binding's lifetime ends immediately upon invocation (equivalent to Rust's move semantics, and safer than C++ `std::move` because the moved-from variable becomes statically inaccessible rather than left in an indeterminate state).
*   **`set` Convention (Definite Out-Initialization)**: Written as `fn init_buf(target: set Buffer, cap: usize)`, `set` accepts *only* an uninitialized variable binding from the caller and statically guarantees that the callee initializes it on all return paths – providing a safe, zero-cost replacement for C++ placement `new` and out-pointers.

#### Solving the Part-Whole Conflict via Subscripts and Method Bundles

A naive implementation of second-class references encounters two expressivity bottlenecks identified by Borretti: how to project a reference to an interior element of a collection (e.g., `vec[i]` or `min(a, b)`) without copying it, and how to represent graphs, string pools, or iterators without storing references in structs. CoreX resolves both cleanly through language-level projections and generational handles.

First, following Hylo, CoreX provides **`subscript` declarations (Coroutine Reference Transforms)** that *project* a value (via a temporary coroutine `yield`) rather than returning it. When a caller invokes `&scores[i] += 10` or binds a local projection `inout elem = &matrix[row, col]`, control enters the subscript, computes the element address, executes `yield &storage[idx]`, suspends while the caller mutates `elem`, and resumes after the caller's last use of `elem` to run any post-projection cleanup or invariant checks. By supporting **Method and Subscript Bundles** – grouping `let`, `inout`, `sink`, and `set` implementations under a single declaration using `yielded` parameter placeholders – a single `subscript min(x: yielded T, y: yielded T): T` works seamlessly for read-only inspection, in-place mutation (`&min[&a, &b] += 1`), and value consumption.

Second, for cyclic data structures, doubly-linked lists, string pools, and retained UI trees where MVS trees cannot share mutable nodes, CoreX elevates generational **`SlotMap[K, V]` arenas** to a core standard library primitive. Instead of raw integer indices (which risk cross-pool misuse, dangling references, and the ABA problem), a `SlotMap` issues strongly typed 64-bit versioned keys (`SlotKey[T]`, holding up to $2^{32} - 2$ concurrent elements and wrapping versions only after $2^{31}$ deletions and insertions to the exact same slot) where insertion, deletion, and lookup all execute in $O(1)$ time. For iteration, CoreX supports direct `for &elem in slice` range loops (which lower to scoped `inout` projections over contiguous memory) alongside stack-bound generator coroutines.

### 3. Data Composition: Algebraic Data Types and Traits vs. Class Inheritance

CoreX enforces **strict composition over inheritance**: it provides product types (`struct`), tagged sum types (`enum`), untagged C-interop unions (`extern union`), and capability interfaces (`trait`), while **completely omitting class inheritance and subtyping**.

> **Visual – Flat Algebraic Composition and Niche Optimization Eliminate Virtual Pointer and Padding Bloat:** Byte-level memory layouts on 64-bit architectures (8-byte word alignment). **Row 1 (Class Inheritance):** Adding a single virtual method to a 1-byte class inserts a hidden 8-byte *vptr* at offset 0 and forces 7 bytes of trailing alignment padding (16x size inflation); diamond multiple inheritance duplicates base subobjects or adds *vbptr*/*VTT* offset tables. **Row 2 (Unoptimized vs Boxed Enum):** A single 512-byte variant forces every instance of *IngestionEvent* to occupy 520 bytes (9 cache lines), whereas boxing the cold payload shrinks the enum to 16 bytes. **Row 3 (Niche Optimization):** Exploiting invalid bit patterns (0x0 for non-null pointers/integers, 0x02..0xFF for booleans) eliminates the discriminant tag entirely, packing `Option[&T]` into 8 bytes and nested `Option[Option[bool]]` into 1 byte.

#### Why Class Inheritance Hurts Zero-GC Memory Layout and Devirtualization

In a zero-GC systems language, class inheritance introduces five severe penalties across memory layout, cache density, and compiler optimization:
1.  **Per-Instance `vptr` Size and Alignment Inflation**: As documented in PVS-Studio's analysis of C++ object layouts, declaring even a single `virtual` function forces the compiler to embed a hidden 8-byte virtual pointer (`vptr`) at offset `0` of every class instance. Because the 8-byte `vptr` becomes the most alignment-restrictive member of the class, it raises the alignment requirement (`align`) of the entire object to 8 bytes. Consequently, a class containing a single 1-byte `char` field sees its raw data size (`dsize`) jump from 1 byte to 9 bytes, and its physical `sizeof` after trailing alignment padding jump to **16 bytes** – a 16x memory footprint inflation.
2.  **Object Slicing and Mandatory Heap Boxing**: Because derived subclasses append additional fields after the base class layout (`nvsize`), polymorphic objects have heterogeneous byte sizes. Passing a derived instance by value to a function expecting a base class slices off the derived fields; storing a heterogeneous collection of subclasses therefore forces every element to be individually boxed on the heap and accessed through an array of pointers (`Vec<Box<Base>>`), destroying spatial cache locality and inducing heap fragmentation.
3.  **Constructor `vptr` Overwriting Chains**: During object instantiation across an inheritance hierarchy, the base constructor executes first and writes the base `vtable` address into `vptr`, after which each derived constructor overwrites `vptr` with its own table address. This sequential pointer mutation complicates constant folding of object headers when constructors are not fully inlined.
4.  **Multiple and Virtual Inheritance Indirection (`vbptr`, `vbtable`, `VTT`)**: In non-virtual multiple inheritance (the Diamond Problem, such as `Player` inheriting from `Movable` and `Renderable`, both inheriting from `Entity`), the physical memory of `Entity` – including its `vptr` and member fields (`Entity::id`) – is duplicated inside `Player`. Resolving this via `virtual` inheritance requires inserting additional Virtual Base Pointers (`vbptr`) into the instance that point to static offset tables (`vbtable`), alongside passing a Virtual Method Table Hierarchy Table (`VTT`, a "table of tables" in the Itanium ABI) as an implicit constructor parameter to dynamically patch subobject pointers.
5.  **Devirtualization Failure and Pipeline Stalls**: While a direct function call can be inlined – unlocking Scalar Replacement of Aggregates (SROA), loop-invariant code motion, and SIMD vectorization – calling a method through an embedded `vptr` requires loading the `vptr` from the instance, indexing into the `vtable` (which also stores negative-index RTTI pointers and index-0 virtual destructors), and executing an indirect jump. Furthermore, embedding the `vtable` pointer inside the data instance couples behavior to storage: a type cannot retroactively implement a new interface outside its defining module, and non-polymorphic storage still pays the 8-byte `vptr` tax.

#### Algebraic Sum Types, Niche Optimization, and Variant Skew Diagnostics

By replacing class hierarchies with **closed algebraic sum types (`enum`)** for known variant sets and **external witness tables (`dyn Trait` fat pointers)** for open polymorphism, CoreX stores polymorphic data inline in contiguous arrays without per-instance heap allocation or `vptr` headers. As Raph Levien notes in the architecture of Xilem and Masonry, restricting UI elements to a semi-fixed set of declarative algebraic primitives eliminates `Box<dyn Widget>` vtable bloat and allows widget methods to be directly inlined.

To ensure sum types remain zero-cost in memory, CoreX adopts two layout mechanisms from Rust and Odin. First, **Bit-Pattern Niche Optimization and Niche Stacking** eliminate discriminant tags whenever a payload type contains invalid bit patterns (niches). Formally, the size of a naive tagged enum is $\text{Max}(\text{Variant Payload}) + \text{Discriminant Tag} + \text{Alignment Padding}$. However, non-null pointers (`OwnPtr[T]`, `NonNull[T]`), scoped projections (`&let T`, `&inout T`), and non-zero integers (`NonZeroU64`, `NonZeroU32`) possess 1 niche at `0x0`, allowing `Option[OwnPtr[T]]` (`OwnPtr[T]?`) and `Option[NonZeroU64]` (`NonZeroU64?`) to occupy **8 bytes** with zero tag overhead (matching Odin's `Maybe(^T)` optimization). Similarly, `bool` occupies 1 byte (`0x00` = `false`, `0x01` = `true`), leaving **254 niches** (`0x02..=0xFF`), while Unicode scalar `char` leaves unused bit ranges above `0x10FFFF`. CoreX propagates remaining niches upward through structs and nested enums (*niche stacking*): `Option[bool]` (`bool?`) consumes byte value `2` for `None` (leaving 253 niches), and `Option[Option[bool]]` (`bool??`) consumes value `3`, fitting up to 254 unit variants wrapping a `bool` inside a **single byte**.

Second, CoreX provides **Variant Size Disparity Mitigation (Cold-Path Boxing)**. A major hazard of inline sum types occurs when one variant's payload dominates all others. As analyzed by Zeba Academy, consider an event stream `enum IngestionEvent { Heartbeat, Ack(u64), Error(DiagnosticPayload) }` where `DiagnosticPayload` is 512 bytes (`u64` + `[504]u8`). The compiler must size every `IngestionEvent` slot to **520 bytes** (512B payload + 1B tag + 7B alignment padding), spanning **9 discrete 64-byte cache lines** (520 / 64 = 8.125). In a 1,000,000-element buffer where 99.99% of events are zero-payload `Heartbeat`s, the array consumes **520 MB** of RAM instead of 1–16 MB, filling 512 of every 520 fetched bytes with dead zero-padding, breaking hardware stride prefetchers, and causing effective L1d cache capacity to plummet by **over 99%**. Wrapping the cold variant in a heap pointer (`Error(OwnPtr[DiagnosticPayload])`) or storing error payloads in a side-band `Diagnostics` struct (as in Zig's `union(enum)` diagnostics pattern) collapses the enum stride from 520 bytes to **16 bytes** – shrinking the 1,000,000-element hot array from 520 MB to **16 MB** so it fits within L3 cache. CoreX therefore mandates a built-in compiler lint (`@warn(variant_size_skew)`) whenever the largest variant exceeds the second-largest variant by more than 64 bytes (one cache line).

## Expression-Orientation, Control Flow, and SSA IR Lowering

### 1. Expression-Oriented Control Flow vs. Statement-Oriented Imperative Flow

Statement-oriented languages (such as C, Go, Odin, and traditional Swift control flow) treat branching constructs (`if`, `switch`) strictly as control-transfer statements rather than value-producing expressions. When initializing a variable conditionally in a statement-oriented language, a developer must either use a terse ternary operator (`a ? b : c`, which scales poorly to multi-line branches and pattern destructuring) or declare a mutable variable outside the branch and assign to it inside each arm:

```cx
// Anti-pattern forced by statement-oriented control flow:
var status_code: u16 = 0 // Forced mutability and dummy zero-init
if request.is_authenticated() {
    status_code = 200
} else {
    status_code = 401
}
```

This statement-oriented pattern degrades both developer ergonomics and compiler verification: it forces bindings that are conceptually constant after initialization to be declared mutable (`var`), introduces dummy default values that mask uninitialized-branch bugs, and splits variable declaration from definition.

By making **control flow expression-oriented** (following Rust, Zig, Kotlin, and ML-family languages), CoreX allows `if ... else`, `match`, `loop { break val }`, and lexical blocks `{ stmt*; final_expr }` to evaluate directly to typed values. Combined with Zig-style **payload captures** (`|val|` for immutable value/projection capture and `|&val|` for `inout` mutable projection capture) across `if`, `while`, `for`, `match`, and `catch`, expression orientation eliminates boilerplate temporary state:

```cx
// Idiomatic CoreX expression-oriented initialization with payload capture:
let status_code: u16 = if req.auth_token |token| {
    match verify_token(token) {
        .Valid(user) => if user.is_admin { 200 } else { 202 },
        .Expired     => 401,
        .Revoked     => 403,
    }
} else {
    400
}
```

To prevent accidental value returns or unreadable deeply nested expressions, CoreX enforces two syntactic guardrails:
1.  **Explicit Unit Semicolon Rule**: In any block `{ s_1; s_2; e }`, if the final item ends with a semicolon (or is a statement keyword like `defer`), the block evaluates to the zero-sized `void` (`()`) unit type; omitting the trailing semicolon on the final expression yields its value as the block result.
2.  **Checked Branch Symmetry**: An `if` expression used in a value-producing position *must* have an exhaustive `else` branch whose type unifies with the `then` branch (or diverges via `return`, `break`, `continue`, or `unreachable`, which inhabit the bottom type `never` / `noreturn`).

> **Visual – Expression Control Flow and MVS Projections Lower Directly to Block-Argument SSA:** The CoreX frontend compilation pipeline. **Stage 1** runs linear-time bidirectional type checking without exponential overload search. **Stage 2** compiles nested pattern matches into optimal decision trees while verifying exhaustiveness and redundancy in a single pass. **Stage 3** lowers expression branches directly into SSA basic blocks using MLIR/Cranelift-style block arguments instead of phi nodes. **Stage 4** runs a forward abstract interpreter over ghost lifetime instructions to verify the Law of Exclusivity and elide copies before machine code generation.

### 2. Direct Lowering to Block-Argument SSA IR

Expression-oriented control flow is not merely an ergonomic convenience; it is structurally isomorphic to **Static Single Assignment (SSA) form**, where every value has a unique definition that dominates all of its uses.

Modern compiler middle-ends and backends – including **MLIR (`cf` / `scf` dialects), Cranelift (CLIF), Swift SIL, and TC-SSA** – replace traditional LLVM-style $\phi$ (phi) nodes at the top of basic blocks with **Basic Block Arguments**. Under block-argument SSA, basic blocks are parameterized like lightweight local functions (`^join(%res: i32):`), and control-flow terminators pass SSA values directly as arguments along the outgoing edge (`br ^join(%v1)`). Out-of-SSA register allocation simply treats terminator arguments as parallel edge copies.

When CoreX compiles an expression-oriented `if` or `match` binding using Matthias Braun et al.'s **Simple and Efficient Forward SSA Construction Algorithm**, lowering proceeds in a single forward AST traversal without requiring a prior dominance frontier pass:
1.  **Acyclic Expression Lowering (`if` / `match`)**: Because every expression branch (`then` and `else`) explicitly yields a value on its final line, the frontend does not need variable look-up recursion across predecessors for the expression result: it emits `cond_br %cond, ^then, ^else`, evaluates each branch to `%val_then` and `%val_else`, emits `br ^join(%val_then)` and `br ^join(%val_else)`, and binds the result directly to the block argument of the sealed join block `^join(%result: T):`.
2.  **Cyclic Variable Mutation (`while` / `for` / `loop` with `var`)**: When a local mutable variable `var acc = 0` is read or mutated inside a loop under construction, the loop header block (`^head`) has an incomplete Control Flow Graph (CFG) because the back-edge from the loop body exit has not yet been constructed. Following Braun's algorithm, `^head` remains **unsealed** during loop body construction: looking up `acc` inside `^head` places a proxy block argument (`%acc_phi`) into `incompletePhis[^head]`. Once the loop body is filled and the back-edge `br ^head(%acc_next)` is wired, the compiler invokes `sealBlock(^head)`, resolving the block argument operands and eliminating trivial single-value proxies.

```llvm
// CoreX Source:
// let res: i32 = if cond { a + 1 } else { b * 2 }
//
// Lowered CoreX Block-Argument SSA IR (TC-SSA / Cranelift style):
^entry(%cond: i1, %a: i32, %b: i32):
  cond_br %cond, ^then, ^else
^then:
  %t0 = add %a, const 1 : i32
  br ^join(%t0)
^else:
  %e0 = mul %b, const 2 : i32
  br ^join(%e0)
^join(%res: i32):
  ret %res
```

### 3. Pattern Matching Compilation via Maranget Decision Trees

To compile `match` expressions over deeply nested algebraic sum types, structs, and tuples into compact jump tables, the CoreX frontend implements **Luc Maranget's Pattern Matrix Decision Tree Algorithm** (2008) augmented with **Jules Jacobs' Clause-Frequency Heuristic** (2021).

Naive top-to-bottom pattern matching tests each arm sequentially from scratch, repeating tag comparisons on outer constructors whenever an inner nested pattern fails. Conversely, Maranget's algorithm represents the `match` arms as a **pattern matrix** (where each row corresponds to a clause and each column corresponds to a sub-scrutinee access path tracked in an **occurrence vector**, with right-hand-side expressions stored in an **action vector**). Tuples and structs are flattened directly into their component columns in the matrix so that matrix cells contain only refutable constructors or wildcards.

The compiler recursively reduces the clauses into primitive single-constructor switch nodes (`match#`) using five deterministic steps:
1.  **Normalize Variable Bindings**: Bare variable patterns (`a is x`) are pushed into the right-hand-side action expression as `let` bindings (`let x = a`), leaving only constructor tests (`a is C(P_1, ..., P_n)`) in the clause list.
2.  **Evaluate Base Cases**: If the first clause has **zero remaining constructor tests** (an irrefutable row of wildcards), matching has succeeded and the compiler emits a leaf node jumping to the right-hand-side action block `^arm_i`; conversely, if the clause list is **empty**, all patterns have failed and the compiler emits a `NonExhaustiveError` leaf node.
3.  **Apply Branching Heuristic to Prevent Code Duplication**: When splitting the matrix on a constructor test `a is C(P_1, ..., P_n)` from the first clause into two sub-problems – `[A]` (where `a` matches `C`) and `[B]` (where `a` does not match `C`) – any subsequent clause that *contains no test on variable `a`* (Case c) must be copied into **both** `[A]` and `[B]`. For example, when matching `Add(Add(x, y), Zero)` and `Add(Mul(x, y), Zero)` followed by `Add(x, Mul(y, z))`, testing the left child `a_1` first duplicates the later clauses across both branches, whereas testing the right child `a_2 is Zero` first produces zero duplication. CoreX therefore selects the candidate test from the first clause that **appears in the maximum number of remaining clauses**, greedily minimizing Case (c) duplication.
4.  **Fuse Multi-Way Switches**: Consecutive `match#` tests on different constructors of the same sum-type occurrence variable `a` are fused into a single multi-way SSA `switch %tag_a [c_1: ^b_1, ..., c_k: ^b_k] default ^def` terminator.
5.  **Verify Exhaustiveness and Redundancy in One Pass**: By tracking the set of remaining possible constructors for each variable's type along every branch, the compiler omits impossible default branches. Once the decision tree is constructed, the `match` expression is exhaustive if and only if **zero** `NonExhaustiveError` leaf nodes exist in the generated tree; furthermore, every original clause right-hand side $e_i$ must appear in at least one leaf of the decision tree, and any clause absent from the leaves is flagged as a redundant/unreachable pattern.

## First-Class Data-Oriented Ergonomics Across Target Workloads

To deliver C-level hardware utilization without forcing application developers to write verbose boilerplate, CoreX integrates four data-oriented layout primitives directly into its type system and standard library.

> **Visual – Contiguous Column Layouts and Packed 64-Bit Tapes Maximize Cache Bandwidth:** Hardware memory efficiency of CoreX data-oriented primitives. **Top Panel (64-Byte Cache Line Utilization):** When updating a single 4-byte *u32* field (such as *hp*) across 64-byte entity structs, a standard Array-of-Structs (AoS) layout wastes 93.75% (60 of 64 bytes) of every DRAM cache-line fetch on unused fields. CoreX's *#soa[]T* slice transposes fields into contiguous columns while preserving *entities[i].hp* syntax, achieving 100% cache-line utilization (16 active elements per 64-byte fetch) and direct SIMD vectorization. **Bottom Panel (Zero-Allocation Web & Systems Primitives):** Exact register-level bit layouts for CoreX's unboxed 32-bit HTTP buffer span, LSB-ordered *bit_field*, and 64-bit *simdjson*-style branchless DOM tape element.

### 1. First-Class `#soa` Containers and `soa_zip` Iteration Views

In languages that relegate Structure-of-Arrays (SoA) to a library container via compile-time reflection – such as Zig's `std.MultiArrayList(T)` – switching a hot collection from AoS (`ArrayList(T)`) to SoA requires rewriting every access site. Instead of writing `monsters[i].hp += 5`, the developer must explicitly extract field slices via `const s = monsters.slice(); s.items(.hp)[i] += 5`, and reassembling a whole struct requires calling `monsters.get(i)` or `monsters.set(i, val)`. Making `a[i].x = 123` act as zero-cost syntactic sugar for `a.x[i] = 123` cannot be achieved purely through library metaprogramming in a language without lvalue-rewriting semantics; it requires language-level semantics.

CoreX adopts Odin's first-class **`#soa` type modifier** across fixed arrays (`#soa[N]T`), slices (`#soa[]T`), and dynamic arrays (`#soa Vec[T]`). Given `struct Particle { pos: Vec3, vel: Vec3, hp: u32 }` and `var p: #soa[1024]Particle`, the compiler physically lays out `p` in memory as three contiguous arrays (`pos: [1024]Vec3`, `vel: [1024]Vec3`, `hp: [1024]u32`). However, the developer can access elements using either AoS syntax (`p[i].hp = 100`) or columnar SoA syntax (`p.hp[i] = 100`), and both expressions resolve to the **exact same memory address** (`&p[i].hp == &p.hp[i]`). For dynamic `#soa Vec[T]` and `#soa[]T` slices, CoreX allocates a single contiguous aligned backing buffer partitioned into field columns while exposing zero-copy column slices (`p.hp` yields `[]u32`) for direct SIMD operations. Furthermore, when working with separate slices (e.g., in web analytics or UI layout passes), `let view = soa_zip(a: xs, b: ys, c: zs)` constructs a virtual `#soa` slice view (and `soa_unzip` recovers the underlying slices) without copying memory. Iterating via `for &v, i in view` does **not** materialize a temporary AoS struct on each loop iteration; instead, the compiler uses a specialized addressing mode where reading or mutating `v.a` lowers directly to `xs[i]`. Projecting an entire element via `&p[i]` to a helper function taking `elem: inout #soa Particle` passes a lightweight fat handle (`base_soa_ptr + index: usize`) rather than gathering/scattering fields onto the stack.

### 2. Deterministic `bit_field` and `bit_set` Types Without Bit-Pointer Footguns

Systems, networking, and embedded/WASM protocols frequently pack sub-byte integers, flags, and enums into compact headers. C's struct bitfields (`int x : 3;`) are non-portable because ISO C99 (§6.7.2.1.10) leaves bit allocation ordering (high-to-low vs. low-to-high) implementation-defined. Conversely, Zig's `packed struct(u64)` defines a portable layout, but because Zig permits taking first-class pointers to arbitrary fields (`&foo.bar`), it had to introduce bit-offset pointers (`*align(8:10:5) u9` or `*packed(u35, 10) u9`) that complicate the type system and break when coerced to volatile or ABI-aligned pointers.

CoreX achieves bit-level determinism *without* bit pointers by combining **Odin's `bit_field` / `bit_set` types** with **Hylo's `inout` value projections**:
*   **Explicit Backing Integer and LSB Ordering**: A `bit_field` in CoreX explicitly declares its backing integer or fixed-length integer array (`bit_field u16`, `bit_field u64`, `bit_field [4]u8`) and packs Integer, Boolean, or Enum fields strictly from **Least-Significant-Bit (LSB)** upward:

    ```cx
    type FrameHeader = bit_field u16 {
        fin:    bool   | 1, // Bit 0
        opcode: Opcode | 4, // Bits 1..4 (enum u8)
        delta:  i16    | 6, // Bits 5..10 (signed integers auto sign-extend on read)
        rsv:    u8     | 5, // Bits 11..15
    }
    ```

*   **Projection-by-Value Instead of Bit Pointers**: Because CoreX uses second-class references, you cannot take a raw byte address (`*u8`) of a non-byte-aligned bitfield. However, passing `&header.delta` to a function expecting `x: inout i16` works safely! Following the Ada parameter-mode and Hylo subscript-synthesis model, the compiler lowers an `inout` projection of a bitfield into a synthesized `let`/`set` subscript bundle: it extracts and sign-extends the 6-bit value into a CPU register before the call (or `yield`), lets the callee operate on a native register-aligned `i16`, and truncates/masks the updated bits back into `header` upon return.
*   **First-Class `bit_set` Flag Sets**: When all fields are 1-bit boolean flags over an enum or character range, CoreX provides `bit_set[MyEnum; u32]` (supporting set union `|`, intersection `&`, difference `&~`, symmetric difference `~`, and membership `e in set`) backed by an explicit integer size.

### 3. Ergonomic Alignment with CoreX's Three Target Workloads

#### High-Throughput, Low-Latency Web Backends and APIs

Web servers spend a substantial share of CPU cycles parsing HTTP headers, serializing/deserializing JSON, and managing per-request memory. CoreX optimizes web backends through three mechanisms. First, **Implicit Context Arena Per Request**: following Odin, CoreX's default calling convention passes an implicit `context` pointer containing `context.allocator` and `context.logger`. When an HTTP worker accepts a connection or request, it binds a stack- or pool-backed bump-pointer `Arena` to `context.allocator` for that scope; all downstream string formatting, dynamic array growth, and routing allocations occur as $O(1)$ pointer bumps in contiguous cache and are released in bulk when the request handler returns – achieving zero GC activity. Second, **Unboxed Small-Integer Spans**: inspired by OxCaml's `httpz` parser, CoreX's standard library provides `Span16 = struct { off: u16, len: u16 }` alongside standard pointer-length slices `[]u8`. When parsing an HTTP request from a 32 KB buffer, header keys and values are returned as unboxed 4-byte `Span16` values packed directly into CPU registers – enabling the zero-allocation, 154 ns parsing latency and 6.5M req/sec throughput demonstrated by `httpz`. Third, **SIMD-Friendly Contiguous Tape DOM (`std.json.Tape`)**: traditional scalar JSON parsers allocate a pointer-heavy tree of heap nodes and branch byte-by-byte on escape rules, causing frequent L1/L2 cache misses and branch mispredictions. CoreX's standard JSON module adopts the **simdjson 64-bit contiguous tape layout** (`[]u64` arena allocation plus a contiguous UTF-8 string buffer where strings carry a 4-byte `u32` length header and null terminator). Each tape node is a single 64-bit little-endian word $\text{Element} = (\text{'c'} \ll 56) + x$, where `'c'` is the 8-bit ASCII node tag (`'t'`, `'f'`, `'n'`, `'l'`, `'u'`, `'d'`, `'"'`, `'{'`, `'}'`, `'['`, `']'`, `'r'`) and the 56-bit payload `x` stores either the string tape byte offset (for `'"'`) or **$1 + \text{the tape index of the matching closing bracket}$** (for `'{'` and `'['`). Calling `obj.skip()` on an unneeded JSON sub-tree simply reads `x` and jumps past the scope in $O(1)$ time, while 64-bit integers (`'l'`, `'u'`) and IEEE 754 doubles (`'d'`) reside inline in the immediately following 64-bit tape word.

#### Ultra-Fast CLI Tools and Rich Terminal UIs (TUIs)

Because CoreX compiles ahead-of-time with zero runtime or GC initialization, CLI tools launch with near-zero cold start. For rich TUIs, CoreX adopts **Ratatui's immediate-mode buffer-diffing architecture**. Every render cycle invokes `terminal.draw(fn(frame: inout Frame) { ... })`, where `Frame` holds a flat, contiguous 2D buffer of `Cell` value structs indexed by `u16` `x` and `y` coordinates. Screen space is partitioned dynamically using a Cassowary constraint solver (`Layout.vertical([.Length(1), .Length(3), .Min(1)]).split(frame.area())`) into stack-allocated `Rect` values. Widgets are lightweight value structs implementing `trait Widget { fn render(self, area: Rect, buf: inout Buffer) }`. At the end of the closure, CoreX diffs the current `Buffer` against the previous frame's `Buffer` (supporting cell-level diff controls like `CellDiffOption`) and emits only the changed cells to the terminal backend. Because MVS guarantees that `frame: inout Frame` is exclusively owned during rendering, widgets can read application state (`let app: AppState`) without borrow-checker conflicts or hidden cloning.

#### Lightweight Web Applications (`wasm32`) and Native GUIs

Targeting both browser `wasm32` and native desktop/mobile GUIs with a single zero-GC language requires tiny binary payloads and a borrow-safe reactive UI architecture. By avoiding a garbage collector, green-thread scheduler, and reflection metadata tables, CoreX matches Rust and Zig in compiling freestanding `wasm32` modules down to **1.5–10 KB** (with first-class `@Vector(N, T)` SIMD128 intrinsics), avoiding Go's 2–10 MB+ WASM download footprint.

For GUI state management, as Raph Levien demonstrated in his evaluation of non-GC Rust UI architectures, pure immediate-mode GUIs (`egui`) struggle with complex layout and accessibility trees, the Elm Architecture (`Iced`) requires verbose global message enums and hinders component modularity, and React-style hooks (`Dioxus`) rely on shared interior mutability that clashes with static exclusivity. CoreX's native and WASM UI framework (`cx.ui`) therefore implements the **Xilem / Masonry layered architecture** tailored to Mutable Value Semantics:
1.  **Stateless Value View Tree**: Application components are pure functions mapping `AppState` to a short-lived, statically typed **View Tree** composed of value structs (with an explicit `AnyView` type-erased escape hatch when dynamic UI reconfiguration is required).
2.  **Library-Owned `SlotMap` Widget Storage**: Instead of parent widgets owning child widgets via pointer vectors (`Vec<Pod<ChildWidget>>` or `Box<dyn Widget>`), all long-lived retained **Widgets** and **View States** are stored centrally in a generational **`SlotMap[WidgetId, WidgetNode]`** owned by the UI framework. Parent containers hold compact `WidgetId` slotmap keys, enabling $O(1)$ focused event targeting, straightforward tree inspection, and zero-vtable inlined widget methods.
3.  **Direct `&inout AppState` Event Routing via `IdPath` and `Adapt` Lenses**: When a user interacts with a widget, the platform tags the event with the widget's **`IdPath`** (the sequence of structural node IDs from root to leaf). The UI runtime routes the event down the View Tree while threading an exclusive mutable projection of the application state (`state: inout AppState`). When passing through a modular sub-component boundary, an **`Adapt` (lens) node** maps the parent state projection into a child state projection (`fn(parent: inout ParentState) -> yielded ChildState`) – allowing the leaf callback `fn(count: inout i32) { &count += 1 }` to mutate application state directly in place without `Rc<RefCell<T>>`, observer patterns, or global Elm message boilerplate.

### Axis 1: Binding Mutability and Scoped State (`let` vs. `var`)

1.  **Default Immutability (`let`)**: Declaring `let x = expr` binds `x` to an immutable value tree. Neither `x` nor any interior field or element of `x` may be reassigned or projected as `inout` (`&x`).
2.  **Explicit Value Mutability (`var`)**: Declaring `var x = expr` binds `x` to a mutable value tree. Any sub-path `x.f1.f2[i]` may be mutated in place, provided all mutations are explicitly marked with a leading ampersand (`&x.f1.f2[i] += 1` or `mutate(&x.f1)`) so state modifications are visually unmistakable at every call and assignment site.
3.  **Explicit Copying vs. Implicit Bitwise `Copy`**: Types whose values fit within 16 bytes and own no heap resources (scalars, small math vectors, `Span16`, `SlotKey[T]`, `bit_field`) may implement the marker trait `Copy`. All heap-owning or resource-owning types (`Vec[T]`, `String`, `Map[K, V]`, `File`, `Socket`) are **move-only (`~Copy`)**: assigning or passing them to a `sink` parameter moves ownership and ends the source binding's lifetime, whereas duplicating their heap buffer requires an explicit `.copy()` or `.clone()` call.

### Axis 2: Value vs. Reference Semantics (Strict MVS, Parameter Modes, and Subscripts)

1.  **Disjoint Topological Value Trees**: Variables never share mutable state. There are no first-class safe reference types (`&'a T` cannot appear as a struct field type or function return type).
2.  **Four Parameter-Passing Conventions**: In `let` (the default), the callee receives an immutable borrow for the duration of the call that cannot escape. In `inout`, the callee receives an exclusive mutable borrow passed with `&arg` at the call site; the parameter must be valid at entry and exit, though the callee may temporarily move or deinitialize it via `sink` if it is re-initialized before exit. In `sink`, ownership transfers from caller to callee (move), consuming the argument at the call site and allowing the value to escape or be destroyed. In `set`, the callee initializes an uninitialized binding passed by the caller (`var out: Packet; init_packet(&set out, raw_bytes)`).
3.  **Subscript Projections and Method Bundles**: Interior access into structs and collections is expressed via `subscript` declarations that `yield` a projected value (`let`, `inout`, `sink`, or `set`) back to the caller's lexical scope without copying or exposing lifetime parameters:

    ```cx
    type RingBuffer[T] = struct {
        buf:  []T,
        head: usize,
        len:  usize,
    }

    impl[T] RingBuffer[T] {
        // Subscript bundle automatically selects let, inout, or set based on caller usage:
        pub subscript(idx: usize): T {
            let {
                assert(idx < self.len)
                yield self.buf[(self.head + idx) % self.buf.len]
            }
            inout {
                assert(idx < self.len)
                yield &self.buf[(self.head + idx) % self.buf.len]
            }
        }

        // Method bundle consolidating let, inout, and sink variants under one name:
        pub fn offset_head(by delta: usize) -> Self {
            let   { return RingBuffer(buf: self.buf, head: (self.head + delta) % self.buf.len, len: self.len) }
            inout { &self.head = (self.head + delta) % self.buf.len }
            sink  { &self.head = (self.head + delta) % self.buf.len; return self }
        }
    }
    ```

### Axis 3: Composition Over Inheritance (Structs, Traits, and DOD Primitives)

1.  **Product Types and Layout Modifiers**: `struct` types have deterministic field ordering optimized for alignment by default (placing largest fields and largest niches first), with explicit `@repr(C)` for FFI, `bit_field BackingInt { ... }` for LSB bit-packing, and `#soa` for columnar arrays/slices.
2.  **Trait Contracts Without Inheritance**: Behavior is shared across types via `trait` definitions (supporting associated types, default method implementations, and method bundles). Structs cannot inherit fields from other structs; instead, CoreX supports Odin-style explicit composition (with optional `using field: BaseStruct` field-access forwarding that entails zero `vptr` overhead and zero subtyping boxing).

### Axis 4: Algebraic Sum Types and Value-Based Error Unions

1.  **Niche-Optimized Tagged Enums**: Sum types (`enum`) support unit variants, tuple payloads, and struct payloads (`enum Shape { Circle(f64), Rect { w: f64, h: f64 }, Point }`). The compiler automatically tracks invalid bit patterns (niches) across all primitives and structs to elide discriminant tags whenever possible.
2.  **Zero-Cost Value Error Handling (`Result[T, E]`) and Diagnostics**: Instead of C++ exceptions (which require complex unwinding tables and hidden control flow), CoreX adopts value-based **`Result[T, E]`** (synthesized from Zig's error unions `E!T` and Rust's niche-optimized `Result` in `DR-03` and `DR-07`) combined with algebraic error sets. When the compiler can prove no error occurs on a path (`Result[u32, never]`), the return type lowers to the exact representation of a plain `u32`. Callers propagate errors via postfix `expr?`, handle them inline via `expr catch |err| { ... }`, and attach rich diagnostic payloads (such as SQLite error codes or file paths) into a scoped `context.diagnostics` slot without inflating the size of the returned error value.

### Axis 5: Expression-Oriented Control Flow and Lexical Resource Cleanup

1.  **Unified Expression Grammar**: `if`, `match`, `loop`, and `{ ... }` blocks are expressions that can appear on the right-hand side of `let`/`var` bindings, as function arguments, or as implicit block return values.
2.  **Explicit Lexical `defer` and `errdefer` + Linear Resource Verification**: To uphold Zig and Austral's "no hidden control flow" guarantee while maintaining Hylo/Rust's compile-time resource safety, CoreX does **not** insert hidden C++-style RAII destructor calls at every scope exit. Instead, types holding external resources (memory allocations, file descriptors, sockets, mutex guards) do not conform to `ImplicitDrop` (they are *linear* or *explicit-deinit* types): the compiler's abstract interpreter statically requires that every such binding is either moved via `sink`, consumed by a destructor method (`file.close()`), or registered in a lexical **`defer`** / **`errdefer |err|`** statement before scope exit. This gives developers visible control flow (`defer arena.reset()`) with a compile-time guarantee that forgetting a cleanup action is a build error rather than a resource leak.

## Deliverable 2: Semantic Invariants for the Compiler Frontend

To guarantee that CoreX compiles large codebases rapidly while upholding strict memory safety and C-level code generation, the compiler frontend enforces six formal invariants.

### 1. Linear-Time Bidirectional Type Checking and Overload Invariants

A critical lesson from Swift's compiler architecture is how easily type inference can degrade into exponential $\mathcal{O}(c^n)$ time complexity and NP-complete Boolean Satisfiability (SAT) problems. As documented by Matt Gallagher (*Cocoa with Love*) and Chris Lattner, in Swift's constraint solver (`CSSolver.cpp`), integer and float literals are untyped protocol constraints (`ExpressibleByIntegerLiteral`), and operators like `infix +` have up to 28 implementations in the standard library. When an expression chains multiple overloaded operators with unannotated closure parameters, the solver constructs an $n$-dimensional Cartesian product of overload disjunctions – requiring up to 1,190 guesses for `let a: Double = 0 + 1 + -(2)` and taking 20 seconds in Swift 3.1 to compile `let g: Double = -(1 + 2) + -(3 + 4) + 5` (or 6.2 seconds in Swift 6 on a single-line `+` type mismatch). Specifically, linearizing type inference becomes impossible whenever: (1) overloaded function signatures have *uninformative parameter configurations* (where knowing one parameter's type does not narrow the remaining overload candidates, such as `X(F,F,T) -> F` vs `X(F,T,F) -> T`), or (2) *cross-branch variable coupling* links unrelated branches of an expression tree through an unannotated closure parameter referenced multiple times.

To guarantee **linear-time type checking**, the CoreX type checker enforces **Mode-Correct Bidirectional Typing** (following Dunfield and Krishnaswami) governed by four frontend invariants:

1.  **Bifurcated Synthesis ($\Rightarrow$) and Checking ($\Leftarrow$) Judgments**: The typing context $\Delta$ maps every in-scope binding to a known synthesized type ($\Delta ::= \cdot \mid \Delta, x \Rightarrow \tau$) without global unification variables. In **Synthesis Mode ($\Delta^+ \vdash e^+ \Rightarrow \tau^-$)**, given context $\Delta$ and expression $e$ as inputs, the compiler computes output type $\tau$ bottom-up (used for variables, literals with default types, field/tuple projections $\pi_i(e)$, annotated expressions $(e : \tau)$, and function calls $e_1(e_2)$). In **Checking Mode ($\Delta^+ \vdash e^+ \Leftarrow \tau^+$)**, given context $\Delta$, expression $e$, and expected target type $\tau$ as inputs, the compiler verifies conformance top-down (used for anonymous closures $\lambda x.\, e$, struct/array literals, implicit enum selectors `.Variant`, and branching expressions `if` / `match`):
    $$\frac{(x \Rightarrow \tau) \in \Delta}{\Delta \vdash x \Rightarrow \tau} \;(\text{Var}\Rightarrow) \qquad \frac{\Delta \vdash e_1 \Rightarrow \tau_2 \rightarrow \tau_1 \quad \Delta \vdash e_2 \Leftarrow \tau_2}{\Delta \vdash e_1(e_2) \Rightarrow \tau_1} \;(\text{App}\Rightarrow)$$
    $$\frac{\Delta, x \Rightarrow \tau_1 \vdash e \Leftarrow \tau_2}{\Delta \vdash (\text{fn}(x)\; e) \Leftarrow \tau_1 \rightarrow \tau_2} \;(\text{Lam}\Leftarrow) \qquad \frac{\Delta \vdash e \Rightarrow \sum_{i \in I}(i : \tau_i) \quad \forall i \in I.\; \Delta, x_i \Rightarrow \tau_i \vdash e'_i \Leftarrow \tau'}{\Delta \vdash \text{match } e \; \{ i(x_i) \Rightarrow e'_i \}_{i \in I} \Leftarrow \tau'} \;(\text{Match}\Leftarrow)$$
2.  **Mandatory Signature Annotations at Function Boundaries**: Top-level and member functions must declare explicit parameter and return types. Hindley-Milner global polymorphic inference across unannotated functions is prohibited.
3.  **Ban on Implicit Ad-Hoc Function Overloading**: CoreX prohibits C++/Swift-style implicit ad-hoc function overloading. Arithmetic and comparison operators (`+`, `-`, `*`, `==`) are bound to single canonical traits (`Add[Rhs = Self]`, `Eq`) where the left-hand operand's synthesized type uniquely determines the implementation in $O(1)$ time without disjunction search. When a developer wants a single procedure name to dispatch across distinct concrete types, CoreX provides Odin's **Explicit Overload Groups** (`to_str :: fn{ bool_to_str, int_to_str }`), which require all member signatures to be mutually disjoint on their first differing parameter.
4.  **Defaulted Untyped Literals and Checked Closures**: Numeric literals adapt to a known target type $\tau$ in Checking Mode ($\Delta \vdash 42 \Leftarrow \text{u16}$ checks range fit `[0..65535]` at compile time) and default immediately to `i64` (`Int`) or `f64` (`Float64`) in Synthesis Mode without creating constraint disjunctions. Unannotated closures (`fn(x) { ... }`) are valid *only* in Checking Mode ($\Leftarrow \tau_1 \rightarrow \tau_2$), propagating $\tau_1$ into $\Delta$ before checking the closure body and preventing cross-branch SAT coupling.

### 2. Strict Evaluation Order and Sequencing Invariants

In C and C++, unsequenced argument evaluation causes undefined behavior and platform-dependent bugs when multiple arguments access or mutate related state. Worse, under Mutable Value Semantics, if a function call `foo(&a, bar(&a))` left argument evaluation order unspecified, the compiler could not deterministically verify whether the two `inout` projections overlap in time.

CoreX adopts **Hylo's Formal Evaluation Sequencing Invariant** across all expressions:
1.  **Immediate Sub-Expression Left-to-Right Sequencing**: For any expression $e$, its immediate sub-expressions – consisting of its explicit operands, any implicit function/projection calls invoked by $e$, the capture list initializations of a closure expression, and any evaluated default argument expressions – are **strictly sequenced from left to right**.
2.  **Post-Argument Callee Sequencing Rule**: In any function call $f(a_1, a_2, \dots, a_n)$ or subscript call $s[a_1, \dots, a_n]$, the arguments $a_1, \dots, a_n$ are evaluated strictly from left to right, and **the callee expression $f$ (including any receiver projection on a method call `receiver.method(a_1, a_2)`) is sequenced *after* the evaluation of the last argument $a_n$**. Under naive left-to-right evaluation where the receiver `&vec` is projected *before* the arguments, a call like `&vec.push(vec.len())` would begin the mutable `inout` projection of `vec` for `.push` before `vec.len()` finishes reading `vec`, triggering a Law of Exclusivity violation. By sequencing the receiver projection `&vec` *after* all arguments (`vec.len()`) have evaluated and ended their immutable projections, nested expressions like `&vec.push(vec.len())` are safe, deterministic, and legal without temporary variables.

### 3. Aliasing Invariants, Ghost Instructions, and Abstract Interpretation

CoreX enforces the **Law of Exclusivity** without a Rust-style lifetime unification solver by lowering the typed AST into Block-Argument SSA IR enriched with **Ghost Lifetime Instructions** (following Racordon and Abrahams' Hylo IR model) and running a single forward **Abstract Interpretation Pass**. During SSA construction, the frontend emits zero-cost verification instructions (erased before machine codegen) that bracket every storage state transition: `%p = access.let %source_path` and `access.end %p` begin and end an immutable projection; `%p = access.inout %source_path` and `access.end %p` begin and end an exclusive mutable projection; and `storage.move`, `storage.init`, and `storage.deinit` track definite initialization, `sink` ownership consumption, and `set` initialization states across control-flow branches. For every rooted variable tree $v$, the abstract interpreter tracks a trie of field paths (e.g., `v`, `v.pos`, `v.pos.x`), where each node holds an initialization state $\in \{\text{Uninitialized}, \text{Initialized}, \text{Moved}, \text{PartiallyMoved}\}$ and an active access state $\mathcal{A}(p) \in \{\text{None}, \text{Shared}(k), \text{UniqueMutable}\}$.

| Exclusivity & Lifetime Invariant | Formal Verification Rule in the Abstract Interpreter | Practical Ergonomic & Optimization Outcome |
| :--- | :--- | :--- |
| **A. Path Disjointness (Law of Exclusivity)** | `access.inout` on path $p$ requires $\mathcal{A}(q) = \text{None}$ for all ancestor, self, and descendant paths $q$ ($p \sqsubseteq q \lor q \sqsubseteq p$). `access.let` requires $\mathcal{A}(q) \neq \text{UniqueMutable}$. | Sibling paths (`&r.pos.x` and `&r.dim.y`) have disjoint subtrees ($\text{Path}(p_1) \cap \text{Path}(p_2) = \emptyset$) and can be passed `inout` simultaneously (`swap(&r.pos, &r.dim)`). |
| **B. Early Last-Use Projection Termination** | An `access.let` or `access.inout` projection (`let y = x.field` or `inout y = &x.field`) ends immediately after the **last dominating SSA use** of `%y`, rather than at the closing brace `}`. | Subsequent statements in the same lexical block can freely mutate `x` as soon as the projection `y` is no longer read. |
| **C. Move-Reinitialization Inside `inout`** | Passing `t: inout T` to a `sink` parameter transitions `t` to $\text{Moved}$. This is legal if and only if every CFG path reaching `ret` executes a dominating `storage.init` on `t`. | Enables zero-copy in-place state-machine transitions (`own_t(t); t = T()`) without `std::mem::replace` dummy values or `unsafe` blocks. |
| **D. Closure Capture Exclusivity** | Closures with `let` or `inout` captures are marked non-escapable (`@local`). While a closure with an `inout` capture `[&sum]` is live, `access.inout` remains active on `sum`, and calling the closure requires `&closure()`. | Prevents Swift's runtime exclusivity crashes at compile time; escaping (`@global`) closures may only capture bindings via `sink` move (`fun[var i = 0]() inout -> Int`). |

### 4. ABI Calling Conventions and Safe Parameter Reference Optimization (PRO)

To achieve C-level function call performance without Zig's Pass-by-Reference Optimization bugs (Issue #16343, where taking the address of a parameter forces a stack copy and breaks pointer identity), CoreX formalizes its native **`cx` ABI Calling Convention**.

For **`let` parameters ≤16 bytes**, values are passed directly in up to two 64-bit general-purpose or vector registers (covering `i64`, `f64`, `Vec2`, `Span16`, `[]T` slices, and `Option[&T]`). For **`let` parameters >16 bytes**, the ABI automatically promotes the parameter to a `const noalias` pointer to the caller's existing memory location. Because CoreX's strict MVS model forbids taking raw pointers to safe `let` bindings and guarantees that no `inout` alias can overlap a `let` parameter during the call, the callee never copies the struct onto its own stack frame, and the backend can keep loaded fields in registers across opaque calls.

For **`inout` and `set` parameters**, arguments are passed as a non-null, `noalias` pointer in a single register (`T* noalias nonnull`). However, for small scalar `inout` parameters (such as `inout i32` or a `bit_field` projection) in non-address-exposed functions, MVS semantics explicitly permit the optimizer to lower `fn update(x: inout i32)` into a register-in/register-out signature `i32 update(i32 x)` – avoiding stack-slot `alloca` spills. For **`sink` parameters**, values ≤16 bytes pass in registers and values >16 bytes pass via a caller-allocated slot pointer, transferring ownership without `memcpy`. Finally, CoreX procedures pass a pointer to the current thread/task `Context` struct (housing `allocator`, `temp_allocator`, `logger`, and `user_ptr`) in a dedicated register by default, but automatically strip the context parameter (`contextless` promotion) whenever call-graph analysis proves a procedure and its transitive callees neither read nor modify `context` (or when marked `@contextless` / `extern "c"`).

### 5. Polymorphism: Static Monomorphization vs. Explicit Dynamic Dispatch

CoreX's polymorphism model is designed to deliver inlinable zero-cost generics on hot paths while preventing both Go's runtime dictionary slowdowns and Rust/C++'s compile-time code bloat:

1.  **Definition-Site Checked Generics (No Use-Site Duck Typing)**: Unlike C++ templates or Zig `anytype` functions (which defer type checking until instantiation), every generic function `fn sort[T: Ord](slice: &mut [T])` in CoreX is **type-checked once at definition time** against its declared `trait` and `where` constraints (including equality constraints `T.Item == u32` and compile-time value constraints `@value N: usize`).
2.  **Default Static Monomorphization with Pointer-Shape Binary Deduplication**: By default, generic functions are **statically monomorphized** so that concrete type sizes, alignments, and trait method targets are known at compile time – enabling full method devirtualization, inlining, and SIMD auto-vectorization. CoreX rejects both Swift's resilient Value Witness Tables (which box unknown-sized stack values at runtime) and Go's `AX`-register GCShape dictionaries (which prevent inlining on pointer method calls). Instead, to keep compile times fast and `wasm32` binaries compact when instantiating container operations (like `Vec[OwnPtr[A]]` and `Vec[OwnPtr[B]]` where the method body does not invoke type-specific trait methods), the CoreX backend performs compile-time Identical Code Folding across instantiations sharing identical size, alignment, and move/destroy semantics – deduplicating binary code *only* when zero runtime dictionary lookup is required.
3.  **Explicit Dynamic Dispatch via Fat-Pointer Trait Objects (`dyn Trait`)**: When runtime heterogeneity or separate compilation is desired, developers opt in explicitly via **`&let dyn Trait`**, **`&inout dyn Trait`**, or **`OwnPtr[dyn Trait]`**. A `dyn Trait` reference is represented as a 16-byte **fat pointer** `(data_ptr: *void, vtable_ptr: *TraitVTable)`, where the vtable is stored externally to the type instance (allowing any struct or enum to conform to a trait without adding an 8-byte `vptr` header to the struct itself). To guarantee zero hidden heap boxing on stack variables, `dyn Trait` is restricted to **dyn-compatible traits** whose methods have statically known argument/return layouts and specified associated types.

### 6. Zero-Cost Abstraction Guarantees

The CoreX compiler frontend and SSA optimizer enforce six concrete zero-cost lowering invariants across all builds:

| High-Level CoreX Abstraction | Guaranteed Machine-Level Lowering Invariant | Enabled Compiler Optimizations |
| :--- | :--- | :--- |
| **MVS Disjoint Value Structs (`let` / `var` / `inout`)** | No hidden `Rc`/`ARC` headers or CoW atomic reference checks; all parameter pointers carry LLVM/Cranelift `noalias` metadata. | **Scalar Replacement of Aggregates (SROA)**, register promotion across opaque function calls, dead-store elimination, and loop-invariant code motion. |
| **Subscript Projections (`subscript ... yield`)** | Non-recursive subscripts are **always inlined** during SSA lowering; `yield &field` collapses into a direct pointer offset (`ptr.offset`) or register bit-extract/insert pair. | Zero coroutine frame allocation; identical machine code to hand-written C pointer indexing or bitwise masking. |
| **Algebraic Sum Types (`Option[T]` / `T?`, `enum`)** | Automatic recursive niche propagation (`0x0` for `&let T`, `&inout T`, `OwnPtr[T]`, `NonZero*`; `2..=255` for `bool`); Maranget decision-tree lowering to jump tables. | `sizeof(Option[OwnPtr[T]]) == 8 bytes`; zero redundant tag checks in nested pattern matches. |
| **Value Error Handling (`Result[T, E]`, `?`, `catch`, `errdefer`)** | Returned in registers `(payload, err_tag)` (or a single register when proven error-free); `errdefer` blocks are emitted strictly on the cold error-branch CFG edge. | **Zero stack-unwinding tables**; zero happy-path instructions beyond a register branch check. |
| **`#soa[]T` Slices & `soa_zip` Loops** | Frontend rewrites `slice[i].field` directly to `slice.field_ptr[i]` before SSA emission; `soa_zip` variables materialize zero stack temporaries. | 100% 64-byte L1d cache-line utilization on single-field loops; automatic SIMD vectorization (`AVX2`/`AVX-512`, `NEON`, `wasm32 SIMD128`). |
| **Unboxed Spans (`Span16`) & `bit_field uN`** | Packed into a single 32-bit or 64-bit hardware register; bitfield accesses lower to direct bitwise extract/insert instructions (`sbfm`, `shr`, `and`). | Zero minor-heap view allocations in HTTP/JSON parsers; portable LSB wire-format compatibility. |
