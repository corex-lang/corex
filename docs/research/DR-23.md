# Empirical and Compiler-Engineering Surface Syntax Audit for CoreX (.cx) – Docstrings, Method Attachment, Conditionals, Scalar Type Casing, Discard Statements, and Type Annotations

Before CoreX (`corex-lang/corex`, sibling VS Code grammar `corex-lang/vscode-ext-corex`) freezes its v1.0 `.cx` surface syntax for **Phase 11** (authoring all 15 `cx.*` standard library packages in `.cx`) and **Phase 12** (rewriting the self-hosted `compiler/*.cx` toolchain), this audit (`DR-23`) resolves six foundational surface-syntax questions inherited from `DR-03` and `DR-22`. Evaluating empirical human-factors and eye-tracking studies alongside formal grammar specifications and compiler frontends across **Rust, Swift, Zig, Go, Kotlin, Python, C#, TypeScript, Scala 3, Odin, Hylo, and Gleam**, CoreX locks **one canonical winner** per domain (`ADR-23A`–`ADR-23F`): (`ADR-23A`) strict line-only documentation comments pairing forward-attached **`///`** with top-of-file-only **`//!`**, banning `/** … */` and `/*! … */` block doc comments; (`ADR-23B`) separate **`impl`** blocks (`impl[…] Type { … }` and `impl[…] Trait for Type { … }`), keeping `struct`, `enum`, `bit_field`, and `union` declarations as pure physical byte-layout headers; (`ADR-23C`) compositional two-token **`else if`** over `elif`; (`ADR-23D`) concise lowercase **`PRIM_TYPE`** machine scalars (`i8`..`i128`, `isize`, `u8`..`u128`, `usize`, `f32`, `f64`, `bool`, `char`, `str`, `unit`, `never`, `opaque`); (`ADR-23E`) bare **`_ = expr;`** (plus partial destructuring `(val, _) = pair;` with at least one bound mutable place) as the sole statement-level discard, retiring non-binding `let _ = expr;` and `var _ = expr;`; and (`ADR-23F`) postfix colon **`x: T`** type annotations across all declaration sites.

Four of the six audited baselines (`ADR-23B`, `ADR-23C`, `ADR-23D`, and `ADR-23F`) withstand empirical and formal parser scrutiny with **zero valid-syntax grammar changes** and **zero `TokenKind` additions**, holding CoreX at `120` contiguous `enum(u8)` variants (`0..119`) and preserving all **8 spare bits (`120..127`)** inside `TokenSet128` (`u128`). Simultaneously, `ADR-23A` and `ADR-23E` close genuine **One Canonical Way** loopholes in `DR-22` without adding a single syntactic token: `ADR-23A` enforces Zig-style compiler-verified doc attachment (`E0118`, `E0229`, `E0230`) so Markdown ```` ```cx ```` examples containing `"""…"""` multiline strings, `{x=}` format holes, and `/* … */` comments never require delimiter escaping, while `ADR-23E` eliminates Rust's `let _ = lock();` immediate-drop trap and establishes a strict five-tier discard safety lattice across `unit` (`E0439`), ignorable values, `@must_use` (`E0413`), `T!E` error unions (`E0414`), and `@linear` resources (`E0304`). Where published empirical studies carry scope limits – such as small novice student cohorts in Stefik and Siebert's accuracy experiments, short primitive-only Python functions in 2026 eye-tracking trials, and the absence of dedicated eye-tracking experiments directly isolating `elif` vs. `else if` or `x: T` vs. `x T` – this report states those evidentiary boundaries explicitly and grounds final decisions in deterministic `LL(k)` / Pratt parsing, `DR-12` `ItemTree` Early Cutoff, and `DR-06` Mutable Value Semantics (MVS) soundness.

### 1.1 ADR-23A: Documentation Comment and Docstring Syntax

**Decision (`ADR-23A`):** CoreX selects **(A) Strict Line-Only Documentation Comments** – pairing outer **`///`** (exact three slashes) with **top-of-file-only `//!`** (module header documentation) – while banning block doc comments (`/** … */` and `/*! … */`), triple-quoted `""" … """` docstrings, `@doc("…")` attributes, and overloaded single-marker `///` module headers.

| Evaluation Criterion | `(A)` Strict `///` + Top-Only `//!` **(Winner)** | `(B)` Single-Marker `///` Only | `(C)` Block `/** … */` Doc Comments | `(D)` Triple-Quoted `""" … """` Docstrings | `(E)` `@doc("…")` Attributes |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Module vs. First-Item Disambiguation** | **100% Syntactic & Whitespace-Free:** `//!` always documents the file's module; `///` always documents the following item. | **Ambiguous / Blank-Line Fragile:** Collides on `mod child;` vs. `mod self;` and silently detaches/steals docs on blank-line edits. | Requires separate `/*!` or `@packageDocumentation` tag; C# lacked namespace docs (`CS1587` / `NamespaceDoc` hack). | Collides with attribute/item docstrings at top of class/module (`PEP 224` rejection). | Requires separate `@moduledoc` vs. `@doc` attribute names (Elixir). |
| **Expression Tail-Return & `{expr}` Safety** | **Zero Collision:** Lives in lexical trivia; never parsed as a runtime `String` or `FmtArgs` expression. | **Zero Collision** (lexical trivia). | **Zero Collision** with expressions, but **severe `*/` and `/*` lexical hazards**. | **Direct Collision:** `"""…"""` is a tail-return `String` literal (`DR-03` §3.2) with live `{expr}` holes (`SE-12`)! | **High Friction:** `{expr}` inside `@doc("""…""")` triggers `SE-12` interpolation unless `r#"""…"""#` is used. |
| **Markdown ```` ```cx ```` Example Nesting** | **100% Unescaped:** Embeds `"""…"""`, `r#"…"#`, `{x=}`, and `/* … */` verbatim on `///` lines. | **100% Unescaped** on `///` lines. | **Broken:** `*/` closes non-nested `/**` (`tsdoc#166`); `/route/*` opens nested comment in KDoc (`KT-28979`). | **Broken:** Nested `"""…"""` inside ```` ```cx ```` closes the docstring prematurely unless backslash-escaped. | **Broken:** Same nested `"""` / `r#"""` delimiter collisions inside string literal arguments. |
| **`corex fmt` & Multiline Editing** | **Linear O(n):** Shifts leading indent without altering Markdown column alignment; no `*` border bugs. | **Fragile:** Formatter cannot distinguish accidental vs. intentional blank line below top `///`. | **Complex & Bug-Prone:** Left-border `*` alignment causes idempotence bugs (`rustfmt#7017`, `ktlint#2982`). | **Body-Coupled:** Indented inside `{ … }` *after* `where` clauses, separating docs from signatures. | **Noisy:** Adds `@doc(` … `)` wrapper lines on every struct field and enum variant. |
| **`LosslessCstArena` & `corex lsp` Hover** | **Zero AST Bloat:** Stored in `TriviaPiece`; `ItemTree` indexes contiguous doc span per `DefId` in O(1). | Requires blank-line heuristic in CST/AST lowering. | Requires multi-line `*`-stripping pass during every hover extraction. | Allocates AST `Expr` nodes inside function bodies, breaching `DR-12` Signature Firewall. | Allocates `Attribute` + `STRING_LIT` AST nodes on every field, variant, and private helper. |

Although no published controlled experiment directly benchmarks `///` against `/** … */` or `""" … """`, a March 2026 eye-tracking study by Peitek, Bergum, and colleagues (*Empirical Software Engineering* 31(4):94, N = 20 CS students across 12 Java snippets) found that developers follow a selective "code-first" gaze strategy in which relevant comments capture up to 23% of fixations and promote linear intra-line reading, whereas noisy or poorly coupled comments degrade comprehension performance by up to 30%. Evaluating candidates `(A)`–`(E)` against these visual-coupling findings and CoreX's compiler invariants eliminates `(C)`, `(D)`, and `(E)` on hard lexical and architectural grounds.

First, block doc comments `(C)` (`/** … */` in Kotlin KDoc, Scala 3 Scaladoc, and TypeScript TSDoc; permitted alongside `///` in Rust, Swift DocC, and C#, while Hylo defines only general `//` and nested `/* … */` comments) suffer from an unsolvable delimiter dilemma when nesting Markdown ```` ```cx ```` examples. In non-nested lexers (JavaScript/TypeScript, Rust's `OUTER_BLOCK_DOC` terminator rule), any `*/` inside a code fence or backtick span – such as `` `glob = "*/*.cx"` `` – prematurely closes the doc comment and causes a syntax error (`microsoft/tsdoc#166`, Rust Reference `[comments.doc.syntax]`). Conversely, because CoreX supports nested `/* … */` ordinary block comments (`PLAN.md` Phase 10.5), allowing `/** … */` imports Kotlin's open `KT-28979` defect: writing an unclosed wildcard path like ``Defines route `/api/*` `` inside a doc comment opens a nested `/*` comment and silently comments out the declaration below it! Block doc comments also fracture formatting between Doxygen `*`-bordered and unbordered styles (`rustfmt#7017`, `ktlint#2982`), which is why Rust RFC 505 explicitly discourages block comments, TypeScript reserves `///` only because legacy `<reference path="…" />` directives occupied it, and Kotlin users filed `KT-23038` requesting `///`. CoreX therefore bans `/** … */` (excluding empty `/**/` and non-doc `/***/`) and `/*! … */` at lex time with **`E0118`** and a machine-applicable `///` / `//!` rewrite.

Second, Python-style `""" … """` docstrings `(D)` (PEP 257) and Elixir/Rust-style `@doc("…")` attributes `(E)` collide directly with CoreX's expression-oriented grammar (`DR-03` §3.2) and `SE-12`/`SE-13` string semantics (`DR-22`). In CoreX, the final expression of `{ … }` is its tail return value and `"…"` / `"""…"""` evaluate live `{expr}` format holes. Placing `"""…"""` inside a single-expression function (`fn banner() -> str { """Usage…""" }`) is syntactically indistinguishable from returning a `str`, triggers `SE-12` interpolation errors on every `{` brace inside code examples unless `r#"""…"""#` is used, cannot embed another `"""…"""` example inside ```` ```cx ```` without backslash escaping, breaches `DR-12`'s `ItemTree` Signature Firewall by burying API documentation inside function bodies (where edits invalidate body hashes rather than remaining trivia-isolated), and cannot document `struct` fields, `bit_field` members, `enum` variants, or `const` items without recreating Python's rejected PEP 224 ambiguity (*"I really have no way to know whether 'foo bar' is a docstring for `a` or for `b`"*, Guido van Rossum). Wrapping strings in `@doc(r#"""…"""#)` `(E)` resolves tail-return ambiguity only by imposing heavy attribute clutter on every struct field, variant, and helper (`AGENTS.md` §7 mandates doc comments on all items and helpers) while allocating `Attribute` AST nodes across non-LSP builds.

Third, comparing dual `///` + `//!` `(A)` (Rust, Zig; analogous to Gleam's `///` + top-of-module `////`) against unified single-marker `///` `(B)` (or Go/Odin's single-marker `//`) exposes a fatal flaw in `(B)` under CoreX's whitespace-insensitivity invariant (`DR-03` §3.2). In CoreX (`DR-21`), files do not write redundant `mod <self>;` headers, and pure hub/barrel files (`core/root.cx`, `core/sys/mod.cx`) begin directly with child submodule declarations (`pub mod primitives;`, `pub mod linux;`). A single `///` at the top of a hub file above `pub mod sys;` is therefore genuinely ambiguous between documenting the parent module and documenting child submodule `sys`. Worse, in Go (`go.dev/doc/comment`) and Dawn, single-marker module comments rely on **significant blank lines** to avoid attaching to the first declaration: deleting or inserting a single blank line silently steals or detaches module documentation with zero compiler feedback, while C#'s single-marker `///` left `.NET` unable to document namespaces in source without dummy `NamespaceDoc` classes (`CS1587`).

CoreX adopts `(A)` and improves directly on Rust by enforcing Zig's strict container-top and declaration-attachment rules in the parser. Where Rust allows `//!` inside arbitrary mid-file blocks (forcing RFC 505 to ban mid-file `//!` by style convention), CoreX restricts **`//!` (`TriviaKind.module_doc_comment`)** strictly to the top of a `.cx` file prior to any `Item` (`mod`, `use`, `const`, `type`, `struct`, etc.), rejecting mid-file or inline-`mod` `//!` with **`E0229`**. Simultaneously, **`///` (`TriviaKind.doc_comment`, exact three slashes so `////`+ remains an ordinary `//` banner comment)** must immediately precede a documentable declaration with no intervening blank line or `//` comment; dangling `///` lines (above `use`, local `let`/`var`, statements, `}`, `EOF`, or followed by a blank line / `//` comment) emit **`E0230`**.

### 1.2 ADR-23B: Method and Trait Attachment Syntax and Keyword Naming

**Decision (`ADR-23B`):** CoreX retains **(A) + (C) Separate `impl` Blocks (`impl[…] Type { … }` and `impl[…] Trait for Type { … }`) using the keyword `impl`** as the **sole canonical mechanism** for inherent methods, associated constants/types, `subscript` bundles, and trait conformances – forbidding inline methods inside `struct`, `enum`, `bit_field`, and `union` bodies (`E0232`) and forbidding `pub impl` (`E0231`).

| Architectural Dimension | `(A)` Separate `impl` Blocks **(Winner)** | `(B)` Inline Methods Inside Type Bodies *(Zig / Kotlin)* | Hybrid Inline + `extension` Blocks *(Swift / Hylo / C# 14)* |
| :--- | :--- | :--- | :--- |
| **One Canonical Way (`AGENTS.md` §4)** | **✓ 100% Canonical:** Exactly one syntax and placement model for all inherent and trait methods. | **✗ Breaks on Specialization:** Cannot attach methods to `Vec[u8]` or `T: Copy` without comptime guards or external blocks. | **✗ Splits Style:** Teams split methods across `struct` and `extension` blocks (`MyType+Additions.swift`). |
| **Cache-Line & Byte-Layout Readability** | **✓ Instant (5–15 LOC):** `struct`, `enum`, and `bit_field` headers show pure contiguous memory fields. | **✗ Obscured:** 24 bytes of fields get buried inside 500–2,000 lines of method bodies. | **⚠ Degraded:** Inline methods obscure stored properties unless manually refactored into extensions. |
| **Orphan / Coherence & Conformance Indexing** | **✓ Flat Top-Level Pass:** `CompilerDb` indexes all `ImplItem` headers in `ItemTree` without walking field ASTs. | **✗ Lacks External Trait Conformance:** Cannot conform a local trait to an upstream package's type. | **⚠ Dual Conformance Sites:** Must merge `struct A: T` header conformances with `extension A: U` blocks. |
| **Conditional Bounds (`impl[T: Copy] Vec[T]`) & `@cfg`** | **✓ First-Class:** Arbitrary bounded, concrete (`impl Vec[u8]`), and `@cfg(…)` `impl` blocks compose cleanly. | **✗ Awkward:** Requires per-method `where` repetition or untyped `comptime` reflection checks. | **✓ Supported** only via the secondary `extension … where` construct. |
| **`AGENTS.md` §6 File Section & `DR-12` Firewall** | **✓ Exact Fit:** Pure layouts in `TYPES`, private `impl` in `INTERNALS`, public `impl` in `PUBLIC API`; CST edits stay isolated. | **✗ Coupled Container:** Forces fields, private helpers, and public APIs into one giant `StructItem` CST subtree. | **✗ Contradicts** single-section placement unless inline methods are banned by lint anyway. |

Across the 12 audited languages, zero-GC value-oriented designs consistently separate physical data layouts from behavior: **Rust** uses separate `impl` blocks, **Go** keeps `struct` field-only and attaches receiver functions externally (`func (r T) m()`), **Odin** and **Gleam** forbid methods inside `struct` / `type` declarations altogether, whereas **Zig** nests functions inside `struct` namespaces (because `struct` doubles as Zig's module container and Zig has no traits), and **Swift, Hylo, Kotlin, Scala 3, and C# 14** require *both* inline type methods and separate `extension` declarations. While no controlled empirical study isolates `impl` blocks against inline `struct` methods in systems languages, four concrete CoreX invariants make separate `impl` blocks the clear architectural winner.

First, every CoreX `struct`, `enum`, `bit_field`, and `union` is an unboxed value governed by exact byte-level ABI contracts: `<= 16 B` two-register MVS parameter passing (`ADR-22B`), `<= 16 B` `swiftcc` + `swifterror` error-union limits (`DR-07`), `24 B` container headers (`DR-15`), `FromBytes`/`IntoBytes` layout-verified wire transmutation (`DR-20` `D-01`), and exact `bit_field` bit-width sums (`ADR-22D`). Keeping type bodies 100% free of methods guarantees that every type declaration is a compact 5–15 line memory-layout specification where `sizeof`, `alignof`, niche bits, and `Copy` / `AutoDrop` / `@linear` ownership tier are visible at a glance. Notably, even in Swift, community style guides routinely move protocol conformances and private helpers out of `struct` bodies into `extension` and `private extension` blocks specifically to keep stored properties readable and avoid suppressing synthesized memberwise initializers.

Second, **Phase 11** standard library types (`Vec[T]`, `SmallVec[T, N]`, `Map[K, V]`, `Span16`) require unconstrained `impl[T] Vec[T]`, conditionally bounded `impl[T: Copy] Vec[T]`, concrete `impl Vec[u8]`, OS-conditional `@cfg(target.os == .Linux) impl File`, and orphan-checked trait conformances `impl[T: Equatable] Equatable for Vec[T]` (where either the trait or the self type is local to the current `corex.toml` package). Inline methods cannot express `impl Vec[u8]` or conform a local `Trait` to an imported `Type` without introducing a *second* `extension` construct – violating **One Canonical Way**. Separate `impl` blocks also align 1-to-1 with `AGENTS.md` §6's mandatory file organization (`TYPES` for pure data layouts, `INTERNALS` for private `impl` helpers, and `PUBLIC API` for `impl` blocks exposing `pub` members – locking `E0231` to reject redundant `pub impl` headers) and maximize `DR-12` incremental compilation: editing a method inside `ImplItem` never overlaps the `StructItem` CST byte span during `reparseIncremental`, guaranteeing zero invalidation of downstream `TypeLayout` queries (`sizeof`, `alignof`, field offsets).

Third, for keyword naming `(C)`, `impl` (`4` chars, already allocated at `TokenKind.kw_impl` index `9`) is strictly clearer than `extend`, `extension` (`9` chars, Swift/Hylo/Scala 3/C# 14), or `given` (Scala 3). Languages with inline methods say `extension` because the type already has inline methods and you are *extending* it after the fact; in CoreX, `struct` has zero methods, so `impl Type` and `impl Trait for Type` state directly that you are *implementing* behavior or a trait contract without conflating conformance with supertrait refinement (`trait Sub: Super`).

### 1.3 ADR-23C: Chained Conditional Keyword (else if vs. elif)

**Decision (`ADR-23C`):** CoreX retains two-token **`else if`** (`IfExpr = "if" CondExpr Block [ "else" ( IfExpr | Block ) ]`) as its sole chained conditional form, rejecting `elif`, `elsif`, and `elseif` with parser recovery diagnostic **`E0233`** and a machine-applicable `SuggestedFix` (`→ "else if"`).

| Comparison Dimension | Two-Token `else if` **(Winner)** | Single-Keyword `elif` *(or `elsif` / `elseif`)* |
| :--- | :--- | :--- |
| **12-Language Reference Cohort Parity** | **10 of 11 `if`-bearing languages (`90.9%`):** **Rust, Swift, Zig, Go, Kotlin, C#, TypeScript, Scala 3, Odin, and Hylo**. *(Gleam uses `case` only.)* | **1 of 11 (`9.1%`):** **Python** only *(contrary to common assumption, Odin uses `else if` and `else when` per `odin.ebnf`, not `elif`)*. |
| **Grammatical Reason for Existence** | `{ }` blocks self-delimit every branch; `else` followed by `IfExpr` requires zero extra closing keywords and zero extra indentation. | Invented to avoid stacked closing `fi`/`end` keywords in Bourne shell/Ada/Ruby and `+4` staircase indentation after `else:` in Python. |
| **HCI & Lexical Vocabulary (`DR-03`, `DR-22`)** | **100% Full English Words:** Composes `else` + `if` directly, matching `and`, `or`, `not`, `is`, **`is not`**, and `orelse` (Hofmeister et al. 2017/2019: full words read **19% faster** than contractions). | **Truncated Non-Word Portmanteau:** Forces polyglot guessing across `elif` (Python/sh), `elsif` (Ruby/Ada), and `elseif` (Lua/Quorum). |
| **Multi-Line & Inline `if` Expression Ergonomics** | Multi-line chains share a uniform **`} else`** left-margin prefix (`} else if c {` / `} else {`); inline `let x = if a { 1 } else if b { 2 } else { 3 };` adds only 3 chars per arm. | Saves 3 chars (`elif` vs. `else if`) on rare 1-line chains, while breaking the shared `} else` visual anchor on multi-line blocks. |
| **`TokenSet128` Budget (`<= 128`)** | **`0` Tokens (`120 / 128`):** Preserves all **8 spare bits (`120..127`)**. | **`+1` Hard Keyword (`121 / 128`):** Consumes **12.5% (`1 / 8`)** of CoreX's remaining `TokenSet128` headroom! |
| **Parser, CST & `MIR` Drop Lowering** | **Zero Extra AST/HIR/MIR Nodes:** `else_branch` holds `IfExpr`, automatically inheriting `SE-01`/`SE-02` `ConditionScope` pre-`else` LIFO drops. | Requires dedicated `ElifArm` lists across `CstNode`, `AstArena`, `DocArena`, and `HIR` desugaring. |

No published eye-tracking study directly compares reading speed on `elif` versus `else if` inside curly-brace languages; however, tracing why `elif` was invented and comparing cross-language grammars and lexical-comprehension studies makes the choice clear. Historically, `elif` arose solely to solve delimiter problems absent from `{ }` grammars: in the Bourne shell (`if … then … elif … fi`) and `end`-terminated languages, writing two-token `else if` opens a nested `if` requiring a matching `fi` or `end` for every branch, while in Python, Guido van Rossum adopted `elif` from the Bourne shell specifically because `else:` followed by a newline would indent each subsequent `if` four spaces further right (*"The keyword 'elif' is short for 'else if', and is useful to avoid excessive indentation"*, Python Tutorial §4.1). Because CoreX mandates `{ }` block delimiters on all conditional branches (`DR-03` §1.5; validated by a 2024 indentation RCT where structured visual indentation cut nested-`if` reading time by 2.13x, p < 0.001, ηp² = 0.198), `else` followed directly by `IfExpr` stays completely flat at the left margin (`if a { … } else if b { … } else { … }`). That is why **10 of the 11** `if`-supporting languages in our cohort – explicitly including **Odin** (`odin.ebnf`: `"else" "if"`) and **Hylo** (`conditional-tail ::= 'else' conditional-expr | 'else' brace-stmt`) – use two-token `else if`.

Ergonomically, `DR-21` (`SE-01`) and `DR-22` (`ADR-22A`) standardized on unabbreviated English words (`and`, `or`, `not`, `is`, and two-token `is not`) rather than contracted jargon. This matches Hofmeister, Siegmund, and Holt's (*EMSE* 2019) controlled finding that full words improve semantic defect comprehension speed by 19% (p = 0.004) over abbreviations, as well as Stefik and Siebert's (2013) Quorum design, which avoided truncated `elif` in favor of `elseif` (noting educators' observations that novices frequently stumble over `elif` as an unfamiliar coined word). On multi-line blocks, `} else if` and `} else` share an identical 6-character `} else` continuation prefix on the left margin; on inline `if` expressions (`let tier = if a { 1 } else if b { 2 } else { 3 };`), `else if` costs just 3 extra characters while sparing `12.5%` (`1` of `8` remaining bits) of `TokenSet128`, matching `AGENTS.md` §6 (`else if` mutual-exclusion rule), and preserving `SE-01`/`SE-02`'s recursive `ConditionScope` pre-`else` drop lowering with zero extra AST node kinds.

### 1.4 ADR-23D: Built-In Primitive Type Casing and Conciseness

**Decision (`ADR-23D`):** CoreX retains **(A) Concise Lowercase `PRIM_TYPE` Keywords** for all 20 built-in machine primitives (`i8`, `i16`, `i32`, `i64`, `i128`, `isize`, `u8`, `u16`, `u32`, `u64`, `u128`, `usize`, `f32`, `f64`, `bool`, `char`, `str`, `unit`, `never`, `opaque`), rejecting `(B)` uppercase-initial concise scalars (`U8`, `U32`, `I32`, `F64`, `Bool`, `Char`, `Str`, `USize`, `Unit`, `Never`, `Opaque`) and `(C)` Swift/Kotlin-style verbose `PascalCase` scalars (`Int32`, `UInt32`, `Float64`, `Bool`).

| Technical & HCI Dimension | `(A)` Lowercase `u32`, `bool`, `str`, `usize` **(Winner)** | `(B)` Concise Uppercase `U32`, `Bool`, `Str`, `USize` | `(C)` Verbose `PascalCase` `UInt32`, `Int32`, `Float64` |
| :--- | :--- | :--- | :--- |

Recent eye-tracking investigations of static type annotations – Alznauer, Peitek, Apel et al. (*ICPC 2026*, N = 40, Tobii X60 on 20 Python snippets using lowercase `int`, `float`, `str`, `bool`, `list`) and Flint, Dyer, and Sharif (*ICPC 2026*, TypeScript) – show that developers actively fixate on type annotations as in-code documentation, producing statistically significantly shorter saccade lengths (p = 0.02) and strong subjective helpfulness ratings (85% task-specific, 91% general), alongside a modest reading-time increase (`67.2 ± 36.0 s` vs. `61.0 ± 37.2 s`, p = 0.02) that grows less than proportionally to added character count. While these studies did not directly pit `u32` against `U32` or `UInt32`, they establish that concise, low-clutter scalar tokens minimize horizontal fixation cost on type-dense lines. In systems, SIMD, cryptographic, and wire-protocol modules (`core/atomic.cx`, `core/mem.cx`, `stdlib/cx/crypto.cx`), replacing `u8`, `u32`, and `f32` with Swift/Hylo/Kotlin-style `UInt8`, `UInt32`, and `Float32` `(C)` inflates scalar character width by **100%–150%** – pushing single-screen signatures like `compare_exchange` from `96` columns past `corex fmt`'s `100`-column limit (`108` columns) and forcing multiline wrapping on otherwise compact signatures.

Testing concise uppercase Option `(B)` (`U8`, `U32`, `I32`, `F64`, `Bool`, `Str`, `USize`, `Unit`, `Never`, `Opaque`, adopted only in niche languages like Vastitas and `0 of 12` reference languages) reveals four severe lexical, parser, and FFI defects in CoreX. First, under CoreX's stateless O(n) identifier partition (`DR-03` §4.3, `DR-21` §1.3), any token of length ≥ 2 matching `^[A-Z][A-Z0-9_]+$` (zero lowercase letters) is a `SCREAMING_SNAKE_CASE` constant (`CONST_IDENT`, e.g., `R12`, `X21`, `PI_2`, `CRC32`). **12 of the 20** Option `(B)` scalars (`I8`, `I16`, `I32`, `I64`, `I128`, `U8`, `U16`, `U32`, `U64`, `U128`, `F32`, `F64`) have zero lowercase characters and collide directly with `CONST_IDENT` morphology! Even if special-cased in `KEYWORD_OR_PRIM_MAP`, `U8`, `I8`, and `F32` visually collide with hardware constants and single-letter generic parameters `[U, I, F]`, while `USize`/`ISize` either violate Rust RFC 430's acronym rule (`Usize`) or obscure the word `Size`, and `Str` (`16 B` `Copy` slice) loses its strong visual silhouette contrast against `String` (`24 B` `AutoDrop` SSO buffer).

Second, `DR-22` `SE-13` defines `_`-separated numeric suffixes (`42_u32`, `0x4358_u32`, `0.5_f32`) matching exact primitive type names. Uppercasing suffixes under `(B)` creates a genuine hexadecimal lexing ambiguity: `0xFF_F32` is a valid hexadecimal integer literal equal to `0xFFF32` (`1,048,370`) because `F` is a hex digit! Keeping lowercase `42_u32` suffixes alongside uppercase `U32` types instead introduces two competing spellings for every scalar (recreating C#'s `int` vs. `Int32` StyleCop `SA1121` split), and similarly clashes with lowercase C FFI platform aliases (`cx.ffi.c_int`, `c_char`, `c_ulong`, matching Odin's `core:c` and Rust's `core::ffi`). Third, in the `LL(k)` parser (`DR-21` §1.3), `(B)` saves **zero** lookahead: inside `expr[…]`, both `lut[u32.MAX]` (`peek(1) == .prim_type`, `peek(2) == .dot` → `IndexExpr`) vs. `alloc[u32](n)` (`peek(2) != .dot` → `TypeArgs`) and `lut[U32.MAX]` (`peek(1) == .type_ident`, `peek(2) == .dot`) require inspecting `peek(2)`. Keeping all 20 built-in scalars lowercase `(A)` – matching **100% of zero-GC C-peer systems languages** in the cohort (**Rust, Zig, and Odin**) – gives `vscode-ext-corex` and human peripheral vision an instant two-tier distinction between built-in machine scalars (`storage.type.primitive.corex`) and nominal types, traits, and Constrained Type Groups (`Number`, `Integer`, `Float`, `Copy` in `entity.name.type.corex`).

### 1.5 ADR-23E: Single Canonical Statement-Level Discard (\_ = expr; vs. let \_ = expr;)

**Decision (`ADR-23E`):** CoreX locks bare **`_ = expr;`** (alongside partial destructuring assignment `(val, _) = pair;` containing at least one bound mutable place) as its **sole statement-level discard form**, rejecting non-binding `let _ = expr;`, `var _ = expr;`, `let _: T = expr;`, and `let (_, _) = pair;` with **`E0234`**, rejecting all-wildcard `(_, _) = expr;` with **`E0235`**, and rejecting pointless `_ = unit_expr;` (or `_ = x;` when `x` is also read elsewhere) discards with **`E0439`**.

In `DR-22` §3.3, permitting both `_ = expr;` (`SE-15` assignment) and `let _ = expr;` (`LocalDeclStmt` with `_` pattern) violated **CoreX Invariant 1 (One Canonical Way)** and inherited a notorious RAII/MVS footgun from Rust. In Rust, `let _guard = mutex.lock();` binds an unnamed-by-convention local whose lock lives until the end of the enclosing `{ }` block, whereas `let _ = mutex.lock();` **binds nothing and drops the guard immediately at `;`** – a 5-character visual trap so bug-prone that Clippy and `rustc` 1.65 had to introduce `let_underscore_lock`, `let_underscore_drop`, `let_underscore_must_use`, and `let_underscore_future` (with Clippy's `let_underscore_must_use` explicitly suggesting `_ = foo();` without `let`). Likewise, during Kotlin 2.3's `KEEP-0412` (*Unused Return Value Checker*) review, reviewers criticized `val _ = computeValue()` because writing a variable-declaration keyword when *not* declaring a variable is a conceptual contradiction (whereas Gleam uses `let _ = …` only because Gleam is purely functional and lacks `=` assignment statements, and Scala 3 split its community between `val _ = f()` and `f(): Unit` type ascriptions in `scala3#21557`). Conversely, **Zig, Go, Swift, C# 7+, Odin, and Hylo** (`discard-stmt ::= '_' '=' expr`) converge cleanly on bare `_ = expr;` (with C# explicitly specifying that `var _ = …` declares an ordinary variable `_` rather than a true discard).

Under `ADR-23E`, CoreX establishes a strict semantic separation: **`let` and `var` always bind at least one named variable into scope** (whose `AutoDrop` lifetime spans the enclosing block; intentionally unread guards or typed assertions use a descriptive `_`-prefixed identifier such as `let _lock = mu.acquire();` or `let _check: u32 = f();` per `DR-03` §4.3), while **`_ = expr;` introduces zero bindings**, evaluates `expr`, and drops any `AutoDrop` temporary immediately at `;`. Partial tuple/struct destructuring in declarations (`let (val, _) = pair;`) and assignments (`(val, _) = pair;`) remains valid whenever at least one identifier/place is bound, whereas zero-binding `let (_, _) = pair;` (`E0234`) and `(_, _) = pair;` (`E0235`) rewrite cleanly to `_ = pair;`.

> [!IMPORTANT]
> **Five-Tier Discard Safety Lattice:** Every statement form in CoreX maps to exactly one valid idiom per return-type category. Bare `_ = expr;` intentionally suppresses `E0413` (`@must_use`) on pure or optional values, while remaining strictly rejected on `unit` (`E0439`), `T!E` error unions (`E0414`), and `@linear` resources (`E0304`) so API refactors into fallible functions never silently swallow errors.

Verifying `_ = expr;` across CoreX's type and memory-safety tiers (`E0413`, `E0414`, `E0304`, and `E0439`) closes two additional cross-language pitfalls. First, `_ = expr;` suppresses **`E0413` (`@must_use`)** on pure or optional values (`_ = desc.classify();`), but **does NOT suppress `E0414` on `T!E` error unions**. As documented in Clippy's `let_underscore_must_use` rationale, allowing an untyped `_ = write_chunk(buf);` to silence `Result` creates a silent refactoring bug when `write_chunk` evolves from returning `usize` (`@must_use`) to `usize!IoError`: the existing `_ =` silently swallows newly introduced I/O errors! Following Zig's error-union rule, `_ = fallible();` emits **`E0414`**, directing the author to write **`fallible() catch {};`** when `T == unit` (e.g., `sock.close() catch {};`) or **`_ = fallible().ok();`** when intentionally discarding both non-`unit` `T` and `E`. Second, `@linear` handles (`File`, `TcpSocket`, `TaskHandle[T]`, `Arena`) can **never** be discarded via `_ = expr;`, `(val, _) = pair;`, or `let (val, _) = pair;` – `MIR` Pass 2 unconditionally rejects unconsumed `@linear` values with **`E0304`**. Finally, `Sema` emits **`E0439`** on pointless `_ = unit_expr;` statements and on Zig-style redundant `_ = x;` discards when `x` is *also* read elsewhere in the same body (`zig#9238`), while allowing `_ = self;` and `_ = param;` when a trait receiver (`&self`) or public keyword-callable parameter (`loc: SourceLoc = @caller_location()`) is genuinely unread and cannot be prefixed with `_` without changing its public signature.

### 1.6 ADR-23F: Type-Annotation Separator (Colon x: T vs. Space Juxtaposition x T)

**Decision (`ADR-23F`):** CoreX retains **postfix colon separation (`x: T`)** across all type-annotated constructs (`FnParam`, `StructField`, `BitFieldMember`, `ClosureParam`, `LocalDeclStmt`, `WalrusCondExpr`, `ConstItem`, and `TypeParam`), rejecting Go-style space juxtaposition (`x T`) with targeted parser recovery diagnostic **`E0236`** (`SuggestedFix` inserting `":"`).

| Syntactic Position in CoreX | Canonical Colon Separation (`x: T`) **(Winner)** | Space Juxtaposition (`x T`) *(Go Style)* | Parser / Ergonomic Failure Under Space Juxtaposition |
| :--- | :--- | :--- | :--- |
| **12-Language Reference Cohort** | **10 of 12 (`83.3%`):** **Rust, Swift, Zig, Kotlin, Python, TypeScript, Scala 3, Odin, Hylo, Gleam**. | **1 of 12 (`8.3%`):** **Go** only (`C#` uses prefix `T x`). | *Note:* Odin keeps Pascal's `:` (`x: u32`, `x, y: int`); Go's `parseParameterList` requires multi-pass reclassification. |
| **MVS, Pointer, Default & `/` / `*` Params** | `var buf: own Buffer, ptr: *mut u8, out_v: &out T, /, *, port: u16 = 8080` | `var buf own Buffer, ptr *mut u8, out_v &out T, /, *, port u16 = 8080` | **Modifier Soup & `*` Clash:** `var buf own Buffer` runs 4 words together; `ptr *u8` next to `, *,` zone separators mimics multiplication! |
| **Closures vs. Callable Types (`SE-19`)** | `\|x\| x + 1` · `\|x: u32\| x + 1` · `\|cb: \|u32\| -> bool\| …` | `\|x\| x + 1` · `\|x u32\| x + 1` · **`\|cb \|u32\| -> bool\| …`** | **Hard `LL(k)` Delimiter Collision:** In `\|cb \|u32\| -> bool\|`, the second `\|` prematurely closes the outer parameter list (`\|cb\|`)! |
| **`struct` / `bit_field` vs. Literals & Calls** | `struct CStr { ptr: *u8 }` · `flags: u8 \| 2` · `CStr { ptr: p }` · `f(timeout: 5_u32)` | `struct CStr { ptr *u8 }` · `flags u8 \| 2` vs. `CStr { ptr: p }` · `f(timeout: 5_u32)` | **Asymmetry & Bit-Width Clash:** Literals (`CStr { ptr -1 }`) and named calls (`f(x -1)`) *must* keep `:` to avoid `ptr - 1` subtraction! |
| **`let` / `var` / `const` Bindings** | `let count: usize = 0;` · `var buf: [u8; 64];` · `const MAX: usize = 8;` | `let count usize = 0;` · **`var buf [u8; 64];`** · `const MAX usize = 8;` | **Whitespace-Invariance Clash:** Because spaces are trivia, `buf [u8; 64]` has the exact same `[IDENT, LBRACKET]` prefix as `buf[i]`! |
| **`corex lsp` Incomplete-Code Recovery** | `fn open(path: █)` → `TokenKind.colon` = **100% `Type` hole** | `fn open(path █)` → ambiguous (`Type` vs. `,` vs. `)` end) | Without `:`, `corex lsp` cannot tell whether `path` is an unfinished parameter awaiting a type or a missing comma/paren mid-edit. |

Contrary to a common grouping of Go and Odin, **Odin explicitly retains Pascal's colon separator** (`proc(x: int, y: int)` and grouped `x, y: int`, `number: int`), leaving **Go (`1 of 12`)** as the sole language in our cohort to omit `:`. In his July 2010 essay *Go's Declaration Syntax*, Rob Pike noted that Go placed names before types for left-to-right readability on complex function and slice types, dropping Pascal's `:` strictly *"in the interests of brevity"*. Even in Go – which has **zero** parameter ownership modifiers, uses `func(…)` instead of `|…|` closures, writes `[N]T` prefix array bounds, and lacks named call arguments – omitting `:` forces `src/go/parser/parser.go` (`parseParameterList`) to speculatively parse mixed expression/type lists before retroactively reclassifying identifiers as parameter names or unnamed types, a complexity worsened by `[T]` generics.

In CoreX, where whitespace is purely non-syntactic trivia (`DR-03` §3.2), omitting `:` causes immediate `LL(k)` delimiter collisions and severe readability degradation across every construct audited in Question 6. In closures (`SE-19`), CoreX uses `|…|` for both closure parameter lists (`|x|`, `|x: u32|`) and `@local` callable types (`|u32| -> bool`); under space juxtaposition, a closure parameter whose type is itself a `@local` closure becomes `|cb |u32| -> bool|`, where the opening `|` of `|u32|` is tokenized as the **closing `|` of `|cb|`**! In `LocalDeclStmt` (`let` / `var`), `var buf [u8; 64];` has the exact same `[KW_VAR, IDENT, LBRACKET]` token stream independent of spaces, colliding with pattern slice/index syntax (`let (a, b) (u32, u32) = …` similarly juxtaposes two `(` `)` groups). In `FnParam`, combining `ADR-22B`/`ADR-22F` modifiers with `SE-11` `/` and `*` parameter zones turns `(var buf: own Buffer, ptr: *mut u8, out_slot: &out T, /, *, port: u16 = 8080)` into `(var buf own Buffer, ptr *mut u8, out_slot &out T, /, *, port u16 = 8080)`, where `var buf own Buffer` merges four unseparated words and `ptr *mut u8` / `ptr *u8` next to `, *,` mimics binary multiplication. Moreover, struct literals (`CStr { ptr: raw_ptr }`), named call arguments (`connect(timeout: 5_u32)`), and attributes (`@route(path: "/v1")`) **cannot** omit `:` without colliding with binary operators (`CStr { ptr -1 }` vs. `ptr - 1`). As Guido van Rossum reported from CWI's user testing of ABC with and without colons, the colon visually anchors the boundary between what is being named and what follows while preserving syntactic redundancy for error detection – giving `corex lsp` an unambiguous `LL(1)` `Type`-completion trigger the instant `:` is typed.

### 2.2 EBNF Grammar Delta Relative to DR-22

Four decisions – **`ADR-23B` (`ImplItem`)**, **`ADR-23C` (`IfExpr`)**, **`ADR-23D` (`PRIM_TYPE`)**, and **`ADR-23F` (`:` Type Annotations)** – require **zero valid-syntax EBNF changes** relative to `DR-21` §3.2 and `DR-22` §3.3. (*   ModItem | ConstItem | TypeAliasItem | StructItem | StructField           *)
(* | BitFieldItem | BitFieldMember | EnumItem | EnumVariant                   *)
(* | UnionItem | TraitItem | TraitMember | ImplItem | ImplMember              *)
(* | SubscriptItem | FunctionItem | ExternStaticItem | ExternBlock | TestItem *)
(* | BenchItem                                                                *)
(* with zero intervening blank lines or non-doc `//` comments (else E0230).   *)

(* ADR-23E: SINGLE CANONICAL DISCARD (`_ = Expr;`) & NON-EMPTY `let`/`var`    *)
(* ========================================================================== *)

                | { Attribute } LocalDeclStmt
                | DeferStmt | ErrDeferStmt | YieldStmt

//!
//! Provides cache-aligned packet slot metadata for zero-allocation I/O rings

use cx.mem.align_up;

// ---------------------------------------- TYPES ----------------------------------------

/// Packed 32-bit slot control word mapped directly into shared DMA ring memory.
pub bit_field SlotFlags: u32 {
    /// Slot currently owns an unconsumed payload frame.
    pub occupied: bool | 1,
    /// Frame marks the end of a logical multi-segment message.
    pub end_of_msg: bool | 1,
    /// Priority class (`0` = bulk, `1` = normal, `2` = control, `3` = urgent).
    pub priority: u8 | 2,
    /// Byte length of the payload slice (`0..=65_535`).
    pub byte_len: u16 | 16,
    /// Reserved zero bits for future hardware offload flags.
    _reserved: u16 | 12,

pub enum SlotTier: u8 {
    /// Slot holds no active payload.
    Idle = 0,
    /// Normal throughput scheduling tier.
    Standard = 1,
    /// Low-latency control or keepalive frame.
    Expedited = 2,
    /// Highest-priority ring management frame.
    Control = 3,

@repr(C)

    /// Physical or IOMMU-mapped buffer address aligned to `RING_ALIGN_BYTES`.
    pub dma_addr: u64,
    /// Packed occupancy, priority, and byte-length control word.
    pub flags: SlotFlags,
    /// Monotonic ABA generation counter.
    pub generation: u32,
}

/// Default cache-line alignment in bytes for shared ring descriptors.
const RING_ALIGN_BYTES: usize = 64;

// -------------------------------------- INTERNALS --------------------------------------

impl SlotDesc {
    /// Advances `generation` using 32-bit wrapping arithmetic.
    @inline @no_alloc @no_panic @must_use
    fn bump_generation(&mut self) -> u32 {
        self.generation +%= 1_u32;
        self.generation
    }
}

// ------------------------------------- PUBLIC API --------------------------------------

impl SlotDesc {
    /// Initializes an empty `SlotDesc` at `raw_buf` aligned up to `RING_ALIGN_BYTES`.
    ///
    /// ```cx
    /// var desc: SlotDesc;
    /// SlotDesc.init_aligned(&out desc, ptr, 512_u16, priority: 2_u8);
    /// ```
    @inline @no_alloc @no_panic
    pub fn init_aligned(
        out_slot: &out Self,
        raw_buf: *mut u8,
        byte_len: u16,
        /,
        *,
        priority: u8 = 1_u8,
    ) {
        let aligned_addr: usize = align_up(raw_buf as usize, RING_ALIGN_BYTES);
        out_slot.* = Self {
            dma_addr: aligned_addr as u64,
            flags: SlotFlags {
                occupied: byte_len > 0_u16,
                end_of_msg: true,
                priority: priority & 0b11_u8,
                byte_len,
                _reserved: 0_u16,
            },
            generation: 1_u32,
        };
    }

    /// Maps a descriptor's flags onto its canonical `SlotTier`.
    @inline @no_alloc @no_panic @must_use
    pub fn classify(&self) -> SlotTier {
        if not self.flags.occupied {

        } else if self.flags.priority == 3_u8 {
            .Control
        } else if self.flags.priority == 2_u8 {
            .Expedited
        } else {
            .Standard
        }
    }

    /// Resets the descriptor to idle and discards the new generation counter.
    @inline @no_alloc @no_panic
    pub fn clear(&mut self) {

        self.flags.byte_len = 0_u16;
        _ = self.bump_generation();
    }

    theme: &Theme,
    /,
    *,
    compact: bool = false,
) -> View {
    @state var muted: bool = false;

    let latest = Computed.new(|| -> ClusterMetric {
        metrics.get().as_slice().last().copied() orelse ClusterMetric {
            timestamp_ms: 0_u64,
            cpu_pct: 0.0_f32,
            active_conns: 0_u32,
        }
    });

    let cur = latest.get();
    let severity_label: str = if muted {
        "MUTED"
    } else if cur.cpu_pct >= CRIT_CPU_PCT {
        "CRITICAL"
    } else if cur.cpu_pct >= WARN_CPU_PCT {
        "WARNING"
    } else {
        "NOMINAL"
    };

    Card(padding: if compact { 8_u16 } else { 16_u16 }, border_color: theme.border_subtle) {
        Row(justify: .SpaceBetween, align: .Center) {
            Text("Worker {node_id}", weight: .Bold, size: 16_u16);
            Badge(label: severity_label, color: cur.status_color());
        }
        ProgressBar(value: cur.cpu_pct, max: 100.0_f32, tint: cur.status_color());
        Row(gap: 8_u16) {
            Button(
                label: if muted { "Unmute Alerts" } else { "Mute Alerts" },
                on_click: |_: u32| {
                    muted = not muted;
                    _ = metrics.touch();
                },
            );
        }
    }
}
