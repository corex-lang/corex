# Compile-Time Execution, Reflection, and Metaprogramming Architecture for CoreX (.cx)

To shift configuration validation, serialization routing, command-line parser synthesis, and lookup-table generation from runtime to compile time without compromising sub-100 ms incremental compilation or Language Server (`corex lsp`) responsiveness, **CoreX (`.cx`)** rejects both Rust-style token-stream procedural macros (`proc_macro`) and Zig-style untyped duck-typed metaprogramming (`anytype` and unrestricted `@Type` reification). Instead, CoreX adopts a **Three-Pillar Metaprogramming Architecture**: (1) **Bounded Parametric `comptime` Execution** of standard `.cx` functions, control-flow blocks (`comptime { ... }`, `comptime if`, `comptime for`), and generic value parameters (`[T, const N: usize]`); (2) **Value-Based Mirror Reflection (`std::meta`)** backed by the compiler's `InternPool` `enum(u32)` handles (`TypeId`, `FieldId`) and explicit field projection intrinsics (`@type_info[T]()`, `@field(val, f)`); and (3) **Signature-Firewall `@derive` and Typed Attribute Schemas (`@attribute_schema`)**. Under this architecture, metaprogramming operates strictly on typed values and read-only structural type mirrors rather than raw syntax tokens, and **no `comptime` block or `@snake_case` attribute is permitted to mutate, delete, or inject unannounced top-level symbols or alter an item's external type signature**.

This **Signature Firewall** resolves the fundamental tension between expressive compile-time metaprogramming and interactive IDE tooling. In Rust, procedural macros require compiling host dynamic libraries (`syn`, `quote`, `serde_derive`), spawning an out-of-process RPC server (`proc-macro-srv`), and re-parsing token streams from scratch on every file edit – imposing a **3.73x to 3.78x single-threaded compile-time penalty** (`syn@2` vs. `facet@0.8` reflection in developer benchmarks by Amos Wenger) and degrading `rust-analyzer` whenever an edited function body contains transiently broken syntax inside an attribute macro. Conversely, in Zig and Mojo, deferring type signature calculation and constraint verification to a late compile-time elaboration interpreter causes language servers (`ZLS` and `mojo-lsp`) to report `unknown` hover types, struggle with `anytype` autocomplete, and emit multi-frame instantiation stack traces. By restricting `@derive(Trait)` to synthesizing bodies for statically declared `impl Trait for Type` blocks and modeling attributes (`@route`, `@cli_command`, `@arg`) as early type-checked struct literals attached to `InternPool` metadata, `corex lsp` resolves type signatures, trait conformances, autocomplete candidates, and rename refactorings during **Phase 1 and Phase 2 (Signature Lowering)** without executing a single instruction of the compile-time virtual machine.

When compile-time body evaluation *is* required – for constant folding, static assertions, compile-time regex/route compilation, or unrolling reflective `@derive` implementations – CoreX executes lowered **Block-Argument SSA Mid-Level IR (`MIR`)** inside a deterministic **64-bit Virtual-Register Bytecode Virtual Machine (`MirVm`)**. Grounded in academic virtual machine research (Shi et al., VEE '05) showing that register architectures eliminate **43.47% of static bytecode instructions** and **more than 47% of dynamic instructions** while cutting execution time by **26.5% to 32.3%** compared to stack machines, and informed by Red Hat engineer Timm Baeder's 2024–2026 benchmarks on Clang's bytecode constant interpreter (`-fexperimental-new-constant-interpreter`, which outperforms Clang's legacy AST interpreter by **6.55x** on initialized heap loops and **more than 2,380x** on large uninitialized array allocations), `MirVm` decouples data bytes from verification metadata. Rather than inflating all ≥16-bit integers to 24 bytes to track pointer provenance or interleaving `InlineDescriptor` headers between struct fields as Clang's bytecode interpreter does, `MirVm` stores pure target-layout bytes in zeroed `BumpArena` slabs paired with side-table bitsets (`InitMask` and `ProvenanceMap` indexed by `ComptimeAllocId`). Non-transient compile-time allocations that survive evaluation are automatically frozen, deduplicated via `Wyhash(0)` content hashing in the `InternPool`, and emitted directly into the binary's read-only data segment (`.rodata`) with zero runtime initialization cost.

## 1. Comparative Evaluation of Metaprogramming Paradigms

Selecting a metaprogramming model for CoreX requires evaluating how existing systems languages balance **compile-time expressiveness**, **incremental build speed**, **IDE/LSP analyzability**, and **binary code size**. A rigorous examination of the three primary paradigms – Zig-style `comptime`, Rust-style token-stream macros, and structured type reflection mirrors (C++26 `P2996`, Mojo, and Odin) – reveals distinct architectural failure modes that CoreX is designed to avoid.

Bottom panel: Compile-time constant evaluation benchmarks (30 runs each) comparing Clang's experimental bytecode interpreter against Clang's legacy AST-walking interpreter and GCC 14.3.1 on 10,000-iteration compile-time heap allocation loops.

### 1.1 Zig-Style `comptime`: Uniform Execution vs. Duck-Typed Generics and `@Type` Fragility

Zig's central insight is that compile-time metaprogramming does not require a separate macro language or template sub-grammar; instead, standard language constructs execute at compile time whenever contexts require a compile-time known constant (such as array bounds, `comptime` parameters, or `comptime { ... }` blocks). Furthermore, because Zig's `comptime` operates on evaluated values rather than unevaluated AST token trees, it preserves **referential transparency**: unlike a Rust macro, which can inspect token structure to distinguish `1 + 1` from `2`, a Zig `comptime` function sees only the evaluated integer `2`.

However, Zig extends `comptime` to replace **parametric generics** and **structured traits** altogether, treating types as ordinary runtime-like values (`comptime T: type`) returned from ordinary functions (`fn LinkedList(comptime T: type) type`) and accepting unconstrained `anytype` parameters. In practice, this conflation of value evaluation with type-system definition introduces three engineering liabilities.

First, `anytype` and `comptime T: type` undermine definition-site type checking and IDE autocomplete. Because `anytype` defers all type logic into imperative `comptime` statements inside the function body, a function signature no longer states its structural contract. As Zig creator Andrew Kelley (`andrewrk`) noted in Zig Issue #17198, `anytype` makes it difficult for developers to know what arguments can be passed into a function, difficult for documentation generators to describe parameter expectations, and difficult for the compiler to determine whether a type mismatch stems from the caller's argument or a bug inside the generic function itself. In editor workflows, the Zig Language Server (`ZLS`) relies on heuristics for simple `comptime` expressions, cannot autocomplete `anytype` parameters across files, and gives up when types depend on complex `comptime` calculations – reporting `unknown` on hover and forcing developers to run a full `zig build` (taking 10–20 seconds on medium codebases) to catch type errors.

Second, arbitrary type reification via `@Type` proved problematic for compiler evolution and incremental analysis. Historically, Zig paired `@typeInfo(T)` with its inverse `@Type(info)`, allowing `comptime` code to construct new types from `std.builtin.Type` tagged unions. Following Zig Issue #10710, Zig 0.16.0 (released in April 2026) removed `@Type` from the language and replaced it with targeted type-creating builtins (`@Int`, `@Float`, `@Pointer`, `@Array`, `@Struct`, `@Enum`, `@Union`). Allowing `@Type` to accept arbitrary union tags – such as `.NoReturn`, `.Undefined`, `.Null`, `.ComptimeInt`, or structs with non-empty `.decls` slices – created redundant representations and prevented the compiler from accurately constraining what can be reified.

Third, interleaved type resolution and `comptime` execution create dependency loop hazards. When type definitions run arbitrary `comptime` expressions to compute field types or alignments (e.g., `foo: [*]align(@alignOf(@This())) u8`), the compiler risks cyclic dependency queries, requiring dedicated cycle detection and acyclic dependency tracking in `Sema` and `InternPool` (`AnalUnit`).

### 1.2 Rust-Style Hygienic Declarative (`macro_rules!`) & Procedural (`proc_macro`) Macros

Rust divides metaprogramming into pattern-based declarative token-tree macros (`macro_rules!`) and out-of-process procedural macros (`#[derive(...)]`, `#[attr]`, and `fn_like!(...)`) compiled as native host dynamic libraries (`proc-macro = true`). While procedural macros enable arbitrary syntax transformations (such as `serde_derive`, `clap_derive`, or embedded HTML/JSX in `rstml`), they conflict with CoreX's compilation speed, tooling, and reproducibility requirements across four dimensions.

First, procedural macros introduce critical-path compilation bottlenecks due to redundant AST parsing. A Rust procedural macro receives an opaque `proc_macro::TokenStream`, meaning that even though `rustc` has already tokenized and parsed the source file into its internal AST, a `syn`-based macro must link against user-space parser crates (`syn`, downloaded over 297.7 million times, alongside `proc-macro2` and `quote`) to **re-parse the entire token stream into a full Rust AST** from scratch. In developer benchmarks published by Amos Wenger (`fasterthanli.me`, May 2025) comparing `facet@0.8` (reflection-based metadata) against `syn@2` and `syn@1`, `facet` compiled in **1.241 s ± 0.003 s** vs. **2.679 s ± 0.035 s** for `syn@2` (**2.16x faster**) on an Apple M4 Pro with default concurrency, and **3.225 s ± 0.035 s** vs. **12.200 s ± 0.106 s** (**3.78x faster**) single-threaded (`-j1`). On GitHub Actions free-tier CI runners, `facet` ran **3.38x faster** at default concurrency (**2.768 s** vs. **9.352 s** for `syn@2`) and **3.73x faster** with `-j1` (**5.726 s** vs. **21.348 s** for `syn@2`). Because `syn` sits on the critical build path of ubiquitous derive crates (`serde_derive`, `clap_derive`, `displaydoc`, `yoke-derive`), downstream crates are blocked until `syn` finishes compiling.

Second, `rustc` does not cache procedural macro invocations across warm builds. Because procedural macros are arbitrary native functions, every time Cargo detects a file change (even touching `main.rs` without changing dependencies), procedural macros must re-execute and re-parse the token stream. In Wenger's `ouroboros-family` benchmarks, declarative macros (`decl`) compiled in **166.2 ms** on cold builds compared to **718.0 ms** for `unsynn` (**4.32x slower**) and **1.574 s** for `syn` (**9.47x slower**, and up to **13.71x–36.76x slower** in broader macro microbenchmarks). On warm builds expanding ~11,000 lines of nested code after touching `main.rs`, `syn` still added ~100 ms of pure re-parsing overhead (**304.8 ms** vs. **197.7 ms** for `decl`, or **1.54x slower**).

Third, token-stream macros degrade LSP reliability and refactoring (`proc-macro-srv`). To analyze macro-heavy code, `rust-analyzer` must compile proc-macro crates and run a standalone `proc-macro-srv` RPC server. When developers write calls inside complex declarative or procedural macros, `rust-analyzer` frequently struggles to provide completion or go-to-definition, and mapping IDE rename refactorings across macro token spans can produce corrupted `TextEdit` offsets (`rust-analyzer` Issue #14137).

Fourth, unsandboxed host execution breaks hermetic reproducibility. Because procedural macros execute arbitrary host code on the developer's machine (including filesystem or network access during `cargo build` or IDE background indexing), they create supply-chain security and cross-compilation reproducibility risks, motivating Rust Pre-RFCs (`proc_macro_sandbox`) to compile procedural macros into sandboxed WebAssembly modules.

### 1.3 Compile-Time Type Reflection Mirrors (C++26 `P2996`, Mojo `@parameter`, and Odin)

Recent systems language designs have moved toward structured compile-time reflection APIs that expose compiler type metadata as values:

*   **C++26 Static Reflection (`P2996R9`) and Expansion Statements (`P1306`):** Reaching feature freeze for C++26 (with experimental support in GCC 15+ and Clang 19+), `P2996` introduces the prefix reflection operator `^^` (updated from `^` in `P3381R0`), which maps a program construct (`^^T`, `^^::`) to a single opaque, pointer-sized reflection value `std::meta::info` (`sizeof(void*)`), paired with `consteval` metafunctions (`std::meta::nonstatic_data_members_of`, `enumerators_of`, `identifier_of`, `type_of`, `define_aggregate`) and grammatical splicers (`[: refl :]` and `typename[: refl :]`). Combined with `template for (constexpr auto mem : ...)` (`P1306`), which unrolls the loop body into distinct statements `S0; S1; ... Sn-1;` at compile time so each iteration can bind a different type or `constexpr` value while supporting `break` early termination, C++26 eliminates recursive template metaprogramming for struct comparison and enum-to-string conversion. Notably, `P2996` chose a **single opaque `std::meta::info` type** rather than a hierarchy of reflection types (`std::meta::variable`, `std::meta::type`) so that internal compiler AST designs are never codified into the standard library type system. However, C++26 reflection carries two major limitations for CoreX: (1) its splicer punctuation (`a.[:member:]`, `typename[:types[N]:]`, `^^E`) introduces dense symbol noise contrary to `DR-03`'s readability goals; and (2) because C++ still lacks general **non-transient `constexpr` allocation** (`P0784R7`), dynamic `std::vector` or `std::map` containers allocated at compile time cannot directly persist into runtime static data (`define_static_array` and `define_static_string` were removed prior to `P2996R9`).
*   **Mojo's Three-Phase Evaluation Model (`@parameter` / `comptime`):** Mojo provides compile-time metaprogramming via square-bracket parameters, `@parameter for` / `@parameter if` (evolving toward a `comptime` modifier and `comptime` alias keyword in 2025–2026 community discussions), and an MLIR compile-time interpreter. However, as Chris Lattner explained on the Modular forum, Mojo separates static evaluation into three sequential phases: **Phase 1 (Parser Time)** for local type checking and overload resolution; **Phase 2 (Early Dataflow Checks)** right after parsing in MLIR; and **Phase 3 (Elaborator / Instantiation Time)** where the `comptime` interpreter actually runs, clones function bodies, and evaluates `@parameter if` and constraint clauses. Crucially, **Mojo's LSP supports only Phases 1 and 2, omitting Phase 3 entirely** to protect interactive editor latency and CPU usage – meaning checks and types resolved during Phase 3 elaboration are unavailable to the LSP and emit multi-frame C++-style stack traces on error.
*   **Odin's RTTI (`core:reflect`) vs. CTTI Exponential Bloat Critique:** Odin provides runtime type reflection (`runtime.Type_Info`, `type_info_of(T)`) alongside compile-time reflection (`$T: typeid`, `#type_info(T)`). In a September 2026 article (*"CTTI is Exponential, RTTI is Linear"*), Odin creator Ginger Bill highlighted a fundamental systems trade-off: whereas a Runtime Type Information (RTTI) type table scales **linearly** (`O(N)` entries for `N` types in a program) and allows a single compiled procedure to serialize or format any type via table lookup, Compile-Time Type Information (CTTI) monomorphizes a new concrete function for each used type combination – scaling as `O(N × K)` in average/general multi-parameter cases and `O(N^K)` in worst-case nested or variadic functions, increasing compile times, bloating binary size, and pressuring the CPU instruction cache (i-cache).

## 2. LSP & Incremental Compilation Compatibility (`corex lsp` & Query Firewall)

A foundational requirement for CoreX is that metaprogramming (`comptime`, `@derive`, `@route`, `@cli_command`) must never blind `corex lsp` (go-to-definition, hover types, rename refactoring, completion) or invalidate downstream modules during incremental builds. Achieving this requires co-designing the language's metaprogramming rules with a **Salsa-inspired Incremental Query Engine** and `DR-01`'s **`InternPool` Dependency Graph**.

> **Visual – The Signature Firewall Decouples Instant LSP Analysis from Compile-Time VM Execution:** CoreX partitions semantic analysis into three strictly isolated phases separated by an incremental **Signature Firewall**. Because attributes and *@derive* annotations can never alter an item's external signature or inject unannounced symbols, *corex lsp* services hover, autocomplete, go-to-definition, and rename refactorings directly from Phase 1 and Phase 2 tables in under 5 milliseconds without invoking the Phase 3 *MIR* Virtual Machine.

### 2.1 Why Existing Metaprogramming Models Blind Language Servers

Language servers operate under an unforgiving real-time constraint: as a developer types in an editor, **roughly 95% of intermediate code states are syntactically or semantically invalid**, yet the developer requires immediate member completion (`.`), hover documentation, and jump-to-definition. Existing metaprogramming systems struggle under this constraint for two distinct reasons:

1.  **The Token-Stream Opacity Trap (Rust `proc_macro`):** When a macro receives raw syntax tokens and returns arbitrary syntax tokens, the compiler cannot know what structs, methods, or trait implementations exist in a module until every macro in that module (and its dependencies) has been compiled into a native shared library and executed. Furthermore, when a function is wrapped in an attribute or declarative macro, syntax errors while typing inside the macro body can cause the parser inside the macro to fail, leaving `rust-analyzer` unable to provide go-to-definition or completion inside the macro block.
2.  **The Late-Elaboration Trap (Zig `comptime` Type Functions & Mojo Phase 3):** When a language uses imperative `comptime` code to compute function parameter types (`anytype`), return types (`fn Matrix(comptime R: usize, comptime C: usize) type`), or conditional declarations, a language server cannot determine the fields or methods of a variable without running a full compile-time interpreter over nested call graphs. Because running a full elaboration interpreter on every keystroke is too expensive (`mojo-lsp` disables Phase-3 elaboration entirely, and `ZLS` limits itself to shallow heuristics), hover and autocomplete degrade whenever types cross a complex `comptime` boundary.

### 2.2 CoreX's Five Invariants for Zero-Blindness LSP and Incremental Caching

CoreX eliminates both failure modes by enforcing five structural invariants across its grammar (`DR-03`), bidirectional type checker (`DR-02`), and `InternPool` incremental database (`DR-01`):

1.  **Invariant 1 – The Signature Firewall (Ban on Unannounced Symbol Injection):** No `comptime` expression, `@derive` clause, or `@snake_case` attribute in CoreX can synthesize a new top-level identifier, add or remove fields on an existing `struct`, or alter the parameter or return types of a `fn` declaration. All generic types are parameterized via explicit square-bracket declarations (`struct Matrix[T, const ROWS: usize, const COLS: usize] { ... }`) whose fields and methods are directly visible in the flat postorder CST (`DR-01`) immediately after parsing.
2.  **Invariant 2 – Two-Phase `@derive(Trait)` Lowering (Header-First, Body-Lazy):** As noted in Rust RFC 3698, derive macros simplify IDE tools like `rust-analyzer` because the tool knows a derive macro will never alter the underlying item definition. CoreX enforces this structurally: `@derive(Serialize, Deserialize, Eq)` on `pub struct User { ... }` is lowered during **Phase 2 (Signature Lowering)** directly into explicit trait conformance headers in the module's symbol table (`impl Serialize for User`, `impl Deserialize for User`, `impl Eq for User`). Because the method signatures of `Serialize`, `Deserialize`, and `Eq` are fixed by their `trait` declarations, **`corex lsp` immediately resolves every derived method signature (`user.serialize_json(&mut writer)`) in Phase 2 without running `MirVm` to expand the derived method body**. The `MirVm` is invoked to unroll the `comptime for` reflection loop inside `Serialize::serialize_json` *only* during Phase 3 (`corex build` codegen or explicit `comptime` evaluation).
3.  **Invariant 3 – Attributes Are Passive, Type-Checked Metadata Structs (`@attribute_schema`):** In CoreX, `@cli_command(name = "cx-scan")`, `@arg(short = 'p', long = "pattern")`, and `@route(method = "POST", path = "/v1/users")` are **not** procedural macros that rewrite ASTs. Instead, every user-defined or standard-library attribute is declared as a plain `.cx` struct annotated with `@attribute_schema`:

    ```rust
    @attribute_schema(targets = .StructField)
    pub struct ArgAttr {
        pub short: char? = .None,
        pub long: str,
        pub env_var: str? = .None,
    }
    ```

    When a developer writes `@arg(short = 'p', long = "pattern")` on a field, the Phase-2 bidirectional type checker validates the attribute arguments against `ArgAttr` in Checking Mode. This gives `corex lsp` **instantaneous autocomplete, hover documentation, and rename refactoring inside `@arg(...)` and `@route(...)` arguments**, and editing transiently broken syntax inside `fn create_user(...)` never invalidates the `@route` metadata or the function's external signature.
4.  **Invariant 4 – Mandatory Explicit Types on `const` Declarations (`DR-03`):** As Zig users observed on `Ziggit`, omitting an explicit type annotation on `const MY_CONST = complex_expr;` leaves `ZLS` reporting `unknown` until `complex_expr` is evaluated, whereas pinning down `const MY_CONST: SomeType = complex_expr;` saves the language server from having to execute `comptime` code just to know the constant's type. Because `DR-03`'s grammar mandates explicit `: Type` annotations on all `const` items (`ConstItem = "const" CONST_IDENT ":" Type "=" Expr ";"`) and function signatures (`FnSignature`), `corex lsp` always knows the exact type of every constant and function in Phase 2 without running `MirVm`. Similarly, signature-position const-generic expressions (`[T; N + M]`) are restricted to literals, `CONST_IDENT` identifiers, and inline builtin arithmetic folded in Phase 1/2.
5.  **Invariant 5 – Salsa-Style Backdating and `InternPool` Memoization (`AnalUnit.memoized`):** Combining the query-firewall architecture of `Salsa` (`#[salsa::tracked]`, `#[salsa::interned]`, backdating) with Zig's `Zcu` / `InternPool` dependency graph (`src_hash_deps`, `nav_val_deps`, `nav_ty_deps`, `interned_deps`), the CoreX compiler isolates function body edits from module signatures. Because signatures act as the module firewall, editing a function body recomputes only that function's local IR while leaving `item_signature(DefId)` unchanged (**backdated**), preventing cascading re-analysis or `comptime` cache invalidation across downstream files.

## 3. Deliverable 1: Recommended Metaprogramming & Compile-Time Execution Architecture for CoreX

### 3.1 Surface Syntax and `LL(k)` Grammar Integration (`DR-03` Alignment)

To integrate compile-time execution and reflection into CoreX v1.0 without introducing a single `FIRST`/`FOLLOW` conflict or breaking `DR-03`'s stateless `LL(1)` / Pratt parser, CoreX includes the hard keyword **`KW_COMPTIME`: `"comptime"`** in the unified 112-variant `TokenKind` table (`DR-03` §5.2) and **nine compiler intrinsics** prefixed with `@snake_case` (reusing `DR-03`'s existing `AT` + `IDENT` token sequence):

```ebnf
(* ========================================================================== *)
(* DR-05 EXTENSIONS TO DR-03 COREX v1.0 EBNF GRAMMAR (100% LL(1) DISJOINT)    *)
(* ========================================================================== *)

(* 1. Top-Level Item Extensions: Comptime Functions & Static Assertions       *)
Item            = { Attribute } [ "pub" ]
                  ( ModItem | UseItem | ConstItem | TypeAliasItem
                  | StructItem | EnumItem | UnionItem | TraitItem
                  | FunctionItem | ComptimeAssertItem )
                | { Attribute } ImplItem ;

ComptimeAssertItem = "comptime" Block ;

FunctionItem    = [ "comptime" ] [ "async" ] [ "unsafe" ] [ "extern" ]
                  "fn" FnSignature ( Block | ";" ) ;

(* 2. Compile-Time Parameters in Functions (Distinct from Runtime Params)     *)
FnParam         = [ "comptime" | "mut" | "own" | "ref" ]
                  ( IDENT | "_" ) ":" Type [ "=" Expr ] ;

(* 3. Compile-Time Unrolling Loops & Branching Statements Inside Blocks       *)
Stmt            = ";"
                | { Attribute } LocalDeclStmt
                | ComptimeStmt
                | DeferStmt | ReturnStmt | BreakStmt | ContinueStmt
                | ForStmt | WhileStmt | LoopExpr [ ";" ]
                | Expr ( AssignOp Expr ";" | ";" ) ;

ComptimeStmt    = "comptime" ( ForStmt | IfExpr | Block ) ;

(* 4. Compile-Time Primary Expressions & Reflection/Projection Intrinsics     *)
PrimaryExpr     = Literal | "self" | "." TYPE_IDENT [ CallArgs ]
                | "(" [ Expr { "," Expr } [ "," ] ] ")"
                | "[" [ Expr ( ";" Expr | { "," Expr } [ "," ] ) ] "]"
                | ClosureExpr | IfExpr | MatchExpr | LoopExpr
                | "comptime" ( Block | IfExpr | MatchExpr | PrefixExpr )
                | IntrinsicExpr
                | "unsafe" Block | "async" Block | Block
                | PathOrConstructExpr ;

IntrinsicExpr   = "@" IDENT [ TypeArgs ] CallArgs ;
```

#### Verification of `LL(1)` Disjointness

Every grammar addition is strictly `LL(1)`-disjoint:
1.  **`comptime` Keyword Disjointness:** At top-level `Item`, `"comptime"` followed by `"{"` parses deterministically as `ComptimeAssertItem` (`comptime { @compile_assert(...); }`), whereas `"comptime"` followed by `"fn"` (or `"unsafe"` / `"extern"`) parses as `FunctionItem` (requiring the function to be called *only* at compile time, analogous to C++20 `consteval`). Inside a `Block`, `"comptime"` followed by `"for"`, `"if"`, `"match"`, `"{"`, or an expression (`comptime sha256("seed")`) disambiguates on `peek(1)` in `O(1)` time.
2.  **`@snake_case` Intrinsic Disjointness:** In `DR-03`, `@` (`TokenKind.AT`) could previously appear only at the start of an `Item`, `StructField`, `EnumVariant`, `TraitMember`, `ImplMember`, or `LocalDeclStmt`. Allowing `IntrinsicExpr = "@" IDENT [ TypeArgs ] CallArgs` inside `PrimaryExpr` has zero overlap with statement attributes because statement attributes precede `let` or `var`, whereas an expression starting with `@` (such as `@type_info[T]()`, `@field(x, f)`, `@compile_assert(cond, "msg")`, or `@embed_bytes("table.bin")`) is always followed by `[` or `(`.

### 3.2 CoreX `comptime` Execution Semantics

CoreX distinguishes between two compile-time callable function categories and three evaluation constructs:

1.  **Regular Pure Functions (`fn`) vs. Compile-Time-Only Functions (`comptime fn`):**
    -   Any regular `fn` in CoreX that does not invoke `extern` FFI calls, inline assembly, or raw pointer-to-integer casts is **automatically `comptime`-callable** without needing a `constexpr` annotation (matching Zig and D's CTFE ergonomics). When called in a runtime context, it compiles to native machine code; when called inside a `const` initializer or `comptime` block, `MirVm` interprets its `MirBody`.
    -   Marking a function `comptime fn` (e.g., `pub comptime fn build_lookup_table() -> [u32; 256]`) enforces that the function can *only* be invoked at compile time (producing zero runtime symbol emissions) and allows it to manipulate compile-time-only reflection types (`std::meta::TypeInfo`).
2.  **`comptime` Parameters (`comptime pattern: str`):**
    -   A function parameter prefixed with `comptime` (`pub fn regex_match(comptime pattern: str, input: str) -> bool`) requires the caller to supply a compile-time constant expression for `pattern`. The compiler partially evaluates the function by memoizing `pattern` into the specialization key `(FnDefId, TypeArgs, ComptimeArgs)` in the `InternPool`, allowing the function body to compile `pattern` into a static DFA table at `comptime` and execute only the branchless table lookup against `input` at runtime.
3.  **`comptime for`, `comptime if`, and `comptime match` (Typed Expansion Statements):**
    -   Inside a generic function, `comptime for field in @type_info[T]().as_struct().fields { ... }` unrolls the loop body once per element at compile time (matching C++26 `template for` `P1306` and Zig `inline for`). Crucially, inside each unrolled iteration `i`, `field` is bound as a compile-time constant (`const field: FieldInfo`), allowing `@field(val, field)` to synthesize a distinct static type for each field in the bidirectional type checker.
    -   Inside each iteration, `comptime if` and `comptime match` statically prune untaken branches before type-checking branch-specific operations, while still supporting `break` and `continue` across the unrolled expansion.

### 3.4 Mitigating CTTI Exponential Bloat: Hybrid Two-Tier Reflection Lowering

As Ginger Bill analyzed in *"CTTI is Exponential, RTTI is Linear"* (September 2026), a major risk of compile-time reflection (`comptime for` / `template for`) is that naively unrolling field-by-field serialization or CLI parsing inline for every struct in a large codebase generates a separate machine-code function for every type – scaling multiplicatively (`O(N × K)`) or exponentially (`O(N^K)`), inflating binary size, and causing instruction-cache misses. Conversely, global RTTI emits type metadata for all declared types regardless of whether they are ever serialized and relies on `any` (`rawptr + typeid`) indirection.

CoreX addresses this trade-off – achieving **zero unused RTTI tables, zero `rawptr` unsafety, and `O(N)` linear binary growth on large types** – through **Two-Tier Reflection Lowering**:
1.  **Tier 1 (Hot Unrolled CTTI for Small Types, ≤8 fields):** For compact domain structs and DTOs (such as `CreateUserResp` with 3 fields), `comptime for` unrolls the field operations directly inline, allowing the backend (`-O2`/`-O3`) to constant-fold JSON keys, merge adjacent buffer writes, and inline scalar formatting.
2.  **Tier 2 (Compile-Time Synthesized Schema Tables for Large Types, >8 fields):** Because CoreX supports **non-transient `comptime` array promotion** into `.rodata`, a serializer or CLI parser can inspect `@type_info[T]()` at `comptime` and emit a compact static descriptor array `const SCHEMA: [FieldDescriptor; FIELD_COUNT] = comptime build_schema[T]();` containing field names, byte offsets (`field.byte_offset`), and primitive type tags (`PrimKind`), passing `&SCHEMA` to a **single, shared runtime driver function**. Adding 100 new 50-field configuration structs adds only compact `.rodata` descriptor rows (`O(N)` data bytes, zero duplicated machine instructions) and **zero metadata for types that never invoke the serializer**.

#### Showcase A: Zero-Overhead `std::serde` JSON Serializer (`serde_json.cx`)

This showcase demonstrates how `@derive(Serialize)` and `@serde(rename = "...")` attributes work in CoreX using a typed `@attribute_schema`, `comptime for` field unrolling, and `@field(val, field)` without any external `syn`/`serde_derive` proc-macro crate.

```rust
// File: std/serde/json.cx
mod json;

use std::meta::{TypeInfo, TypeKind, PrimKind, FieldInfo};
use std::io::{ByteWriter, IoError};

/// Typed attribute schema validated in Phase 2 by the bidirectional type checker.
/// Provides instant `corex lsp` autocomplete for `@serde(rename = "…", skip = true)`.
@attribute_schema(targets = .StructField | .EnumVariant)
pub struct SerdeAttr {
    pub rename: str? = .None,
    pub skip: bool = false,
}

pub trait Serialize {
    fn serialize_json(&self, out: &mut ByteWriter) -> Result[unit, IoError];
}

/// Default reflective implementation invoked automatically by `@derive(Serialize)`.
/// Phase 2 registers `impl Serialize for T` immediately; Phase 3 unrolls this body.
pub fn derive_serialize_json[T](val: &T, out: &mut ByteWriter) -> Result[unit, IoError] {
    const INFO: TypeInfo = @type_info[T]();

    comptime match INFO.kind {
        .Struct(s_info) => {
            out.write_byte('{')?;
            var is_first = true;

            comptime for field in s_info.fields {
                const ATTR: SerdeAttr? = field.get_attr[SerdeAttr]();
                const SHOULD_SKIP: bool = match ATTR {
                    .Some(a) => a.skip,
                    .None => false,
                };

                comptime if not SHOULD_SKIP {
                    const KEY_NAME: str = match ATTR {
                        .Some(a) => a.rename.unwrap_or(field.name),
                        .None => field.name,
                    };
                    // Pre-compute the exact JSON key prefix `"key":` at compile time!
                    const KEY_PREFIX: str = comptime concat_str("\"", KEY_NAME, "\":");

                    if not is_first {
                        out.write_byte(',')?;
                    }
                    is_first = false;
                    out.write_str(KEY_PREFIX)?;

                    // `@field(val, field)` projects `&FieldType` with static MVS checking
                    Serialize::serialize_json(&@field(val, field), out)?;
                }
            }
            out.write_byte('}')?;
            .Ok(())
        }
        _ => @compile_error("`@derive(Serialize)` requires a struct or enum type"),
    }
}
```

#### Showcase B: Compile-Time Validated `@cli_command` Argument Parser (`cli_parser.cx`)

In `DR-03` Showcase 1 (`log_scan.cx`), `ScanOptions` used `@cli_command` and `@arg(short = 'p', long = "pattern")` and called `env::parse_args[ScanOptions](&mut arena)`. Below is the implementation of `env::parse_args[T]` in pure CoreX using `comptime` reflection, catching duplicate short or long flags (`-p` used twice) at **compile time** via `@compile_assert`:

```rust
// File: std/env/cli.cx
mod cli;

use std::meta::{TypeInfo, FieldInfo};
use std::mem::Arena;

@attribute_schema(targets = .Struct)
pub struct CliCommandAttr {
    pub name: str,
    pub version: str = "0.1.0",
}

@attribute_schema(targets = .StructField)
pub struct ArgAttr {
    pub short: char? = .None,
    pub long: str,
}

/// Validates at compile time that no two `@arg` fields on `T` share a short or long flag.
comptime fn validate_cli_schema[T]() -> unit {
    const FIELDS: [FieldInfo] = @type_info[T]().as_struct().fields;
    var i: usize = 0;
    while i < FIELDS.len() {
        if let .Some(attr_a) = FIELDS[i].get_attr[ArgAttr]() {
            var j: usize = i + 1;
            while j < FIELDS.len() {
                if let .Some(attr_b) = FIELDS[j].get_attr[ArgAttr]() {
                    @compile_assert(
                        attr_a.long != attr_b.long,
                        "duplicate @arg long flag detected in @cli_command struct",
                    );
                    if let .Some(sa) = attr_a.short {
                        if let .Some(sb) = attr_b.short {
                            @compile_assert(sa != sb, "duplicate @arg short flag in struct");
                        }
                    }
                }
                j += 1;
            }
        }
        i += 1;
    }
}

pub fn parse_args[T](arena: &mut Arena) -> Result[T, str] {
    // Runs inside MirVm once per type `T`; halts build immediately on flag collision!
    comptime { validate_cli_schema[T](); }

    let raw_args = std::env::raw_args_slice(arena);
    var result = @default_init[T]();
    var idx: usize = 1;

    while idx < raw_args.len() {
        let token = raw_args[idx];
        var matched = false;

        comptime for field in @type_info[T]().as_struct().fields {
            const ARG_META: ArgAttr? = field.get_attr[ArgAttr]();
            comptime if let .Some(meta) = ARG_META {
                const LONG_FLAG: str = comptime concat_str("--", meta.long);
                if token == LONG_FLAG {
                    idx += 1;
                    if idx >= raw_args.len() {
                        return .Err("missing value for argument {LONG_FLAG}");
                    }
                    parse_into_field(&mut @field(result, field), raw_args[idx])?;
                    matched = true;
                }
            }
        }
        if not matched {
            return .Err("unknown CLI flag: {token}");
        }
        idx += 1;
    }
    .Ok(result)
}
```

## 4. Deliverable 2: `MIR` Compile-Time Virtual Machine (`MirVm`) Blueprint

To execute compile-time functions, lookup-table generators, and reflective loops at high speed while upholding `DR-01`'s strict reproducible build guarantees (`Stage 3 === Stage 4`), CoreX implements a dedicated **Virtual-Register Bytecode Evaluator (`MirVm`)** operating over `DR-02`'s **Block-Argument SSA `MIR`**.

> **Visual – Out-of-Band Bitsets and Virtual Registers Keep Compile-Time Memory Compact and Target-Exact:** Unlike Clang's bytecode interpreter – which interleaves *InlineDescriptor* headers between struct fields and inflates every integer to 24 bytes to track pointer provenance – CoreX's **MirVm** stores contiguous, target-exact raw bytes inside zeroed *BumpArena* slabs. Initialization state and pointer provenance are tracked out-of-band via dense *u64* bitsets (*InitMask* and *ProvenanceMap*), allowing surviving compile-time allocations to freeze directly into the *InternPool* as *.rodata* constants with zero re-serialization.

### 4.1 Why a 64-Bit Register VM Over Block-Argument SSA Beats AST and Stack VMs

Compiler constant evaluators generally follow one of three designs: (1) recursive AST-walking visitors (such as Clang's legacy `ExprConstant.cpp`); (2) stack-based bytecode interpreters (such as Clang's new `clang/lib/AST/ByteCode` evaluator); or (3) virtual-register machines operating over lowered SSA IR.

Empirical benchmarks and VM architecture studies strongly favor a **virtual-register VM over lowered Block-Argument SSA `MIR`**:
1.  **Eliminating AST Visitor and `APValue` Overhead:** As Timm Baeder's October 2025 benchmarks on Clang's constant interpreters demonstrate, an AST-walking interpreter must repeatedly inspect AST node types and allocate boxed `APValue` structures on every loop iteration. On a 10,000-iteration loop allocating and initializing a 1,024-byte `char` buffer (30 runs), Clang's legacy AST interpreter took **27.792 s ± 0.263 s** and GCC 14.3.1 took **43.829 s ± 0.308 s**, whereas Clang's bytecode interpreter completed in **4.241 s ± 0.103 s** (**6.55x faster** than Clang AST and **10.33x faster** than GCC). On a 10,000-iteration loop allocating an uninitialized `1024 * 1024` byte (1 MiB) buffer without writing to it, Clang's AST interpreter took **1,048.113 s ± 19.781 s (~17.4 minutes)** due to zero-initializing `APValue` structures for large arrays, whereas Clang's bytecode interpreter took **439.9 ms ± 19.2 ms** (**2,382x faster**) and GCC 14.3.1 took **116.8 ms ± 23.8 ms** (as GCC either elides unused heap allocations or optimizes empty `new`/`delete` pairs). Baeder also noted that on pure `#embed` array initialization without a function call, the bytecode interpreter was initially slower than the AST interpreter until array-initialization checks were optimized.
2.  **Register VM vs. Stack VM Efficiency:** While Clang's bytecode interpreter is a stack machine (`This`, `GetPtrFieldPop`, `LoadPopFloat`, `RetFloat`), CoreX already lowers all functions into **Block-Argument SSA `MIR`** for its path-sensitive SAST verifier (`DR-01` and `DR-02`). In Yunhe Shi et al.'s peer-reviewed study (*Virtual Machine Showdown: Stack Versus Registers*, VEE '05), translating stack bytecode into a virtual-register architecture eliminated **43.47% of static VM instructions** (including 2.84% NOP elimination from stack `pop`/`pop2`, 33.67% from copy propagation, and 6.95% from constant optimization) and **more than 47% of dynamically executed VM instructions**. Although register bytecode is roughly 25% larger in static code size (requiring 1.07 extra instruction-fetch loads per eliminated instruction), it eliminates 1.53 variable/register memory accesses per eliminated instruction – requiring **67.8% as many real machine loads** and **55.07% as many real machine writes** (62.58% overall memory traffic) and reducing total execution time by **32.3%** under C `switch` dispatch and **26.5%** under threaded dispatch. Combined with **tail-call instruction dispatch** (adopted by Clang's bytecode interpreter in 2026), a register VM over Block-Argument SSA avoids redundant `push`/`pop` stack traffic.

### 4.2 Avoiding Clang's 24-Byte Integer Tax and Interleaved `InlineDescriptor` Bloat

Two critical engineering lessons emerge from Timm Baeder's October 2026 update on the Clang bytecode interpreter:
*   **Lesson 1 (The 24-Byte Integer Tax):** Because C/C++ permits casting pointers to `uintptr_t`, performing integer arithmetic `(void*)(((uintptr_t)(void*)&a) + 3)`, and computing label address differences `(long)&&a - (long)&&b`, Clang's bytecode interpreter had to expand **all integers ≥16 bits (`short`, `int`, `long`, `uintptr_t`) to 24 bytes in memory** to store pointer validity bits, offsets, and dual-pointer label references.
*   **Lesson 2 (Interleaved `InlineDescriptor` Bloat):** To track whether individual struct fields or array elements are initialized, mutable, or volatile, Clang's bytecode interpreter interleaves an `InlineDescriptor` struct immediately before *every single field and element* inside an allocated `Block` (`| InlineDescriptor | data for a | InlineDescriptor | data for c |`). This inflates struct layouts (for instance, a 3-field `Player` struct occupies 96–104 bytes) and requires copying and stripping metadata when serializing a compile-time `Block` into an `APValue` or target data section.

**How CoreX's `MirVm` Solves Both Problems Cleanly:**
1.  **Compile-Time Ban on Pointer-to-Integer Casts:** Following Rust's `rustc_const_eval` / Miri and Zig's `@Restricted` pointer rules, CoreX **forbids casting a memory address to an integer (`ptr as usize`) at compile time**. Because integers never carry disguised pointer provenance, every scalar register in `MirVm` is a standard **8-byte `u64` word** (rather than 24 bytes), and a pointer in a register is encoded as a compact 64-bit pair: `SymbolicPtr { alloc_id: ComptimeAllocId, byte_offset: u32 }`.
2.  **Contiguous Target-Layout Bytes + Out-of-Band `InitMask` and `ProvenanceMap`:** Following `rustc_middle::mir::interpret::Allocation`, every `ComptimeAllocation` in `MirVm` stores its payload as a **contiguous, unpadded `[]u8` byte slice in the exact size, alignment, and endianness of the target architecture**. Initialization state is tracked in an out-of-band bitset (`init_mask: []u64`, costing **1 bit per byte**, or 1.56% overhead), and nested pointers stored inside memory are tracked in a sparse sorted `provenance` array mapping `byte_offset -> ComptimeAllocId`.
3.  **Zero-Copy String & Opaque Pointers:** Adopting Clang's 2026 `String Pointer` and `Opaque Pointer` optimizations, string literals in `MirVm` are never copied into mutable heap blocks; a `ComptimeAllocId` with its high tag bit set (`0x8000_0000 | string_id`) points directly to the immutable UTF-8 bytes in `DR-01`'s `StringInterner`.

### 4.3 Concrete `MirVm` Memory & Evaluator Blueprint (`stage0/src/mir_vm.zig` -> `src/mir_vm.cx`)

The following Zig Stage-0 implementation (`stage0/src/mir_vm.zig`) builds directly on `DR-01`'s `mem_foundation.zig` (`BumpArena`, `StringInterner`, `StringId`, `MirBlockId`, `MirValueId`, `Wyhash(0)`) and translates 1-to-1 into self-hosted CoreX (`src/mir_vm.cx`):

```zig
//! CoreX Stage-0 Compiler (`stage0/corex`)
//! Module: Deterministic Register-Based MIR Virtual Machine (`MirVm`)
//! Aligns with DR-01 (`BumpArena`, `StringInterner`, `u32` handles) and DR-02 (Block-Argument SSA).

const std = @import("std");
const assert = std.debug.assert;
const mem = @import("mem_foundation.zig");
const BumpArena = mem.BumpArena;
const StringId = mem.StringId;
const TypeId = mem.TypeId;
const MirBlockId = mem.MirBlockId;

/// Strongly typed 32-bit handle for a virtual memory allocation inside MirVm.
/// High bit (0x8000_0000) tags immutable StringInterner literals (Clang 2026 StringPtr pattern).
pub const ComptimeAllocId = enum(u32) {
    null_ptr = 0,
    none = std.math.maxInt(u32),
    _,

    pub const STRING_TAG_BIT: u32 = 0x8000_0000;

    pub inline fn fromStringId(id: StringId) ComptimeAllocId {
        return @enumFromInt(STRING_TAG_BIT | id.toIndex());
    }
    pub inline fn isStringLiteral(self: ComptimeAllocId) bool {
        return (@intFromEnum(self) & STRING_TAG_BIT) != 0;
    }
};

/// 8-byte Virtual Register slot. Holds either a 64-bit scalar (int/float/bool/TypeId)
/// or a symbolic pointer `(alloc_id: u32, byte_offset: u32)` with zero 24-byte bloat.
pub const RegSlot = extern union {
    scalar_u64: u64,
    scalar_i64: i64,
    scalar_f64: f64,
    sym_ptr: SymbolicPtr,

    pub const SymbolicPtr = extern struct {
        alloc_id: ComptimeAllocId,
        byte_offset: u32,
    };
};

/// Sparse provenance entry for pointers stored inside a `ComptimeAllocation`'s byte buffer.
pub const ProvenanceEntry = extern struct {
    byte_offset: u32,
    target_alloc: ComptimeAllocId,
};

/// Target-exact virtual memory block (Miri / rustc_const_eval `Allocation` pattern).
/// Stores raw target-endian bytes in `BumpArena` with out-of-band `init_mask` and `provenance`.
pub const ComptimeAllocation = struct {
    bytes: []u8,
    /// 1 bit per byte in `bytes` (1 = initialized, 0 = uninitialized).
    init_mask: []u64,
    /// Sorted list of pointer provenances stored at aligned offsets within `bytes`.
    provenance: std.ArrayListUnmanaged(ProvenanceEntry) = .{},
    align_log2: u8,
    is_mutable: bool,
    is_freed: bool = false,
    /// Set to true if allocation escapes as part of the returned constant value.
    escaped_to_rodata: bool = false,

    pub fn isRangeInitialized(self: *const ComptimeAllocation, offset: u32, len: u32) bool {
        var i: u32 = offset;
        while (i < offset + len) : (i += 1) {
            const word = self.init_mask[i >> 6];
            if ((word & (@as(u64, 1) << @intCast(i & 63))) == 0) return false;
        }
        return true;
    }

    pub fn markRangeInitialized(self: *ComptimeAllocation, offset: u32, len: u32) void {
        var i: u32 = offset;
        while (i < offset + len) : (i += 1) {
            self.init_mask[i >> 6] |= (@as(u64, 1) << @intCast(i & 63));
        }
    }
};

/// Compact 8-byte Register-SSA Bytecode Instruction over Block-Argument MIR.
pub const MirOp = enum(u8) {
    load_const_u64,
    move_reg,
    add_i64_checked,
    sub_i64_checked,
    mul_i64_checked,
    alloc_local,
    load_mem,
    store_mem,
    gep_field_offset,
    branch,
    cond_branch,
    call_fn,
    ret_val,
    compile_assert,
};

pub const MirInst = extern struct {
    op: MirOp,
    flags: u8 = 0, // Encodes byte-width (1, 2, 4, 8) or signedness
    dst_reg: u16,
    src_a: u16,
    src_b: u16,
};

/// Activation Frame on the MirVm CallStack.
pub const CallFrame = struct {
    fn_def_id: u32,
    current_block: MirBlockId,
    ip: u32,
    /// Base index into `MirVm.register_file` for this frame's SSA virtual registers.
    reg_base: u32,
    return_dst_reg: u16,
    /// Stack allocations owned by this frame (marked freed on return to catch dangling pointers).
    local_allocs_start: u32,
};

/// Deterministic, Sandboxed Compile-Time Virtual Machine (`MirVm`).
pub const MirVm = struct {
    pub const DEFAULT_STEP_BUDGET: u64 = 10_000_000; // `--comptime-limit=10000000`
    pub const DEFAULT_MEM_LIMIT: usize = 64 * 1024 * 1024; // 64 MiB per evaluation
    pub const MAX_CALL_DEPTH: usize = 512;

    arena: *BumpArena,
    string_interner: *const mem.StringInterner,
    target_endian: std.builtin.Endian,
    target_ptr_byte_width: u8, // 4 for wasm32, 8 for x86_64/aarch64

    /// Contiguous virtual register file shared across call frames.
    register_file: std.ArrayListUnmanaged(RegSlot) = .{},
    call_stack: std.ArrayListUnmanaged(CallFrame) = .{},
    /// Virtual memory table indexed by `ComptimeAllocId` (`0` = null_ptr sentinel).
    allocations: std.ArrayListUnmanaged(ComptimeAllocation) = .{},

    steps_executed: u64 = 0,
    step_budget: u64 = DEFAULT_STEP_BUDGET,
    bytes_allocated: usize = 0,
    mem_limit: usize = DEFAULT_MEM_LIMIT,

    pub const EvalError = error{
        StepBudgetExceeded,
        ComptimeMemoryLimitExceeded,
        CallStackOverflow,
        NullPointerDereference,
        UseAfterFree,
        OutOfBoundsMemoryAccess,
        UninitializedMemoryRead,
        IntegerOverflow,
        ForbiddenPointerToIntCast,
        CompileAssertionFailed,
    };

    pub fn allocateBlock(
        self: *MirVm,
        size: u32,
        align_log2: u8,
        is_mutable: bool,
    ) EvalError!ComptimeAllocId {
        if (self.bytes_allocated + size > self.mem_limit) {
            return error.ComptimeMemoryLimitExceeded;
        }
        // BumpArena (`DR-01`) guarantees deterministic zero-initialization of all bytes!
        const bytes = self.arena.allocBytesAligned(size, @as(usize, 1) << @intCast(align_log2)) catch
            return error.ComptimeMemoryLimitExceeded;
        const mask_words = (size + 63) / 64;
        const init_mask = self.arena.allocSlice(u64, mask_words) catch
            return error.ComptimeMemoryLimitExceeded;

        self.bytes_allocated += size;
        const id: u32 = @intCast(self.allocations.items.len);
        self.allocations.append(self.arena.backing_allocator, .{
            .bytes = bytes,
            .init_mask = init_mask,
            .align_log2 = align_log2,
            .is_mutable = is_mutable,
        }) catch return error.ComptimeMemoryLimitExceeded;

        return @enumFromInt(id);
    }

    /// Reads an integer of `byte_width` (1, 2, 4, 8) from virtual memory,
    /// enforcing spatial bounds, temporal liveness, initialization, and target endianness.
    pub fn readScalarInt(
        self: *const MirVm,
        ptr: RegSlot.SymbolicPtr,
        byte_width: u32,
    ) EvalError!u64 {
        if (ptr.alloc_id == .null_ptr) return error.NullPointerDereference;
        if (ptr.alloc_id.isStringLiteral()) {
            const str_id: StringId = @enumFromInt(@intFromEnum(ptr.alloc_id) & ~ComptimeAllocId.STRING_TAG_BIT);
            const slice = self.string_interner.get(str_id);
            if (ptr.byte_offset + byte_width > slice.len) return error.OutOfBoundsMemoryAccess;
            return self.decodeTargetInt(slice[ptr.byte_offset .. ptr.byte_offset + byte_width]);
        }

        const idx = @intFromEnum(ptr.alloc_id);
        if (idx >= self.allocations.items.len) return error.OutOfBoundsMemoryAccess;
        const alloc = &self.allocations.items[idx];

        if (alloc.is_freed) return error.UseAfterFree;
        if (ptr.byte_offset + byte_width > alloc.bytes.len) return error.OutOfBoundsMemoryAccess;
        if (!alloc.isRangeInitialized(ptr.byte_offset, byte_width)) return error.UninitializedMemoryRead;

        return self.decodeTargetInt(alloc.bytes[ptr.byte_offset .. ptr.byte_offset + byte_width]);
    }

    inline fn decodeTargetInt(self: *const MirVm, buf: []const u8) u64 {
        return switch (buf.len) {
            1 => buf[0],
            2 => std.mem.readInt(u16, buf[0..2], self.target_endian),
            4 => std.mem.readInt(u32, buf[0..4], self.target_endian),
            8 => std.mem.readInt(u64, buf[0..8], self.target_endian),
            else => unreachable,
        };
    }
};

comptime {
    assert(@sizeOf(ComptimeAllocId) == 4);
    assert(@sizeOf(RegSlot) == 8);
    assert(@sizeOf(MirInst) == 8);
}
```

### 4.4 Sandboxing, Cross-Compilation Determinism, and Incremental Caching Invariants

To guarantee that `MirVm` can run safely inside `corex lsp` on untrusted third-party packages and produce bit-for-bit identical outputs (`Stage 3 === Stage 4` in `DR-01`) across Linux, macOS, and Windows hosts, the evaluator enforces five strict sandboxing and caching invariants:

| Sandboxing & Caching Axis | Enforced `MirVm` Architectural Invariant | Problem Prevented |
| :--- | :--- | :--- |
| **1. Zero Host Syscall Capability** | `MirVm` has no instruction or intrinsic mapped to OS filesystem (`open`/`read`), network sockets, environment variables (`getenv`), wall-clock time (`clock_gettime`), or process spawning. Only `@embed_bytes("rel/path.bin")` is allowed, resolved through the compiler's tracked virtual filesystem table (`FileId` dependency edge). | Eliminates Rust `proc_macro` supply-chain malware execution and untracked file-system cache invalidation bugs. |
| **2. Deterministic Execution Fuel (`--comptime-limit`)** | Every backward CFG branch (`MirOp.branch` where `target_block <= current_block`) and function call (`MirOp.call_fn`) increments `steps_executed`. Exceeding `step_budget` (default `10,000,000`, configurable via `--comptime-limit` or `@comptime_quota(N)`) immediately aborts evaluation with a source-spanned call trace. | Prevents infinite loops or runaway recursion from hanging `corex` or freezing `corex lsp` worker threads. |
| **3. Target-Aware Endianness & Pointer Width** | `MirVm` is parameterized by `target_endian` and `target_ptr_byte_width` (`4` for `wasm32`, `8` for `x86_64`/`aarch64`). All memory loads/stores (`readScalarInt` / `writeScalarInt`) serialize bytes in **target endianness**, and `@size_of[usize]()` returns `target_ptr_byte_width`. | Guarantees cross-compiling from an `x86_64` little-endian host to `wasm32-wasi` or a big-endian target produces bit-identical `.rodata` tables. |
| **4. IEEE-754 Canonical NaN & Zeroed Padding** | Floating-point operations in `MirVm` canonicalize quiet NaNs to a single deterministic bit pattern (`0x7FF8_0000_0000_0000` for `f64`), and `BumpArena` zeroes all allocation slabs upon creation and `restore()`. | Prevents host CPU NaN payload differences or uninitialized struct padding from polluting `.cxmod` caches or binary hashes. |
| **5. Non-Transient Promotion & `Wyhash(0)` Deduplication** | When a top-level `const` or `comptime` block returns a value containing `ComptimeAllocId` pointers (e.g., a slice or radix-trie array), `MirVm` walks the reachable allocation graph, verifies that no pointed-to block has `is_freed == true` (catching dangling stack pointers at compile time), marks reachable blocks `is_mutable = false`, hashes their bytes + provenance via `Wyhash(0)`, and interns them in the `InternPool`. | Enables C++26's long-sought **non-transient compile-time allocation** out of the box, deduplicating identical lookup tables across modules and emitting them directly into `.rodata`. |

### 4.5 Constant Folding and Single-Flight Query Integration

Finally, `MirVm` serves both explicit metaprogramming (`comptime`, `const`, `@derive`) and opportunistic **MIR Constant Propagation** during `-O1`/`-O2`/`-O3` builds. During the `MirConstProp` optimization pass, whenever all block arguments and operands to a pure function call or basic block are constant `InternPool` values, the optimizer invokes the tracked query `eval_comptime(FnDefId, ArgInternIds)` using `Checkpoint` / `restore()` on the thread-local `BumpArena` (`DR-01`) so transient scratch allocations cost zero heap fragmentation. Following the single-flight memoization pattern (`picante` / `Salsa` / Zig `AnalUnit.memoized`), if multiple parallel semantic worker threads request the same compile-time evaluation (for instance, `validate_cli_schema[ScanOptions]()` or `compile_radix_trie(...)`), the first caller becomes the leader and computes the `ConstValId` in the `InternPool` while concurrent followers await and reuse the canonical 32-bit `ConstValId` handle in `O(1)` time.
