# High-Performance, Ergonomic Error Handling Architecture for CoreX (.cx)

To achieve compile-time exhaustiveness, effortless readability, zero hidden control flow, and zero runtime overhead on the happy path, **CoreX (`.cx`)** unifies the authoritative surface syntax of **`DR-03`** with the value-oriented semantic and register-level ABI guarantees of **`DR-01`** and **`DR-02`**. At the surface level, CoreX standardizes on **square-bracket `Result[T, E]`**, **postfix option sugar `T?` (`Option[T]`)**, **postfix `?` propagation (`expr?`)**, and **contextual dot-variant constructors (`.Ok(v)`, `.Err(e)`, `.Some(v)`, `.None`)**. Rather than introducing a competing Zig-style `E!T` type operator or prefix `try` keyword – which would conflict with `DR-03`'s unary `!` boolean negation token and break left-to-right postfix `.await?` and `|>` pipeline chaining – CoreX endows `Result[T, E]` directly with the three foundational systems capabilities of `DR-02`: (1) a **Split-Register and Hardware Status-Flag Calling Convention (`cx_result_cc`)** that eliminates stack-spilled `sret` structs when `sizeof(T)` and `sizeof(E)` diverge; (2) **lexical `errdefer` and `errdefer |err|` scope guards** emitted strictly on cold error-exit control-flow edges alongside deterministic scope drops; and (3) **infix `catch` recovery expressions** alongside `let .Ok(x) = expr else { ... };` guards for localized recovery and error context transformation.

At the machine-code level (`x86_64`, `aarch64`, and `wasm32`), standard C and Rust calling conventions treat `Result<T, E>` as an ordinary memory-padded struct, creating a severe performance cliff whenever `max(sizeof(T), sizeof(E)) + alignment_padding` exceeds 16 bytes. For example, returning a 16-byte two-word value `(u64, u64)` paired with a 2-byte `IoError` inflates a standard tagged union to 24 bytes in memory, forcing the compiler to allocate a caller stack slot, pass a hidden `sret` pointer in `RDI` or `X8`, and execute redundant stack stores and reloads on every call. CoreX eliminates this cliff through a dual-representation architecture. In memory (structs, arrays, and `#soa` slices), `Result[T, E]` and `T?` use recursive **Bit-Pattern Niche Optimization** – storing `(&T)?` and `OwnPtr[T]?` in 8 bytes and `Result[[u8], IoError]` in 16 bytes by encoding `IoError` inside the slice's second word whenever the non-null pointer word is `0x0`. Across function return boundaries, `cx_result_cc` decouples the return ABI from memory padding: for payloads up to 32 bytes (up to 4 registers: `RAX, RDX, RCX, R8` on `x86_64`; `X0–X3` on `aarch64`; and Wasm multi-value stack tuples on `wasm32`), `T` and `E` share the primary return registers while the success/failure discriminant is transmitted via the **CPU Carry Flag (`CF`)** in native codegen or the 4-register `swiftcc` return tuple in the LLVM backend.

To guarantee that cold error payloads never inflate hot return registers or L1 data caches, CoreX enforces a compile-time size ceiling (`@warn(error_size_limit)` when `sizeof(E) > 16` bytes and `@warn(variant_size_skew)` at `> 64` bytes) paired with two zero-overhead diagnostic mechanisms. First, annotating an error enum or rich variant with `@cold_box` automatically boxes extended failure payloads via a non-inlined `@cold` constructor path only when an error is actually instantiated, collapsing `sizeof(E)` to a single 8-byte pointer word. Second, leveraging `DR-01`'s `BumpArena` and `enum(u32)` handles alongside `DR-02`'s implicit `context` pointer, CoreX separates **control-flow error codes** from **human-readable diagnostic payloads**. Failing operations can record structured key-value context and source locations into `context.diagnostics` (via `errdefer context.note(...)` or factory methods) and return a 4-byte `DiagId` (`enum(u32)`) inside `E` – achieving zero allocation and zero formatting overhead on the happy path while avoiding C++ DWARF unwind table bloat (which in WG21 benchmarks adds 382 KB of initial exception machinery plus 57 KB of unwind tables on Clang x64 and runs over 100x slower on the error path than value returns).

## 1. Reconciling `DR-02` and `DR-03` into a Unified Error Architecture

### 1.1 Resolving the Surface Syntax Tension: Why `Result[T, E]` + Postfix `?` Wins Over `E!T` + Prefix `try`

A central architectural objective for CoreX is reconciling the surface syntax of **`DR-03`** (`Result[T, E]`, `T?`, postfix `?`, `.Ok(v)` / `.Err(e)`, and `let ... else`) with the value-based error union model highlighted in **`DR-02`** (Zig-style `E!T`, `try`, `catch |err|`, and `errdefer`). Evaluating both models against CoreX's `LL(k)` / Pratt grammar invariants (`DR-03`), bidirectional type-checking constraints (`DR-02`), and empirical developer ergonomics demonstrates why **`Result[T, E]` + postfix `?` must serve as the single canonical surface representation**, while directly absorbing `catch` and `errdefer` from `DR-02`.

| Architectural Dimension | `DR-02` Candidate: `E!T` / `!T` + Prefix `try expr` | `DR-03` Authoritative: `Result[T, E]` + Postfix `expr?` | Unified CoreX v1.0 Decision & Engineering Rationale |
| :--- | :--- | :--- | :--- |
| **Lexical & Grammar Disjointness (`LL(1)`)** | Overloads `!` (`TokenKind.BANG`) as both unary boolean negation (`!cond`) and binary/prefix error union type constructor (`IoError!u32`, `!u32`). | Uses standard square-bracket generic instantiation `Result[T, E]` (`TYPE_IDENT`) and unambiguous postfix `?` (`TokenKind.QUESTION`). | **Adopt `Result[T, E]` + `expr?`.** Preserves 100% disjoint `FIRST(PrimaryType)` sets in `DR-03` and keeps `!` exclusively as unary boolean negation. |
| **Chaining & Pipeline Ergonomics (`\|>`, `.await`)** | Prefix `try` forces inside-out parentheses when chaining calls or `.await`: `try (try fetch().await).parse()`. | Postfix `?` composes linearly left-to-right with method calls, `.await`, and `\|>`: `fetch().await?.parse()?`. | **Adopt Postfix `expr?`.** Eye-tracking linearity studies (`DR-03` §1.3) show left-to-right execution order reduces backward saccades. |
| **Type Inference & Module Boundaries** | Zig's inferred `!T` relies on closed-world whole-program cross-function error set inference, exposing internal changes across signatures. | Explicit `Result[T, E]` enforces definition-site signature checking (`DR-02` §2.1) and stable module boundaries. | **Adopt Explicit `Result[T, E]`.** Module-local type aliases (`type IoResult[T] = Result[T, IoError];`) provide brevity without global inference stalls. |
| **First-Class Value & Combinator Uniformity** | In Zig, `E!T` is a special language construct rather than an ordinary generic sum type with standard methods. | `Result[T, E]` is a first-class algebraic `enum` supporting standard methods, traits, and `\|>` pipelines, plus compiler-known ABI lowering. | **Unify `Result[T, E]` with `cx_result_cc`.** `Result[T, E]` is a standard library `enum` annotated with `@lang("result")` so the compiler applies custom register/flag ABI lowering. |
| **Inline Recovery & Scope Cleanup** | Provides concise `expr catch \|err\| ...` and `errdefer` / `errdefer \|err\|` scope cleanup. | `DR-03` specified `match`, `let ... else`, and `defer`, but omitted `catch` and `errdefer` from its initial token table. | **Integrate `catch` and `errdefer` into `DR-03`.** Adds `KW_CATCH` and `KW_ERRDEFER` to the lexer, combining `Result[T, E]` + `?` with `catch` and `errdefer`. |

Rejecting `E!T` as a duplicate surface type syntax avoids the ecosystem fragmentation seen in languages that split fallibility across two incompatible mechanisms, such as Swift's historical divide between `throws` and `Result<Success, Failure>` prior to `SE-0413`, or C++'s split between `throws` and `std::expected`. In CoreX, every fallible function returns `Result[T, E]` (or `T?` when no error payload is needed), and every `Result[T, E]` automatically benefits from the register/flag return ABI and `errdefer` integration.

### 1.2 First-Class Algebraic Definition of `Result[T, E]` and `Option[T]` (`T?`)

In CoreX's standard library (`core::result` and `core::option`), `Result[T, E]` and `Option[T]` are defined as canonical algebraic sum types bound to compiler intrinsics via `@lang` and `@must_use` attributes:

```rust
// File: core/option.cx
mod option;

@lang("option")
pub enum Option[T] {
    None,
    Some(T),
}

// File: core/result.cx
mod result;

@lang("result")
@must_use("Result[T, E] may contain an unhandled .Err(e) that must be propagated with '?', handled via 'match'/'catch'/'let..else', or explicitly discarded")
pub enum Result[T, E] {
    Ok(T),
    Err(E),
}
```

Coupling `@lang("result")` and `@lang("option")` with `DR-03`'s contextual dot-variant shorthand establishes three foundational ergonomic and safety invariants. First, whenever a function's return type or target checking type is `Result[T, E]` or `T?`, bidirectional type checking (`DR-02` Checking Mode $\Delta \vdash e \Leftarrow \tau$) resolves `.Ok(val)`, `.Err(err)`, `.Some(val)`, and `.None` directly without requiring `Result::Ok(val)` or polluting the global value namespace. Second, following Zig's syntactic discard invariant, an unconsumed expression statement `fallible_call();` is a compile error, and writing `let _ = fallible_call();` when `fallible_call()` returns `Result[T, E]` still triggers an unhandled-error diagnostic unless the error channel itself is explicitly acknowledged via `fallible_call() catch {};` or `let _ = fallible_call() catch {};`. This prevents a common defect where an initially infallible function whose return value was ignored (`let _ = compute();`) is later refactored to return `Result[T, E]` and has its errors silently dropped at existing call sites. Third, postfix `?` operates uniformly on `Result[T, E]` inside functions returning `Result[U, F]` (where `F: FromError[E]`) and on `T?` (`Option[T]`) inside functions returning `U?` (`Option[U]`), while `Option::ok_or(err: E) -> Result[T, E]` and `Result::ok() -> T?` bridge between optional and error-carrying pipelines without nested `match` blocks.

## 2. Deliverable 1: Canonical Error Handling Specification for CoreX

### 2.1 Lexical & EBNF Grammar Extensions (Updating `DR-03` v1.0)

To integrate `errdefer` and infix `catch` into `DR-03`'s context-free `LL(k)` + Pratt grammar without introducing any `FIRST`/`FOLLOW` conflicts or parser backtracking, CoreX adds two hard keywords to the `DR-03` lexical scanner (`TokenKind`):
1.  **`KW_ERRDEFER` (`"errdefer"`)**: Added to *Memory, Async & Safety Keywords* alongside `KW_DEFER` (`"defer"`), initiating an `ErrDeferStmt` in the statement grammar.
2.  **`KW_CATCH` (`"catch"`)**: Added to *Control-Flow Keywords*, acting as a binary infix recovery operator at Pratt Precedence Level `1.5` (`(l_bp, r_bp) = (3, 2)`, binding tighter than `|>` pipeline `(2, 3)` and looser than `||` / `or` `(4, 5)` so that `a |> parse() catch |e| default_val` parses naturally as `(a |> parse()) catch (|e| default_val)`).

The updated EBNF productions extending `DR-03` §5.4 are specified below:

```ebnf
(* ========================================================================== *)
(* UPDATED STATEMENT & ERROR HANDLING PRODUCTIONS FOR COREX v1.0 (DR-07)      *)
(* ========================================================================== *)
Stmt            = ";"
                | { Attribute } LocalDeclStmt
                | DeferStmt
                | ErrDeferStmt
                | ReturnStmt
                | BreakStmt
                | ContinueStmt
                | ForStmt
                | WhileStmt
                | LoopExpr [ ";" ]
                | Expr ( AssignOp Expr ";" | ";" | /* omitted ';' after Block-bodied Expr */ ) ;

(* Guard statement: 'let .Ok(x) = expr else { return .Err(e); };' *)
LocalDeclStmt   = ( "let" | "var" ) [ "mut" ] Pattern [ ":" Type ]
                  [ "=" Expr [ "else" DivergingBlock ] ] ";" ;

(* Scope cleanup: 'defer' runs on all exits; 'errdefer' runs ONLY on .Err exits *)
DeferStmt       = "defer" ( Block | Expr ";" ) ;
ErrDeferStmt    = "errdefer" [ "|" IDENT "|" ] ( Block | Expr ";" ) ;

(* DivergingBlock is statically verified in Sema to have type 'never' *)
DivergingBlock  = Block ;

(* Infix 'catch' recovery expression at Pratt Binding Power (3, 2) *)
CatchSuffix     = "catch" [ "|" IDENT "|" ] ( Block | PrefixExpr ) ;
```

### 2.2 Bidirectional Typing Rules for `?`, `catch`, `let ... else`, and `errdefer`

Following `DR-02` Deliverable 2 (§1, *Mode-Correct Bidirectional Typing*), all error handling constructs type-check in linear time without constraint disjunction search:

1.  **Postfix Propagation (`e?`) inside a Function Returning $\tau_{\text{ret}} = \text{Result}[U, F]$**:
    $$\frac{\Delta \vdash e \Rightarrow \text{Result}[T, E] \quad \tau_{\text{ret}} = \text{Result}[U, F] \quad F : \text{FromError}[E]}{\Delta \vdash e? \Rightarrow T} \;(\text{TryResult}\Rightarrow)$$
    If the enclosing function returns $\tau_{\text{ret}} = \text{Option}[U]$ (`U?`) and $\Delta \vdash e \Rightarrow \text{Option}[T]$, then $\Delta \vdash e? \Rightarrow T$ immediately without trait lookup. Applying `?` inside an infallible function (where $\tau_{\text{ret}}$ is neither `Result` nor `Option`) produces a targeted compile error suggesting either updating the function return signature or handling the value locally via `catch` or `let ... else`.
2.  **Infix Recovery (`e_1 \text{ catch } |err|\; e_2` or `e_1 \text{ catch } e_2`)**:
    $$\frac{\Delta \vdash e_1 \Rightarrow \text{Result}[T, E] \quad \Delta, \text{err} \Rightarrow E \vdash e_2 \Leftarrow T}{\Delta \vdash (e_1 \text{ catch } |\text{err}|\; e_2) \Rightarrow T} \;(\text{CatchResult}\Rightarrow)$$
    Because `e_2` is checked top-down against the synthesized success type $T$ ($\Leftarrow T$) – and because the bottom type `never` (produced by `return`, `break`, `continue`, or `panic`) can coerce to any expected branch type – the right-hand side of `catch` can either evaluate to a fallback value of type $T$ (`parse_port(s) catch 8080`) or diverge early with a transformed error (`read_file(p) catch |e| return .Err(.IoFailed(p, e))`). The same rule applies when $e_1 \Rightarrow \text{Option}[T]$ (`T?`), omitting the `|err|` binding (`e_1 catch fallback_val`).
3.  **Refutable Guard Statement (`let P = e_1 \text{ else } B_{\text{div}};`)**:
    $$\frac{\Delta \vdash e_1 \Rightarrow \tau_1 \quad \Delta \vdash P \Leftarrow \tau_1 \dashv \Delta_{\text{pat}} \quad \Delta \vdash B_{\text{div}} \Leftarrow \text{never}}{\Delta \vdash (\text{let } P = e_1 \text{ else } B_{\text{div}};) \dashv \Delta, \Delta_{\text{pat}}} \;(\text{LetElse})$$
    The compiler verifies via its pattern decision tree (`DR-02` §3.3) that $B_{\text{div}}$ has type `never` (every control-flow path inside `else { ... }` exits the enclosing scope via `return`, `break`, `continue`, or `panic`) and extends the typing context $\Delta$ with the pattern bindings $\Delta_{\text{pat}}$ for all subsequent statements in the block.
4.  **Payload-Capturing Error Defer (`errdefer |err| B`)**:
    Inside a function with return type $\tau_{\text{ret}} = \text{Result}[U, F]$, an `errdefer |err| B` statement binds `err` as an immutable `let` projection of type $F$ ($\Delta, \text{err} \Rightarrow F \vdash B \Leftarrow \text{unit}$).

### 2.3 Seamless Error Composition Across Module Boundaries

As matklad's *The Second Great Error Model Convergence* analysis emphasizes, low-level modules require **closed, exhaustive sum-type enums** so callers can handle specific failure modes and verify API contracts, whereas higher-level orchestrators and entrypoints need to **compose errors from multiple subsystems** without repetitive conversion boilerplate. CoreX bridges low-level exhaustiveness and high-level composition through four zero-cost mechanisms:

1.  **Zero-Macro Structural Error Upcasting (`trait FromError[Src]` + `@from`)**:
    CoreX defines a canonical conversion trait in `core::result`:

    ```rust
    pub trait FromError[Src] {
        fn from_error(src: own Src) -> Self;
    }
    // Reflexive identity implementation: every error converts to itself at zero cost
    impl[E] FromError[E] for E {
        @inline(always)
        fn from_error(src: own E) -> E { src }
    }
    ```

    When defining a composite module error enum, annotating a single-field tuple variant with `@from` instructs the compiler frontend to synthesize the corresponding `FromError` implementation automatically during AST-to-HIR lowering:

    ```rust
    pub enum StorageError {
        @from Io(IoError),
        @from Json(JsonParseError),
        CorruptHeader { magic: u32, offset: u64 },
        QuotaExceeded,
    }
    ```

    Inside any function returning `Result[T, StorageError]`, calling `File::open(path)?` (`Result[File, IoError]`) or `Json::parse[Header](buf)?` (`Result[Header, JsonParseError]`) automatically invokes `StorageError::from_error` on the cold error branch without `map_err` ceremony.

2.  **Telescopic Block-Level Context via `errdefer context.note(...)`**:
    A frequent source of error boilerplate in Rust (`anyhow::Context::with_context`) is having to attach `.with_context(|| format!("failed on {}", path))?` to every individual `?` call site inside a function that performs multiple operations on the same resource. Worse, embedding a dynamic string inside an enum variant forces heap allocation and couples error producers to error formatting. CoreX adopts and refines the **Telescopic `errdefer` Context** pattern:

    ```rust
    pub fn load_manifest(path: str) -> Result[Manifest, StorageError] {
        errdefer |err| context.note("while loading manifest path='{path}' (error={err})");

        let file = File::open(path)?;
        defer file.close();
        let raw = file.read_all()?;
        let doc = Json::parse[Manifest](raw)?;
        .Ok(doc)
    }
    ```

    Because `errdefer` is emitted exclusively on the function's cold error-exit block (`^err_exit`), **zero instructions and zero string formatting occur on the happy path**. When any of `File::open(path)?`, `file.read_all()?`, or `Json::parse(raw)?` fails, control jumps to `^err_exit`, which appends a lightweight diagnostic frame into the implicit thread/task `context.diagnostics` buffer (backed by `context.temp_allocator`, the 64 KiB `BumpArena` from `DR-01`). Moreover, if a caller higher up the stack catches and handles the error (`load_manifest(p) catch |e| fallback()`), the `catch` handler automatically rewinds the `context.diagnostics` cursor to its pre-call checkpoint – eliminating the false-positive log pollution that matklad identified as the main drawback of logging directly to `stderr` inside `errdefer`.

3.  **Out-of-Band Diagnostics Factory (`DiagId` Handle Pattern)**:
    For compilers, parsers, linters, and validation engines where rich errors with source spans and suggestions are produced, CoreX supports the **Diagnostics Sink / Factory Pattern** (`DR-01` + `DR-02` + matklad's `Errors` factory). Instead of returning a 512-byte `ParseError` enum variant, the producer calls a factory method `diag.add_unexpected_token(file_id, token_span, expected)` which formats or stores the payload inside the `Diagnostics` arena and returns `.Err(DiagId(idx))` (a 4-byte `enum(u32)` handle).

4.  **Type-Erased Universal Application Error (`std::err::AnyError`)**:
    For top-level application entrypoints, CLI commands, and scripts where exhaustive error enums are unnecessary (`fn main() -> Result[unit, AnyError]`), CoreX provides `AnyError`: a **16-byte, two-register value type** modeled on Herb Sutter's `P0709` `std::error` / Niall Douglas's `P1028` `status_code` and Rust's bit-packed `std::io::Error`:

    ```rust
    @repr(C)
    pub struct AnyError {
        domain: *const ErrorDomainVTable, // Register 1 (8B): static constexpr domain table
        payload: u64,                     // Register 2 (8B): inline error code/enum or DiagId
    }
    ```

    Because any error type `E` whose size is `<= 8` bytes fits directly inside `AnyError.payload` alongside a static pointer to its compile-time `ErrorDomainVTable`, converting any domain error into `AnyError` via `?` requires **zero heap allocation, zero RTTI dynamic casts, and fits in two CPU registers**.

### 2.4 Deterministic Scope Cleanup (`defer`, `errdefer`, Scope Drops) and MVS Verification

In `DR-02`, CoreX established explicit lexical `defer` and `errdefer` cleanup for external resources alongside compile-time resource verification via its **Ghost-Instruction Abstract Interpreter**. The interaction between postfix `?`, `defer`, `errdefer`, and automatic scope drops is governed by three deterministic rules:

1.  **Strict LIFO Reverse-Declaration Interleaving Across `defer`, `errdefer`, and Scope Drops**:
    Every `defer` statement, `errdefer` statement, and scope-managed binding in a lexical block `{ ... }` is pushed onto the block's compile-time cleanup stack at the exact program point where the statement or binding is reached. Any cleanup registered *after* an early-returning `expr?` is never executed if that `expr?` fails. On a **Normal Exit** (block tail expression, `return .Ok(v)`, `break`, or `continue`), all active `defer` statements and scope drops registered in the exiting block execute in strict reverse lexical order (Last-In, First-Out), while all `errdefer` statements are bypassed. On an **Error Exit** (`expr?` evaluating to `.Err(e)` or explicit `return .Err(e)`), **both** active `errdefer` and `defer` statements (along with any active scope drops) in the current block and all enclosing blocks up to the function boundary execute in strict reverse order of their lexical registration.
2.  **Definite Ownership Transfer Without Runtime Drop Flags**:
    A classic performance penalty in C++ and Rust stack unwinding occurs when a resource `conn` is created, conditionally moved into a return value on the happy path, or cleaned up on the error path: compilers must often emit hidden boolean "drop flags" on the stack to track at runtime whether `conn` was moved. In CoreX, `errdefer conn.close();` is emitted *only* on the cold `^err_cleanup` CFG edge, while the happy path moves `own conn` into `.Ok(PoolEntry { conn: own conn })`. The Ghost-Instruction Abstract Interpreter verifies that `conn` is consumed along both disjoint CFG edges (`^ok_ret` via `storage.move`, and `^err_cleanup` via `conn.close()`), guaranteeing resource safety at compile time with **zero runtime drop-flag variables**.
3.  **Ban on Control-Flow Escapes Inside Cleanup Blocks**:
    To prevent the hazard where a `defer` block executes `return` and silently overwrites or discards an active error, the CoreX frontend forbids `return`, `break`, `continue`, and uncaught `?` inside any `defer` or `errdefer` block. If a cleanup operation inside `defer` is itself fallible (such as flushing a write buffer before closing a file), the developer must either invoke the fallible flush on the main control-flow path (`file.flush()?;`) before scope exit or handle the failure locally inside `defer` via `catch` (`defer { file.close() catch |e| context.log_warn("close failed: {e}"); }`).

### 2.5 Boundary Between Recoverable Errors (`Result[T, E]`) and Unrecoverable Bugs (`panic` / `assert`)

Following Herb Sutter's `P0709` (§4.2, *"Program bugs are not recoverable run-time errors"*), Ben Craig's `throws_nothing` policy, and Joe Duffy's *Error Model*, CoreX enforces a strict semantic and ABI separation between **operational failures** and **programming bugs**:

| Failure Classification | CoreX Mechanism & Signature | Examples | Machine-Level Lowering & Runtime Behavior |
| :--- | :--- | :--- | :--- |
| **1. Recoverable Operational & Domain Errors** | `Result[T, E]` or `T?` (`Option[T]`) propagated via `?` or handled via `match` / `catch` / `let..else`. | File/network I/O failure, malformed user JSON/HTTP payload, DB deadlock/conflict, bounded pool/arena exhaustion (`try_alloc`). | Lowered via `cx_result_cc` register/flag value returns; **zero** stack-unwinding tables; compile-time exhaustiveness. |
| **2. Checked Preconditions & Invariants (All Builds)** | `assert(cond, "msg");` and slice bounds checks `slice[idx]`. | Out-of-bounds array/slice index, integer division by zero, violated API contract or security invariant. | Conditional branch to a shared `@cold` panic trampoline (`call core::panic_bounds`); does not pollute return types. |
| **3. Debug-Only Internal Verification** | `debug_assert(cond, "msg");`. | Internal compiler/algorithmic invariants (e.g., `BumpArena` alignment checks, AVL balance factor checks). | Emitted in `Debug` / `ReleaseSafe` builds; compiled to a zero-cost no-op in `ReleaseFast` / `ReleaseSmall`. |
| **4. Explicit Unrecoverable Trap (`never`)** | `panic("msg")` and `unreachable` (both return primitive type `never`). | Corrupted internal state machine, exhausted `SlotMap` generation counter, impossible CFG branch. | Emits cold panic hook (walks frame pointers to print compact source trace) followed by immediate hardware trap (`ud2` / `brk #1` / Wasm `unreachable`). |

As Ben Craig notes in `throws_nothing` (`freestanding_proposal`), once a program detects a contract violation or logic bug, executing thousands of instructions of unwinding cleanup across potentially corrupted state is dangerous. Therefore, `panic` in CoreX **never unwinds the stack through `defer` blocks by default**; it immediately invokes the panic handler, dumps the compact return-address stack trace and any active `context.diagnostics` notes, and aborts the process (or traps the isolated WebAssembly instance).

### 2.6 Comprehensive `.cx` Showcase: Idiomatic Error Handling & Deterministic Cleanup

The following `.cx` module demonstrates all elements of Deliverable 1 working together – square-bracket `Result[T, E]`, postfix `T?`, postfix `?` propagation, `@from` structural error composition, `let ... else` guards, infix `catch` recovery, `defer` and `errdefer |err|` cleanup, and `context.note` telescopic diagnostics – strictly adhering to `DR-01`, `DR-02`, and `DR-03` syntax and casing rules:

```rust
// File: src/storage/wal_writer.cx
mod wal_writer;

use std::fs::{File, OpenFlags};
use std::io::IoError;
use std::hash::crc32;
use std::mem::{BumpArena, Slice};

const WAL_MAGIC: u32 = 0x4358_574C; // "CXWL"
const MAX_RECORD_BYTES: usize = 65_536;

pub enum WalError {
    @from Io(IoError),
    InvalidMagic { found: u32 },
    RecordTooLarge { size: usize, limit: usize },
    ChecksumMismatch { expected: u32, actual: u32 },
    CorruptHeader,
}

pub struct WalHeader {
    pub magic: u32,
    pub sequence_id: u64,
    pub payload_len: u32,
    pub checksum: u32,
}

pub struct WalTransaction {
    file: File,
    start_offset: u64,
    records_written: u32,
}

pub fn append_verified_batch(
    arena: &mut BumpArena,
    wal_path: str,
    records: &[Slice[u8]],
    fallback_seq: u64?,
) -> Result[u32, WalError] {
    // [1] Telescopic block-level diagnostic context (zero cost on happy path!)
    errdefer |err| context.note("wal_path='{wal_path}', batch_len={records.len()}, err={err}");

    // [2] Arena checkpoint with unconditional 'defer' restoration
    let cp = arena.checkpoint();
    defer arena.restore(cp);

    // [3] Open file with postfix '?' automatic IoError -> WalError::Io upcasting
    var file = File::open_with(wal_path, OpenFlags::ReadWrite | OpenFlags::Create)?;
    defer file.close();

    // [4] Infix 'catch' for localized single-expression recovery with fallback
    let base_seq: u64 = read_last_sequence(&mut file) catch |err| {
        // Recover from empty/corrupt header if caller supplied a fallback sequence
        let .Some(seq) = fallback_seq else {
            return .Err(err);
        };
        seq
    };

    let initial_offset = file.seek_end()?;
    var tx = WalTransaction {
        file: own file,
        start_offset: initial_offset,
        records_written: 0,
    };

    // [5] 'errdefer' transactional rollback: truncates partial writes ONLY if loop fails
    errdefer {
        let _ = tx.file.truncate(tx.start_offset) catch {};
    }

    for payload in records {
        if payload.len() > MAX_RECORD_BYTES {
            return .Err(.RecordTooLarge {
                size: payload.len(),
                limit: MAX_RECORD_BYTES,
            });
        }

        let next_seq = base_seq + (tx.records_written as u64) + 1;
        let hdr = WalHeader {
            magic: WAL_MAGIC,
            sequence_id: next_seq,
            payload_len: payload.len() as u32,
            checksum: crc32::compute(payload),
        };

        tx.file.write_struct(&hdr)?;
        tx.file.write_all(payload)?;
        tx.records_written += 1;
    }

    tx.file.sync_data()?;
    .Ok(tx.records_written)
}

fn read_last_sequence(file: &mut File) -> Result[u64, WalError] {
    let hdr_opt: WalHeader? = file.try_read_struct[WalHeader]()?;
    let .Some(hdr) = hdr_opt else {
        return .Err(.CorruptHeader);
    };

    if hdr.magic != WAL_MAGIC {
        return .Err(.InvalidMagic { found: hdr.magic });
    }
    .Ok(hdr.sequence_id)
}
```

## 3. Register-Level ABI & Codegen Performance Analysis

### 3.1 The "16-Byte `sret` Cliff" and Why Naive Struct Returns Penalize the Happy Path

To design an optimal calling convention for `Result[T, E]` and `T?` (`Option[T]`), we must examine what happens at the hardware register level when a compiler lowers `Result[T, E]` using the standard platform C ABI (`X86_64_SysV`, `Win64_C`, or `AAPCS64`).

In both System V AMD64 (`x86_64`) and ARM64 (`AAPCS64`), composite structs returned by value are returned in general-purpose registers **only if their total padded byte size is ≤ 16 bytes** (`RAX` + `RDX` on `x86_64`; `X0` + `X1` on `aarch64`). On Windows `x86_64` (`Win64_C`), the C ABI is even more restrictive: any struct whose size is not 1, 2, 4, or 8 bytes – including a 16-byte struct – is spilled to memory via a hidden `sret` pointer. Whenever a returned struct exceeds 16 bytes on System V / ARM64 (or 8 bytes on Win64), the ABI triggers **Indirect Structure Return (`sret`)**. The caller must allocate stack space in its own frame, compute the stack address (`lea rdi, [rsp + offset]` on `x86_64` or `add x8, sp, #offset` on `aarch64`), and pass that hidden pointer to the callee – shifting all normal argument registers on `x86_64` right by one slot. The callee writes the success payload `T` and the discriminant tag byte into the stack buffer pointed to by `sret`, and immediately upon return the caller must load the discriminant tag back from stack memory to branch on `?`, and then reload `T` into registers – incurring store-to-load forwarding latency, register shuffling, and instruction cache bloat.

As Niall Douglas (`N2289`), matklad's `std::io::Error` study, and our layout calculations demonstrate, a naive tagged union `struct { union { T val; E err; }; u8 tag; }` suffers from two compounding layout penalties. First, **Tag and Alignment Padding Inflation (`16B` to `24B` `sret` Cliff)** occurs whenever `T` is a 16-byte value without an available bit-pattern niche – such as a two-word tuple `(u64, u64)`, a 128-bit UUID, or a raw fat pointer `(*u8, usize)` – and `E` is a 2-byte `IoError` enum. Appending a 1-byte discriminant tag to a 16-byte union with 8-byte alignment adds **8 bytes** (1-byte tag + 7 bytes of alignment padding), pushing `sizeof(Result[T, E])` from 16 bytes to **24 bytes** and forcing `sret` stack spilling on every call. Second, **Cold Error Payload Inflation (`4B` to `520B` Cache Cliff)** occurs when `T` is a small 4-byte `File` handle (`u32`) and `E` is an unboxed 512-byte `DiagnosticPayload`. In a naive inline `Result`, the on-the-stack size of `E` is paid on **every single happy-path call**: `sizeof(Result[File, DiagnosticPayload])` becomes **520 bytes** (9 cache lines), inflating the stack frame of every caller in the chain even when no errors occur.

> **Visual – CoreX Split-Register and Carry-Flag ABI Eliminates Both the 16-Byte sret Stack Cliff and Exception Unwind Bloat:** Top: Empirical WG21 benchmarks show that C++ table-based exceptions add up to 439 KB of static binary and unwind table overhead on Clang x64 and run over 100x slower on the error path than value returns. Middle: In standard System V and ARM64 ABIs, adding a 1-byte discriminant tag and 7-byte padding to a 16-byte payload pushes Result[(u64, u64), IoError] to 24 bytes, crossing the 16-byte sret threshold and forcing caller stack spills. CoreX overlays T and E in registers and transmits the discriminant in the CPU Carry Flag (CF) or 4-register swiftcc tuple, while collapsing 512-byte diagnostic payloads into 4-byte DiagId arena handles. Bottom: Exact register and flag assignments across CoreX's three Tier-1 compilation targets.

### 3.2 Comparative Evaluation of Modern Value-Return ABIs (`P0709`/`N2289`, Swift `SE-0413`, and Zig)

Three major compiler designs have addressed the value-error ABI problem, each providing crucial insights that shape CoreX's `cx_result_cc` convention:

1.  **Herb Sutter `P0709` and Niall Douglas `N2289` (`fails(E)` + Carry Flag `CF`)**:
    In WG14 `N2289` and WG21 `P0709`, Douglas and Sutter observed that because a fallible function returns *either* `T` *or* `E`, their storage should form an untagged `union { T value; E error; }` allocated in the standard return registers (`RAX`/`RDX` on `x86_64`, `X0`/`X1` on `aarch64`), while the 1-bit boolean discriminant (`failed`) is transmitted via the **CPU's Carry Flag (`CF`)**. On `x86_64`, clearing `CF` on `.Ok` (`clc`) or setting `CF` on `.Err` (`stc`) is a single-byte, 1-cycle instruction (or free when folded into a preceding comparison instruction), and the caller tests for failure with a 2-byte `jc .Lerr` (`b.cs .Lerr` on `aarch64`) without consuming a general-purpose register or causing status-register pipeline stalls. Furthermore, `std::error` (`status_code<erased<intptr_t>>`) is strictly bounded to **two CPU registers (16 bytes)** so error propagation never touches the heap or stack.
2.  **Swift `swiftcc` (`swifterror` in `R12` / `X21`) and Swift 6 `SE-0413` Typed Throws**:
    In LLVM's `X86CallingConv.td` (`RetCC_X86_64_Swift`) and `AArch64CallingConvention.td`, `swiftcc` makes two key modifications to the C ABI. First, it expands direct register returns from 2 GPRs (16 bytes) to **4 GPRs (32 bytes)** (`[RAX, RDX, RCX, R8]` and `[XMM0, XMM1, XMM2, XMM3]` on `x86_64`; `[X0..X7]` on `aarch64`), allowing 3-word and 4-word value types to return entirely in registers without `sret`. Second, it reserves a dedicated callee-saved register for `swifterror` (**`R12` on `x86_64`** and **`X21` on `aarch64`**). While expanding return registers to 4 GPRs is a major optimization that CoreX adopts, dedicating a callee-saved GPR (`R12`/`X21`) exclusively to `swifterror` was designed for Swift's untyped `throws` (`any Error`), where `R12`/`X21` holds an 8-byte pointer to a heap-allocated existential error box. Even with Swift 6's `SE-0413` Typed Throws (`throws(E)`) – which avoids existential boxing for concrete error types in local and Embedded Swift scopes while retaining ABI compatibility shims (`@_silgen_name`, `@backDeploy`) for standard library evolution – reserving `R12`/`X21` across non-error code paths ties up a callee-saved register when `E` can instead overlay `RAX`/`RDX` (`X0`/`X1`) on the cold error path.
3.  **Zig Error Union (`E!T`) and Diagnostic Sinks**:
    Zig assigns every error in a compilation unit an integer tag and optimizes `!T` to a bare `T` whenever static analysis proves no error can be returned. For rich error reporting, Zig separates control flow (`error{OutOfMemory, ParseZon}!T`) from diagnostic data (`diag: ?*Diagnostics`). CoreX builds on Zig's model by allowing `E` to be any expressive algebraic enum (`sizeof(E) <= 16` bytes) while threading the `Diagnostics` arena automatically through CoreX's implicit `context` register (`DR-02` §4) so function signatures remain clean.

## 4. Deliverable 2: Register-Level ABI & Block-Argument SSA `MIR` Lowering Specification

### 4.1 Dual-Representation Layout Rules: In-Memory Niche Layout vs. Register Return ABI

CoreX formally distinguishes between **Storage Layout (`ReprStorage`)** – used when a `Result[T, E]` or `T?` is stored inside a struct field, array, `#soa` slice, or pointer target – and **Return ABI Layout (`cx_result_cc`)** – used when returning `Result[T, E]` or `T?` from a function call.

#### A. In-Memory Storage Layout (`ReprStorage`) via Multi-Layer Niche Exploitation

When computing `sizeof(Result[T, E])` and `sizeof(T?)` in memory, the CoreX layout engine (`stage0/src/layout.zig` and self-hosted `src/sema/layout.cx`) applies five deterministic layout tiers before ever allocating an explicit discriminant tag byte:

| Layout Tier | Condition on `T` and `E` | In-Memory Representation (`ReprStorage`) | Concrete CoreX Examples & Exact Byte Size (`64-bit`) |
| :--- | :--- | :--- | :--- |
| **Tier 0: Uninhabited Elimination** | `E == never` (infallible) or `T == never` (always fails). | Collapses directly to `T` (if `E == never`) or `E` (if `T == never`) with **0 tag bits**. | `Result[u64, never]` = **8 B** (`u64`); `Result[never, IoError]` = **8 B** (`IoError`). |
| **Tier 1: Pointer / NonZero Null Niche** | `T` has a `0x0` niche (`&T`, `&mut T`, `OwnPtr[T]`, `NonNull[T]`, `NonZeroU64`, `fn(...)`) and `sizeof(E) == 0` (`T?` or unit error). | `0x0` bit pattern represents `.None` / `.Err`; all non-zero values represent `.Some(T)` / `.Ok(T)`. | `(&User)?` = **8 B**; `OwnPtr[AvlNode[K, V]]?` = **8 B**; `NonZeroU32?` = **4 B**. |
| **Tier 2: Multi-Word Niche + Payload Stashing** | `T` is a multi-word struct where Field 0 has a `0x0` niche (e.g., slice `[u8]` = `{ ptr: NonNull[u8], len: usize }`) and `sizeof(E) <= sizeof(T) - sizeof(Field0)`. | When `Field0 == 0x0` (null pointer), the remaining bytes (`len` word at offset `+8`) store the entire `E` payload inline. | `Result[[u8], IoError]` = **16 B** (`ptr == 0` signals `.Err`, and `IoError` lives in the 8-byte `len` word – **0 B tag overhead**). |
| **Tier 3: Scalar Range Niche Stacking** | `T` has `N >= \|variants(E)\|` unused scalar bit patterns (`bool` has 254 niches `2..=255`; `char` above `0x10FFFF`; `enum` tags; LSB pointer alignment bits). | Variants of `E` (or `.None`) are mapped directly onto the contiguous niche range `N` inside `T`'s byte footprint. | `bool?` = **1 B** (`.None = 2`); `bool??` = **1 B** (`.Some(.None) = 2, .None = 3`); `Result[bool, ParseErr]` = **1 B**. |
| **Tier 4: Padded Tagged Union (Fallback)** | Neither `T` nor `E` has sufficient niches to encode the other. | `struct { payload: union { ok: T, err: E }, tag: u8 }` aligned to `max(alignof(T), alignof(E))`. | `Result[u64, u16]` = **16 B** in memory (but returned in **1 register + `CF`** in `cx_result_cc`). |

#### B. Cold Error Payload Mitigation (`@cold_box`, `context.diagnostics`, and Bit-Tagged `IoError`)

To ensure `sizeof(E)` never exceeds **16 bytes** (two 64-bit registers), the CoreX compiler enforces three layout rules on error types. First, if any type `E` used as the error parameter of `Result[T, E]` has `sizeof(E) > 16` bytes, the compiler emits `@warn(error_size_limit)`, and if an enum variant exceeds the second-largest variant by `> 64` bytes, it emits `@warn(variant_size_skew)` (`DR-02` §3.2). Second, applying `@cold_box` to a large enum variant (e.g., `@cold_box DetailedSyntaxError(BoxedDiag)`) or to an entire error struct transforms its inline representation into a single 8-byte `OwnPtr[Payload]` (or arena handle). Following matklad's `std::io::Error` optimization, the compiler synthesizes a non-inlined `@cold` constructor helper for the boxed variant so that instruction cache on the caller's hot path is never polluted by allocation or field-initialization code, shrinking `sizeof(E)` to **8 bytes**. Third, following Rust's bit-packed `std::io::Error` design, CoreX's `std::io::IoError` occupies a **single 64-bit word (8 bytes)** with 4-byte alignment niche preservation: when `bits[1:0] == 0b00`, the word is a pointer to a `@cold_box` `CustomIoError` allocated with alignment ≥ 4 bytes; when `bits[1:0] == 0b10`, the upper 32 bits (`bits[63:32]`) store the raw 32-bit OS error code (`errno` / `NTSTATUS` / `HRESULT`) and `bits[15:8]` store the `ErrorKind` enum; and because `bit[0]` is always `0` for every valid `IoError`, `bit[0] == 1` remains available as a **1-bit niche** so `IoError?` or `Result[i32, IoError]` fits inside a single 8-byte register (`RAX` / `X0`).

### 4.2 Target-Specific Register & Flag Calling Convention (`cx_result_cc`)

For all non-`extern "c"` CoreX functions returning `Result[T, E]` or `T?`, the compiler classifies the return signature into one of three physical ABI classes across `x86_64`, `aarch64`, and `wasm32`:

| Physical ABI Class | Activation Condition | `x86_64` Register & Flag Mapping | `aarch64` Register & Flag Mapping | `wasm32` (`+multivalue`) Stack Mapping |
| :--- | :--- | :--- | :--- | :--- |
| **`ABI_NICHE_REG`** (Hardware Zero-Niche Return) | Tier 1 or Tier 2 Niche applies (`(&T)?`, `OwnPtr[T]?`, `NonZeroU64?`, `Result[[u8], E]`). | Word 0 in `RAX` (`0` = `.None`/`.Err`); Word 1 (`len` or `E`) in `RDX`. Caller checks `test rax, rax; jz .Lerr`. | Word 0 in `X0` (`0` = `.None`/`.Err`); Word 1 (`len` or `E`) in `X1`. Caller checks `cbz x0, .Lerr`. | `(result i32/i64 ...)` on Wasm stack; result 0 == `0` signals `.Err`. Caller checks `i32.eqz; br_if $err`. |
| **`ABI_SPLIT_VAL_FLAG`** (Overlaid Register Union + Status Flag) | `sizeof(T) <= 32B` (1–4 words), `sizeof(E) <= 16B` (1–2 words), and no zero-niche applies. | `T` in `[RAX, RDX, RCX, R8]` (`[XMM0..3]` for floats); `E` overlays `[RAX, RDX]`. Native emitter sets **Carry Flag `CF`** (`clc` = `.Ok`, `stc` = `.Err`, caller `jc .Lerr`); LLVM `swiftcc` passes tag in `RCX` / `R12`. | `T` in `[X0, X1, X2, X3]` (`[D0..3]`/`[Q0..3]` for floats); `E` overlays `[X0, X1]`. Native emitter sets **`NZCV.C` Carry Flag** (`cmn` = `.Ok`, `cmp` = `.Err`, caller `b.cs .Lerr`); LLVM `swiftcc` passes tag in `W2` / `X21`. | Flat multi-value tuple `(result ValTypes... i32)` where `T` and `E` share leading stack slots and trailing `i32` is `0` (`.Ok`) or `1` (`.Err`). |
| **`ABI_SRET_INPLACE_OK`** (In-Place `sret` for `T > 32B` + Register `E`) | `sizeof(T) > 32B` and `sizeof(E) <= 16B`. | Caller passes `T* noalias sret` in `RDI` (holds **only `T`**, never `Result`). On `.Ok`, `T` is written in-place to `*RDI` with `CF = 0`; on `.Err`, `E` returns in `[RAX, RDX]` with `CF = 1`. | Caller passes `T* noalias sret` in `X8` (holds **only `T`**). On `.Ok`, `T` is written in-place to `*X8` with `C = 0`; on `.Err`, `E` returns in `[X0, X1]` with `C = 1`. | Caller passes `T* sret` as `param 0`; function returns `(result i64 i64 i32)` carrying `E` and `err_tag` in registers/stack on failure. |

In `ABI_SRET_INPLACE_OK`, keeping the error payload `E` and the failure flag strictly in registers while restricting the indirect `sret` buffer to `T` alone directly implements the rationale identified in Swift's `CallingConvention.rst`: contorting an indirect `sret` slot into a tagged union of `T` and `E` prevents the caller from evaluating the call directly into the final destination variable's memory address. By guaranteeing that `*sret` is written only on `.Ok`, a CoreX statement `let big_matrix: Matrix4x4 = compute_matrix()?;` passes `&big_matrix` directly as the `sret` pointer with zero intermediate stack copies.

### 4.3 Concrete `stage0/corex` Zig Data Structures for Block-Argument SSA `MIR`

Aligning directly with `DR-01` §4.1 (`mem_foundation.zig`: `MultiArrayList` SoA storage, `enum(u32)` handles with `0xFFFF_FFFF` sentinel, and `extra_data: []u32` trail) and `DR-02` §3.2 (Block-Argument SSA IR with Ghost Lifetime Instructions), the following Zig Stage-0 specification defines the exact `MIR` representation of `Result[T, E]`, `?` propagation, and `defer`/`errdefer` cleanup scopes:

pub const MirValueId = mem.MirValueId;

    root = 0,
    none = std.math.maxInt(u32),

};

    /// Infallible or non-Result return type.
    standard_val = 0,

    sret_inplace_ok = 3,

    kind: Kind,

        defer_action = 0,
        /// Conditional `errdefer`: runs ONLY when exiting scope via `.Err` / `?`.
        errdefer_action = 1,
        /// Ghost verification marker for move-only resource bindings (`DR-02` §3.3).
        ghost_resource_check = 2,
    };
};

    ty: TypeId,
    data: Data,

        result_wrap_err,

        result_project_ok,
        /// Extracts E payload from known-.Err Result value `lhs` (zero-cost register alias).

        /// Unconditional jump with block arguments: `br ^target(args…)`
        term_br,
        /// Conditional branch on boolean/niche: `cond_br %cond, ^then, ^else`
        term_cond_br,
        /// Fused fallible call + status-flag/register branch for `call(args…)?`:
        /// Calls `callee`; on `.Ok(v)` jumps to `^ok_bb(%v)` (fall-through hot path);
        /// on `.Err(e)` jumps to `^err_bb(%e)` (cold error/cleanup edge).
        term_call_try,
        /// Branch on an already-materialized Result/Option value `scrutinee?`:
        /// On `.Ok(v)` jumps to `^ok_bb(%v)`; on `.Err(e)` jumps to `^err_bb(%e)`.
        term_branch_try,
        /// Returns `.Ok(val)` from current function using `cx_result_cc` (`CF = 0`).
        term_ret_ok,
        /// Returns `.Err(err)` from current function using `cx_result_cc` (`CF = 1`).

        err_target_bb: MirBlockId,

    };

### 4.4 Deterministic AST-to-`MIR` Lowering Algorithm for `?`, `catch`, `defer`, and `errdefer`

Lowering a CoreX function into Block-Argument SSA `MIR` (`stage0/src/mir_lower.zig`) proceeds in a single forward pass using Matthias Braun's SSA construction algorithm (`DR-02` §3.2) augmented with a **Cascading Cold-Cleanup Chain Generator**:

1.  **Maintaining the Active Cleanup Scope Stack**: The lowering context maintains `current_scope: CleanupScopeId` (initialized to `.root`). When the traversal encounters `defer { body }`, it allocates a new `CleanupScope` record with `kind = .defer_action` and `parent = current_scope`, and updates `current_scope`. When the traversal encounters `errdefer |err| { body }`, it allocates a `CleanupScope` record with `kind = .errdefer_action`, `parent = current_scope`, and records the AST node of `body` to be lowered lazily if at least one error edge reaches this scope.
2.  **Lowering Postfix `expr?` via Cascading Cold Landing Blocks**: When lowering `let x = call_fn(args...)?;` at scope depth $S_k$ inside a function returning `Result[U, F]`, if `expr` is a direct call to a CoreX function returning `Result[T, E]`, the compiler fuses the call and the `?` check into a single `term_call_try` terminator (or `term_branch_try` if `expr` is a local variable or pipeline value). The compiler creates the next hot-path continuation block `^bb_ok(%x: T)` and marks it as the layout fall-through successor so the hardware branch predictor predicts not-taken on the error jump. For the error target `^err_target`, if `E != F`, the compiler emits a cold conversion block `^err_conv(%raw_err: E)` that calls `%mapped_err = F::from_error(%raw_err)` and jumps to the **materialized error-unwind block for scope $S_k$ (`^err_unwind_Sk(%mapped_err: F)`)**. Crucially, each scope $S_k$ materializes its error-unwind block `^err_unwind_Sk(%err: F)` at most once: inside `^err_unwind_Sk(%err: F)`, the compiler emits the cleanup body of $S_k$ (whether `defer` or `errdefer`) and terminates with `br ^err_unwind_S{k-1}(%err)`. If ten different `?` expressions fail after scope $S_2$, they all branch to the single shared `^err_unwind_S2(%err: F)` block, which executes $S_2$'s cleanup and falls into $S_1$'s cleanup – preventing combinatorial code duplication while requiring zero runtime state variables.
3.  **Lowering Normal Block Exits (Tail Expressions and `return .Ok(v)`)**: When a lexical block or function reaches a normal exit at scope $S_k$, the compiler walks the scope chain from $S_k$ up to the target block's ancestor scope, emitting **only** the `CleanupScope` nodes where `kind == .defer_action` (and scope drops) in reverse lexical order, while bypassing all `.errdefer_action` nodes.
4.  **Lowering Infix `e_1 catch |err| e_2`**: When lowering `let res = e_1 catch |err| e_2;` where `e_1 : Result[T, E]`, if `e_1` may record telescopic notes into `context.diagnostics`, the compiler first records a diagnostic checkpoint (`%diag_cp`). Next, `e_1` is lowered with `term_call_try` or `term_branch_try` whose `.Ok` edge jumps to `^catch_join(%val_ok: T)` and whose `.Err` edge jumps directly to `^catch_handler(%err: E)` without triggering the enclosing function's `errdefer` chain. Inside `^catch_handler(%err: E)`, the compiler emits `diag_checkpoint_restore %diag_cp` (discarding uncommitted diagnostic notes from the handled failure), evaluates `e_2` to `%val_fallback: T` (unless `e_2` diverges via `return`), and jumps via `br ^catch_join(%val_fallback)`.

### 4.5 Machine-Code Generation Across `x86_64`, `aarch64`, and `wasm32`

To verify the register-level efficiency of `cx_result_cc`, we examine the machine instructions emitted for a representative fallible function `parse_and_scale(buf: [u8], factor: u64) -> Result[(u64, u64), ParseError]` calling `read_pair(buf: [u8]) -> Result[(u64, u64), ParseError]`.

Here, the success payload `T = (u64, u64)` is **16 bytes** (`2 * u64`) and `E = ParseError` is **8 bytes** (an enum with a `u32` byte offset and `u16` token kind). Under the standard C / Rust ABI, `Result[(u64, u64), ParseError]` is **24 bytes**, which crosses the 16-byte threshold and forces `sret` stack spilling. Under CoreX's `cx_result_cc` (`ABI_SPLIT_VAL_FLAG`), `T` and `E` share the return registers with **zero stack spills**:

```rust
// CoreX Source:
pub fn parse_and_scale(buf: [u8], factor: u64) -> Result[(u64, u64), ParseError] {
    if factor == 0 {
        return .Err(.ZeroScaleFactor);
    }
    let (a, b) = read_pair(buf)?;
    .Ok((a * factor, b * factor))
}
```

#### 1. `x86_64` Assembly Output (System V / Windows 64 with `cx_result_cc`)

On `x86_64`, `buf` (`ptr`, `len`) arrives in `RDI, RSI` and `factor` arrives in `RDX`. `read_pair` returns `a` in `RAX`, `b` in `RDX` (or `ParseError` in `RAX` on failure), and sets `CF = 0` on `.Ok` (`clc`) or `CF = 1` on `.Err` (`stc`):

```nasm
; CoreX Native Direct Emitter / LLVM Backend (x86_64 cx_result_cc)
; Arguments: RDI = buf.ptr, RSI = buf.len, RDX = factor
; Return:    Ok((u64, u64)) -> RAX = a*factor, RDX = b*factor, CF = 0
;            Err(ParseError)-> RAX = ParseError (8B),          CF = 1
parse_and_scale:
    test    rdx, rdx                ; factor == 0? (also clears CF = 0!)
    jz      .Lerr_zero_factor       ; cold forward conditional jump (predicted not-taken)
    push    rbx                     ; save callee-saved RBX to hold 'factor' across call
    mov     rbx, rdx                ; RBX = factor
    call    read_pair               ; returns (a, b) in RAX, RDX; sets CF=1 on .Err
    jc      .Lerr_propagate         ; 2-byte Carry Flag check! Zero GPR tag overhead!
    imul    rax, rbx                ; a * factor
    imul    rdx, rbx                ; b * factor
    clc                             ; 1-byte Clear Carry Flag -> signals .Ok((rax, rdx))
    pop     rbx
    ret                             ; Happy path: 0 stack allocas, 0 sret pointers!

.Lerr_propagate:                    ; Cold out-of-line propagation path (CF is already 1!)
    pop     rbx                     ; pop RBX does NOT modify EFLAGS.CF!
    ret                             ; RAX already holds ParseError, CF is already 1!

.Lerr_zero_factor:                  ; Cold out-of-line error construction
    mov     eax, 1                  ; RAX = ParseError::ZeroScaleFactor
    stc                             ; 1-byte Set Carry Flag -> signals .Err(rax)
    ret
```

In `.Lerr_propagate` above, because `pop rbx` and `ret` on `x86_64` do not modify `EFLAGS.CF`, and `RAX` already contains the `ParseError` returned by `read_pair`, propagating an error of the same type across a function boundary takes **only two instructions (`jc .Lerr_propagate` followed by `pop rbx; ret`)** without moving or repackaging a single register. In the LLVM `swiftcc` path where the discriminant is passed in `RCX` instead of `CF`, `jc .Lerr_propagate` becomes `test ecx, ecx; jnz .Lerr_propagate`, which remains entirely register-resident and leaves `ECX = 1` untouched on `.Lerr_propagate`.

#### 2. `aarch64` Assembly Output (ARM64 Linux / macOS Apple Silicon / Windows)

On `aarch64`, `buf` arrives in `X0, X1` and `factor` in `X2`. `read_pair` returns `(a, b)` in `X0, X1` (or `ParseError` in `X0`) and sets the `NZCV` Carry Flag (`C = 0` for `.Ok`, `C = 1` for `.Err`):

```armasm
// CoreX Native Direct Emitter (aarch64 cx_result_cc)
// Arguments: X0 = buf.ptr, X1 = buf.len, X2 = factor
// Return:    Ok((u64, u64)) -> X0 = a*factor, X1 = b*factor, NZCV.C = 0
//            Err(ParseError)-> X0 = ParseError (8B),          NZCV.C = 1
parse_and_scale:
    cbz     x2, .Lerr_zero_factor   // factor == 0? Branch to cold error block
    stp     x19, x30, [sp, #-16]!   // save X19 (factor) and LR (X30)
    mov     x19, x2                 // X19 = factor
    bl      read_pair               // returns (a, b) in X0, X1; sets C=1 on .Err
    b.cs    .Lerr_propagate         // Branch if Carry Set (C == 1) -> .Err!
    mul     x0, x0, x19             // a * factor
    mul     x1, x1, x19             // b * factor
    cmn     xzr, xzr                // Clear Carry Flag (C = 0) in 1 ALU cycle
    ldp     x19, x30, [sp], #16
    ret

.Lerr_propagate:                    // Cold propagation path: X0 holds ParseError, C == 1
    ldp     x19, x30, [sp], #16     // ldp does NOT modify NZCV flags!
    ret

.Lerr_zero_factor:
    mov     w0, #1                  // X0 = ParseError::ZeroScaleFactor
    cmp     xzr, xzr                // Set Carry Flag (C = 1, since 0 >= 0 unsigned)
    ret
```

#### 3. `wasm32` Output (WebAssembly Multi-Value Stack ABI)

On `wasm32` (`-mcpu=generic+multivalue` enabled across modern browsers, Wasmtime, and CoreX's `wasm2c` bootstrap translator), standard C and Rust compilers without `+multivalue` spill any `Result` > 8 bytes into linear memory via the global `__stack_pointer`. CoreX instead uses **WebAssembly Multi-Value Returns** (`(result i64 i64 i32)`), keeping `(a, b, is_err)` directly on the Wasm virtual operand stack so the JIT compiler maps them to host CPU registers:

```wat
;; CoreX Wasm32 Multi-Value Lowering (+multivalue)
;; Signature: (param $ptr i32) (param $len i32) (param $factor i64) -> (result i64 i64 i32)
;; Stack result tuple: (ok_0 / err_payload: i64, ok_1: i64, err_tag: i32)
(func $parse_and_scale
  (param $ptr i32) (param $len i32) (param $factor i64)
  (result i64 i64 i32)
  (local $a i64) (local $b i64) (local $err_tag i32)

  ;; if factor == 0 { return .Err(.ZeroScaleFactor) }
  (if (i64.eqz (local.get $factor))
    (then
      (return (i64.const 1) (i64.const 0) (i32.const 1)) ;; (err=1, pad=0, is_err=1)
    )
  )

  ;; Call read_pair(buf) -> pushes (i64, i64, i32) directly onto Wasm operand stack
  (call $read_pair (local.get $ptr) (local.get $len))
  (local.set $err_tag)
  (local.set $b)
  (local.set $a)

  ;; Postfix '?' check: if $err_tag != 0, propagate immediately
  (if (local.get $err_tag)
    (then
      (return (local.get $a) (i64.const 0) (local.get $err_tag))
    )
  )

  ;; Happy path: return .Ok((a * factor, b * factor)) with err_tag = 0
  (i64.mul (local.get $a) (local.get $factor))
  (i64.mul (local.get $b) (local.get $factor))
  (i32.const 0)
)
```

### 4.6 Summary Verification Checklist for `stage0/corex` & `src/` Implementation

To operationalize this error-handling architecture across the Zig Stage-0 compiler (`stage0/corex`) and the self-hosted `.cx` compiler (`src/`), the implementation enforces six concrete invariants:
1.  **Single Authoritative Surface Syntax**: Standardize on `Result[T, E]`, `T?` (`Option[T]`), postfix `expr?`, `.Ok(v)` / `.Err(e)` / `.Some(v)` / `.None`, `let ... else`, infix `catch`, and `defer` / `errdefer` (`DR-03` + `DR-07`).
2.  **Stateless Lexer & `LL(1)` / Pratt Parser Integration**: Add `KW_CATCH` and `KW_ERRDEFER` (statement starter) to `DR-03`'s unified 112-token table (`DR-03` §5.2) with zero lookahead conflicts.
3.  **Compile-Time Discard & Skew Lints**: Enforce `@must_use` on `Result[T, E]` (requiring explicit error handling or `catch {}` discard), `@warn(error_size_limit)` when `sizeof(E) > 16` bytes, and `@warn(variant_size_skew)` when variant size skew exceeds 64 bytes.
4.  **Multi-Layer Niche Layout Engine (`ReprStorage`)**: Exploit `0x0` pointer/non-zero niches, multi-word slice `len` payload stashing (`Result[[u8], E]` in 16 bytes), and scalar range niches (`bool?` in 1 byte) for in-memory storage.
5.  **Split-Register & Status-Flag Calling Convention (`cx_result_cc`)**: Return `Result[T, E]` in overlaid registers (`RAX, RDX, RCX, R8` on `x86_64`; `X0–X3` on `aarch64`; multi-value stack tuples on `wasm32`) with Carry Flag (`CF`) or `swiftcc` register discriminants – eliminating the 16-byte `sret` stack cliff.
6.  **Cascading Cold-Cleanup SSA `MIR` Lowering**: Emit `errdefer` and `@from` error conversions strictly on shared out-of-line cold CFG blocks (`^err_unwind_Sk`) in reverse lexical order, guaranteeing zero happy-path instructions and zero stack-unwinding tables.
