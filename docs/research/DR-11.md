# Zero-Friction Package Management, Content-Addressable Global Cache, and Reproducible Lockfile Architecture for CoreX (.cx)

To deliver zero-friction developer ergonomics alongside bit-for-bit build reproducibility (`Stage 3 === Stage 4`) and zero disk duplication, **CoreX (`.cx`)** unifies an **On-Demand Auto-Synchronizing Package Manager**, a **Hybrid Minimal Version Selection (MVS) + PubGrub Diagnostic Resolver**, and a **BLAKE3 Content-Addressable Global Store (`~/.corex/cache/`)** mapped directly into the compiler's Virtual File System (`SourceMap`) without per-project `node_modules` or `vendor` copies[cite: 1, 2, 3]. In this architecture, developers do not need to run manual `install` rituals before compiling: invoking `corex run` or `corex build` inspects the `.cx` AST `use` declarations against `corex.toml` and `corex.lock`, resolves any newly referenced short registry packages or versioned Git/GitHub URLs (`github.com/org/pkg@v1.2.0`), verifies their cryptographic hashes against a tile-based transparency log, streams missing content blobs into `~/.corex/cache/blake3/`, and maps the read-only source files directly into `corexc`'s memory space[cite: 1, 2]. Single-file `.cx` scripts (`#!/usr/bin/env corex`) support the same workflow via embedded TOML frontmatter (`---`) with out-of-tree lockfiles and build caches under `~/.corex/target/scripts/<blake3-path-hash>/`.

For version resolution, CoreX addresses the trade-off between Go's predictable linear-time **Minimal Version Selection (MVS)** and Cargo/uv's expressive **PubGrub** solver by adopting **Bounded-MVS with PubGrub Conflict Explanation**[cite: 3]. Standard dependency specifications in `corex.toml` express minimum compatible SemVer bounds (`serde-json = "1.4.2"`), allowing the resolver to compute the minimal build list in deterministic $O(|\Delta_{\min}| + |R|)$ graph-traversal time without SAT-solver search overhead or unpinned build drift[cite: 3]. When explicit version exclusions (`exclude`), upper bounds (permitted for security advisories or known upstream regressions), or conflicting constraints make a graph unsatisfiable, CoreX transitions into a **PubGrub Conflict-Driven Clause Learning (CDCL)** pass to derive the root-cause incompatibility chain and render a plain-English proof tree explaining which package constraints must be relaxed.

At the storage and compiler boundary, CoreX eliminates per-workspace file duplication by content-addressing every downloaded package at two granularities using **BLAKE3** (`1,024`-byte chunks, `64`-byte blocks, and **Bao** verified streaming trees): individual source files are stored once by their 256-bit BLAKE3 content digest in `~/.corex/cache/blake3/blobs/`, while whole-package directory structures are represented as immutable, lexicographically sorted Merkle manifest files in `~/.corex/cache/blake3/trees/`[cite: 2]. During compilation, `corexc` reads `corex.lock` and constructs an in-memory **Virtual File System (`VfsSourceMap`)** that maps each package's logical module tree directly to the read-only global blob store—loading files `<16 KiB` into `corexc`'s zero-initialized `BumpArena` and mapping files `≥16 KiB` via OS page-cache sharing (`mmap` on POSIX, `CreateFileMapping` on Windows) while assigning deterministic `FileId(u32)` handles and sanitizing debug paths (`-fdebug-compilation-dir .`) so builds remain reproducible across machines and operating systems[cite: 2].

## 1. Deliverable 1: Complete `.cx` Package Import Rules, `corex.toml` Manifest, and `corex.lock` Schemas

### 1.1 Lexical Alignment Between `corex.toml` (`kebab-case`) and `.cx` (`snake_case`)

In accordance with the CoreX Canonical Casing Matrix (`DR-03`), external package names in `corex.toml` and registry URLs are strictly **`kebab-case`** (`^[a-z][a-z0-9]*(-[a-z0-9]+)*$`, such as `corex-http`, `serde-json`, or `crypto-sha3`), whereas module identifiers (`mod` and `use`) inside `.cx` source files are strictly **`snake_case`** (`IDENT` matching `^[a-z][a-z0-9_]*$`, such as `corex_http`, `serde_json`, or `crypto_sha3`)[cite: 1]. Keeping `-` exclusively as the subtraction operator (`MINUS`) in `.cx` expressions preserves context-free `LL(1)` / Pratt parsing, while `kebab-case` package names match URL and CLI conventions[cite: 1].

CoreX bridges these two namespaces through a **Bijective Canonical Identifier Mapping Invariant**. Every `kebab-case` package key declared in `[dependencies]`, `[dev-dependencies]`, or `[build-dependencies]` of `corex.toml` is deterministically exposed to `.cx` source files as a root module identifier by replacing every ASCII hyphen (`0x2D`) with an ASCII underscore (`0x5F`)[cite: 1]. For example, `serde-json = "1.4.0"` is imported in `.cx` as `use serde_json::{Serialize, Deserialize};`[cite: 1]. Because `a-b` and `a_b` would otherwise normalize to the same `.cx` module identifier `a_b`, `corex.toml` forbids underscores in package names (`E_MANIFEST_INVALID_PKG_NAME`), and the CoreX registry rejects registration of any package name that differs from an existing package only by hyphen/underscore substitution[cite: 1]. When a project depends on two packages from different sources—or two simultaneous major versions of the same package, such as `corex-http` v1 and v2—the manifest key serves as the local alias (`http-v1 = { package = "corex-http", version = "1.8.0" }` and `http-v2 = { package = "corex-http", version = "2.1.0" }`), which normalize to disjoint root modules `use http_v1::Client;` and `use http_v2::Client;`[cite: 1, 3].

| :--- | :--- | :--- | :--- | :--- |

### 1.2 Zero-Friction Source Imports & Auto-Synchronization Protocol

CoreX eliminates the context switch between source editors and terminal package-install commands (`npm install`, `cargo add`, `pip install`) by unifying three import workflows inside `corex run`, `corex build`, `corex test`, and `corex check`.

In multi-file projects with a `corex.toml` manifest, developers write standard module imports such as `use serde_json::{Serialize, Deserialize};` in any `.cx` file[cite: 1]. Before semantic analysis, the compiler's fast `LL(k)` import scanner extracts all root `IDENT` segments of `use` declarations that do not match `std`, `core`, `pkg`, `self`, `super`, or local sibling modules[cite: 1]. When a referenced package is already present in both `corex.toml` and `corex.lock`, `corexc` mounts the locked BLAKE3 tree from `~/.corex/cache/blake3/` (or fetches missing blobs by exact BLAKE3 digest on a fresh machine) in $O(1)$ time without querying registry index metadata[cite: 2]. If a developer edits `corex.toml` by hand (for example, adding `crypto-sha3 = "0.9.1"`), `corex build` detects that `root_manifest_blake3` in `corex.lock` is stale, runs incremental version resolution, updates `corex.lock`, populates `~/.corex/cache/blake3/`, and compiles immediately without a separate install step. Furthermore, if an unresolved root identifier `use foo_bar::...;` is encountered during an interactive terminal session (when `--frozen`, `--locked`, and `CI=true` are not active), `corex` looks up `foo-bar` in the sparse registry index, selects the latest stable release `vX.Y.Z`, appends `foo-bar = "X.Y.Z"` to `corex.toml`, updates `corex.lock`, and continues compilation while printing a notification (`Auto-added dependency 'foo-bar = "1.3.0"' to corex.toml`)[cite: 1].

For rapid prototyping or decentralized packages hosted directly on Git repositories, CoreX extends the `UseItem` grammar rule (`DR-03`) to accept a versioned string literal specifier paired with an explicit `as IDENT` alias:

```rust
use "github.com/corex-labs/http-router@v1.2.0" as http_router;
use "registry:serde-json@1.4.2" as serde_json;
```

When `corex run` or `corex build` encounters an inline string-literal `use` inside a project backed by `corex.toml`, it automatically hoists the dependency into `corex.toml` (`http-router = { git = "https://github.com/corex-labs/http-router", tag = "v1.2.0" }`) and records its commit SHA and BLAKE3 tree hash in `corex.lock`, allowing `corex fmt --tidy` to normalize the source import to `use http_router;`[cite: 1].

For standalone utilities and reproducible bug reports, CoreX supports single-file `.cx` executable scripts (`#!/usr/bin/env corex`), modeled on Cargo Script (RFC 3502). Running `./script.cx` or `corex script.cx` acts as a direct shortcut for `corex run --manifest-path script.cx`, where dependencies are declared in a top-of-file `---` TOML frontmatter block or via inline string-literal `use` statements. Following RFC 3502's security boundary, invoking `corex script.cx` loads global configuration strictly from `~/.corex/config.toml` rather than any `.corex/config.toml` in the current working directory, preventing untrusted files in shared or download directories from injecting malicious registry overrides. Single-file scripts are bin-only packages and disallow multi-target workspace tables (`[workspace]`, `[lib]`, `[[bin]]`, `package.publish`). To avoid cluttering the script's directory with adjacent lockfiles or build folders, CoreX computes `script_path_hash = BLAKE3(canonical_realpath(script.cx))` and stores the script's lockfile and compiled artifacts out-of-tree at `~/.corex/target/scripts/<script_path_hash>/corex.lock`.

#### Single-File `.cx` Script Showcase (`fetch_metrics.cx`)
All syntax below conforms to `DR-02` and `DR-03` (`[T]` generics, `@derive`, postfix `?`, contextual `.Ok`/`.Err`, `|>` pipelines, and `{expr}` string interpolation)[cite: 1]:

```rust
#!/usr/bin/env corex
---
[dependencies]
corex-http = "2.1.0"
serde-json = { version = "1.4.2", features = ["simd-tape"] }
cli-ansi   = { git = "https://github.com/corex-labs/cli-ansi", tag = "v0.4.1" }
---
// File: fetch_metrics.cx
mod fetch_metrics;

use std::io::{Stdout, IoError};
use std::mem::Arena;
use corex_http::Client;
use serde_json::{Json, Deserialize};
use cli_ansi::{Color, style};

const ENDPOINT_URL: str = "https://api.example.com/v1/cluster/health";

@derive(Deserialize)
pub struct ClusterHealth {
    pub cluster_id: str,
    pub active_nodes: u32,
    pub p99_latency_ms: f64,
    pub healthy: bool,
}

pub async fn run_check(arena: &mut Arena, out: &mut Stdout) -> Result[unit, IoError] {
    let client = Client::with_timeout_ms(arena, 2_500);
    let resp_bytes = client.get_bytes(ENDPOINT_URL).await?;

    let health = resp_bytes
        |> Json::parse[ClusterHealth]()
        |> Result::map_err(|e| IoError::invalid_data(e.message()))?;

    let badge = if health.healthy {
        style("HEALTHY", Color::Emerald)
    } else {
        style("DEGRADED", Color::Red)
    };

    out.write_fmt(
        "[{badge}] Cluster {health.cluster_id}: {health.active_nodes} nodes (p99: {health.p99_latency_ms} ms)\n"
    )?;
    .Ok(())
}

pub async fn main() -> i32 {
    var arena = Arena::with_capacity(262_144);
    defer arena.release();

    var stdout = Stdout::locked();
    match run_check(&mut arena, &mut stdout).await {
        .Ok(_) => 0,
        .Err(err) => {
            std::io::stderr().write_fmt("health check failed: {err}\n");
            1
        }
    }
}
```

## 2. Deliverable 2: Global Content-Addressable Cache (`~/.corex/cache/blake3/`) and Zero-Copy VFS Mapping Specification

### 2.1 BLAKE3 Merkle Tree Hashing for Files and Package Manifests

Traditional package managers either duplicate unpacked source trees across every project on disk (`node_modules` in npm) or unpack whole `.crate`/`.tar.gz` archives into version-named cache directories (`~/.cargo/registry/src/`), duplicating unchanged files across patch releases. CoreX eliminates both redundancies by building its storage and verification layer on **BLAKE3** (`256-bit` / `32-byte` digests, formatted as 64 lowercase hexadecimal characters).

As defined in the BLAKE3 specification, every input is partitioned into contiguous **1,024-byte (`1 KiB`) chunks**, and each chunk is compressed across up to 16 sequential **64-byte blocks** using a 7-round compression function with explicit domain-separation bit flags (`CHUNK_START`, `CHUNK_END`, `PARENT`, `ROOT`, `KEYED_HASH`, `DERIVE_KEY_CONTEXT`, `DERIVE_KEY_MATERIAL`). For inputs larger than $n > 1,024$ bytes, chunks are arranged as the leaves of a binary Merkle tree where every left subtree is a complete binary tree containing the first $2^{10 + \lfloor \log_2(\lfloor (n - 1) / 1024 \rfloor) \rfloor}$ bytes and the right subtree contains the remainder.

CoreX applies BLAKE3 across two storage tiers, augmented by **Bao** verified streaming for large blobs:
1. **Per-File Content Blob Digest (`file_blake3`):** Every file inside a package is hashed using standard unkeyed `BLAKE3-256(raw_file_bytes)`. Before hashing `.cx` source files or `corex.toml` during `corex publish` or when ingesting a Git checkout, CoreX normalizes CRLF (`\r\n`) line endings to LF (`\n`) on UTF-8 text files (`.cx`, `.toml`, `.md`, `.c`, `.h`) so that a Git checkout on Windows and a tarball unpacked on Linux yield the exact same `file_blake3` digest[cite: 2].
2. **Package Directory Merkle Tree (`tree_blake3`):** A package version is canonically identified not by its outer compression container, but by its **Canonical Package Directory Tree Manifest (`*.cxtree`)**[cite: 2]. To enforce cryptographic domain separation between raw file blobs and directory trees, CoreX computes `tree_blake3` using BLAKE3's **`derive_key` mode** with context string `"corex-pkg-tree-v1 2026-01-01"` over a deterministic binary record sequence sorted strictly in **bytewise lexicographical UTF-8 order of relative POSIX path** (`/` separator, no leading `./`, excluding `.git/` and OS metadata files)[cite: 2]:
   $$\text{Entry}_i = \text{u8}(\text{kind}_i) \;\|\; \text{u16\_le}(\text{len}(\text{path}_i)) \;\|\; \text{utf8}(\text{path}_i) \;\|\; \text{u64\_le}(\text{size}_i) \;\|\; \text{bytes32}(\text{file\_blake3}_i)$$
   where $\text{kind}_i \in \{ \text{0x01 (regular file)}, \text{0x02 (executable file)} \}$. Because `tree_blake3` commits strictly to normalized relative paths, file modes, byte sizes, and file content hashes, two developers fetching the same dependency via different transports (one from the sparse HTTP registry `.cxpkg` archive, another from a Git tag or local vendor directory) always compute the exact same `tree_blake3`[cite: 2].
3. **Bao Outboard Slice Verification (`.obao`):** For large blobs (`≥64 KiB`), CoreX supports storing a **Bao outboard tree file (`<hash>.obao`)** alongside the blob. Because Bao encodes the intermediate 64-byte parent chaining values of BLAKE3's binary tree without duplicating the leaf data, encoding a 1,000,000-byte file produces a 1,062,472-byte Bao stream (~6.25% overhead at 1 KiB chunk resolution, or smaller with 64 KiB chunk groups) and allows clients to extract and verify arbitrary byte ranges (`SliceExtractor::new_outboard`) against the root hash while streaming.

### 2.2 Global Cache Directory Layout (`~/.corex/cache/`)

All downloaded registry indices, transparency log tiles, package trees, and file content blobs reside under a single machine-wide directory (`$COREX_HOME/cache`, defaulting to `~/.corex/cache` on Linux/macOS and `%LOCALAPPDATA%\corex\cache` on Windows). Files inside `blobs/` and `trees/` are sharded using a two-level hex prefix (`<h[0..2]>/<h[2..4]>/<h[0..64]>`) to cap directory fan-out at ≤256 subdirectories per level across `ext4`, `APFS`, `XFS`, and `NTFS`:

| Cache Subdirectory Path | Stored Artifact Type | Mutability & OS Permissions | Purpose in Build & Resolution Pipeline |
| :--- | :--- | :--- | :--- |
| `blake3/blobs/<aa>/<bb>/<64-hex>` | Raw uncompressed file content blob (`file_blake3`) | **Immutable Read-Only** (`0444` / `FILE_ATTRIBUTE_READONLY`) | Mapped directly into `corexc` `SourceMap` via `BumpArena` read or `mmap` / `CreateFileMapping`; deduplicated across all package versions and projects[cite: 2]. |
| `blake3/blobs/<aa>/<bb>/<64-hex>.obao` | Bao outboard Merkle tree nodes for files `≥64 KiB` | **Immutable Read-Only** (`0444`) | Enables streaming slice verification (`bao decode-slice`) without reading the entire blob. |
| `blake3/trees/<cc>/<dd>/<64-hex>.cxtree` | Canonical Binary Package Manifest (`tree_blake3`) | **Immutable Read-Only** (`0444`) | Maps a locked package's `tree_blake3` to its sorted array of `(rel_path, size, file_blake3)` entries in $O(1)$ via `mmap`[cite: 2]. |
| `blake3/staging/<pid>-<tid>-<nonce>.tmp` | In-flight download and hash-verification scratch files | Read-Write (`0600`, process-isolated) | Receives streamed bytes while computing BLAKE3; atomically renamed into `blobs/` or `trees/` only after digest match. |

| `locks/gc.lock` & `locks/index-<hash>.lock` | Advisory OS lock files (`flock` / `LockFileEx`) | Read-Write (`0600`) | Coordinates concurrent `corex` processes and `corex cache gc`. |

> **Visual — BLAKE3 Content-Addressable Store and Zero-Copy Compiler VFS Mapping:** **Tier 1 (Acquire & Verify):** Concurrent HTTP/2 streams verify BLAKE3 chunks in staging before atomic rename. **Tier 2 (Global CAS):** Deduplicated blobs and binary `.cxtree` manifests eliminate cross-project file copies. **Tier 3 (Zero-Copy VFS):** `corexc` maps cached blobs directly into deterministic `FileId(u32)` slots via `BumpArena` (<16 KiB) or OS `mmap` (≥16 KiB).

### 2.3 Concurrent Multi-Process File Locking & Atomic Cache Writes

When an IDE language server (`corex lsp`), a background test runner (`corex test`), and a CLI build (`corex build`) execute simultaneously on the same workstation—or when parallel CI jobs share a mounted host cache—multiple processes may attempt to fetch and write the exact same package or blob concurrently[cite: 2]. CoreX prevents race conditions and partial-write corruption by combining a **Lock-Free Content-Addressed Atomic Rename Protocol** with **Two-Tier Advisory Locking (`flock` on POSIX, `LockFileEx` on Windows)**.

Because the filename of every object inside `blake3/blobs/` and `blake3/trees/` is its cryptographic BLAKE3 digest, two processes writing the same target filename are guaranteed to be writing byte-for-byte identical content. Consequently, populating `blobs/` and `trees/` requires zero per-file locks and proceeds in four deterministic steps:
1. **Process-Unique Staging:** The worker opens a scratch file in `~/.corex/cache/blake3/staging/<pid>-<tid>-<monotonic_seq>.tmp` on the exact same filesystem mount as `blake3/blobs/` and `blake3/trees/` so that the subsequent `rename` never crosses a mount point (`EXDEV`).
2. **Streaming BLAKE3 Verification:** As chunks arrive from the network or archive decompressor, the worker updates its incremental BLAKE3 state while writing to the `.tmp` file. If the finalized `file_blake3` (or `tree_blake3`) diverges from the expected digest in `.cxtree` or `corex.lock`, the worker immediately `unlink`s the `.tmp` file and aborts with `E_CACHE_HASH_MISMATCH`.
3. **Read-Only Permission Hardening:** Prior to publication, the worker strips write permissions (`fchmod(fd, 0444)` on POSIX; `SetFileAttributesW(..., FILE_ATTRIBUTE_READONLY)` on Windows) and flushes dirty pages (`fdatasync` / `FlushFileBuffers`) so no external editor or plugin can mutate cached blobs in place.
4. **Atomic Rename Commit:** On POSIX (`Linux`, `macOS`, `BSD`), `rename(staging_path, final_blob_path)` atomically replaces any existing directory entry in the kernel VFS. On Windows, CoreX invokes `MoveFileExW(staging_path, final_blob_path, MOVEFILE_REPLACE_EXISTING)`. If Windows returns `ERROR_ACCESS_DENIED` or `ERROR_SHARING_VIOLATION` because another `corexc` process has already committed and memory-mapped `final_blob_path`, the writer verifies that `final_blob_path` exists with the expected byte size, treats the commit as an idempotent success, and removes its redundant `staging_path`.

To coordinate garbage collection (`corex cache gc`) and mutable sparse index updates without blocking concurrent readers, every running `corexc` compiler or `corex` CLI process acquires a non-blocking **shared reader lock** on `~/.corex/cache/locks/gc.lock` via `flock(fd, LOCK_SH)` on POSIX or `LockFileEx(hFile, 0, 0, 1, 0, &overlapped)` on Windows. Conversely, `corex cache gc` requests an **exclusive writer lock** (`LOCK_EX | LOCK_NB` / `LOCKFILE_EXCLUSIVE_LOCK | LOCKFILE_FAIL_IMMEDIATELY`), ensuring that no blob is ever unlinked while a compilation is actively reading or memory-mapping it.

### 2.4 Zero-Copy VFS Mapping (`VfsSourceMap`) and `FileId(u32)` Determinism

Rather than materializing per-project `node_modules` or `vendor` copies on disk, `corexc` embeds a **Content-Addressable Virtual File System (`VfsSourceMap`)** modeled on `rustc_span::SourceMap`'s `FileLoader` and `FilePathMapping` abstractions paired with `DR-01`'s Data-Oriented `u32` handles[cite: 2]. For each resolved package in `corex.lock`, `corexc` memory-maps `~/.corex/cache/blake3/trees/<c1>/<c2>/<tree_blake3>.cxtree`, which begins with a fixed 32-byte `CxTreeHeader` followed by a contiguous array of 48-byte `CxTreeEntry` records (`rel_path_off: u32`, `rel_path_len: u16`, `file_mode: u16`, `file_size: u64`, `file_blake3: [32]u8`) pre-sorted in UTF-8 order. Resolving `use serde_json::parser::tape;` (`src/parser/tape.cx`) inside `serde-json` performs a zero-allocation binary search over the `.cxtree` table in $O(\log K)$ time and extracts `file_blake3` directly.

Once `VfsSourceMap` resolves a module to its `file_blake3` and `file_size`, it loads the source bytes from `~/.corex/cache/blake3/blobs/<b1>/<b2>/<file_blake3>` using a size-adaptive strategy at the **`16 KiB` (`16,384-byte`) threshold**[cite: 2]. For small source files (`file_size < 16 KiB`), issuing individual `mmap` and `munmap` syscalls per file would fragment kernel virtual memory descriptors (`vm_area_struct`); instead, `VfsSourceMap` allocates a contiguous slice inside `corexc`'s deterministic **64 KiB `BumpArena`** (`DR-01`) with a trailing NUL byte (`0x00` sentinel for branchless lexer scanning) and populates it via a single `pread` / `ReadFile` call[cite: 2]. For medium and large source files (`file_size ≥ 16 KiB`, up to the `4 GiB` `u32` limit), `VfsSourceMap` maps the read-only blob directly into virtual memory (`mmap(NULL, size, PROT_READ, MAP_PRIVATE, fd, 0)` on POSIX; `CreateFileMapping` + `MapViewOfFile` on Windows)[cite: 2]. This split also eliminates a classic `mmap` hazard noted in `rustc` and SQLite: if a file is truncated on disk while mapped, accessing the mapped region raises a fatal `SIGBUS` signal. Because blobs in `~/.corex/cache/blake3/blobs/` are immutable (`0444`) and protected by `gc.lock`, they are never truncated in place; meanwhile, mutable workspace source files (`src/*.cx` in the developer's working directory) are always read into the `BumpArena` via `pread` and hashed on load, preventing concurrent editor saves from triggering `SIGBUS` during `corex lsp` or `corex build`[cite: 2].

To uphold `DR-01`'s bit-for-bit compiler reproducibility (`Stage 3 === Stage 4`), `FileId(u32)` assignments and global `BytePos(u32)` spans must remain independent of OS thread scheduling jitter and the host machine's filesystem layout[cite: 2]. Before spawning parallel `AstGen` worker threads, `corexc` sorts all resolved packages in `corex.lock` by `(name, version, tree_blake3)` and pre-allocates contiguous `FileId(u32)` handles in strict lexicographical `(PackageId, relative_path)` order[cite: 2]. Each `FileId` stores both its physical cache path and a canonical `VirtualPath` formatted as `/cx/<pkg_name>@<version>/<rel_path>` (for example, `/cx/serde-json@1.4.2/src/tape.cx`)[cite: 2]. All compiler `__FILE__` expansions, DWARF `DW_AT_comp_dir` attributes, and PDB line tables emit the canonical `/cx/...` virtual path, while CLI error diagnostics translate spans back to clickable local paths on demand[cite: 2].

#### Concrete Zig Stage-0 / Self-Hosted `.cx` `VfsSourceMap` Layout (`stage0/src/vfs_sourcemap.zig`)
Aligning directly with `stage0/src/mem_foundation.zig` from `DR-01`[cite: 2]:

```zig
//! CoreX Stage-0 Compiler (`stage0/corex`)
//! Module: Content-Addressable Zero-Copy Virtual File System (`VfsSourceMap`)
//! Maps ~/.corex/cache/blake3/ blobs directly into deterministic FileId(u32) slots.

const std = @import("std");
const assert = std.debug.assert;
const mem_foundation = @import("mem_foundation.zig");
const BumpArena = mem_foundation.BumpArena;
const StringId = mem_foundation.StringId;

/// Canonical 32-bit handle for a source file in the compilation graph.
/// Pre-assigned deterministically in lexicographical (PackageId, relative_path) order.
pub const FileId = enum(u32) {
    none = std.math.maxInt(u32),
    _,

    pub inline fn toU32(self: FileId) u32 {
        assert(self != .none);
        return @intFromEnum(self);
    }
};

/// Canonical 16-bit handle for a resolved package in `corex.lock`.
pub const PackageId = enum(u16) {
    root_workspace = 0,
    std_lib = 1,
    none = std.math.maxInt(u16),
    _,
};

/// Binary layout of ~/.corex/cache/blake3/trees/<c1>/<c2>/<tree_blake3>.cxtree
pub const CxTreeHeader = extern struct {
    magic: [4]u8 = .{ 'C', 'X', 'T', 'R' },
    version: u32 = 1,
    entry_count: u32,
    string_table_bytes: u32,
    pkg_name_str_off: u32,
    _reserved: [12]u8 = [_]u8{0} ** 12,
};

pub const CxTreeEntry = extern struct {
    rel_path_off: u32,
    rel_path_len: u16,
    file_mode: u16, // 0x01 = regular, 0x02 = executable
    file_size: u64,
    file_blake3: [32]u8,
};

pub const BackingKind = enum(u8) {
    unloaded = 0,
    /// Used for all mutable workspace files and cached blobs < 16 KiB
    arena_slice = 1,
    /// Used for immutable read-only cached blobs >= 16 KiB
    os_mmap = 2,
};

pub const VfsFileEntry = struct {
    pkg_id: PackageId,
    /// Canonical hermetic path emitted into DWARF/PDB & __FILE__:
    /// e.g. "/cx/serde-json@1.4.2/src/tape.cx" or "src/main.cx"
    virtual_path: StringId,
    /// Expected 32-byte BLAKE3 digest from .cxtree (or computed on load for workspace files)
    expected_blake3: [32]u8,
    file_size: u32,
    /// Global starting BytePos offset in the monotonic SourceMap span space
    start_byte_pos: u32,
    backing_kind: BackingKind = .unloaded,
    bytes_ptr: ?[*]const u8 = null,
};

pub const VfsSourceMap = struct {
    /// Files < 16 KiB are read into `arena`; files >= 16 KiB are read-only mmap'd
    pub const MMAP_THRESHOLD_BYTES: u32 = 16 * 1024;

    arena: *BumpArena,
    cache_root_dir: std.fs.Dir,
    /// Struct-of-Arrays (SoA) storage indexed directly by `FileId(u32)`
    files: std.MultiArrayList(VfsFileEntry) = .{},
    next_global_byte_pos: u32 = 1,

    /// Registers a file slot deterministically prior to parallel AstGen.
    pub fn registerFileSlot(
        self: *VfsSourceMap,
        gpa: std.mem.Allocator,
        pkg_id: PackageId,
        virtual_path: StringId,
        file_size: u64,
        expected_blake3: [32]u8,
    ) !FileId {
        if (file_size > std.math.maxInt(u32) - 1) return error.FileTooLarge;
        const size_u32: u32 = @intCast(file_size);
        const start_pos = try std.math.add(u32, self.next_global_byte_pos, 0);
        // Reserve size + 1 byte for trailing NUL sentinel
        self.next_global_byte_pos = try std.math.add(u32, start_pos, size_u32 + 1);

        const id: u32 = @intCast(self.files.len);
        try self.files.append(gpa, .{
            .pkg_id = pkg_id,
            .virtual_path = virtual_path,
            .expected_blake3 = expected_blake3,
            .file_size = size_u32,
            .start_byte_pos = start_pos,
        });
        return @enumFromInt(id);
    }

    /// Loads or memory-maps an immutable blob from ~/.corex/cache/blake3/blobs/<b1>/<b2>/<hex>
    pub fn getOrMountCachedBlob(self: *VfsSourceMap, id: FileId) ![]const u8 {
        const idx = id.toU32();
        const slice = self.files.slice();
        if (slice.items(.backing_kind)[idx] != .unloaded) {
            const ptr = slice.items(.bytes_ptr)[idx].?;
            return ptr[0..slice.items(.file_size)[idx]];
        }

        const digest = slice.items(.expected_blake3)[idx];
        const hex = std.fmt.bytesToHex(digest, .lower);
        var rel_buf: [80]u8 = undefined;
        const blob_rel_path = try std.fmt.bufPrint(
            &rel_buf,
            "blake3/blobs/{s}/{s}/{s}",
            .{ hex[0..2], hex[2..4], hex[0..64] },
        );

        const file = try self.cache_root_dir.openFile(blob_rel_path, .{ .mode = .read_only });
        defer file.close();

        const size = slice.items(.file_size)[idx];
        if (size < MMAP_THRESHOLD_BYTES) {
            const buf = try self.arena.allocBytesAligned(size + 1, 1);
            const n_read = try file.preadAll(buf[0..size], 0);
            if (n_read != size) return error.TruncatedCacheBlob;
            buf[size] = 0; // NUL sentinel for branchless lexer
            slice.items(.bytes_ptr)[idx] = buf.ptr;
            slice.items(.backing_kind)[idx] = .arena_slice;
            return buf[0..size];
        } else {
            const mapped = try std.posix.mmap(
                null,
                size,
                std.posix.PROT.READ,
                .{ .TYPE = .PRIVATE },
                file.handle,
                0,
            );
            slice.items(.bytes_ptr)[idx] = mapped.ptr;
            slice.items(.backing_kind)[idx] = .os_mmap;
            return mapped[0..size];
        }
    }
};

comptime {
    assert(@sizeOf(FileId) == 4);
    assert(@sizeOf(PackageId) == 2);
    assert(@sizeOf(CxTreeHeader) == 32);
    assert(@sizeOf(CxTreeEntry) == 48);
}
```

## 3. Deliverable 3: Dependency Resolution Algorithm and Offline/Hermetic Build Protocol

### 3.1 Formal Comparison: Minimal Version Selection (MVS) vs. PubGrub in the Package Calculus

To design a dependency resolver that is simultaneously **fast, deterministic, and transparent upon failure**, we ground our evaluation in the **Package Calculus**[cite: 3]. Formally, let $N$ be the set of package names, $V$ be the totally ordered set of versions for each name under Semantic Versioning ($\le_v$), and $R \subseteq N \times V$ be the universe of available package versions $p = (n, v)$[cite: 3]. A dependency relation $\Delta \subseteq (N \times V) \times (N \times \mathcal{P}(V))$ maps each package $p$ to its required dependency sets $p \Delta (n', \llbracket \phi \rrbracket_{n'})$, where $\llbracket \phi \rrbracket_{n'} = \{ v \in V_{n'} \mid v \text{ satisfies formula } \phi \}$[cite: 3]. Given a root package $r \in R$, a valid resolution $S \subseteq R$ must satisfy three conditions[cite: 3]:
1. **Root Inclusion:** $r \in S$[cite: 3].
2. **Dependency Closure:** $\forall p \in S.\; p \Delta (n, V') \implies \exists v \in V'.\; (n, v) \in S$[cite: 3].
3. **Version Uniqueness (within a compatibility namespace):** $\forall (n, v), (n, v') \in S.\; v = v'$[cite: 3].

As shown by Russ Cox (2016) and formalized in the Package Calculus via polynomial-time reduction from 3-SAT, deciding whether a valid resolution $S \in \mathcal{S}(\Delta, r)$ exists under general upper-and-lower version constraints ($\ge, <, \ne$) and single-version uniqueness is **NP-complete**[cite: 3]. Real-world package managers navigate this complexity boundary using two distinct strategies: **Go's Minimal Version Selection (MVS)** and **Weizenbaum's PubGrub (Conflict-Driven Clause Learning)**[cite: 3].

| Architectural Dimension | Minimal Version Selection (MVS — Go) | PubGrub CDCL Solver (Dart `pub`, `uv`, SwiftPM, Cargo) | **CoreX Hybrid (`Bounded-MVS + PubGrub`)** |
| :--- | :--- | :--- | :--- |
| **Version Constraint Expressivity** | Lower bounds only: $p \Delta_{\min}(n, v)$ requires $v' \ge_v v$ within the same major version[cite: 3]. | Arbitrary version ranges & intervals ($\ge, <, =, \ne$, unions of disjoint ranges)[cite: 3]. | **Default:** MVS lower bounds (`"1.4.2"` $\equiv$ `>=1.4.2, <2.0.0`). **Opt-in:** Root `[resolution].exclude` & security upper bounds[cite: 3]. |
| **Version Selection Policy** | **Oldest (Minimal)** version that satisfies all lower bounds: $v_{\text{sel}} = \max \{ v_i \mid p_i \Delta_{\min}(n, v_i) \}$[cite: 3]. | **Newest (Maximal)** available version in the registry at the moment of resolution. | **Deterministic Minimal Selection (MVS)** during normal builds; explicit `corex upgrade` advances bounds. |
| **Time Complexity** | **$O(\|\Delta_{\min}\| + \|R\|)$ linear graph traversal** (zero backtracking)[cite: 3]. | **NP-complete worst case**; fast in practice via CDCL unit propagation & backjumping (reported as 8–10x faster than `pip` cold in `uv` documentation)[cite: 3]. | **$O(\|\Delta_{\min}\| + \|R\|)$ fast path** on standard graphs; invokes **PubGrub** only when exclusions/upper bounds trigger a conflict[cite: 3]. |
| **Reproducibility Without Lockfile** | **High-Fidelity:** Publishing a new upstream version `1.5.0` never alters a build that only requires `1.4.2`. | **Time-Dependent Drift:** Without a lockfile, resolving today vs. tomorrow pulls different newest versions. | **Deterministic** both with and without `corex.lock` (MVS invariant preserved). |
| **Conflict Failure UX** | Basic conflict error (occurs if an explicit `exclude` removes versions $\ge v_{\max}$). | **Human-Readable Proof Tree:** Derives root-cause incompatibility via logical resolution and explains failure in plain English. | **Full PubGrub Proof-Tree Diagnostics** whenever version constraints, exclusions, or `corex` toolchain bounds conflict. |

> **Visual — Hybrid MVS Fast-Path Resolution and PubGrub Conflict Derivation Architecture:** **Panel 1:** MVS deterministically selects the maximum of stated lower bounds (`v1.4.2`) without consulting newer unrequested registry releases (`v1.6.0`). **Panel 2:** When a security exclusion or upper bound causes a conflict, PubGrub combines incompatibilities via logical resolution to emit a human-readable proof tree. **Panel 3:** Coexisting major versions and additive feature sets unify cleanly in a single pass.

### 3.2 Why CoreX Combines MVS with PubGrub Conflict Resolution

Evaluating MVS and PubGrub in detail shows that their operational strengths and limitations are complementary. In Go Modules, every dependency requirement `pkg vX.Y.Z` specifies only a minimum compatible version within that major version series[cite: 3]. Because upper bounds are omitted in `go.mod`, any version $v' \ge \max_i(v_i)$ satisfies all requirements simultaneously[cite: 3]. Constructing the build list requires no backtracking: the resolver initializes list $L$ with the root module's requirements, recursively appends transitive requirements via graph traversal, and retains the highest version seen for each module path ($v_{\text{selected}} = \max(v_1, \dots, v_k)$, which is the minimum version that satisfies all lower bounds). Under MVS, if a project requires `serde-json = "1.4.0"` and a transitive dependency requires `serde-json = "1.4.2"`, the resolver deterministically selects `1.4.2` even if `1.5.0` and `1.6.0` are published to the registry later. However, pure MVS exhibits friction in two scenarios: when a transitive dependency `v1.4.2` introduces a regression or security vulnerability and `v1.4.3` is not yet released, downgrading `v1.4.2` to `v1.4.1` requires cascading downgrades of every intermediate parent package that required `>= 1.4.2` (or `[resolution].exclude` rules); and when exclusions, minimum toolchain `corex = "1.1"` bounds, or target constraints conflict, a simple graph traversal cannot explain why resolution failed or automatically search non-excluded downgrade combinations.

Designed by Natalie Weizenbaum (2018) and adopted by Dart's `pub`, Python's `uv` and `Poetry`, Swift Package Manager, Elixir's `Hex`, and Ruby's `Bundler`, **PubGrub** represents all dependency rules and conflicts as **Incompatibilities**—sets of **Terms** (positive or negative version intervals, such as `{menu >=1.1.0, not dropdown >=2.0.0}`, meaning `menu >=1.1.0` depends on `dropdown >=2.0.0`) that cannot be simultaneously satisfied. PubGrub maintains a chronological `PartialSolution` distinguishing *decision assignments* from *derived assignments*. During **Unit Propagation**, whenever all terms in an incompatibility except one ($t$) are satisfied by the `PartialSolution`, PubGrub derives the negation $\neg t$ and propagates it until reaching a fixpoint. When unit propagation encounters an incompatibility where *every* term is satisfied by the `PartialSolution`, **Conflict Resolution** iteratively combines the conflicting incompatibility with the antecedent incompatibility that derived its most recent term using the logical resolution inference rule:
$$\frac{\{S, T\} \quad \{U, \neg T\}}{\{U, S\}}$$
This step repeats until it produces a **root-cause incompatibility** satisfied by an earlier decision level, allowing the solver to backjump directly to that level and learn the new incompatibility clause so the conflicting subspace is pruned. If conflict resolution reaches decision level `0` (meaning the root package itself is incompatible), PubGrub walks the binary Directed Acyclic Graph (DAG) of derived incompatibilities from leaf requirements to the root conflict, folding linear chains and numbering branched sub-proofs to emit a human-readable explanation.

### 3.3 The CoreX Two-Phase Hybrid Resolution Algorithm

CoreX combines both mechanisms into a deterministic two-phase resolver:
1. **Phase 1 — Major-Version Namespace Partitioning:** Following the Package Calculus concurrent-version reduction, CoreX partitions package identities by their **Compatibility Series Key**:
   $$\text{SeriesKey}(n, v) = \begin{cases} (n, \text{major}(v)) & \text{if } \text{major}(v) \ge 1 \\ (n, 0, \text{minor}(v)) & \text{if } \text{major}(v) = 0 \;\text{(SemVer } 0.y.z \text{ initial development)} \end{cases}$$
   Unlike Go—which requires library authors to hardcode `/v2`, `/v3` suffixes into internal import paths (`import "github.com/org/pkg/v2/sub"`)—CoreX performs **Automatic Compiler Symbol Mangling by `(SeriesKey, tree_blake3)`** (analogous to Cargo's `ActivationsKey`)[cite: 3]. Library authors do not need to rewrite internal `use pkg::...;` paths when releasing `v2.0.0`, and downstream applications can link both `corex-http` `v1.9.4` and `v2.1.0` in the same binary[cite: 3].
2. **Phase 1 — Bounded-MVS Fast Path & Feature Unification ($O(|\Delta_{\min}| + |R|)$):** The resolver initializes worklist $Q$ and map $\text{Selected}: \text{SeriesKey} \to (\text{Version}, \mathcal{P}(\text{Feature}))$ with the root package's dependencies[cite: 3]. It pops `(series_key, req_min_ver, req_features)` from $Q$ in lexicographical order, updates $v_{\text{cur}} \leftarrow \max(v_{\text{cur}}, \text{req\_min\_ver})$, and unifies features via set union $F_{\text{cur}} \leftarrow F_{\text{cur}} \cup \text{req\_features}$ (implementing the Package Calculus product construction $(n, (v, F))$ over $R' = N \times (V \times \mathcal{P}(\text{Features}))$)[cite: 3]. Whenever $v_{\text{cur}}$ increases or $F_{\text{cur}}$ gains a feature, the resolver reads the sparse index entry for $(n, v_{\text{cur}})$ and enqueues its newly activated dependencies into $Q$[cite: 3]. If no selected version violates a `[resolution].exclude` rule, a toolchain `corex` version bound, or a native `links = "..."` C-library uniqueness constraint, Phase 1 finishes and writes `corex.lock`.
3. **Phase 2 — PubGrub Conflict-Driven Fallback & Upgrade/Downgrade Solver:** If Phase 1 hits a violated `[resolution].exclude` directive, an upper bound, or an explicit `corex downgrade pkg@vX.Y.Z` invocation, the resolver encodes the visited package series into PubGrub `Incompatibility` records, ordering candidate versions within each `SeriesKey` in ascending MVS preference order $\ge v_{\min}$ (or descending order below the target ceiling during `corex downgrade`). If PubGrub finds a satisfying assignment that routes around the excluded version (for example, advancing `corex-tls` from excluded `0.8.1` to `0.8.2`), it commits that resolution to `corex.lock`; otherwise, it traverses the root-cause incompatibility DAG and emits a plain-English conflict trace.

#### Handling Diamond Dependencies, Feature Flags, and Local Path Overrides
When a diamond dependency occurs within the **same major series** (`A -> B -> D@1.2.0` and `A -> C -> D@1.4.2`), CoreX unifies `D` to a single instance `D@1.4.2` via MVS $\max(1.2.0, 1.4.2) = 1.4.2$ with unified feature set $F_B \cup F_C$[cite: 3]. When a diamond spans **different major series** (`A -> B -> D@1.4.2` and `A -> C -> D@2.0.1`), both `D@1.4.2` and `D@2.0.1` coexist in the build graph under distinct mangled symbols (`_CX7D_v1_...` and `_CX7D_v2_...`), and if `B` publicly re-exports a type from `D@1.4.2` that `A` passes to `C` expecting `D@2.0.1`, `corexc` emits a targeted cross-major diagnostic citing both versions in `corex.lock`[cite: 3]. Feature flags in `[features]` must be **strictly additive** (enabling a feature may add `pub` items, trait implementations, or optional dependencies, but must not remove public items or alter method signatures) so that the feature union $(n, (v, F_1 \cup F_2))$ always compiles[cite: 3]. Finally, `[patch]` directives in the **root workspace `corex.toml`** override any matching `(name, SeriesKey)` across the entire transitive graph with a local `path` or `git` fork, while `[patch]` tables inside non-root transitive dependencies are ignored so top-level application owners retain authority over their dependency graph.

### 3.4 Static Git/HTTP Sparse Registry Protocol & Cryptographic Supply-Chain Security

To eliminate the clone overhead of monolithic Git registry indices while enabling static hosting on GitHub Pages, S3/R2 object storage, or corporate artifact proxies, CoreX adopts an **RFC 2789 Sparse HTTP Registry Protocol** paired with a **Tile-Based Transparency Log (`sum.corex.dev`)**.

At the root of the registry (`GET /config.json`), the server provides the download URL template (`"dl"`), API endpoint (`"api"`), transparency log URL (`"tlog"`), and whether private authentication headers are required (`"auth-required"`):

```json
{
  "dl": "https://pkg.corex.dev/blobs/{prefix}/{crate}/{version}/{archive_blake3}.cxpkg",
  "api": "https://registry.corex.dev",
  "tlog": "https://sum.corex.dev",
  "auth-required": false
}
```

Following Cargo's RFC 2789 specification, the client substitutes `{crate}`, `{version}`, `{prefix}`, `{lowerprefix}`, and `{archive_blake3}` into `"dl"` to construct the immutable CDN download URL, and maps any ASCII `kebab-case` package name of length `L` to its canonical lowercase index file path (`IndexPathFor`):

| Package Name Length (`L`) | Sparse Index Relative Path Rule | Canonical Examples |
| :--- | :--- | :--- |
| **`L = 1`** | `1/{name}` | `1/x` |
| **`L = 2`** | `2/{name}` | `2/ui` |
| **`L = 3`** | `3/{name[0..1]}/{name}` | `3/t/tcp` |
| **`L ≥ 4`** | `{name[0..2]}/{name[2..4]}/{name}` | `se/rd/serde-json`, `co/re/corex-http` |

Each non-blank line in a package's sparse index file (`se/rd/serde-json`) is a newline-delimited JSON (NDJSON) object recording one published version's dependencies, features, BLAKE3 digests, publisher Ed25519 signature, and transparency log index:

```json
{"name":"serde-json","vers":"1.4.2","corex":"1.0.0","deps":[{"name":"corex-simd","req":"0.3.0","features":["avx2"],"optional":true,"default_features":true,"target":"cfg(target_arch = 'x86_64')","kind":"normal"}],"archive_blake3":"2233445566778899aabbccddeeff00112233445566778899aabbccddeeff0011","tree_blake3":"1679091c5a880faf6fb5e6087eb1b2dc2233445566778899aabbccddeeff0011","features":{"default":["alloc"],"alloc":[],"simd-tape":["dep:corex-simd"]},"yanked":false,"pub_key":"ed25519:cxpub_7c6d5e4f3a2b1c0d","sig":"fedcba9876543210...","tlog_idx":13890112}
```

To protect against registry compromises, mutable Git tags, and targeted split-view attacks, CoreX enforces three cryptographic checks before any external `.cx` file is mounted into `VfsSourceMap`:
1. **Content-Addressed BLAKE3 Tree & Archive Pinning:** Every downloaded package is verified against both `archive_blake3` (over the compressed `.cxpkg` stream) and `tree_blake3` (recomputed over the `.cxtree` manifest and individual `file_blake3` blobs). Even if an upstream repository owner deletes and re-creates a Git tag `v1.0.0` pointing to a different commit, any project with `corex.lock` rejects the mutated tree (`tree_blake3` mismatch).
2. **Tile-Based Transparency Log Verification (`sum.corex.dev`):** To protect developers resolving a package version for the first time, `sum.corex.dev` maintains an append-only RFC 6962 binary Merkle tree (`0x00` leaf prefix, `0x01` internal node prefix) of canonical `(pkg_identity, version, tree_blake3, pub_key, sig)` records served as static height-8 Merkle tiles (`/tile/8/<level>/<index>`). When `corex` adds a new dependency, it verifies an $O(\log N)$ **Merkle Inclusion Proof** against the signed tree head (`checkpoint`) and an $O(\log N)$ **Merkle Consistency Proof** confirming that the new tree is an append-only extension of the client's previously cached checkpoint in `~/.corex/cache/tlog/` (with support for `c2sp.org/tlog-witness` co-signatures to prevent split-view logs).
3. **Publisher Ed25519 Signature Verification:** During `corex publish`, the author signs `"corex-publish-v1\n" || name || "\n" || version || "\n" || tree_blake3` with their Ed25519 key. Both `publisher_key_id` and `publisher_sig` are recorded in the sparse index, transparency log, and `corex.lock`.

### 3.5 Offline, Frozen, and Hermetic Build Protocol

For air-gapped environments, Linux distribution builders (Debian, Gentoo, GNU Guix, Nix), and hermetic monorepos (`DR-01`), CoreX provides five explicit build and vendoring modes[cite: 2]:

| CLI Flag / Command | Network Access | `corex.lock` Mutation | Primary Use Case & Verification Behavior |
| :--- | :--- | :--- | :--- |
| **`corex build` / `corex run`** *(Default)* | Allowed (on cache miss) | Allowed (if `corex.toml` changed) | Interactive local development; auto-synchronizes new `corex.toml` entries and downloads missing `~/.corex/cache/blake3/` blobs[cite: 1]. |
| **`corex build --locked`** | Allowed (blob fetch only) | **Forbidden** (`E_LOCKFILE_DRIFT`) | Standard CI pipelines; verifies `root_manifest_blake3` matches `corex.toml` and fetches only exact `tree_blake3` blobs pinned in `corex.lock`. |
| **`corex build --offline`** | **Strictly Forbidden** | Allowed (if satisfied by local cache) | Air-gapped development; resolves constraints using only cached sparse index files and blobs already present in `~/.corex/cache/`. |
| **`corex build --frozen`** | **Strictly Forbidden** | **Strictly Forbidden** | Hermetic production & distro builds (`--locked` + `--offline`); zero network calls permitted; fails immediately if any `tree_blake3` or blob is missing locally. |
| **`corex vendor [dir]`** | Allowed during export | Verifies `corex.lock` | Exports all locked `.cxtree` manifests and `blobs/` into `./vendor/blake3/` (with `vendor/modules.toml`) for self-contained source tarballs. |

#### Step-by-Step Hermetic Build Verification Checklist (`corex build --frozen`)
When invoked with `--frozen` (or when `COREX_HERMETIC=1` is set in the environment), `corexc` executes a six-step deterministic verification pipeline:
1. **Network Syscall Sandboxing:** Disable the HTTP/Git transport client subsystem in-process before reading any workspace files.
2. **Manifest-to-Lockfile Integrity Check:** Compute `BLAKE3-256` over the normalized dependency tables of `corex.toml` and assert exact equality with `root_manifest_blake3` in `corex.lock`.
3. **Tree & Blob Presence Verification:** For every `[[package]]` in `corex.lock`, open `<cache_or_vendor>/blake3/trees/<c1>/<c2>/<tree_blake3>.cxtree`. When `--verify-checksums` is passed (analogous to `go mod verify`), recompute `BLAKE3-256` over every referenced blob and `.cxtree` file to confirm zero bit-rot or local tampering.
4. **Canonical `FileId(u32)` Pre-Allocation:** Construct the `VfsSourceMap` in lexicographical `(PackageId, relative_path)` order so every `FileId(u32)` and `BytePos(u32)` span is invariant across host operating systems[cite: 2].
5. **Deterministic Arena & InternPool Execution:** Initialize the 64 KiB zero-filled `BumpArena` (`@memset(mem, 0)`) and `Wyhash(0)`-seeded `StringInterner` (`DR-01`), parsing all mounted VFS blobs in parallel shards and merging in strict `FileId(u32)` order[cite: 2].
6. **Hermetic Codegen & Embedded `lld` Linking:** Export `SOURCE_DATE_EPOCH=0` and `ZERO_AR_DATE=1`, emit `/cx/<pkg>@<ver>/<rel_path>` virtual debug paths (`-no-canonical-prefixes -fdebug-compilation-dir .`), and invoke the in-process `lld::lldMain` linker with deterministic content-hashed build IDs (`--build-id` on ELF, default content-hashed `LC_UUID` on Mach-O, `/Brepro` on Windows PE/COFF)[cite: 2].
