# Optimal Bootstrap Implementation Language and Self-Hosting Architecture for CoreX (.cx)

To achieve **100% self-hosting prior to Version 1.0** while delivering rapid compilation, compile-time path-sensitive memory safety (SAST), and C-level runtime execution speed, CoreX (`corex-lang/corex`) should implement its disposable Stage-0 bootstrap compiler (`stage0/corex`) in **Zig**, paired with a hybrid backend architecture (**self-hosted C99 backend + custom x86_64/AArch64 debug emitter + static LLVM/LLD release backend** via an isolated C++ wrapper). Once the self-hosted `.cx` compiler reaches feature parity prior to v1.0, Stage 0 should be retired in favor of a **committed, Zstandard-compressed `wasm32-wasi` bootstrap seed (`stage1/corex1.wasm.zst`, ~500–650 KB)** executed via a **~4,000-line dependency-free C99 `wasm2c` translator and WASI shim (`bootstrap.c`)**.

This dual architecture resolves the central engineering trade-off of compiler bootstrapping: maximizing **Stage-0 implementation velocity and 1-to-1 translation fidelity** without trapping the project in dual-compiler maintenance or multi-gigabyte binary bootstrap chains. Writing Stage 0 in Zig provides native support for the exact Data-Oriented Design (DoD) idioms that `.cx` itself is designed around – Struct-of-Arrays (`MultiArrayList`) AST/IR storage, non-exhaustive `enum(u32)` index handles with zero-cost sentinel optionals (`0xFFFFFFFF`), explicit `BumpArena` allocators free of lifetime contagion, and turnkey cross-compilation across Linux, macOS, and Windows via `zig build` and `zig cc`. Conversely, while **Rust** (Ranked #2) offers strong algebraic pattern matching for a path-sensitive MIR dataflow verifier, arena-allocating recursive ASTs in Rust introduces pervasive `'a` / `'tcx` lifetime annotations and encourages Rust-specific trait and borrow-checker idioms that create high friction during the 1-to-1 rewrite into `.cx`.

For long-term self-hosting across platforms, Zig's `wasm32-wasi` + `wasm2c` seed architecture outperforms both Nim-style committed C sources (`csources`) and Rust/Go-style version-chained binary releases. As documented by Andrew Kelley during Zig's self-hosting transition, machine-generated C code from a full compiler is target-dependent and balloons to ~80 MiB for a single target, whereas a `wasm32-wasi` compiler built with `-OReleaseSmall` and only its C backend enabled compiles to 2.4 MiB after `wasm-opt` (`637 KB` compressed with `zstd`), requires only **23 WASI Preview 1 syscalls**, drops peak bootstrap RAM usage by roughly **two-thirds** (from 10.3–11.3 GiB down to 3.2–3.8 GiB), and preserves full `git bisect` reproducibility on any host with a C99 compiler. To satisfy strict software supply-chain auditability ("Trusting Trust") for source-only distributions such as Debian and GNU Guix, CoreX can archive the final Stage-0 source commit (`v0.9.0-stage0-anchor`) and maintain a bootstrap interpreter profile to allow Diverse Double-Compiling (DDC) verification from source.

#### Context and Problem Statement

CoreX is a zero-GC, statically typed systems and application language targeting instant compilation, compile-time path-sensitive safety (SAST), and C-level runtime execution speed. Because the entire toolchain must be rewritten in `.cx` prior to v1.0, the Stage-0 compiler (`stage0/corex`) is a **scaffolding artifact** whose architecture must optimize for two outcomes. First, it must enable high-velocity construction of a production-grade compiler architecture featuring arena-allocated Data-Oriented Design (DoD) AST/HIR/MIR tables, a fault-tolerant CST/AST parser usable by the CLI and LSP, and a path-sensitive CFG/bitset static memory verifier. Second, it must minimize translation friction during the self-hosting rewrite, enabling compiler engineers to port Stage-0 modules 1-to-1 into `.cx` without redesigning memory ownership, lifetimes, or control flow, followed by a deterministic, platform-independent bootstrap pipeline after Stage 0 is retired.

#### Decision

1.  **Stage-0 Implementation Language:** Implement `stage0/corex` in **Zig** (specifically targeting Zig 0.14/0.15+ stable conventions). Enforce Data-Oriented Design across all passes: contiguous `MultiArrayList` (Struct-of-Arrays) storage, `u32` non-exhaustive typed index handles (`0xFFFFFFFF` sentinel), an append-only `extra_data: []u32` trail for variable-length payloads, and a custom page-aligned `BumpArena`.
2.  **Backend Code Generation & Linker Strategy:** Implement a **three-tier backend architecture** behind CoreX's Mid-Level IR (MIR). Tier A is a **Self-Hosted C99 Emitter (`-ofmt=c`)**, built first in Stage 0 and ported first to Stage 1 `.cx`, which emits portable, deterministic C99 code to power the `wasm32-wasi` bootstrap pipeline. Tier B is the **Production Optimizing Backend (LLVM + Embedded `lld`)**, which interfaces with static pre-built **LLVM 20–23** and **LLD** archives (`c3lang/llvm-for-c3` model) via a single isolated C++17/20 bridge (`src/corex_llvm.cpp` + `src/corex_llvm.h`, modeled on `zig_llvm.cpp`) that wraps LLVM IR generation and calls `lld::lldMain` in-process for ELF, PE/COFF, Mach-O, and WebAssembly linking. Tier C is a **Fast Debug Backend (Self-Hosted x86_64/AArch64 Direct Emitter)**; because LLVM consumes 85%–98% of unoptimized build times in benchmarks from Odin and C3, CoreX will bypass LLVM in `-O0` / Debug builds using a direct machine-code emitter modeled on Zig 0.15's self-hosted x86_64 backend.
3.  **Post-Stage-0 Self-Hosting Seed Strategy:** Upon achieving Stage-1 `.cx` feature parity, retire `stage0/` from the active build graph and commit a Zstandard-compressed WebAssembly bootstrap binary (`stage1/corex1.wasm.zst`, compiled to `wasm32-wasi` with `-OReleaseSmall` and only the `-ofmt=c` backend enabled) alongside a ~4,000-line C99 `wasm2c.c` translator, `wasi.c` runtime shim, and a ~200-line `bootstrap.c` driver. Tag the final Stage-0 commit (`v0.9.0-stage0-anchor`) to preserve an unbroken, binary-free source bootstrap chain for security auditors and Linux distribution packagers.

## 2. Deep-Dive Engineering Evaluation: Stage-0 Bootstrap Languages

### 2.1 Velocity and Safety of Arena-Allocated AST/HIR/MIR Data Structures

Modern compiler throughput is heavily governed by CPU cache hierarchy utilization rather than raw instruction count. As detailed in compiler microarchitecture analyses (`hiraditya.github.io`), a conventional object-oriented compiler allocates AST nodes individually on the heap and links them via 64-bit pointers – for example, a `BinaryExpr` holding `Expr* lhs` (8 bytes), `Expr* rhs` (8 bytes), `SourceRange` (8–16 bytes), `QualType`, and `Opcode` (1 byte), plus alignment padding. Traversing this pointer tree during semantic analysis creates a **serial dependent load chain**: the CPU cannot compute the memory address of a child node until the parent load completes, collapsing hardware **Memory-Level Parallelism (MLP) toward 1**. Hardware stride prefetchers disengage on irregular heap addresses, forcing the CPU to pay serial cache-miss latencies of a couple of hundred cycles each while utilizing only 1 to 4 bytes of each fetched 64-byte (or 128-byte on Apple Silicon) cache line.

To achieve instant compilation, `stage0/corex` should implement a **Data-Oriented Design (DoD)** pipeline from day one, drawing directly from the architectures of **Zig** (`std.zig.Ast`, `Zir`, `Air`, `InternPool`) and **Carbon** (`Parse::Tree` and `SemIR`). By capping individual source files at 4 GiB (`2^32` bytes), all token offsets, AST links, HIR/MIR instruction references, and interned string/type identifiers can be represented as **32-bit unsigned integers (`u32`)** rather than 64-bit pointers. This halves reference memory (4 bytes vs. 8 bytes), reduces struct alignment requirements from 8 bytes to 4 bytes, and keeps indices stable when backing arrays reallocate or are `memcpy`'d to disk for incremental caching. Furthermore, instead of an Array-of-Structs (AoS) where mixed field sizes introduce alignment padding, Zig's `MultiArrayList(Node)` decomposes each struct field into its own contiguous parallel array (`tags: []u8`, `main_tokens: []u32`, `datas: []Data`). In Mitchell Hashimoto's analysis of Zig's parser (`mitchellh.com`), decomposing a struct with a `u32` (4 bytes) and a `bool` (1 byte) into a `MultiArrayList` removes 3 bytes of padding per element, reducing memory consumption by **37.5%**, while Andrew Kelley reported that applying these DoD refactorings to Zig's tokenizer and AST pipeline yielded a **22% faster wall-clock execution time**. Similarly, Carbon stores its `Parse::Tree` in a flat `llvm::SmallVector` at **12 bytes per parse node** (targeting 8 bytes) and its semantic IR (`SemIR`) as a flat array of **16-byte instructions** with two `InstId` operands, interned `TypeId`s, and `NameId`s.

Evaluating our four candidate languages on implementing this DoD arena foundation highlights clear differences in developer velocity and safety:

-   **Zig:** Zig's standard library and type system were co-designed with its DoD compiler. `std.MultiArrayList(T)` is a built-in generic container that automatically decomposes any struct `T` into parallel field slices. Strongly typed `u32` handles are expressed natively via non-exhaustive enums (`pub const Index = enum(u32) { none = std.math.maxInt(u32), _ };`), providing compile-time type safety (preventing accidental mixing of a `TokenIndex` with a `NodeIndex` or `TypeId`) while occupying 4 bytes even when representing optional values. Arena allocation (`std.heap.ArenaAllocator` or a custom `BumpArena`) takes an explicit `Allocator` value without infecting struct definitions with lifetime parameters.
-   **Rust:** Rust's ownership model introduces noticeable friction for arena-allocated compiler graphs unless carefully sidestepped. As documented in the Oxc JavaScript compiler performance notes (`oxc.rs`), migrating an AST from heap-allocated `Box`/`Vec` nodes (which suffered from sequential `drop` overhead) to the `bumpalo` arena allocator yielded a **~20% performance improvement** (complemented by a **~10% speedup** from boxing >200-byte enum variants down to 16 bytes, and **up to 5% on large files** from shrinking `Span` offsets from `usize` to `u32`). However, the Oxc author noted that allocating the AST inside `bumpalo` took **five attempts** because every AST struct, visitor trait, and compiler pass had to be parameterized with explicit `'a` lifetime annotations. Furthermore, building parent-pointing trees for linting cannot use standard Rust references without violating borrowing rules, prompting Oxc and `rustc` to use integer index vectors (`indextree::Arena` or `rustc_index::IndexVec` / `newtype_index!`).
-   **C (C11/C23):** C23 modernizes C for compiler construction by introducing fixed underlying types for enumerations (`enum NodeTag : uint8_t`, `enum NodeId : uint32_t`), `constexpr`, `nullptr`, `typeof`, `_BitInt(N)`, single-argument `static_assert`, and the `{}` empty initializer (guaranteed by C23 to zero-initialize both fields and alignment padding bits). The C3 compiler (`c3c`) demonstrates that a multi-target systems compiler can be written in C. However, C lacks generic Struct-of-Arrays containers, slice bounds checking, and exhaustive compile-time checking when switching over tagged unions – meaning a missed IR opcode or SAST state can silently corrupt memory.
-   **C++20/23:** As demonstrated by Carbon and Odin, C++20/23 supports compact wrapper types (`Parse::Node` wrapping `int32_t`) and `llvm::SmallVector`. However, C++ lacks built-in Struct-of-Arrays reflection, and standard C++ `std::variant` incurs heavier visitation syntax compared to Zig's `union(enum)` or Rust's `enum`.

### 2.2 Fault-Tolerant Incremental Parser and Path-Sensitive SAST Verifier

CoreX requires a unified frontend architecture capable of serving both batch CLI compilation (`corex build`) and interactive IDE/tooling workflows (`corex lsp`, `corex fmt`, `corex migrate`), followed by a path-sensitive static memory vulnerability verifier (SAST).

#### Fault-Tolerant Incremental Parsing: Red-Green Trees vs. Flat Postorder CSTs

Two fault-tolerant parsing architectures are widely used in modern language toolchains. The first is the **Red-Green Lossless Syntax Tree** (`rowan` in `rust-analyzer` and `JuliaSyntax.jl`), which builds an immutable, reference-counted "green tree" storing every source byte (including whitespace and comments as explicit trivia tokens) with structural sharing across edits, overlaid by transient "red" parent-pointer cursors and a typed AST layer that dynamically traverses child lists. Syntax errors are recovered by wrapping unexpected tokens inside an `Error` node. While well-proven for IDEs, `rust-analyzer` maintainers noted in issue `#17491` that benchmarking `rowan` against a contiguous non-sharing syntax tree library (`syntree`) showed **`rowan` tree construction is twice as slow**, slowing initial workspace loading. Moreover, `rust-analyzer` reparses edited files from scratch on change because parsing a single file is fast; incremental tree sharing primarily serves to stabilize syntax fragments for downstream `Salsa` query memoization. Additionally, `rowan`'s internal header pattern has documented soundness issues under Rust's Stacked Borrows / Tree Borrows aliasing rules.

The second approach – **recommended for CoreX** – is the **Flat Postorder Parse Tree with Explicit State Stack** pioneered by Carbon (`Parse::Tree::Parse`). To avoid recursive descent call-stack limits on deeply nested expressions, Carbon's parser maintains an explicit `state_stack_` of `Parse::State` enums and loops in `Parse::Tree::Parse`, transforming a flat `Lex::TokenizedBuffer` into a contiguous postorder vector of 12-byte `Parse::Node` records with a 1-to-1 correspondence to tokens on valid input. When a syntax error is encountered, the parser emits a diagnostic, replaces the placeholder bracketing node with `InvalidParseStart` (or inserts an `InvalidParse` leaf node with `has_error = true`), skips past the malformed construct using indentation and semicolon heuristics (`context.SkipPastLikelyEnd(...)`, always consuming at least one token to prevent infinite loops), and closes the subtree with `InvalidParseSubtree`. This produces a well-formed, bracketed flat parse tree on broken code with contiguous cache locality, directly supporting round-trip formatting, migration tools, LSP queries, and semantic checking (`SemIR`) without pointer chasing or atomic reference counting.

#### Path-Sensitive Static Memory Vulnerability Verifier (SAST)

Because CoreX is zero-GC and enforces compile-time memory safety (preventing use-after-free, double-free, uninitialized reads, and invalid aliasing), its SAST verifier should operate on a lowered **Mid-Level Intermediate Representation (MIR)** modeled on `rustc`'s `rustc_middle::mir` and `rustc_mir_dataflow` (with potential extensions for compile-time group borrowing as explored in Valen). In this model, the frontend lowers typed HIR into a per-function `MirBody` consisting of a flat array of typed local declarations (`LocalDecl`, where `_0` is the return place, `_1..` are arguments, and the rest are temporaries/user variables) and a flat array of `BasicBlock` nodes indexed by a 32-bit handle (`BasicBlock(u32)`). Each basic block contains a linear sequence of `Statement` records (`Assign`, `StorageLive(Local)`, `StorageDead(Local)`) and ends with a single control-flow `Terminator` (`Goto`, `SwitchInt`, `Call`, `Drop`, `Return`, `Assert`, `Unreachable`). Every program point is uniquely addressed by a compact `Location { block: BasicBlock, statement_index }`.

Path-sensitive verification – tracking whether each local or `MovePath` is initialized, live, moved, or borrowed across branching control flow – is formulated as a forward or backward monotone dataflow analysis (`Analysis` with `GenKill` transfer functions) over **dense bitsets** (`DenseBitSet` backed by arena-allocated `[]u64` words). While Rust's `rustc_mir_dataflow` and `rustc_borrowck` are the canonical reference for this architecture, implementing a worklist fixpoint engine over `[]u64` bitsets in Zig is equally concise: Zig enforces exhaustive compile-time `switch` checking over `StatementKind` and `TerminatorKind` tagged unions while avoiding Rust's lifetime propagation (`Body<'tcx>`, `ResultsCursor<'mir, 'tcx>`) across dataflow cursors.

### 2.3 Backend Code Generators and Embedded Linker Integration

Coupling a new compiler exclusively to LLVM from day one introduces a severe compilation-speed bottleneck and a ~100–150 MiB binary footprint. The table below compares the candidate backends and linkers across CoreX's engineering requirements.

#### Synthesis of Backend and Linker Trade-Offs

Both Christoffer Lernö (author of the C3 compiler) and Ginger Bill (author of Odin) independently reported that in their compilers, lexing, parsing, and semantic analysis account for only **1%–2% of total compile time**, whereas **LLVM codegen and linking consume 85% to 98%+ of total compile time** even in unoptimized (`-O0`) single-threaded builds. Relying solely on LLVM makes sub-second developer turnaround difficult on large projects. By pairing LLVM (for `-O1`/`-O2`/`-O3` release builds) with a self-hosted C backend (for bootstrapping) and a custom direct machine-code emitter (for `-O0` debug builds, where Zig 0.15 reported a **5x debug compile speedup** and a **70.1% wall-time reduction** on `hello.zig`), CoreX achieves both rapid debug iteration and LLVM-grade release optimization.

Neither Cranelift nor QBE can serve as CoreX's primary backend across Windows, macOS, and Linux. Cranelift is written in Rust with no official C API (`wasmtime#1164`), meaning a Stage-0 or Stage-1 compiler not written in Rust must maintain custom `#[no_mangle] extern "C"` FFI wrappers (`craneliftc`). Furthermore, the Rust project's 2025H2 goal document for `rustc_codegen_cranelift` notes that Cranelift reduces codegen time by ~20% (~5% total clean build time) on large projects like Zed and Tauri, but still lacks production-ready Windows support, complete stack unwinding, and full debug info. QBE 1.3 (`c9x.me/compile`), while impressively compact (~8k LOC of C) and reaching 63%–70% of `gcc -O2` on CoreMark, accepts only textual SSA files, emits textual AT&T assembly requiring an external assembler, **omits function inlining entirely** because inlining conflicts with its streaming per-function compilation model, and has limited Windows/DWARF support.

To integrate LLVM and `lld` cleanly without using the official `LLVM-C` bindings directly – which erase C++ type safety into opaque `LLVMValueRef` handles and omit key target, sanitizer, and `lld` driver APIs – CoreX should adopt the **Zig + C3 integration pattern**. First, maintain a dedicated CI repository (`corex-lang/llvm-for-corex`, modeled on `c3lang/llvm-for-c3` and `hylo-lang/llvm-build`) that builds lean, stripped static archives of LLVM + `lld` + `compiler-rt` across Linux (`x86_64`, `aarch64`, `riscv64`), macOS (`x86_64`, `arm64`), and Windows (`x86_64`, `arm64`). Second, isolate all C++ header inclusions inside a single translation unit (`src/corex_llvm.cpp` + `src/corex_llvm.h`, modeled on `zig_llvm.cpp`) that exports a bespoke `extern "C"` API to Zig (in Stage 0) and directly to `.cx` (in Stage 1+), including in-process invocation of `lld::lldMain` for ELF, COFF, Mach-O, and WebAssembly linking.

### 2.4 Cross-Compilation Ergonomics and 1-to-1 Translation into `.cx`

When building `stage0/corex` across Linux, macOS, and Windows hosts, **Zig** provides exceptional operational ergonomics. Because the Zig toolchain bundles Clang, LLD, and cross-platform C/C++ standard library headers, `zig build` can compile both the Zig Stage-0 frontend and the `corex_llvm.cpp` C++ wrapper across all three host OSes from a single build script without requiring developers to configure Visual Studio (`vsvarsall.bat`), Xcode Command Line Tools (`xcrun`), or distro-specific LLVM CMake packages – a capability so effective that the Odin community evaluated `zig c++` specifically to simplify Odin's cross-platform LLVM builds.

Crucially, **Stage 0 exists to be rewritten into `.cx` and retired**. When a Stage-0 compiler is written in Rust, compiler engineers naturally structure passes around Rust-specific mechanisms: `'tcx` lifetime trees, borrow-checker workarounds, trait objects, procedural macros, and Cargo crates. Rewriting that codebase into `.cx` forces an architectural redesign during the port. By contrast, Zig's idioms – explicit `BumpArena` pointers, flat `struct` and tagged `union(enum)` definitions, bounds-checked slices (`[]T`), `defer`/`errdefer` cleanup, and `u32` index handles – map **1-to-1** to a streamlined, zero-GC systems language like CoreX. Every `stage0/*.zig` file can be translated module-for-module into `src/*.cx` with identical struct layouts and control flow.

## 3. Self-Hosting Bootstrap Pipeline and Trust/Reproducibility Chain

### 3.1 Comparative Analysis of Modern Self-Hosted Compiler Bootstrap Strategies

Every self-hosted language faces the "chicken-and-egg" bootstrap problem: if the compiler for version *N* is written in language *L*, what compiles the compiler on a fresh machine or a newly supported CPU architecture? Modern compilers have converged on the patterns compared below.

| Language / Compiler | Current Self-Hosting Status | Bootstrap Seed Mechanism | Cross-Platform & New-Arch Strategy | Supply-Chain & Maintenance Trade-Offs |
| :--- | :--- | :--- | :--- | :--- |
| **Zig** (`0.10+` to `0.15+`) | **100% Self-Hosted** (deleted 80k LOC C++ Stage 1 in Dec 2022) | Committed `stage1/zig1.wasm.zst` (**637 KB**, C backend only) + **4,000 LOC C99 `wasm2c`** + `wasi.c` + `bootstrap.c` (199 LOC). | **Universal from any C99 compiler:** `zig1` emits `zig2.c` targeting the detected `host_triple`. | **Peak RSS dropped from 11.3 GiB to 3.8 GiB**; every Git commit is bisectable; requires updating `zig1.wasm.zst` only when the compiler uses a new language feature. |
| **Rust** (`rustc`) | **100% Self-Hosted** (since 2011; retired OCaml boot) | Downloads pre-compiled **prior beta/stable binary (`stage0` `rustc` + `cargo` + `stage0` `std`)** for version *N* - 1. | Requires cross-compiling a `stage0` binary from an existing host, or running the external C++ **`mrustc`** source bootstrap chain. | Complicates arbitrary `git bisect` without fetching historical binaries; 1.9 GB unpacked source tree; source-only distros (Guix/Gentoo) use `mrustc` (`1.54` / `1.74` / `1.90` jump-points) emitting ~46M LOC of C. |
| **Go** (`gc`) | **100% Self-Hosted** (since Go 1.5; Go 1.4 was C) | **Rolling *N* - 2 Binary Chain:** Go `1.N` requires Go `1.M` (*M* = *N* - 2 rounded down to even: e.g., Go 1.24/1.25 require Go 1.22; Go 1.26 requires Go 1.24). | Cross-compile bootstrap tree via `GOOS=... GOARCH=... ./bootstrap.bash` on an existing Go host, or use `gccgo`. | Pure source bootstrap from C requires chaining `C -> Go 1.4 -> Go 1.17 -> Go 1.20 -> Go 1.22 -> Go 1.24 -> Go 1.26`; Go 1.4 C sources do not support newer targets like `darwin/arm64`. |

### 3.2 Evaluating CoreX's Three Post-Stage-0 Seed Candidates

When CoreX completes its self-hosting rewrite prior to v1.0 and deletes the Zig `stage0/` directory, it must choose how to seed compilation of `src/*.cx`. Comparing the three candidate strategies demonstrates why **Option A (Compressed `wasm32-wasi` Seed + Minimal C99 `wasm2c` + In-Tree `-ofmt=c` Backend)** is the strongest engineering choice.

#### 1. Version-Chained Binary Releases (Rust / Go Model)

Requiring version *N* of `corex` to be compiled by a downloaded binary of version *N* - 1 (as in `rustc`, which recently redesigned its initial bootstrap sequence in May 2025 to download both pre-built beta `rustc` and pre-built beta `std` to eliminate `cfg(bootstrap)` in `std`) or version *N* - 2 (as in Go) introduces three structural liabilities for CoreX. First, it **breaks self-contained Git bisection**: when a developer runs `git bisect` across historical commits, a cached host binary will fail to compile older commits whenever compiler flags, intrinsics, or language syntax shifted. Second, it creates **platform lock-out**: building from source on a new OS or CPU architecture (such as `riscv64` or a BSD variant) is impossible unless a cross-compiled binary seed already exists. Third, it creates **Linux distribution packaging friction**: source-first distributions (Debian, Gentoo, GNU Guix) prohibit opaque binary downloads during package builds, forcing packagers to maintain complex external bootstrap chains such as `mrustc` (which originally stepped through 10 sequential Rust releases from `1.19.0` to `1.28.0` and later added jump-points at `1.54.0`, `1.74.0`, and `1.90.0`, converting `rustc` into ~46 million lines of C).

#### 2. Committed C-Transpilation Sources (`csources` Model)

Maintaining a minimal C-transpilation backend (`-ofmt=c`) inside the self-hosted `.cx` compiler is **essential**, because it enables the bootstrap compiler to emit portable C code without linking the ~100 MiB LLVM library into the bootstrap seed. However, committing the *generated C output* (`corex1.c`) directly to Git (like Nim's `csources` / `csources_v1` repositories) has two major drawbacks. First, it causes **severe repository bloat**: when Zig evaluated compiling its compiler directly to C and committing the result, the single-target generated C file was **80 MiB**. Second, **generated C code is not target-independent**: high-level compilers lowering to C bake target-specific pointer sizes (`32-bit` vs `64-bit`), endianness, struct alignments, and OS header definitions into the emitted C files. As documented in Nim's build guides, `csources` must store separate generated C directories across 8 operating systems and 7+ CPU architectures (`c_code/1_2`, etc.), and adding a new platform requires backporting platform definitions to the frozen `csources` compiler and pushing new generated C trees.

#### 3. Hybrid `wasm32-wasi` Seed + `wasm2c` + `-ofmt=c` Architecture (Recommended)

By compiling the self-hosted `.cx` compiler (with only its `-ofmt=c` backend enabled and LLVM disabled) to **`wasm32-wasi`**, CoreX captures all the benefits of C transpilation while eliminating target dependence and repository bloat. WebAssembly (`wasm32`) provides a single OS- and architecture-agnostic 32-bit little-endian target that benefits from LLVM's `-Oz` (`ReleaseSmall`) optimization passes and Binaryen's `wasm-opt -Oz --enable-bulk-memory`. In Zig's production bootstrap pipeline, this reduced a 250,000-line compiler down to a 2.6 MiB `.wasm` binary, 2.4 MiB after `wasm-opt`, and **637 KB** after `zstd` compression (`stage1/zig1.wasm.zst`); similarly, the Nurl language (`v0.9.3`) achieved a **501,204-byte** `nurlc.wasm` seed with a verified `stage1 === stage2` fixed point at 1,772,342 bytes.

Rather than running `corex1.wasm` in a slow bytecode interpreter or depending on the 60,000-line C++ WABT `wasm2c` tool, CoreX will include a bespoke **~4,000-line C99 `wasm2c.c` translator and `wasi.c` runtime** that omits sandboxing checks and implements only the **23 WASI Preview 1 syscalls** required for file I/O, using strictly standard C `libc` with no POSIX or `windows.h` headers. Crucially, this architecture only requires updating `corex1.wasm.zst` (`corex build update-seed`) when the compiler source code *uses* a newly added language feature or requires a bugfix to compile itself. To address the "Trusting Trust" concern raised by Debian and Guix maintainers regarding binary blobs in source trees, CoreX will: (a) permanently tag the final Zig Stage-0 commit (`v0.9.0-stage0-anchor`) so any auditor can build Stage 0 from source and regenerate `corex1.wasm`, and (b) keep the `dev == .bootstrap` compiler profile restricted so a lightweight third-party AST interpreter (written in C or Lua, as discussed by Andrew Kelley on Ziggit) can interpret `src/main.cx` directly into `corex2.c`, proving `corex1.wasm` contains no hidden logic.

## 4. Concrete Memory and Arena Foundation Blueprint (Deliverable 2)

To ground `stage0/corex` in the recommended bootstrap language (**Zig**) and ensure a direct 1-to-1 translation into `.cx`, this section specifies the exact, byte-accurate memory foundation:
1.  **`BumpArena`**: A deterministic, page-aligned slab bump allocator that **zero-initializes all allocated memory** (preventing uninitialized struct padding bytes from leaking into serialized artifacts) and supports O(1) checkpoints/resets for per-function temporary scratch memory.
2.  **Strongly Typed `u32` ID Handles**: Non-exhaustive `enum(u32)` handles (`StringId`, `TokenIndex`, `NodeIndex`, `MirBlockId`, `MirValueId`, `TypeId`) with `none = 0xFFFF_FFFF` (`std.math.maxInt(u32)`) so optional handles occupy 4 bytes with zero tag overhead, plus a bit-packed 32-bit handle (`PackedOperand`) modeled on Zig's `InternPool.CaptureValue`.
3.  **`StringInterner`**: A contiguous arena-backed UTF-8 byte buffer paired with an `EntryMeta` table and an open-addressed, power-of-two `Wyhash(0)` deduplication hash table, reducing string equality across the compiler to a single 32-bit integer comparison (`a == b`).
4.  **`AstStore` & `ExtraData` Trail**: A Struct-of-Arrays (`MultiArrayList`) node store with an append-only `extra_data: []u32` payload buffer.

```zig
/// Deterministic, page-aligned slab bump allocator.
/// - Standard slabs are 64 KiB (65,536 bytes).
/// - All slabs are deterministically zero-filled (`@memset(0)`) upon allocation
///   to guarantee zero padding entropy if arena structures are serialized.
/// - Supports O(1) `Checkpoint` save/restore for per-function SAST/MIR passes.
pub const BumpArena = struct {
    pub const DEFAULT_SLAB_SIZE: usize = 64 * 1024; // 64 KiB

    /// Intrusive header placed at the start of every allocated slab (32 bytes on 64-bit).
    pub const SlabHeader = extern struct {
        prev: ?*SlabHeader,
        capacity: usize,
        used: usize,
        _pad: usize = 0, // Explicit padding to 32-byte boundary (4 * 8 bytes)
    };

    backing_allocator: Allocator,
    current_slab: ?*SlabHeader = null,
    oversized_head: ?*SlabHeader = null,
    total_bytes_reserved: usize = 0,

    pub const Checkpoint = struct {
        slab: ?*SlabHeader,
        used: usize,
    };

    pub fn init(backing_allocator: Allocator) BumpArena {
        return .{ .backing_allocator = backing_allocator };
    }

    pub fn deinit(self: *BumpArena) void {
        self.freeSlabChain(self.current_slab);
        self.freeSlabChain(self.oversized_head);
        self.* = undefined;
    }

    fn freeSlabChain(self: *BumpArena, head: ?*SlabHeader) void {
        var it = head;
        while (it) |slab| {
            const prev = slab.prev;
            const total_len = @sizeOf(SlabHeader) + slab.capacity;
            const raw_ptr: [*]align(16) u8 = @ptrCast(@alignCast(slab));
            self.backing_allocator.free(raw_ptr[0..total_len]);
            it = prev;
        }
    }

    /// Saves the current arena bump position for temporary pass scoping.
    pub inline fn checkpoint(self: *const BumpArena) Checkpoint {
        return .{
            .slab = self.current_slab,
            .used = if (self.current_slab) |slab| slab.used else 0,
        };
    }

    /// Rewinds the arena to a prior checkpoint, zeroing the reclaimed region
    /// to preserve strict determinism across subsequent allocations.
    pub fn restore(self: *BumpArena, cp: Checkpoint) void {
        while (self.current_slab != cp.slab) {
            const slab = self.current_slab orelse break;
            self.current_slab = slab.prev;
            const total_len = @sizeOf(SlabHeader) + slab.capacity;
            const raw_ptr: [*]align(16) u8 = @ptrCast(@alignCast(slab));
            self.backing_allocator.free(raw_ptr[0..total_len]);
        }
        if (self.current_slab) |slab| {
            assert(cp.used <= slab.used);
            const payload = self.slabPayload(slab);
            @memset(payload[cp.used..slab.used], 0);
            slab.used = cp.used;
        }
    }

    inline fn slabPayload(self: *const BumpArena, slab: *SlabHeader) [*]u8 {
        _ = self;
        const base: [*]u8 = @ptrCast(slab);
        return base + @sizeOf(SlabHeader);
    }

    /// Allocates `n` elements of type `T` with natural alignment, guaranteed zero-initialized.
    pub fn allocSlice(self: *BumpArena, comptime T: type, n: usize) ![]T {
        if (n == 0) return &[_]T{};
        const byte_count = std.math.mul(usize, @sizeOf(T), n) catch return error.OutOfMemory;
        const raw = try self.allocBytesAligned(byte_count, @alignOf(T));
        const typed_ptr: [*]T = @ptrCast(@alignCast(raw.ptr));
        return typed_ptr[0..n];
    }

    /// Allocates a single instance of `T` in the arena and initializes it to `val`.
    pub fn create(self: *BumpArena, comptime T: type, val: T) !*T {
        const slice = try self.allocSlice(T, 1);
        slice[0] = val;
        return &slice[0];
    }

    pub fn allocBytesAligned(self: *BumpArena, size: usize, alignment: usize) ![]u8 {
        assert(std.math.isPowerOfTwo(alignment));
        assert(alignment <= 16);

        // Fast path: bump within current slab
        if (self.current_slab) |slab| {
            const aligned_offset = std.mem.alignForward(usize, slab.used, alignment);
            if (aligned_offset + size <= slab.capacity) {
                const payload = self.slabPayload(slab);
                slab.used = aligned_offset + size;
                return payload[aligned_offset..slab.used];
            }
        }

        // Slow path: oversized allocation (> 50% of default slab) goes to dedicated chain
        if (size > (DEFAULT_SLAB_SIZE / 2)) {
            const slab = try self.allocateNewSlab(size);
            slab.prev = self.oversized_head;
            self.oversized_head = slab;
            slab.used = size;
            return self.slabPayload(slab)[0..size];
        }

        // Allocate a fresh standard 64 KiB slab
        const slab = try self.allocateNewSlab(DEFAULT_SLAB_SIZE);
        slab.prev = self.current_slab;
        self.current_slab = slab;
        slab.used = size;
        return self.slabPayload(slab)[0..size];
    }

    fn allocateNewSlab(self: *BumpArena, capacity: usize) !*SlabHeader {
        const total_bytes = @sizeOf(SlabHeader) + capacity;
        const mem = try self.backing_allocator.alignedAlloc(u8, 16, total_bytes);
        // CRITICAL FOR REPRODUCIBLE BUILDS: Zero all slab bytes including any future struct padding
        @memset(mem, 0);
        self.total_bytes_reserved += total_bytes;

        const header: *SlabHeader = @ptrCast(mem.ptr);
        header.* = .{
            .prev = null,
            .capacity = capacity,
            .used = 0,
        };
        return header;
    }
};

// ============================================================================
// [3] DETERMINISTIC STRING INTERNER (WYHASH SEED = 0)
// ============================================================================

/// High-density, deterministic String Interner.
/// - Stores all UTF-8 bytes contiguously in `BumpArena` slabs (plus a trailing NUL byte for C/LLVM FFI).
/// - Uses open-addressed linear probing with `std.hash.Wyhash` seeded deterministically at `0`.
/// - Insertion order deterministically assigns `StringId` (`0, 1, 2, …`).
pub const StringInterner = struct {
    /// Compact 16-byte metadata record per unique interned string (on 64-bit).
    pub const EntryMeta = extern struct {
        ptr: [*]const u8,
        len: u32,
        hash: u32,
    };

    pub const EMPTY_SLOT: u32 = std.math.maxInt(u32);

    arena: *BumpArena,
    backing_allocator: Allocator,
    /// Dense array indexed directly by `StringId` (`0..entries.items.len`).
    entries: std.ArrayListUnmanaged(EntryMeta) = .{},
    /// Open-addressed hash table mapping `hash & mask` -> `StringId` (or `EMPTY_SLOT`).
    /// Load factor is kept <= 70% (`capacity` is always a power of two).
    buckets: []u32 = &[_]u32{},

    pub fn init(backing_allocator: Allocator, arena: *BumpArena, initial_capacity: u32) !StringInterner {
        var self = StringInterner{
            .arena = arena,
            .backing_allocator = backing_allocator,
        };
        const cap = std.math.ceilPowerOfTwoAssert(u32, @max(initial_capacity, 64));
        self.buckets = try backing_allocator.alloc(u32, cap);
        @memset(self.buckets, EMPTY_SLOT);

        // Guarantee StringId.empty == 0 is always ""
        const empty_id = try self.intern("");
        assert(empty_id == .empty);
        return self;
    }

    pub fn deinit(self: *StringInterner) void {
        self.entries.deinit(self.backing_allocator);
        if (self.buckets.len > 0) {
            self.backing_allocator.free(self.buckets);
        }
    }

    /// Deterministic 32-bit hash using Wyhash with fixed seed 0.
    pub inline fn hashString(bytes: []const u8) u32 {
        const h64 = std.hash.Wyhash.hash(0, bytes);
        return @truncate(h64 ^ (h64 >> 32));
    }

    /// Interns `str` and returns its canonical `StringId`.
    pub fn intern(self: *StringInterner, str: []const u8) !StringId {
        assert(str.len <= std.math.maxInt(u32));
        const hash_val = hashString(str);

        // Grow hash table if load factor exceeds 70%
        if ((self.entries.items.len + 1) * 10 >= self.buckets.len * 7) {
            try self.rehash(@intCast(self.buckets.len * 2));
        }

        const mask: u32 = @intCast(self.buckets.len - 1);
        var slot: u32 = hash_val & mask;

        while (true) {
            const existing_id = self.buckets[slot];
            if (existing_id == EMPTY_SLOT) break;

            const meta = self.entries.items[existing_id];
            if (meta.hash == hash_val and meta.len == str.len) {
                if (std.mem.eql(u8, meta.ptr[0..meta.len], str)) {
                    return @enumFromInt(existing_id);
                }
            }
            slot = (slot + 1) & mask;
        }

        // Not found: copy string into BumpArena with trailing NUL byte for C/LLVM FFI
        const arena_buf = try self.arena.allocBytesAligned(str.len + 1, 1);
        @memcpy(arena_buf[0..str.len], str);
        arena_buf[str.len] = 0;

        const new_id: u32 = @intCast(self.entries.items.len);
        assert(new_id < EMPTY_SLOT);

        try self.entries.append(self.backing_allocator, .{
            .ptr = arena_buf.ptr,
            .len = @intCast(str.len),
            .hash = hash_val,
        });
        self.buckets[slot] = new_id;
        return @enumFromInt(new_id);
    }

    /// O(1) lookup returning a NUL-terminated UTF-8 slice `[:0]const u8`.
    pub inline fn get(self: *const StringInterner, id: StringId) [:0]const u8 {
        const meta = self.entries.items[id.toIndex()];
        return meta.ptr[0..meta.len :0];
    }

    fn rehash(self: *StringInterner, new_cap: u32) !void {
        assert(std.math.isPowerOfTwo(new_cap));
        const new_buckets = try self.backing_allocator.alloc(u32, new_cap);
        @memset(new_buckets, EMPTY_SLOT);

        const mask = new_cap - 1;
        for (self.entries.items, 0..) |meta, idx| {
            var slot = meta.hash & mask;
            while (new_buckets[slot] != EMPTY_SLOT) {
                slot = (slot + 1) & mask;
            }
            new_buckets[slot] = @intCast(idx);
        }

        self.backing_allocator.free(self.buckets);
        self.buckets = new_buckets;
    }
};

    /// Fixed 8-byte payload per node (two 32-bit indices).
    /// Zero implicit padding inside `Data`.
    pub const Data = extern struct {
        lhs: u32,
        rhs: u32,
    };

    /// Extra payload structure stored in `AstStore.extra_data` for `fn_decl`.
    pub const FnDeclExtra = extern struct {
        name: StringId,
        params_start: u32,
        params_end: u32,
        return_type: NodeIndex,
    };
};

pub const AstStore = struct {
    allocator: Allocator,
    /// Struct-of-Arrays (SoA) storage:
    /// Decomposes `AstNode` into 3 dense, padding-free arrays:
    /// - `tags: [*]AstNode.Tag` (1 byte per node)
    /// - `main_tokens: [*]TokenIndex` (4 bytes per node)
    /// - `datas: [*]AstNode.Data` (8 bytes per node)
    /// Total: 13 bytes per AST node (vs 16–24 bytes in AoS), 0 padding bytes!
    nodes: std.MultiArrayList(AstNode) = .{},
    /// Contiguous 32-bit trail for variable-length node children & metadata.
    extra_data: std.ArrayListUnmanaged(u32) = .{},

    pub fn init(allocator: Allocator) AstStore {
        return .{ .allocator = allocator };
    }

    pub fn deinit(self: *AstStore) void {
        self.nodes.deinit(self.allocator);
        self.extra_data.deinit(self.allocator);
    }

    pub fn appendNode(self: *AstStore, node: AstNode) !NodeIndex {
        const idx: u32 = @intCast(self.nodes.len);
        try self.nodes.append(self.allocator, node);
        return @enumFromInt(idx);
    }

    /// Encodes any extern/packed struct `T` composed of 32-bit fields into `extra_data`.
    pub fn addExtra(self: *AstStore, extra: anytype) !u32 {
        const T = @TypeOf(extra);
        comptime {
            assert(@sizeOf(T) % @sizeOf(u32) == 0);
            assert(@alignOf(T) == @alignOf(u32));
        }
        const word_count = @sizeOf(T) / @sizeOf(u32);
        const start_idx: u32 = @intCast(self.extra_data.items.len);
        const words: *const [word_count]u32 = @ptrCast(&extra);
        try self.extra_data.appendSlice(self.allocator, words);
        return start_idx;
    }

    pub inline fn getExtra(self: *const AstStore, comptime T: type, start_idx: u32) T {
        const word_count = @sizeOf(T) / @sizeOf(u32);
        const slice = self.extra_data.items[start_idx..][0..word_count];
        const ptr: *const T = @ptrCast(slice.ptr);
        return ptr.*;
    }
};

// Compile-time memory layout & zero-padding invariants
comptime {
    assert(@sizeOf(StringId) == 4);
    assert(@sizeOf(TokenIndex) == 4);
    assert(@sizeOf(NodeIndex) == 4);
    assert(@sizeOf(PackedOperand) == 4);
    assert(@sizeOf(MirLocation) == 8);
    assert(@sizeOf(AstNode.Data) == 8);
    assert(@bitSizeOf(AstNode.Data) == @sizeOf(AstNode.Data) * 8);
    assert(@sizeOf(BumpArena.SlabHeader) == 32);
}
```

## 5. Deterministic Bootstrap Pipeline Specification (Deliverable 3)

### 5.1 Two-Phase Lifecycle: Stage-0 Retirement to `corex1.wasm.zst` Fixed-Point Verification

CoreX's bootstrap architecture operates across two distinct project eras. In **Era 1 (Initial Self-Hosting Cutover prior to retiring Zig Stage 0)**, the host builds `stage0/corex` (written in Zig) with its `-ofmt=c` backend enabled. Next, `stage0/corex` compiles the self-hosted `.cx` compiler source (`src/main.cx`) with `-target wasm32-wasi -OReleaseSmall -Dhave_llvm=false` (enabling *only* the `-ofmt=c` C backend inside the output binary), runs `wasm-opt -Oz --enable-bulk-memory` and `zstd -19`, and writes `stage1/corex1.wasm.zst`. Finally, the repository is tagged at `v0.9.0-stage0-anchor`, and `stage0/` is deleted from `main`.

In **Era 2 (Permanent Self-Hosted Bootstrap on Any Fresh Linux, macOS, or Windows Machine)**, building `corex` from source requires **only a standard C99 compiler (`cc`, `clang`, `gcc`, or `cl.exe`)** and optional static LLVM/LLD libraries for the final stage.

### 5.2 Cross-Platform Bootstrap Driver Specification (`bootstrap.c`)

In Zig's upstream `bootstrap.c` (`199 lines`), Windows child-process execution was left as a `#error TODO` stub. For CoreX to bootstrap out-of-the-box on any fresh **Windows, Linux, or macOS** host without requiring CMake, Python, or Bash, `corex-lang/corex` should commit a complete, dependency-free C99 `bootstrap.c` driver that handles both POSIX (`fork`/`execvp`/`waitpid`) and Windows (`CreateProcessA`/`WaitForSingleObject`) and enforces deterministic environment variables (`SOURCE_DATE_EPOCH=0`, `ZERO_AR_DATE=1`):

```c
/*
 * CoreX Self-Hosting Bootstrap Driver (`bootstrap.c`)
 * Compiles with any C99 compiler on Linux, macOS, BSD, or Windows:
 *   POSIX:   cc -O2 -std=c99 bootstrap.c -o bootstrap && ./bootstrap
 *   Windows: cl /O2 bootstrap.c /Fe:bootstrap.exe && bootstrap.exe
 */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <stdbool.h>

static void panic(const char *msg) {
    fprintf(stderr, "corex-bootstrap fatal: %s\n", msg);
    abort();
}

#if defined(_WIN32)
#define WIN32_LEAN_AND_MEAN
#include <windows.h>
static void set_deterministic_env(void) {
    _putenv_s("SOURCE_DATE_EPOCH", "0");
    _putenv_s("ZERO_AR_DATE", "1");
    _putenv_s("TZ", "UTC");
    _putenv_s("LC_ALL", "C");
}
static void run_process(const char *const *argv) {
    char cmdline[8192];
    size_t pos = 0;
    for (size_t i = 0; argv[i] != NULL; ++i) {
        int written = snprintf(cmdline + pos, sizeof(cmdline) - pos,
                               (i == 0) ? "\"%s\"" : " \"%s\"", argv[i]);
        if (written < 0 || (size_t)written >= sizeof(cmdline) - pos)
            panic("command line overflow");
        pos += (size_t)written;
    }
    STARTUPINFOA si;
    PROCESS_INFORMATION pi;
    ZeroMemory(&si, sizeof(si));
    si.cb = sizeof(si);
    ZeroMemory(&pi, sizeof(pi));
    if (!CreateProcessA(NULL, cmdline, NULL, NULL, TRUE, 0, NULL, NULL, &si, &pi))
        panic("CreateProcessA failed");
    WaitForSingleObject(pi.hProcess, INFINITE);
    DWORD exit_code = 1;
    GetExitCodeProcess(pi.hProcess, &exit_code);
    CloseHandle(pi.hProcess);
    CloseHandle(pi.hThread);
    if (exit_code != 0) panic("child process exited with non-zero status");
}
#else
#include <unistd.h>
#include <sys/wait.h>
static void set_deterministic_env(void) {
    setenv("SOURCE_DATE_EPOCH", "0", 1);
    setenv("ZERO_AR_DATE", "1", 1);
    setenv("TZ", "UTC", 1);
    setenv("LC_ALL", "C", 1);
}
static void run_process(const char *const *argv) {
    pid_t pid = fork();
    if (pid < 0) panic("fork() failed");
    if (pid == 0) {
        execvp(argv[0], (char *const *)argv);
        perror("execvp");
        _exit(127);
    }
    int status = 0;
    if (waitpid(pid, &status, 0) < 0) panic("waitpid() failed");
    if (!WIFEXITED(status) || WEXITSTATUS(status) != 0)
        panic("child process failed");
}
#endif

static void print_and_run(const char *const *argv) {
    fprintf(stderr, "[bootstrap]");
    for (size_t i = 0; argv[i] != NULL; ++i) fprintf(stderr, " %s", argv[i]);
    fprintf(stderr, "\n");
    run_process(argv);
}

static const char *get_host_cc(void) {
    const char *cc = getenv("CC");
    return (cc != NULL && cc[0] != '\0') ? cc : "cc";
}

static const char *get_host_triple(void) {
    const char *override = getenv("COREX_HOST_TRIPLE");
    if (override != NULL) return override;
#if defined(__x86_64__) || defined(_M_X64)
    #define CX_ARCH "x86_64"
#elif defined(__aarch64__) || defined(_M_ARM64)
    #define CX_ARCH "aarch64"
#elif defined(__riscv) && (__riscv_xlen == 64)
    #define CX_ARCH "riscv64"
#else
    #error "Specify COREX_HOST_TRIPLE for this architecture"
#endif
#if defined(_WIN32)
    return CX_ARCH "-windows-gnu";
#elif defined(__APPLE__)
    return CX_ARCH "-macos-none";
#elif defined(__linux__)
    return CX_ARCH "-linux-gnu";
#else
    #error "Specify COREX_HOST_TRIPLE for this OS"
#endif
}

int main(void) {
    set_deterministic_env();
    const char *cc = get_host_cc();
    const char *triple = get_host_triple();

    /* Step 1: Compile the 4,000-line C99 wasm2c + zstd decompressor */
    {
        const char *argv[] = {
            cc, "-o", "corex-wasm2c", "stage1/wasm2c.c", "-O2", "-std=c99", NULL
        };
        print_and_run(argv);
    }
    /* Step 2: Translate stage1/corex1.wasm.zst -> corex1.c */
    {
        const char *argv[] = {
            "./corex-wasm2c", "stage1/corex1.wasm.zst", "corex1.c", NULL
        };
        print_and_run(argv);
    }
    /* Step 3: Compile corex1.c + stage1/wasi.c (23 WASI syscalls) -> ./corex1 */
    {
        const char *argv[] = {

            "-std=c99", "-Os", "-lm", NULL
        };
        print_and_run(argv);
    }
    /* Step 4: Write deterministic bootstrap config.cx */
    {
        FILE *f = fopen("config.cx", "wb");
        if (!f) panic("failed to open config.cx");
        fprintf(f,
            "pub const HAVE_LLVM: bool = false;\n"
            "pub const VERSION: str = \"0.10.0-bootstrap\";\n"
            "pub const DEV_PROFILE: Profile = .bootstrap;\n");
        fclose(f);
    }
    /* Step 5: Run corex1 (Wasm seed) to transpile current in-tree .cx -> corex2.c */
    {
        const char *argv[] = {
            "./corex1", "build-exe", "src/main.cx",
            "-ofmt=c", "-OReleaseSmall", "-target", triple,
            "--name", "corex2", "-femit-bin=corex2.c", NULL
        };
        print_and_run(argv);
    }
    /* Step 6: Compile corex2.c + compiler_rt.c with host C compiler (256 MiB stack) */
    {
        const char *argv[] = {
            cc, "-o", "corex2", "corex2.c", "stage1/compiler_rt.c",
            "-std=c99", "-O2", "-fno-stack-protector", "-Istage1",
#if defined(__APPLE__)
            "-Wl,-stack_size,0x10000000",
#elif !defined(_WIN32)
            "-Wl,-z,stack-size=0x10000000", "-pthread",
#endif
            NULL
        };
        print_and_run(argv);
    }
    /* Step 7: Use corex2 to build Stage 3 (full self-hosted compiler) & verify Stage 4 */
    {
        const char *argv[] = {
            "./corex2", "build", "--stage3-verify-fixed-point", NULL
        };
        print_and_run(argv);
    }
    return 0;
```

#### The 23 WASI Preview 1 Syscalls Required in `stage1/wasi.c`

Following Zig's `wasi.c` design, the entire OS abstraction layer required by `corex1` to read `.cx` source files, query directory trees, and emit `corex2.c` consists of **23 functions** imported from `"wasi_snapshot_preview1"` mapped onto standard C `stdio.h` / `stdlib.h` calls:
1.  **Process & Command-Line Arguments (3):** `args_sizes_get`, `args_get`, `proc_exit`.
2.  **Preopened Directories & Path Operations (7):** `fd_prestat_get`, `fd_prestat_dir_name`, `path_open`, `path_create_directory`, `path_remove_directory`, `path_unlink_file`, `path_rename`.
3.  **File Descriptor I/O (6):** `fd_read`, `fd_write`, `fd_pread`, `fd_pwrite`, `fd_close`, `fd_readdir`.
4.  **Metadata & File Stat Queries (5):** `fd_fdstat_get`, `fd_filestat_get`, `fd_filestat_set_size`, `fd_filestat_set_times`, `path_filestat_get`.
5.  **Clock & Entropy (2):** `clock_time_get` (returns constant `0` in deterministic bootstrap mode) and `random_get` (returns a deterministic PRNG stream seeded with `0` in bootstrap mode).

### 5.3 Protocol for Eliminating All Binary Non-Determinism (`Stage 3 === Stage 4`)

Note on stage numbering conventions: In Rust's `x.py` build system, `stage0` is the pre-compiled seed binary, `stage1` is built from current in-tree sources by `stage0`, `stage2` is built by `stage1`, and `stage3` is built by `stage2` to verify `stage2 === stage3` byte-for-byte identity. In Zig's Wasm bootstrap pipeline, because `zig1` is the Wasm-to-C seed binary and `zig2` is compiled from generated C by the *host C compiler* (`gcc`/`clang`/`msvc`), `zig2` has the final compiler logic but host-optimized machine code; therefore, `zig2` builds `stage3` (`zig3`, the first binary optimized by Zig itself), and `stage3` builds `stage4` (`zig4`) so that fixed-point verification checks `stage3 === stage4`. CoreX's `corex2 build --stage3-verify-fixed-point` command executes this exact verification gate (`SHA-256(corex3) == SHA-256(corex4)`).

For the fixed-point verification gate to hold across Linux, macOS, and Windows, the compiler and build system must eliminate six distinct classes of entropy:

| Entropy Vector | Root Cause of Non-Determinism | Mandatory CoreX Mitigation Protocol |
| :--- | :--- | :--- |
| **1. Hash-Table Iteration Order** | Iterating over randomized hash maps (e.g., SipHash with OS random seeds) emits symbols, types, or IR blocks in different orders per run. | **Ban unordered hash-map iteration.** Use insertion-ordered arrays (`AutoArrayHashMap` / `IndexMap` pattern) where iteration always walks the dense `0..len` `u32` index slice, paired with `Wyhash(0)`. |
| **2. Parallel Thread Scheduling Jitter** | Multi-threaded `AstGen` or semantic workers inserting into a shared `StringInterner` or `InternPool` assign different `u32` IDs depending on OS thread wakeup order. | **Sharded InternPool + Canonical Sort:** Assign each file a deterministic `FileId(u32)` after sorting `readdir` results lexicographically. Parallel `AstGen` workers write into thread-local/per-file shards (packing the deterministic `tid`/shard ID into the high bits of the `u32` index, or merging shards in strict `FileId` order before single-queue `Sema`). |
| **3. Struct Padding & Uninitialized Memory** | C/C++/Zig structs with alignment holes (e.g., `u8` followed by `u32`) copy uninitialized stack/heap garbage into `.cxmod` caches or object sections. | **Zeroed Arenas + SoA + `comptime` Asserts:** 1) `BumpArena` runs `@memset(mem, 0)` on every slab allocation. 2) Use `MultiArrayList` (SoA) to eliminate internal padding. 3) For any `extern struct` written to disk, assert `@bitSizeOf(T) == @sizeOf(T) * 8` or insert explicit zeroed `_pad` fields (and use `{}` in C23). |
| **4. Compiler & Archive Timestamps** | `__DATE__`/`__TIME__` macros, `ar` archive member `mtime`/UID/GID headers, PE `TimeDateStamp`, and Mach-O `N_OSO` stabs embed wall-clock time. | Export `SOURCE_DATE_EPOCH=0` and `ZERO_AR_DATE=1`. Pass `-Wdate-time -Wno-builtin-macro-redefined -D__DATE__= -D__TIME__= -D__TIMESTAMP__=`. Normalize archive timestamps when creating static libraries. |
| **5. Host Path Leakage in Debug Info & Macros** | `__FILE__`, DWARF `DW_AT_comp_dir`, and Windows `.pdb` paths embed `/home/user/...` or `C:\Users\...`, breaking cross-directory/cross-machine reproducibility. | Invoke compilers from inside the build directory using relative source paths (`../../src/main.cx`) and pass `-no-canonical-prefixes -fdebug-compilation-dir . -Wa,-fdebug-compilation-dir,.` (or `-ffile-prefix-map=$(ROOT_DIR)=.` when not using `-grecord-gcc-switches`). |
| **6. Linker Build-IDs, UUIDs & Incremental State** | Random ELF `.note.gnu.build-id`, random Mach-O `LC_UUID`, or MSVC `/INCREMENTAL` `.ilk`/`.pdb` GUIDs change on every link. | Enforce deterministic content-hashed linker flags via embedded `lld::lldMain` across all three OS families (detailed below). |

By combining **Zig** for Stage 0, the **zero-padded `BumpArena` + `Wyhash(0)` `StringInterner` + `MultiArrayList` `u32` index architecture**, and the **`corex1.wasm.zst` + `wasm2c.c` + embedded `lld` deterministic pipeline**, CoreX achieves rapid pre-1.0 self-hosting while ensuring that any developer or distribution maintainer on Linux, macOS, or Windows can reproduce the compiler bit-for-bit from source.
